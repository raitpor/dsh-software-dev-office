# 读数与里程碑门

## 1. 读数是什么

里程碑门不是“感觉做完了”，而是**一组可复跑的读数**：每条有一个问题、一条命令、一段输出、一个结论。

```markdown
## R3 权限撤销后，待审项是否消失
- 问题：撤权后同一个人还能看到队列吗？
- 命令：`node scripts/readings/r3.mjs --json`
- 输出：`{"before":{"rows":2},"after":{"rows":0},"apply_entry":"/apply"}`
- verdict：pass
- caveat：只覆盖 task 派生行；其它派生行按设计不消失（已签边界）
```

字段固定五项：`id / question / command / raw / verdict`，可加 `caveat`。

## 2. 读数必须量到真路径

- 数“日志里出现过”不算；数**真的发生了**（行数、文件内容、字节码、退出码）。
- 硬编码常量不是测量：把输入改一下，数字**必须跟着变**；不变 ⇒ 假读数。
- 每个读数写“变异会怎样”：把被测逻辑改坏，读数必须变红；不变 ⇒ 这条读数无效。
- 两遍一致：同一命令跑两次，除时间戳与随机 id 外**逐键相同**。

## 3. 树冻结

取证前：

1. 冻结范围（哪些目录/文件一行不许改），写进读数文件头部。
2. `git status --porcelain` 必须干净；未提交的卡/台账先提交。
3. 记录被签树：`HEAD` + 生成物 sha256。
4. 跑一遍全量检查（测试/自检/台账列数），把命令与汇总写进读数文件。

取证后再改任何东西 ⇒ 这次读数作废，必须重跑（“绿只对那棵树成立”）。

## 4. 门签

```markdown
# 签字 S<n> · M<n> 里程碑门
- 时间 / 被签树 / 读数文件 sha256
- 多条读数逐条 verdict：R1 pass … R5 partial（无人类样本）
- overall：partial
- 当场确认：接受 partial 的理由、遗留项去向、谁在什么时点补
- 选项：一律以三选一开头——`签：…` / `改：…` / `不签：…`；门签在「签：」后写清接受范围（例：`签：接受 overall partial`）。**不接受 partial 就写「改」或「不签」并写理由**，不要发明第四种前缀
```

标题必须写成 `# 签字 S<n> · M<n> 里程碑门`（门签识别只认这个形态，以及旧形态 `# S<n>（M<n> 门）`）；`S<n>` 用下一个数值编号（追加签才用 `S<n>-<A>`）。

规则：
- overall 由读数推出来，**不许**“多数 pass 就算 pass”。
- partial 必须写两条：为什么现在消不掉、什么条件能消掉。
- 遗留项写去向（哪张卡/哪个里程碑），否则视为遗忘。

## 5. 基线漂移、需求认领与 trace 的先后

### 5.1 `baseline_drift`

`check --plan` 报 `baseline_drift` 表示：里程碑冻结段的 `- 基线 hash：` 与当前 `.sdo/baseline/` 四份算出的 hash 不一致（或声明格式不对）。

- **修法是更新冻结段 + 追加签，不是改基线去迁就旧 hash**：先跑 `node skills/sdo-flow/scripts/check.mjs --plan --milestone <M> --print-frozen-hash`，把新值写进冻结段 `hash:`，再走追加签（`- 冻结段 hash：<new>` + `- 上一版 hash：<old>`）。
- 若确实要基于旧基线继续（例如基线在计划后合法变更），在冻结段写 `基于旧基线：<旧前8>（变更请求：D-<n>；理由：<≥8 字>）`；`check` 会要求该 D 行在台账里。
- 不要手算 hash；`--print-frozen-hash` 是唯一算法来源（见 `references/04` §5.3）。

### 5.2 `requirement.claimed_or_na`

`checkRequirementClaim` 要求每个里程碑文件二选一：

```markdown
认领需求：R-01、R-02、R-03
```

或

```markdown
需求：无（本里程碑只修工具，不认领需求）
```

只写 `需求：无` 不带具体理由（或理由过短/套话）会报 `requirement_missing`。同一里程碑多张卡引用同一 R 正常；跨里程碑重复认领会报 `trace_duplicate_claim`。

### 5.3 `--trace` 与门签的先后

- `check` 默认**不跑** `--trace`（只做格式/台账/签字/卡/读数结构检查）。
- **门签前必须单独跑** `node skills/sdo-flow/scripts/check.mjs --trace`，达到 exit 0 且 0 问题；否则不许送门签。
- 顺序固定：先 `--trace` 绿，再 `gate.mjs --file` 绿，最后人签门签；`--trace` 与 `--plan` 互斥，不能合成一条命令。
- **`gate.mjs` 不替你做这一步**：它只核门表结构与 preset 判据，不跑 `--trace`（`grep trace gate.mjs` 无命中）。机检只到 `check --trace` 为止；“trace 是否绿”由评审核对、由门签为它负责。
