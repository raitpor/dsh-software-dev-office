# M3-4 · 渲染器注册目录（收口 D-034）

## 意图

M1-6 时 `claim.derived_by` 只靠 `view_catalog` + 常量代理（D-034），M3 补真目录：`renderer_catalog` 登记“渲染器 id → 实现模块 → 可渲染哪些视图”，`claim` 行只认已登记渲染器；未注册 ⇒ `renderer_unregistered`。目录行由 `renderer.registered` 事件投影（事件流是唯一真源），登记时动态 `import()` 校验实现真的存在。

## 对齐

**复述**：结论行不是谁都能写：只能由**已登记的渲染器**从视图行渲染出来，登记即代码（注册行指向 `src/` 里的实现），没有第二条路。M1-6 的常量代理是临时替身，本卡换成真目录，并让 `verifyClaims` 能核对“这条 claim 的 `derived_by` 真的存在且能渲染它引用的来源表”。

**人确认**：pending（等 reviewer 判据全绿后交签署者）

**正例 2**
1. `registerRenderer({id:'renderer:test-v1', module_path:'src/claim/render.ts', views:['board']})` ⇒ `renderer.registered` 事件入库、目录行出现、`writeClaimRows` 接受 `derived_by:'renderer:test-v1'`；未注册 id（`renderer:not-registered`）⇒ `renderer_unregistered`、0 行。
2. `verifyClaims` 检查 `derived_by` 在目录内，并按声明 `views[]` 的 SQL 检查来源表覆盖：登记 `views:['release']` 而 claim 的 frontier 来自 `task.created` ⇒ `views_not_covered`、`missing_tables:['task']`。

**反例 1**
- 手写 claim 行（不经渲染器）⇒ 拒（`renderer_unregistered`）；绕过网关直插库 ⇒ `verifyClaims` 报 `mismatch`/`unexpected`。
- 登记指向不存在模块或导出不了渲染函数的模块（如 `src/claim/types.ts`）⇒ `renderer_module_invalid`、目录 0 行新增。

## 已知边界

1. 目录行“真源”是 `renderer.registered` 事件流；唯一例外是迁移播种 + `rebuildRendererCatalog` 兜底的内置渲染器（D-091）。若有人删掉迁移种子并清空事件，兜底仍会把内置渲染器补回。
2. `views[]` 覆盖检查是**启发式**（P2-1）：只静态扫 `view_catalog.sql` 的 `FROM/JOIN`，不追踪 CTE 间接来源，故降级为早期信号；真覆盖以 `verifyClaims` 重算 claim 行 + 渲染器实际输出对账为准。
3. `module_path` 只接受 `src/**.ts`（编译后 `lib/**.js` import），不允许第三方包/运行时拼接路径；`import()` 超时 2s。
4. `renderer_conflict` 只比较 `module_path` 与 `views` 集合；同 id 同 views 不同 `at` 视为幂等返回 `created:false`（不新增事件）。
5. 登记权固定 `config`+`admin@domain`+`domain:renderers`（D-090）；没有“域内渲染器”粒度。
6. C4 只校验 claim 的 frontier 事件来源表被声明视图覆盖（启发式），不证明渲染器真的从这些视图渲染（渲染函数在 claim 路径上仍由 `renderClaimRows` 实现）。
7. `projection_guard` 只给 `renderer_catalog` 建了哨兵/触发器；其它同性质投影表（claim、stage_run、review 等）仍是“事件流真源 + verify 重算”，直写风险由 D-095 记、M4 统一补守卫。
8. P1-2 的一次性能力存在进程内 `Set`，绑 `payload_hash` 但**不跨进程/不持久**；这是写路径守卫（防本进程外的直 append），不是权限体系本身——跨进程伪造由 `append` 的链/hash 与 verify 兜。
9. 生产里目录只由 `append` 物化；`rebuildRendererCatalog` 是 `@internal` 维护/CLI 面（产品路径不调用，E19 为证），只在迁移/修复时用，且必须和事件链对账（`verifyClaims`）。
10. **哨兵可被解除（第 2 轮 P2-1 实测）**：能执行任意 SQL 的进程可 `UPDATE projection_guard SET active=1` 后直插目录。`projection_guard` 阻断的是“未在 append 事务窗口内的直写”，不是防同 uid 恶意进程；该场景已在威胁模型外（与 M2-0 同 uid 威胁模型一致）。不加 `projection_guard` 自触发器（递归风险不值）。
11. **mint 导出边界（第 2 轮裁定）**：`mintRendererRegistrationAuthority` 为 `@internal`，产品路径不当入口调用；能 import 内部模块的代码已在威胁模型外，故不为此改代码。
12. **`views[]` 声明与实际渲染无直接绑定（已知缺口）**：目前只有内置行有用例证明 `import()` 出的函数能对声明视图出渲染行；任意登记只做模块导出校验。M4 加渲染器时必须要求“登记时跑一次 dry-render（在 `registerRenderer` 内做）”作为后续卡。
13. **P3 边界**：一次性能力绑 `payload_hash` 而非 event id——append 失败会留下未消费能力（进程内，不持久；下次成功 append 同 payload 会被允许，属预期）。
14. **P3 边界**：011 的触发器只覆盖 `renderer_catalog`；其它投影表（claim、stage_run、review 等）同缺口记 D-095，M4 统一补守卫。
