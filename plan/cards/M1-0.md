# M1-0 · 写网关与 7 表物化（四域 + `decision` + `restatement*`）

## 意图

M0 只能读：`docs/02` 的事件流没有写入路径（D-012 记着这件事）。M1 的每一条链——意图、spec、判据、证据、结论、对齐——都要真的落库，否则后面的 P15、`sdo_check`、`rework_units` 全是空转。

这张卡建**唯一写入口**：`append(events)`。它要保证三件事：**不认识的 kind 进不来**、**事件链不许断**、**重放不重复**。然后让四个有事件来源的域（intent/spec/criterion/evidence）写完后，投影表里的行与 `fold` 内存状态逐字段相等。

## 对齐

**复述**：这不是“写个 INSERT 函数”，而是把 `docs/02` §10（信封规则）、§11（事件类型）、§12（折叠）三条约束收束到一个入口上；绕过它写库要么被库层拒绝、要么被 `verify` 抓出来。物化口径这版选“全量重放后 diff 落库”，不做增量 reducer 优化——M1 事件量小，先把“对”钉住。

**人确认**：pending（收卡前必须确认）

**正例 2**
1. 一批合法事件（含 `intent.signed`/`spec.defined`/`criterion.registered`）经 `append` 写入后：`event` 行数 = 批大小、四张投影表（`intent`/`spec`/`criterion`/`evidence`）的行与 `fold(空状态, 全部事件)` 的结果逐字段相等、`verify()` 返回 `ok=true`。
2. 同一个批次连写两次：第二次不报错、`event` 行数不变、投影不变（幂等键生效）。

**反例 1**
- 在 `src/db/` 以外直接 `INSERT INTO event ...`；或先写事件行再 fold、fold 失败时留下半截事件（没有事务回滚）。

## 范围裁定（Lead，2026-11-13）

impl-core 读卡后报出两个冲突，裁定如下（**不发明 kind、不改冻结区**）：

1. **`scenario` 没有写入路径**：`docs/02` §11 全量登记里没有 `spec.scenario.added` 一类 kind，`docs/03` §2 却定义了 `scenario(id,steps,expected,kind)` 表。这是**设计缺口**（记 `plan/03` D-024 `gap`）。本卡**不做** `scenario` 物化，也不许自己发明 kind；`scenario` 的写入路径在 M1-2（对齐 / 判据 / 场景）里裁定，需要人签才进设计 v2.1。
2. **`claim` 不是 fold 投影**：`docs/03` §3 写死“`claim` 只能由 `derived_by` 指向的渲染器写入；渲染器的输入只能是视图。**没有第二条写 claim 的路**”，`docs/07:477` 也让接口层拒绝 agent 写 claim。所以 `claim` 有**独立的写入网关（注册 renderer）**，不属于本卡的 `append()`；它的网关属于 **M1-6**（v1 → `claim` 重建 20/20）。

因此：
- **C5 收窄为 7 张物化表**：`intent` / `spec` / `criterion` / `evidence` / `decision` / `restatement` / `restatement_diff`（第 64 轮 P2-3 统一口径；第 62 轮复认 B 起物化面即 7 张，A4/E12 走的就是 7 张）。四域用例（`write.materialize.test.ts` 的 fourDomain 流）不产生 `restatement*` 行——它一条 restatement 事件都没有——所以那 2 张表的“真行”证据由 `write.supported-kinds.test.ts` 的 `restatement.recorded` / `diff_dispositioned` / `invalidated` 三条用例提供。
- **C1 只管 `event` 表**：往 `event` 写行的地方只有 `append()` 一处。`claim` 的写入走 renderer 网关，是**第二类写入**，不是绕过（它的 DB 权限在 M1-6 收紧到“只有 renderer 模块”）。
- 本卡不许动 `claim`/`scenario` 的写入路径。
