# M2-2 · 门禁判定（`stage_run.baseline_hash` + `gate.judged`）

## 意图

M1-4 的 `sdo_check` 是**只读预览**：它算判据三态，但**不落判定行**——因为判定必须绑一版已冻结的 `baseline.hash`，而 M1 没有 baseline（`docs/04` §5.2 规则 1：“没有 baseline 的判定无效”，M1 刻意不给“先判后冻”开口子）。

M2-1 把 baseline 冻结立起来之后，这张卡才允许写判定：`stage_run` 绑 `baseline_hash`，门禁现算按**有效绑定五条件**（`docs/04` §6）判，结论落 `gate.judged`。同时这张卡负责**复跑 M1 读数 R7**——`gate` 表建起来后，R7 从“0 行平凡真”变成非平凡断言。

依据：`docs/04` §5.2 / §6（有效绑定五条件、检查点不连续）、`docs/03` 的 `stage_run`/`gate.judged`、`docs/02` §11 事件表。

## 对齐

**复述**：不是“把 `sdo_check` 的结果存一行”，而是**每次判定都能回答“当时用的是哪把尺子、这把尺子在当时是否真的绑着这条判据”**。所以判定行的 `baseline_hash` 必填且指向已冻结版本；判据是不是“有效绑定”要**现算**（五条件全满足 + 检查点连续），不能照抄 P15 的结论——P15 判的是 baseline 文件，这里判的是**这一次判定**。

**人确认**：pending

**正例 2**
1. 冻结一版 baseline（`spec_set.signed` 等三条 core 有效绑定）→ 开一个 `stage_run`（`kinds` 与 core 相交）→ 门禁现算 ⇒ 落 `gate.judged` 行：`baseline_hash` = 当前冻结版、`result='pass'`、`readings[]` 含每条判据的三态。
2. 同一 `stage_run` 换一版 baseline（合法收紧）后重判 ⇒ **新** `gate.judged` 行（旧行不改），两条各绑各自的 hash；`verify` 按“引用的那版”对账两条都绿。

**反例 1**
- baseline 里 `spec_set.signed` 只绑在 `any_of` 门 ⇒ 判定必须 `core_not_effective` 红，**不是**“P15 已放行所以绿”。

## 判据

| # | 判据 | 怎么验 |
|---|---|---|
| C1 | **唯一写入口**：`gate.judged` 只能由门禁判定流程写；`stage_run.baseline_hash` 只能由该流程设置（`stage.entered` 时为空） | 静态扫描：`src/` 里 `gate.judged` 只在 `src/core/gate/` 构造；裸 append ⇒ 写网关拒（`unsupported_scope` 或专用码） |
| C2 | **判定必绑已冻结 baseline**：`baseline_hash` 非空、指向 `baseline` 表一行且该行 `status` 已冻结、内容 hash 可复算；引用不存在/未冻结 ⇒ 拒（`baseline_not_frozen`） | 用例：未冻结 hash、伪造 hash、已 `rolled_back` 的 release 引用的 baseline 各一条 |
| C3 | **有效绑定现算（五条件）**：判据已注册 + 在某 gate 的 `criteria[]` 中 + `stage.kinds ∩ criterion.applies_to ≠ ∅` + `policy_mode='all_of'` + `waivable=false`；**任一条不满足就不算绑定** | 用例：①绑到 `na` stage ②放进 `any_of` 门 ③放进可豁免 gate ④applies_to 不相交 ⑤未注册——五种各一条，全部判“未生效” |
| C4 | **检查点不连续即红**：凡 `kinds` 与 `applies_to` 相交的 stage 出口都必须有效绑定，缺一个 ⇒ `core_not_effective`（复用 M1-1/M1-3 的结构性前置，**不得两套口径**） | 用例：req 出口绑了、build 之后没绑 ⇒ 红；两处都绑 ⇒ 绿 |
| C5 | **判定不可改**：`gate.judged` 是 append-only（同 id 同内容幂等、异内容拒）；重判建新行，不覆盖旧行 | 用例：改一条判定再 append 同 id ⇒ 拒；重复判定 ⇒ 两行且都能 verify |
| C6 | **`readings[]` 可对账**：每条判据的三态（pass/fail/na）与原因码落进判定行，且与 `sdo_check` 对同一 baseline+frontier 的现算结果一致 | 用例：同一输入下 `sdo_check` 与判定行逐判据相等；变异一条判据实现 ⇒ 两者一起变 |
| C7 | **core 三条不许有后门**：core 判据未有效绑定 ⇒ 判定 `fail` 且 `reason_code='core_not_effective'`，不得因“其它判据全绿”而降级为 warning | 用例：core 未绑 + 其余全绿 ⇒ 判定 fail；core 绑齐 ⇒ pass |
| C8 | **R7 复跑（M1 遗留）**：`gate`/`gate.judged` 表建起后重出 M1 读数 ⑦，断言 `stage_run` 行数与 `gate.judged` 行数都来自真实查询（非平凡），并保留“表名两种都探测”的口径 | 命令：`npm run readings:m1`；断言 R7 从 `partial` 变成 `pass`（或如实 `fail` 并说明），测试里“两表不存在”的旧断言必须同步改 |
| C9 | **判定与发布证据同版**：`release` 的发布证据只能来自同一 `baseline_hash` 的判定；跨版引用 ⇒ 拒（`baseline_mismatch`） | 用例：用旧版判定做发布证据 ⇒ 拒 |
| C10 | **拒绝码稳定**：`baseline_not_frozen`/`baseline_mismatch`/`core_not_effective`/`gate_empty`/`judgement_mismatch` 进 README | 用例：每码一条 |
| C11 | 冻结区零改动 | `git diff f37f4dc --name-only -- docs design probe` 为空 |
