# M2-2 · 门禁判定（`stage_run.baseline_hash` + `gate.judged`）

## 意图

M1-4 的 `sdo_check` 是**只读预览**：它算判据三态，但**不落判定行**——因为判定必须绑一版已冻结的 `baseline.hash`，而 M1 没有 baseline（`docs/04` §5.2 规则 1：“没有 baseline 的判定无效”，M1 刻意不给“先判后冻”开口子）。

M2-1 把 baseline 冻结立起来之后，这张卡才允许写判定：`stage_run` 绑 `baseline_hash`，门禁现算按**有效绑定五条件**（`docs/04` §6）判，结论落 `gate.judged`。同时这张卡负责**复跑 M1 读数 R7**——`gate` 表建起来后，R7 从“0 行平凡真”变成非平凡断言。

依据：`docs/04` §5.2 / §6（有效绑定五条件、检查点不连续）、`docs/03` 的 `stage_run`/`gate.judged`、`docs/02` §11 事件表。

## 对齐

**复述**：不是“把 `sdo_check` 的结果存一行”，而是**每次判定都能回答“当时用的是哪把尺子、这把尺子在当时是否真的绑着这条判据”**。所以判定行的 `baseline_hash` 必填且指向已冻结版本；判据是不是“有效绑定”要**现算**（五条件全满足 + 检查点连续），不能照抄 P15 的结论——P15 判的是 baseline 文件，这里判的是**这一次判定**。

**人确认**：pending

**正例 2**
1. 冻结一版 baseline（`spec_set.signed` 等三条 core 有效绑定）→ 开一个 `stage_run`（`kinds` 与 core 相交）→ 门禁现算 ⇒ 落 `gate.judged` 行：`baseline_hash` = 当前冻结版、`result='pass'`、`readings[]` 含每条判据的三态。
2. 同一 `stage_run` 换一版 baseline（合法收紧）后重判 ⇒ **新** `gate.judged` 行（旧行不改），两条各绑各自的 hash；`verify` 按“引用的那版”对账两条都绿。

**反例 1**
- baseline 里 `spec_set.signed` 只绑在 `any_of` 门 ⇒ 判定必须 `core_not_effective` 红，**不是**“P15 已放行所以绿”。
