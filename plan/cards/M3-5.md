# M3-5 · 权限撤销与待审项（含 `escalate` 独立性）

## 意图

撤权之后，**待审项必须从队列消失**，界面显示“申请入口”——不是静默消失让人以为丢了。`escalate` 的独立性也在此卡收口：升级给人的提问只能由提出者撤回、只能升到自己有权看的域。

## 对齐

**复述**：撤权不是删行，而是让“你能看到的待审项”跟着权走：撤了 `decide@release`，你的待审队列里不再出现发布决定，页面给一条“向 X 申请”的入口。已发生的决策不受影响（历史不可改），只影响“接下来你能审什么”。

**人确认**：pending

**正例 2**
1. 撤销 human-B 的 `decide@release` ⇒ B 的待审队列该行消失、页面出现 `apply_entry`；恢复权限 ⇒ 行回来。
2. `escalate@scope` 只允许升到自己有 read 的域；跨域 ⇒ `no_permission`；撤回只能撤自己提的。

**反例 1**
- 撤权后仍能看到待审项（投影/缓存未刷新）⇒ 检查红。

## 已知边界

1. **撤权页面只给入口、不给过滤后数字**（D-102）：过滤后的行数不是任何目录视图的行数，不新造不可复算 Figure；启用 `SDO_CONSOLE_ACTOR` 且有过滤时 `to_decide` 整个不出现。
2. **deny-all 是显式标记**：`RightsPort.denied` 由控制台对无有效 grant 的身份设置（`dbRightsPort` 读不到 grant ⇒ `denyAllRightsPort`），不靠“能力表恰好为空”推断；否则空 `review_queue` + deny-all 会出假 `to_decide=0`（P2-1）。
3. **申请入口只在总览 `/`**：`/board`、`/plan` 的 `apply_entries` 恒为空（`src/ui/README.md` 已注明）；跨页入口属后续卡。
4. **review 可见性 = read + decide 双查**：有 session 时 `readReviewQueueAccess` 把 session 透传给 `query()`（query 只判视图级 `min_right`）；行级域判定唯一在 PM 侧双查——两者维度不同，不是重复判权（无 session 的纯数据层调用才走兼容 `right:'decider'`）。
5. **域归属仍是临时口径**：`taskScopes` 从 `task.inputs` 的 `release:`/`domain:` 前缀取、空则 `domain:pm`；M3-1 的 `scope_owns`(013) 已交付但本卡仍用前缀推断，接线归属链随 M4 一并改（D-101 accepted）。
6. **`historySnapshot` 含 decision/attention 的 id 与内容哈希**（P3），撤权前后逐字段可比；不做全表快照。
7. **测试夹具授权**（协作偏差，Lead m06080/m06182/m06476）：M3-1 的 append 鉴权生效后，PM/UI 测试在 `test/core/pm/helpers.ts` 的 `openTempDb` 里用 M3-1 的 `seedRights(db, [{actor,scope,right}])` **点状**授权（plan@domain:core、assign/escalate/write/withdraw_attention@module:core；无 `*`），不用 `grantFixtureRoster` 大礼包；M3-1 的 kind→action 映射按真实矩阵取 module scope，`attention.raised`=escalate@module:core、`attention.withdrawn`=withdraw_attention@module:core。拒绝用例仍由 `test/db/*` 承接。session/鉴权迁移现由 impl-core 统一做（Lead m06476），本卡不再动这三处。
