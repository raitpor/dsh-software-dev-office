# M1-3 · P15 静态校验器（对 baseline 文件）

## 意图

`docs/04` 的 baseline 是“尺子”，但尺子本身要先能验：空 gate、未注册判据、core 三条没真绑上、缺 `engine`——任何一条不过就不该冻。M1 还没有签字链，所以这张卡**只做校验**：吃一个 baseline 文件（JSON），吐出 `{ok, reason_codes[]}`。

关键边界（`docs/09` §16.2 写死）：**不落冻结、不写 `baseline.rejected`、不产生任何事件**。`baseline.rejected` 是“冻结失败”的记录，属于 M2 的冻结事务；这里只是“文件校验不过”。

## 对齐

**复述**：不是“写个 schema 校验”，而是把 `docs/04` §5.2 的 ①–⑪ 十一条**机械判定**做实，尤其第 ⑦ 条——**先按判据的保证元数据算出 `guarantee_delta`，再查 core 三条是否在每个适用的 stage 出口都“有效绑定”**。这条是整套东西最容易被糊过去的地方：绑在 `na` 阶段、塞进 `any_of` 门、放进可豁免的 gate、只在某一个 stage 绑过——四种都算没查。

**人确认**：pending（收卡前必须确认）

**正例 2**
1. 一份合法 baseline（水落 preset，三 stage，每 stage 一个 `all_of`/`waivable=false` gate，gate 内含 core 三条）⇒ `{ok:true, guarantee_delta:{1:'kept',2:'kept',3:'kept'}, reason_codes:[]}`。
2. lite preset（缺 `design`/`review` kind）⇒ `{ok:true}`，但 `guarantee_delta` 里保证 1 与保证 3 记 `degraded` 并列出缺的判据（**不是拒**，因为 core 三条仍有效）。

**反例 1**
- `criteria: []` 的空 gate ⇒ `{ok:false, reason_codes:['gate_empty']}`。

## 判据

| # | 判据 | 怎么验 |
|---|---|---|
| C1 | ① stage 的 `id` 唯一、`kinds[]` 非空、`kinds ⊆ {requirement,design,implement,review,deliver}` ⇒ 违者 `stage_bad_kind` | 三个用例（空 kinds / 非法 kind / 重复 id） |
| C2 | ② `after` 边指向存在的 stage、**图无环**、所有 stage 从入口（`after` 为空的集合，允许多根）可达 ⇒ `stage_bad_after`；数组顺序不承载语义 | 用例：环、悬空边、孤岛节点 |
| C3 | ③ `gates{}` 的键都是存在的 stage ⇒ `stage_unknown`；④ 每个 stage 至少绑一个 gate ⇒ `stage_no_gate` | 两用例 |
| C4 | ⑤ 每个 gate 至少一条判据 ⇒ `gate_empty`；⑥ 每条判据已注册（M1-1 的目录 + 注册面）⇒ `criterion_unregistered` | 两用例；`criterion_unregistered` 要带判据 id |
| C5 | ⑦a **`guarantee_delta` 由工具算**：按目录的 `保证` 元数据，逐条查 §6 有效绑定；任一条不达 ⇒ 该保证 `degraded` + 列出缺的判据；**文件里手写的 delta 一律忽略** | 用例：文件里写 `kept` 但实际缺绑定 ⇒ 输出仍是 `degraded` |
| C6 | ⑦b **core 三条在每个适用 stage 出口都必须有效绑定**，四种漏法（`na` 阶段 / `any_of` 门 / 可豁免 gate / 只在某一 stage 绑）都 ⇒ `core_not_effective` | 四个反例各一（这是本卡的**主判据**） |
| C7 | ⑦c **没有“写降级就放行”**：policy 结构上缺 core 需要的 kind（lite 缺 `requirement`）⇒ `core_not_effective`，不因 `guarantee_delta` 里写了降级而通过 | 用例 + 代码审查（无该分支） |
| C8 | ⑧ `artifact_kinds` 的枚举键覆盖 `prototype`/`product`/`throwaway` ⇒ `artifact_kinds_incomplete`；⑨ `assurance.na_stages[]` 必须**由 stages×applies_to 推出**、与推导值相等（多/少都拒）⇒ `na_stages_mismatch` | 两用例（手填错的 `na_stages`） |
| C9 | ⑩ `engine.version` 与 `engine.criteria_manifest_hash` 必填 ⇒ `engine_missing`；⑪ `review.sample_every` ∈ **[2,10]** 整数、`sample_seed` 整数 ⇒ `review_params_invalid`（`0`/超大 N 都在此拒） | 用例：缺 engine；`sample_every=0`；`sample_every=1000` |
| C10 | **纯函数、无副作用**：不写库、不发事件、不落 `baseline.rejected`；同一文件两次 ⇒ 同一输出 | 用例：校验前后 `event` 行数与 `baseline` 行数不变；两次输出 `JSON.stringify` 相等 |
| C11 | 冻结区零改动 | `git diff f37f4dc --name-only -- docs design probe` 为空 |
