# M3-0 · actor/scope/right 身份层与决策权矩阵机器化

## 意图

把「权」从代码里散落的 `if` 变成可查的真源：`actor`（谁）、`scope`（在哪）、`right`（能做什么）三张表 + 迁移 008；`docs/07` §2 的决策权矩阵变成**机器可解析的目录**（动作 → 所需权 → 可否自签 → 可否双人），代码只查目录、不写死判断。`actor` 必须由会话凭据证明，不能由调用方在 payload 里自称（收口 D-056）。

## 对齐

**复述**：不是「加个登录」，而是**一次动作先回答三个问题**：谁在做（actor 来自会话）、在哪个域做（scope 前缀）、有没有这个权（right 查表）。权绑 scope 而不是绑角色——同一个人可以在 A 模块写、在 B 模块只能评审。矩阵是数据不是代码：新增动作要在目录里登记，未登记一律拒（fail-closed）。

**人确认**：pending

**正例 2**
1. `hasRight(human-1, 'write', 'module:src/db')` ⇒ allow；同一 actor 对 `module:src/ui` 无 write ⇒ 拒 `no_permission`（结构化，带 action/scope/actor_kind）。
2. 迁移 008 在空库建三张表并写缺省矩阵行；二次迁移 `applied=[]`；矩阵目录与 `docs/07` §2 表格机器比对（文档新增动作而未登记 ⇒ 红）。

**反例 1**
- payload 自带 `actor: 'someone-else'` ⇒ 拒（`actor_not_from_session`），不许「以 payload 为准」。

### 边界声明（第 4 轮裁定，Lead 2026-11-15）

1. 本卡只交付**“权”的判定**：`hasRight(action, scope)` 回答“该 actor 是否持有所需 right 且 scope 覆盖”。
2. `defect.close` 的“`verify_run` 通过之后才能写”、`verify_finding` 的“只认对象 `producer` 本人”是**动作级对象条件**，与“权”正交，**不由矩阵表达**（矩阵只有 required 权列表，无对象条件列）。它们在 M3-1 接线时由动作实现强制（M3-1 会写成新判据）。
3. 因此 `hasRight` 对这两个动作返回“有权”**不等于**“允许写”；任何调用点不得只看 `hasRight` 就放行。
4. **`AuthActorContext.by` 是调用方自证**：M3-0 不校验 `by` 的真实性（没有凭据链），M3-0 期间可伪造 admin 上下文；M3-1 必须从会话固定 actor（不得由模型/工具自报）。

### 实现期裁定（Lead，2026-11-15，已记台账）

- **D-087 建卡权冲突**：`docs/07` §2 第 1 行「建卡/认领/阻塞 ⇒ `write@module`」与第 3 行「建卡（create）⇒ `plan@domain`」是同一动作两种权。裁定：**建卡 = `plan@domain`**（第 3 行，符合 A-4「树只能由人签的 plan 长」）；第 1 行按「认领 `claim` / 阻塞 `block`」登记。矩阵按 label 拆分后共 **26 个动作**（21 行中 4 行拆成 2/3/2/2）。
- **D-086 跨前缀边界**：动作要求 `plan@domain` 而目标是 `module:` 前缀时，仓内与设计都没有 module→domain 归属来源。M3-0 口径：**跨前缀一律拒**（`no_permission` + `reason:'cross_prefix_denied'`，不猜归属）；M3-1 放开前须先建 module→domain membership 解析（归属表 or 改 `plan@module`）。
