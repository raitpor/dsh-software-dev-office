# M1-1 · 判据框架（注册门槛 + 适用性 + 有效绑定）

## 意图

`docs/04` 说判据不是检查清单，是**可复算的断言**；而它值不值维护成本，取决于「冤枉过几次人」和「抓到过几条真缺陷」。这套东西要能跑，先得有**注册路径**：一条判据没有 `remedy`、没有正例、**没有负例**、超预算、或者没声明守哪条保证——都不许进。

这张卡不给 24 条判据写实现（那是后续卡的事），只建**框架**：目录（code → 适用性 / 保证 / remedy 形状）、注册（五道门槛）、以及**有效绑定**的机械算法（M1-3 的 P15 要用它判 `core_not_effective`）。

## 对齐

**复述**：这卡交付的不是“判据库”，而是“**判据能不能进门的规矩**”。其中最贵的一条是负例——v1 只管“改坏会红”，从不管“不该红的不红”，于是“逼人灌水才过”的判据只能靠评审肉捕。所以**负例缺失 = 注册被拒**，不是警告。

**人确认**：pending（收卡前必须确认）

**正例 2**
1. 注册一条判据：`remedy` 非空、1 正例夹具（跑 `pass`）、1 负例夹具（跑 `fail`）、单次 < 200ms、`guarantee='1'` ⇒ 成功，`criterion` + `criterion_fixture` 行落库，`verify` 绿。
2. 对 core 三条（`spec_set.signed` / `assumption_set.signed` / `provenance.present`）跑有效绑定：全部 5 条条件满足 ⇒ `effective=true`；把某道门的 `waivable` 改成 true ⇒ 该判据 `effective=false`、原因 `waivable_gate`。

**反例 1**
- 注册一条**只有正例、没有负例**的判据：`docs/04` §6 明写“没有负例夹具的判据不可 `active`——由注册校验（写入路径）保证”，实现却放行 ⇒ 这条判据将来红的时候没人知道是不是冤枉人。

## 判据

| # | 判据 | 怎么验 |
|---|---|---|
| C1 | **目录是数据**：`docs/04` §4 的 24 条判据的 `code → {保证, applies_to}` 在代码里有一份**快照**，与文档表逐条相等（多一条/少一条/值不同都红） | 用例：把文档表解析成 24 行（或写死快照 + 注释锚点），与 `src/core/criteria/catalog.ts` 比对 |
| C2 | **注册门槛五条**：`remedy` 空 ⇒ `criterion_invalid`；无正例 ⇒ `no_positive_fixture`；无负例 ⇒ `no_negative_fixture`；单次 ≥200ms ⇒ `budget_exceeded`；`guarantee` 缺/非法 ⇒ `guarantee_invalid`。**五条都拒，且一行不写** | 五条负例各一，断言拒绝码 + `criterion` 表行数不变 |
| C3 | **负例的语义是“不该红的不红”**：注册时夹具必须实跑——正例跑出 `pass`、负例跑出 `fail`；反过来（正例 `fail` / 负例 `pass`）⇒ `fixture_mismatch` | 用例：夹具 `expected_status` 与实跑结果不符 |
| C4 | **只强制 core 三条**：M1 的有效绑定只对 `spec_set.signed`/`assumption_set.signed`/`provenance.present` 算，其余 21 条按 `na`（未实现）处理，不参与拒绝 | 用例：只有 core 三条绑定时 `coreEffective=3`；删一条绑定 ⇒ 不给 2 |
| C5 | **有效绑定五条件**（`docs/04` §6）：①已注册 ②某 gate 的 `criteria[]` 含它 ③该 gate 的 stage `kinds ∩ applies_to ≠ ∅` ④`policy_mode='all_of'` ⑤`waivable=false`。缺任一 ⇒ `effective=false` 并给**具体原因码**（`not_registered`/`not_in_gate`/`stage_not_applicable`/`policy_mode_any_of`/`waivable_gate`） | 五条各一个反例 + 一个全满足的正例 |
| C6 | **“检查点不连续”也要报**：某个 `kinds` 与判据 `applies_to` 相交的 stage 出口没绑它 ⇒ 该判据 `effective=false`（原因 `stage_gap`），不是“某处绑了就行” | 用例：两个 stage 都适用，只在一个出口绑 ⇒ 红 |
| C7 | **core 没有后门**：policy 结构上就没有 core 判据需要的 kind（如 lite 缺 `requirement`）⇒ 结果必须是 `core_not_effective`，**不许**因为 `guarantee_delta` 里写了降级就放行 | 用例：构造缺 kind 的 policy ⇒ `effective=false`；断言实现里没有任何“看 delta 就跳过”的分支（代码审查 + 用例） |
| C8 | 写路径仍只经 `append()`；注册走 `criterion.registered` 事件，不新增第二条写口 | 复用 M1-0 的 C1 静态扫描口径 |
| C9 | 不污染冻结区 | `git diff f37f4dc --name-only -- docs design probe` 为空 |
| C10 | **夹具必须有事件载体**（台账 D-032 裁定 ①）：`criterion.registered` 的载荷扩展为带 `fixtures[]{polarity,input,expected_status}`，reducer 在**同一事务**写 `criterion` 行 + `criterion_fixture` 行；注册门槛（C2/C3）读的就是这些行，**测试不许再直插 `criterion_fixture`**（M1-2 的 C5 因此在 M1-1 收卡后才算生产绿） | 用例：走 `append()` 注册带 2 正 1 反的判据 ⇒ `criterion_fixture` 3 行、`verify()` 绿；删掉 `fixtures[]` ⇒ `no_negative_fixture`；同一 `criterion_id` 已有夹具换个 `input` 重放 ⇒ 幂等或显式冲突（不产生半套夹具） |
| C11 | **物化集随之扩到 8 张**：`criterion_fixture` 有 `id` 主键、无 fold-only 列，加进 `MATERIALIZED_TABLES`；否则 M1-0 的“fold 产出落在集外表 ⇒ 失败”安全网会让任何一次 `criterion.registered` 直接 `materialize_failed` | 用例：注册成功后 `append` 成功且 `criterion_fixture` 表有行；`verify` 对账口径同步（若纳入对账，需说明为什么不与 `VERIFIED_TABLES` 冲突） |
