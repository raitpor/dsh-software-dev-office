# M2-3 · 假设处置链（先签后处置、失效 fold、撤销级联）

## 意图

“先签后处置”是 SDO 的防代签核心：工具可以**渲染**一张处置清单（哪条假设 confirm / reject / convert），但**授权只能来自人签的 `decision(kind='assumption_set')`**；`assumption.disposed` 只是把已生效的处置**投影**进状态，不能自己当授权源（`docs/02` §8、`docs/03` 先签后处置、`design/03` P12）。

M1 只做到“事件能写进去”（M1-0 的 `assumption.disposed` 有 `requireSignedDecision` 前置），但没有做完整的链：批量签字载荷里的 `dispositions[]` 与 `assumption.disposed` 的逐条对账、`invalidated → open` 的失效回填、以及撤销 `assumption_set` 时的级联（覆盖的假设回 `open`、覆盖的需求集合失效、必须重签）。

依据：`docs/02` §8/§14（`assumption.recorded` 只建 `open`；`disposed` 是唯一状态迁移生产者）、`docs/03` 先签后处置段、`docs/06` §5 `dispositions[]` 与 `content_hash` 覆盖、`docs/04` §5.2 core 判据 `assumption_set.signed`。

## 对齐

**复述**：不是“给假设加个状态机”，而是**把“处置”拆成两件事**：一件是人签的集合（谁在什么时候、按什么命题、处置了哪几条），一件是工具按签名投影出的状态。状态永远不能先于签名存在，签名覆盖不到的那条假设必须还是 `open`。撤销也一样：撤的是那份签名，撤回后覆盖的假设**回到未处置**，不是“删掉痕迹”。

**人确认**：pending

**正例 2**
1. 2 条 `open` 假设 → 渲染处置清单（1 confirm / 1 reject）→ 人签 `decision(kind='assumption_set')`（payload 带 `spec_ids[]`/`dispositions[]`/`readings_hash`）→ 工具按载荷写 2 条 `assumption.disposed` ⇒ 两条状态分别 `confirmed`/`rejected`，`decision_id` 都指向同一份 decision，`verify` 绿。
2. 某假设的 `inputs[]` 里一条 spec 被 `spec.revised` 改了 hash ⇒ 该假设自动 `invalidated`（fold 检测），之后重新签字把它处置为 `open`（再讨论）；`invalidated → open` 只能由新签名触发，不能工具自己改。

**反例 1**
- 人签的 `assumption_set` 只覆盖 1 条，工具却写 2 条 `assumption.disposed` ⇒ 第 2 条必须被拒（`not_covered_by_decision`），且**第 1 条也不许半截生效**（同一批要么都按签名投，要么都不投）。

## 判据

| # | 判据 | 怎么验 |
|---|---|---|
| C1 | **签名是唯一授权**：`assumption.disposed` 必须带 `decision_id`，该 decision 必须 `status='valid'` 且**已签名**、`kind='assumption_set'`、其载荷 `spec_ids[]` 覆盖该假设、`dispositions[]` 中该条的处置与事件一致 | 用例：无 decision、unsign、kind 错、未覆盖、处置不一致——五种各一条，全部拒且 `assumption` 状态不变 |
| C2 | **覆盖名单只认签名载荷**：`disposed` 事件里若带 `covered_spec_ids` 之类字段，**只用于对账，不得作为授权依据**（签名载荷才是源） | 用例：事件 payload 声称覆盖 3 条、签名只覆盖 1 条 ⇒ 只投 1 条（或整批拒），不得按事件放宽 |
| C3 | **`recorded` 只建 `open`**：`assumption.recorded` 带 `status` 非 `open` ⇒ 拒 | 用例：`status:'confirmed'` ⇒ 拒；不带 ⇒ 落 `open` |
| C4 | **处置是唯一迁移生产者**：`open → confirmed/rejected/converted` 只能由 `disposed`；`invalidated → open` 只能由新签名（重新处置）；任何别的路径改状态 ⇒ 拒 | 用例：直接 `assumption.recorded` 改状态、工具侧直接 UPDATE ⇒ 均拒/被 verify 抓 |
| C5 | **失效 fold 正确**：假设 `inputs[]` 里的 spec 版本变了（hash 变）或消失 ⇒ 状态 `invalidated` 且**不删行**（保留历史）；幂等键 `(spec_id, input_id, 旧 hash)`，同一失效只记一次 | 用例：改一条 input 的 spec ⇒ 失效一次；重复投同一事件 ⇒ 幂等；恢复旧 hash 不自动复活（要新签） |
| C6 | **撤销级联**：`decision(kind='assumption_set')` 被 `decision.revoked` ⇒ 该签名覆盖的假设全部回 `open`（不是 `invalidated`）、并触发 `spec_set` 侧失效（覆盖的需求集合失效、必须重签）；级联本身也落事件，可 verify | 用例：撤前 2 条 confirmed ⇒ 撤后 2 条 open + 需求集合标记失效；撤销不存在的 decision ⇒ 拒 |
| C7 | **批量原子性**：一批 `disposed` 中任一条不合法 ⇒ 整批不生效（事件 0 行或全回滚），不得部分成功 | 用例：3 条里第 3 条不覆盖 ⇒ event 0 行、状态不变 |
| C8 | **`verify` 双向对账**：每条有效 `assumption_set` 的 `dispositions[]` 都必须有对应 `assumption.disposed`（缺 ⇒ 按 `decision_id` 幂等重放，重放后仍缺 ⇒ 红）；每条 disposed 的 decision 必须有效 | 用例：删一条 disposed 事件 ⇒ verify 红并指出缺失条；重放后恢复正常 |
| C9 | **core 判据连上**：`assumption_set.signed` 的有效绑定/门禁接入 M2-2（空集也必须有人签）；M2-2 的判定里这条能真红 | 用例：有 open 假设却没签 ⇒ `assumption_set.signed` fail |
| C10 | 冻结区零改动 | `git diff f37f4dc --name-only -- docs design probe` 为空 |
