# M3-2 · 冲突可见（`conflicts` 不是 `disputed`）

## 意图

两人并发改同一对象的同一字段：**一个成功、一个 409**，失败者的主张不丢——进 `conflicts`（双方主张 + 时间 + 各自基于哪版），等人裁决。与 `disputed`（对同一事实的两种判断，走评审）严格分开：冲突是“写不进去”，不是“说得不一样”。

## 对齐

**复述**：冲突不是错误、也不是分歧，是**同一处被两个人同时写了**这个事实。系统必须让失败者看到“你要写什么、对方写了什么、你基于哪版”，并且**不许自动合并**（M3 不做 CRDT、不做 last-write-wins）。冲突行由事件派生，裁决走人签，不进 `disputed` 通道。

**人确认**：pending

**正例 2**
1. A、B 同时改 `spec` 同一字段 ⇒ 先提交者 `ok`，后者 `conflict`（409 语义、带 `conflict_id` 与 `base_hash`），`conflicts` 视图出现一行含双方摘要。
2. 人签 `decision(kind='conflict_resolution')` 采纳一方 ⇒ 冲突行 `resolved`、被采纳方重放回链、另一方 payload 留在冲突行里可追溯。

**反例 1**
- 把冲突写进 `disputed`（或反过来）⇒ 检查红：两个集合不许互相污染。

## 判据

| # | 判据 | 怎么验 |
|---|---|---|
| C1 | 并发写同一对象同一字段：一个 `ok`、一个 `conflict`（带 `conflict_id`/`base_hash`/双方摘要），事件只落成功那条 | 同进程 + 两进程各一组用例 |
| C2 | `conflicts` 视图一行一冲突：`subject`/`field`/`winner_actor`/`loser_actor`/双方摘要/`at`/`status ∈ {open,resolved}` | 视图用例 + 与事件逐条对账 |
| C3 | **`conflicts` 与 `disputed` 分离**：冲突不产 `dispute.*` 事件，`disputed` 集合不出现冲突项 | 互污染负例即红 |
| C4 | 裁决只认人签 `decision(kind='conflict_resolution')`，工具不自动选边 | 无签字 ⇒ 仍 `open`；有签字 ⇒ `resolved` 且采纳方入链 |
| C5 | `verify` 对账：冲突行可从事件重算，直改行被抓 | 直改 `status` 用例 |
| C6 | 冻结区零改动 | `git diff f37f4dc -- docs design probe` 为空 |
