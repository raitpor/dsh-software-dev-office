# SDO v2 接管自己的开发流程

> 问题不是“什么时候用上 SDO”，而是**每一步接管换掉了哪一层控制**。接管分三层，可以分别接管、分别回退。

## 1. 三层控制

| 层 | 现在（手工） | 接管后（SDO） | 最早可接管 |
|---|---|---|---|
| **记录层**：这张卡干了什么、依据是什么 | 聊天记录 + 提交信息 | `intent`/`spec`/`task`/`evidence`/`claim` 事件链 | **M1 中段**（六表 + 对齐三件套可用） |
| **判定层**：这张卡算不算完成 | Lead 看测试 + reviewer 说 pass | `gate.judged` 绑 `baseline.hash`；判据 24 条 + core 三条 | **M2**（冻结要人签，判定要 `stage_run.baseline_hash`） |
| **调度层**：下一张卡给谁、能不能并行 | Lead 拍脑袋 + 写域约定 | `pm_queue` + 预占 + `lease` + `block_code` | **M3 末 → M4**（先有权限与独立性，再有预占） |

**接管不是开关，是三次换层**。任何一层没准备好就接管，都会退化成“用新工具记旧流程”。

## 2. 四个阶段

| 阶段 | 时间 | 记录 | 判定 | 调度 | 人做什么 |
|---|---|---|---|---|---|
| **S0 影子** | M1 中段起 | SDO 真记（卡先建后做） | 人工（reviewer + Lead） | 人工 | 照旧，只多一步“先建卡再动手” |
| **S1 并行** | M2 冻结 baseline 后 | SDO | **双判**：SDO 门禁 + reviewer 手工，两边都记 | 人工 | 两边不一致时人裁 |
| **S2 接管** | M3 末 | SDO | **SDO 判定即结论**，reviewer 退为抽样 | 人工派发 + SDO 队列 | 只签字、只裁红卡 |
| **S3 自举** | M4 | SDO | SDO | **SDO 派发**（预占/lease/block） | 只看 `pm_queue` 与红卡 |

### S0 的纪律：先建卡再动手

影子期最容易变成“干完了补录”。补录的记录没有预测力，也测不出返工。规则只有一条：**卡在动手前建，判据在动手前写**；做不到就说明这张卡还没想清楚，不许开工。

### S1 的纪律：双判必须真双判

SDO 判绿、reviewer 判红 ⇒ **记 `gate_miss`**（这是最有价值的样本）。SDO 判红、reviewer 判绿 ⇒ 记 `gate_overstrict`。两者都进 `gaps`，并在每周对账里逐条解释。**双判不许互相抄**：reviewer 看不到 SDO 的判定结果，只看 diff 与证据。

## 3. 接管判据（每条都可测，缺一条不接管）

| # | 判据 | 怎么测 | 不达标的含义 |
|---|---|---|---|
| G1 | **真实工作量**：≥ 30 张卡在 SDO 里走完生命周期（建卡 → 判据 → 证据 → 判定 → 收口），其中 ≥ 10 张由 agent 执行 | `task` 表按 `closed_at` 统计；抽查 5 张看建卡时间是否早于首次提交 | 只是演练，没接住真实流程 |
| G2 | **门禁真的挡住过**：并行期 ≥ 5 次 `gate_miss` 或真红被挡下的提交 | 事件链里 `gate.judged=fail` 且随后有修复提交 | 尺子从没红过 = 摆设 |
| G3 | **无越权**：连续 2 周 `verify` 日检无“未授权写入/未签基线判定” | `verify` 报告 + `decision` 与 `gate.judged` 的 join 为空 | 门禁是装饰 |
| G4 | **签字不贵**：单次签字中位 ≤ 10 秒；并行期内 ≥ 5 次真实签字（含 1 次 baseline 收紧） | 签字事件的时间差；`baseline` 里 `direction=tighten` 至少 1 行 | 签字贵 = 人会绕过 |
| G5 | **闭环**：连续 3 个工作日 `pm_queue` 只靠 SDO 工具推进到空（人只回 `attention`），期间 0 次绕过 SDO 直接改文件 | 每日 `pm_queue` 读数 + `verify` | 还有手工旁路 |
| G6 | **回退演练**：主动切回手工流程一次、再切回，数据无损（`verify` 全绿） | 演练记录 + 两次 `verify` | 接管不可逆 = 不敢接管 |

> 判据 G2 最容易被糊弄：如果门禁从来没红过，那不是“质量好”，是**判据没咬住**。所以它被写进接管条件，而不是“质量指标”。

## 4. 每次接管门要交的证据包

一个目录（或一份台账页），四样东西：

1. **读数**：G1–G6 的原始查询结果（不是结论，是行）；
2. **样本**：随机 10 张卡的完整链路（建卡 → 证据 → 判定 → 收口），含 2 张红过的；
3. **对账**：双判期的不一致清单与逐条解释；
4. **回退单**：这次接管如果失败，怎么切回去（具体到命令与数据）。

没有这四样，不签字；签了也不算接管——**接管的定义是“有证据的换层”，不是“宣布换层”**。

## 5. 回退（反接管）

触发任一条件，**当天回退到上一阶段**，不等周会：

| 触发 | 阈值 |
|---|---|
| 门禁误判导致返工 | 一周 ≥ 2 次 `gate_miss` 且都是“SDO 绿、人红” |
| `verify` 红无法定位 | > 1 个工作日 |
| 签字失败/超时 | 一周 > 10% |
| 数据损坏或无法重放 | 任意一次 |
| 有人绕过 SDO 改了该走判定的东西 | 任意一次，且未在当天补记 |

回退不是“关掉 SDO”，是**把判定层换回人工**：`baseline` 记一次 `direction=loosen` 的临时降级要人签——**降级本身也要签字**，否则回退就成了新的旁路。记录层继续留在 SDO 里，回退不删数据。

## 6. 自举的两个坑

**坑一：用 SDO 判 SDO 的引擎代码。** 门禁引擎自己有 bug 时，它会把错的判成对的。规则：`src/core/**`、`src/sign/**`、判据引擎的改动**必须人签 baseline + 独立 reviewer 双审**，不能只靠门禁自判。接管的是“流程”，不是“引擎的正确性”。

**坑二：接管后设计不再被挑战。** 接管让“按约定做对”变便宜，但**约定本身对不对**仍要靠评审。所以每 M 一次的整套评审不因为接管而取消；接管只是把“增量检查”自动化了。

## 7. 与里程碑的对应

```
M0 ── M1 ──────── M2 ────────── M3 ────── M4
      │           │             │         │
      S0 影子      S1 双判        S2 接管    S3 自举
      (记录层)     (+判定层)      (判定生效)  (+调度层)
```

- **M1 中段**：六表 + 对齐可用 ⇒ 开始真记卡。此时 SDO 还不判，只回答“这卡当初说要做啥”。
- **M2 末**：baseline 冻结 + 门禁 + 签字链齐 ⇒ 双判。**这是接管的实际起点**。
- **M3 末**：权限、独立性齐 ⇒ 判定层正式接管；回退路径每月演练一次。
- **M4**：预占与 lease 齐 ⇒ 调度层接管，SDO 开始给自己派卡。
