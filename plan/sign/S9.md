## 签署者当场确认的四件事

1. **物化集扩到 28 张**（`MATERIALIZED_TABLES = TABLE_NAMES − NON_MATERIALIZED`），不再存在“事件合法写入、投影静默不落”的 kind；无 `id` 列的表按**DDL 真主键**建键（`config.key`、`snapshot_parent(snapshot_id,parent_id)`、`release_item(release_id,kind,target)`），取不到主键的表 **fail-closed** 拒绝，不用代理 id 列糊过去。
2. **28 个 create 语义 kind 统一走 `createOnce`**：同 id 同内容 ⇒ no-op；同 id 不同内容 ⇒ `materialize_failed`（“already exists with different content; this projection is append-only”），原行保留、事件数不变。**但它不焊死状态机**：`stage.entered` 走 `createOnce` 之后，`stage.exited`/`gate.judged` 仍能 patch 同一行（有 DB 用例证明）。
3. **证据从“表非空”升级为“逐列快照”**：`test/fixtures/per-kind-fold.json` 56 条整行（含 fold-only 列）与 fold 结果 deepEqual；`write.supported-kinds.test.ts` 不再只断 `ok`。这正是第 1 轮抓到的假绿：把 `taskDependenciesChanged` 换成空函数，两文件仍 9/9 全绿。
4. **`release.frozen.frozen_by` 以冻结 DDL 为准**（JSON 数组、≥2 human），改 fold 不改设计；`migrations/004` 让 `stage_run.gate_id`/`baseline_hash` 在开闸时可空（升级保留存量行）。

**两条诚实边界**：

- **`at` 不参与 create 一致性比较**：同 id、同业务列、不同 `at` 的新事件 ⇒ 静默 no-op（M1 的 create 语义下可接受，但必须写明）。
- 静态断言（“函数体必须到达 `createOnce(`”）按“文件名 + 函数名”定位，将来两个文件出现同名 reducer 会取错——已记入卡「已知边界」。
