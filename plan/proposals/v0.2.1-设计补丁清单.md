# v0.2.1 设计补丁清单（接管后第一批设计工作）

> **来源**：`plan/03-偏差台账.md` 里 `gap`（47 条）与 `defect`（7 条）中**还没写回设计**的那些——它们在实现期被裁定成“先这样做”，都带着“v2.1 人签追认/补文档”的尾巴。
> **性质**：这是**设计变更**清单，不是实现任务。每条都要：改 `docs/`（冻结区，需人签）→ 重跑 P15/门禁 → 若动了 baseline 字段或判据集合，还要走 `baseline.amended`/`loosened`。
> **时机**：M5 接管成功后再动（用户 2026-11-16 指令：“若基本完成，则接管后将这些补丁列到 0.2.1 版本”）。接管期间不动冻结区。
> **编号约定**：`P-xx` 是本清单的组内编号；`D-xxx` 指向台账原条目。

## 8. 明确**不补**（已签边界，别再翻案）

- 单钥只证 actor 级独立性（不证“两个不同的人”）；多签名者并发不保证——S23 边界。
- 探针可直接改库绕 `verify`（`verify` 是发现器，不是防护）；`projection_guard` 哨兵可被任意 SQL 解除——S24 边界。
- `scope_owns` 是部署数据（无 INSERT 入口），不是用户可改的配置——S26 边界。
- M2 只强制 core 三条判据、其余 `na` 必须带 `not_enforced_in_m2`——D-075（M3+ 递进）。
- 列级裁剪 M3 只做 `team.rights`，`team.kind` 同泄露面保留——S27 边界。

## 9. 版本与签字建议

1. **0.2.1 = 设计对齐版**（只改 `docs/` + `design/`，不加功能）：上面 P-01…P-39 一次走完，出一版 `frozen/design-v2.1`，并在 `FREEZE.md` 记 manifest sha256。
2. 若其中某条会**放宽**现有 baseline（例如 P-23 的 TTL 语义、P-16 的裁剪真源），必须先 `baseline.loosened` 人签，再改文档——顺序不能反。
3. 0.3 之后再谈新机制（例如多 PM、多宿主、跨项目记忆共享），先把 0.2.1 的账清完。
