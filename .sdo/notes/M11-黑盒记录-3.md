### 白盒：文档与脚本行为不一致的一处

`init.mjs` 生成的 `.sdo/意图.md:41-47` 的 §12 小节是「12.1 需求与基线 / 12.2 设计与测试」，而 `sdo-flow/templates/意图.md:41-48` 是「12.1 流程状态可读 / 12.2 门禁与读数可复跑」；SKILL.md:57 又让「`cp templates/意图.md .sdo/意图.md` 后填」。照 SKILL 做会覆盖 init 的版本，两版 §12 小节名不同，判据里写 `（依据：§12.x）` 时可能踩 `basis_section_missing`。第二处同性质：`view.mjs next` 把只有 `- 判定：待填` 的 `.sdo/sign/S1.md` 显示成「M1 计划：已签 S1」，而同一时刻 `check.mjs` 报 WARN `plan_sign_unsigned`——「已签」的判据只是文件存在，不是判定非空。

### 黑盒：必须靠猜的环节

**门 → 判据的映射**。`milestone.mjs declare --list` 只列 15 个门和 41 条判据池，没有说「哪个门要哪几条」；SKILL §5.3 只说「不写映射会并集闭合」。我只能按语义自选 7 条并用 `--map` 分配，`gate.mjs init` 照单生成 17 行，`gate.mjs --file` 只报「没有判定」，并不告诉我漏没漏 preset 要求的判据——选错不可见。第二处是 trace 的认领口径：我先按 SKILL §5.1 在 `.sdo/milestones/M1.md:7` 写 `认领需求：R-01、R-02、R-03`，`check --trace` 仍报 3 条 `trace_orphan_requirement`；改成卡面 `.sdo/cards/M1-0.md:5` 的 `references: [R-01, R-02, R-03]` 才 0 问题——同段并列的两种登记，实际只有卡面算数。

### 系统：没写清楚的前置条件

**git 的提交时机与范围**。SKILL §5.7 只说 draft 有 git 时「需要可解析的 git HEAD（先 commit）」，没说卡面 `write_scope` 里的文件必须已存在且已入库；我先跑 draft 得到 `TREE_MISMATCH` 与 `黑盒记录.md sha256=缺失`（§6）。其次**目录位置**：SKILL §11 的「项目内 `skills/sdo-flow` 优先」和 write_scope 的 `skills/sdo-flow/` 归一都以该目录名为前提，本环境技能目录是 bb3 根下的 `sdo-flow/`，而 bb3 又嵌在外层 git 仓库里（`git rev-parse --show-toplevel` 指外层）；「仓库相对路径」以哪个仓库为根没有明文，我按 `.sdo/` 所在目录当根，才和 draft 的「被签文件」清单对上。权限与联网不是问题（全程只写 bb3，未装依赖）。

### 集成：产物接口对不上的两个命令

**`gate.mjs init` 的输出不是 `gate.mjs --file` 的合法输入**：init 写出的 `.sdo/gates/M1.md` 每行判定是 `待判`、证据是 `待填`，`gate.mjs --file` 对 `待判` 一律判「没有判定」并 exit 1；中间没有任何命令能把 init 产物补成 gate 输入，必须人手填 17 行（且 core 三条要人签）。**`card.mjs new --write-scope` 的输出被 `sign.mjs draft` 当成「被签文件」清单**：卡先建、记录后写，draft 在 `黑盒记录.md` 存在前就报 `sha256=缺失`/`TREE_MISMATCH`——A 的写域声明成了 B 的存在性前置。

### 故障与恢复：靠什么恢复、哪条信息本该更早

红字链与恢复：`check --plan` 的「尚无计划签 + hash 不匹配」→ 先 `milestone.mjs freeze` 再 `--print-frozen-hash`（SKILL §5.3 有写）；`check --trace` 的 3 条孤儿需求 → 卡面补 `references:`；`gate` 的 17 条「没有判定」→ 按任务书 §2.10 如实记为「骨架待填判定」，不硬填 pass；`draft` 的 `DIRTY`/`TREE_MISMATCH` → `git add -A && git commit` 后重跑得 `CLEAN`，但锚点对照是 `AHEAD 1`（不是 `SAME`，见 §7）：S1 的锚点停在 8c88，之后 card/gate/readings/记录每多一次 commit 就多落后一格。本该更早出现的是：①「draft 需要 write_scope 文件已入库」应写在 `card.mjs new` 或第 7 步；②`sign.mjs new` 的锚点是当时的 HEAD，而任务书把它排在第 6 步、后面还有 card/gate/readings 三次写盘，天然会落后——应提示「最后一次 commit 之后再 `sign.mjs new`（或用 `--force` 重签）」。

读数（原文）：## overall：partial @ .sdo/readings/M1.md:21

说明：`AHEAD n` 不是恢复失败，而是 git 下 `sign.mjs new` 的锚点机制造成的——S1 在 8c88 时生成，其后 card/gate/readings/记录与本次记录修订各 commit 一次，HEAD 前移 n 次，而 S1 的「被签对象」不会自己更新。任务书第 6 步把 `sign.mjs new` 排在 card/gate/readings 之前，等于让锚点天生落后；SKILL §5.7 只写了「先 commit」，没写「最后一次 commit 之后要 `sign.mjs new --force` 重签（重签后 S1 又未入库，会换来 DIRTY）」。两个目标（锚点=HEAD、工作树干净）在「签文件本身也入库」的前提下无法同时成立，这一点应在文档里明说。
