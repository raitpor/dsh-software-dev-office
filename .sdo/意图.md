# 意图（intent）：SDO 流程 skill（文件与命令实现）

状态：**已签 S1**（2026-11-18T17:30+08:00，选项：签：复述准确；2026-11-19 追加口径，见 §10；2026-11-21 追加初衷重述 §12，**待签 S1-A**）
版本：intent-001

## 1. 一句话

把这套项目管理流程（意图→计划评审→卡→两轮评审→签字→读数门→台账）做成**一种纯文件与命令的实现形式**：真源是 Markdown 账本与可复跑命令，人证是真人选的问答选项，门禁是出口勾选表 + 检查脚本。

## 2. 为什么

- 这套流程的价值不在某个存储引擎里，而在**约束的形状**：先对齐再动手、每步可判死、每步留证、每次签字有复述。
- 换一个环境（客户机器、临时会话、别人的仓库、纯 Web 会话）时，应该能按同一套规矩干活，而不是把规矩留在这个仓库的操作习惯里。
- 所以它需要一种**不依赖额外运行环境**的实现形式：一个 skill、几份模板、三份生命周期 preset、一个文本检查脚本。

## 3. 三条保证怎么落地（本实现形式）

| 保证 | 本实现的载体 | 诚实说法（不夸大） |
|---|---|---|
| 对齐 | 意图/计划文件 + 复述 + **人签（问答选项）** | 人点过“对，这是我要的”；**没有密码学签名**，靠人亲自读复述 |
| 可审计 | 追加式 Markdown 账本 + 每条带日期与出处 + `git` 提交 | 账本是文本，**同 uid 可改**；`git` 只在你提交后留痕，不防篡改 |
| 防漂移 | 判据清单 + 出口勾选表 + 检查脚本 + 计划评审 | 门禁靠**人按清单判读 + 脚本查格式**，没有运行时强制 |

三条保证都成立，只是**载体不同**：事件表/签名进程换成账本/问答选项，机器强制换成清单 + 可复跑命令 + 独立评审。

## 4. 做什么（范围）

1. `skills/sdo-flow/`：`SKILL.md` + `references/`（八篇）+ `presets/`（三份）+ `templates/`（九份）+ `scripts/{check,view}.mjs`（文本检查器与快捷视图，Node 零依赖）。
2. 三份**流程 preset**（生命周期：`waterfall` / `prototype` / `incremental`，与设计 `docs/08` §1 一致），各含阶段序列、出口判据勾选表与可迁移的 `policy` YAML。
3. 检查脚本（Node，Windows/Linux 通用）：账本 7 列与 id 递增、表格列数/游离行、签字文件必备字段、卡必备段落、读数 verdict、`--presets` 与设计文档比对。
4. 快捷视图：从 `.sdo/` 的 Markdown 拼出 `state`/`queue`/`board`/`ledger`/`signs`/`plan`，支持 `--json`，只读。
5. 人签模板：一律 `ask_user_question` 三选项（签：复述准确 / 改：复述不准 / 不签：先不做）。

## 5. 不做什么（非目标）

- 不实现事件表、写网关、哈希链重算、签名密钥、运行时门禁。
- 不复制 `docs/` 全文；文档不设行数上限，按三条可判要求：
  - 能读懂：冷启动 agent 只读 `SKILL.md` 能说清下一步；R44 中额外 reference ≤3、脚本源码 0、卡点 ≤2。
  - 能记住：`SKILL.md` 内有硬约束锚点表（判据类型/基线四份/门签/冻结 hash/需求认领/追溯链）；M10-2 C4 表行数=6，缺一红。
  - 能跟着走：照 `SKILL.md` 从 `init.mjs` 到建卡 + `check` 绿 + 生成待签草案；R44 全程卡点清零。
- 不假装等价：每条边界必须写进「已知边界」，并且能被一条命令演示（R4）。

## 11. 信任前提（2026-11-20T09:54+08:00）

本 skill 的流程成立，依赖以下前提；它们不是可执行保证，而是使用时的约定：

1. **假设模型可信但会犯错**：模型按 `SKILL.md` 与 references 执行，不故意绕流程；机制挡的是误操作与漏步，不是恶意模型。
2. **假设替身不代签**：模型可以把复述和选项呈给人，但只能由真人选择；模型不得自答、不得把“问过”写成“签过”。
3. **人签 = 真人在问答里选选项**：回答文本可改、可伪造，本 skill 不做密码学签名；需要强证明时在仓库外另加。
4. **不提供密码学保证**：签字文件、台账、卡面都是可改的 Markdown；审计边界由 `references/07` 逐条写明，不夸大。
5. **判定权在人**：证据列只记命令与输出，判定由评审据证据填；检查器只查格式与合法值，不判断判定是否正确。

## 12. 初衷重述（2026-11-21，待签 S1-A）

以上各节描述的是“怎么做成一套可用的流程”。本节补回**为什么做它**——用户 2026-11-21 的原始意图：

> 这套东西的本质是**软件工程理论的落地实践**：需求工程、设计方法（面向对象建模、结构化设计等）、实现阶段方法论、测试方法论（黑盒、白盒、系统测试、集成测试等）。
> 流程约束的意义是**让 agent 切实做了这些内容**，而不是把流程本身当成目的；此前 M1–M7 做的是为后续开发搭骨架。

### 12.1 四个理论维度（本流程要真正促成的活动）

| 维度 | 要真的发生的事（不是“写个标题”） | 当前是否被流程逼出来 |
|---|---|---|
| 需求工程 | 需求获取与澄清、需求规格化、可追溯（需求↔设计↔测试）、需求变更控制 | **部分**：意图/复述/评审强制“先对齐”，但没有需求规约产物，也没有需求↔卡↔测试的追溯链 |
| 设计方法 | 面向对象建模（类图/时序图/状态图、职责分配、SOLID、设计模式取舍）；结构化设计（数据流→模块结构、耦合与内聚、接口契约） | **弱**：卡面有“设计”段与评审，但没有强制的设计产物形态（如类图、接口签名、决策记录） |
| 实现方法论 | 编码规范、单元设计先于编码、小步提交、重构、增量集成、错误处理与边界约定 | **部分**：一卡两笔、写域、变异红证约束了“怎么做”，但没有编码规范/重构/集成节奏的判据 |
| 测试方法论 | 测试设计先于实现；黑盒（等价类、边界值、判定表、场景法）；白盒（语句/分支/路径覆盖）；集成（自顶向下/自底向上/持续集成）；系统测试（功能、非功能、回归） | **部分**：判据要求“反例 + 变异红证”（本质是白盒/变异测试），但没有测试计划、覆盖口径与系统/集成测试的明确产出 |

### 12.2 流程约束与理论活动的关系（判据成立的依据）

- 每个阶段必须有**可检查的产物**（意图、计划、卡、设计说明、测试、读数），否则门红。
- 每个产物必须有**判据**，判据要有**证据**（可复跑命令），判定由评审给出。
- 判据里必须至少有**语义判据**（M6-1 起强制），因为纯结构判据只能证“写了”，不能证“想对了”。
- 因此：流程不是形式主义，而是**把“理论要求的活动”变成“不做就红”的机制**；评价这套 skill 的标准不是“流程跑完了”，而是“四个维度的活动真的发生了，且产物经得起评审”。

### 12.3 现状定位（诚实说法）

- M1–M7 交付的是**骨架**：真源与账本、签字与复述、计划/卡/门三层评审、读数门、检查器与变异红证、归档与减重。
- 骨架已能挡“跳过步骤、伪造证据、事后补签”这类**流程性错误**；但**领域活动是否发生**仍主要靠评审判（§11.5 的信任前提），尚无“需求↔设计↔测试”的追溯与覆盖口径。
- 所以下一步（m8 及以后）的主题应是**让四个维度各自有产物、有判据、有追溯**，而不是继续加流程闸。

### 12.4 与既有条款的关系

- 本节不推翻 §1–§11：目标仍是“纯文件与命令的实现形式”，边界与信任前提照旧。
- 本节把“流程”降级为实现手段、把“软件工程活动”提为真正目的；冲突时以本节为准（待 S1-A 签署后生效）。

### 12.5 两层结构：项目基线 与 里程碑切片

本 skill 目前只有“里程碑”一层，导致里程碑里重复定义需求（漂移），或各里程碑各说各话（无法追溯）。从 M8 起分两层，判断标准是一句话：**“这一轮取消后，它还需要存在吗？”** 需要 ⇒ 项目基线；不需要 ⇒ 里程碑切片。

| 层 | 放什么 | 生命周期 |
|---|---|---|
| **项目基线**（`.sdo/baseline/`） | 需求基线 `R-xx`（含非功能 `NFR-xx` 与验收口径）、架构决策 `ADR-xxx`、测试策略（变更类型→测试技术）、质量属性与风险登记 | 只定一次，变更走追加签 |
| **里程碑切片**（`.sdo/milestones/M<n>.md`） | 本轮认领的 `R-xx`、细化设计、测试设计、读数与门 | 每轮重写 |

五条咬合规则（M8 起逐条落成判据）：

1. **引用而非复制**：里程碑只写 `R-03, R-07`，不重写需求正文。复制一份就必然漂移——这与 M6 抓到的“同一判定两份实现”是同型错误。
2. **单向依赖**：里程碑读基线，不能改；要改只能提变更请求，走项目级追加签并写明方向（扩展/收窄/修正）。
3. **覆盖率闭合**：每个 `R-xx` 恰好被一个里程碑认领（或进 backlog 并写理由）；每张卡引用至少一个 `R-xx`；每条测试引用卡与判据；不许有孤儿需求、孤儿卡、孤儿测试。
4. **版本绑定**：里程碑冻结段记录**项目基线 hash**；基线变更后，未收口的里程碑必须显式声明“基于旧基线（理由）”。
5. **门分层**：项目门（基线冻结、发布）与里程碑门（增量出口）互不替代；里程碑门全绿不等于可发布。

分工：前四条可机检（四向闭合、基线 hash、策略允许的技术集合）；第 5 条与“需求质量/架构合理性/覆盖是否足够”只能靠评审与人签。

**不引入 SQLite**（2026-11-21 裁定）：真源必须是可读、可签、可 diff 的文本；规模阈值出现前不付数据库的维护税。将来若需要，只引入**可丢弃的派生索引**（能重建、能与正文对账），不做“DB 真源 + 导出”。
