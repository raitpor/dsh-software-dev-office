# 意图（intent）：SDO 流程 skill（文件与命令实现）

状态：**已签 S1**（2026-11-18T17:30+08:00，选项：签：复述准确；2026-11-19 追加口径，见 §10）
版本：intent-001

## 1. 一句话

把这套项目管理流程（意图→计划评审→卡→两轮评审→签字→读数门→台账）做成**一种纯文件与命令的实现形式**：真源是 Markdown 账本与可复跑命令，人证是真人选的问答选项，门禁是出口勾选表 + 检查脚本。

## 2. 为什么

- 这套流程的价值不在某个存储引擎里，而在**约束的形状**：先对齐再动手、每步可判死、每步留证、每次签字有复述。
- 换一个环境（客户机器、临时会话、别人的仓库、纯 Web 会话）时，应该能按同一套规矩干活，而不是把规矩留在这个仓库的操作习惯里。
- 所以它需要一种**不依赖额外运行环境**的实现形式：一个 skill、几份模板、三份生命周期 preset、一个文本检查脚本。

## 3. 三条保证怎么落地（本实现形式）

| 保证 | 本实现的载体 | 诚实说法（不夸大） |
|---|---|---|
| 对齐 | 意图/计划文件 + 复述 + **人签（问答选项）** | 人点过“对，这是我要的”；**没有密码学签名**，靠人亲自读复述 |
| 可审计 | 追加式 Markdown 账本 + 每条带日期与出处 + `git` 提交 | 账本是文本，**同 uid 可改**；`git` 只在你提交后留痕，不防篡改 |
| 防漂移 | 判据清单 + 出口勾选表 + 检查脚本 + 计划评审 | 门禁靠**人按清单判读 + 脚本查格式**，没有运行时强制 |

三条保证都成立，只是**载体不同**：事件表/签名进程换成账本/问答选项，机器强制换成清单 + 可复跑命令 + 独立评审。

## 4. 做什么（范围）

1. `skills/sdo-flow/`：`SKILL.md` + `references/`（八篇）+ `presets/`（三份）+ `templates/`（九份）+ `scripts/{check,view}.mjs`（文本检查器与快捷视图，Node 零依赖）。
2. 三份**流程 preset**（生命周期：`waterfall` / `prototype` / `incremental`，与设计 `docs/08` §1 一致），各含阶段序列、出口判据勾选表与可迁移的 `policy` YAML。
3. 检查脚本（Node，Windows/Linux 通用）：账本 7 列与 id 递增、表格列数/游离行、签字文件必备字段、卡必备段落、读数 verdict、`--presets` 与设计文档比对。
4. 快捷视图：从 `.sdo/` 的 Markdown 拼出 `state`/`queue`/`board`/`ledger`/`signs`/`plan`，支持 `--json`，只读。
4. 人签模板：一律 `ask_user_question` 三选项（签：复述准确 / 改：复述不准 / 不签：先不做）。

## 5. 不做什么（非目标）

- 不实现事件表、写网关、哈希链重算、签名密钥、运行时门禁。
- 不复制 `docs/` 全文；SKILL.md ≤ 120 行，每篇 reference ≤ 80 行。
- 不假装等价：每条边界必须写进「已知边界」，并且能被一条命令演示（R4）。

## 7. 假设

- A1：目标环境至少能读文件、能跑 `git`；不能跑 Node 时用人工对账。
- A2：人签由会话里的真人点选项完成；没有真人时流程阻塞（不许模型自签）。
- A3：skill 只依赖“读文件 / 写文件 / 跑命令 / 问人”四类能力。

## 11. 信任前提（2026-11-20T09:54+08:00）

本 skill 的流程成立，依赖以下前提；它们不是可执行保证，而是使用时的约定：

1. **假设模型可信但会犯错**：模型按 `SKILL.md` 与 references 执行，不故意绕流程；机制挡的是误操作与漏步，不是恶意模型。
2. **假设替身不代签**：模型可以把复述和选项呈给人，但只能由真人选择；模型不得自答、不得把“问过”写成“签过”。
3. **人签 = 真人在问答里选选项**：回答文本可改、可伪造，本 skill 不做密码学签名；需要强证明时在仓库外另加。
4. **不提供密码学保证**：签字文件、台账、卡面都是可改的 Markdown；审计边界由 `references/07` 逐条写明，不夸大。
5. **判定权在人**：证据列只记命令与输出，判定由评审据证据填；检查器只查格式与合法值，不判断判定是否正确。
