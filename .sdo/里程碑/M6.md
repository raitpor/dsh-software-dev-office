### M6.4 阶段

preset：agent-driven
preset 选择理由：本里程碑全程是“给已有 skill 加机检”，需要 `agent.*` 自检项盯住假绿与实现偏离，且改动集中在脚本与文档，没有业务交付阶段，故不用 waterfall/prototype。

`frame`（本计划 + 五卡）→ `build`（M6-0…M6-3）→ `verify`（每卡多轮评审 + 变异红证）→ `review`（门签前独立复认）→ `sign`（S27 计划 / 卡签 S27-A…/ 门签 S28）→ `deliver`（读数门 + 同步已安装副本）。

- 签后冻结：本段与五卡判据不再改；要改按“追加签 S27-A”，原段保留。
- 已知边界：
  1. **不做动工闸**：不假定目标环境有 git；“先动工后立项”“口头授权当流程放行”只能靠 SKILL 文本与 agent 自律（R30 只证明文本在）。要绕过的人可以换会话或自己动手，这不在本机制能管的范围。
  2. **探底行是声明**：检查器只验“行存在、命令形态合法”，不验命令真的跑过、也不绑定当日输出。
  3. **冻结段 hash 只防“改了忘更新”**：同权限同盘的一致伪造（改正文 + 改 hash）它防不了；真伪以 git 追加历史为准（无 git 时以签字文件的时间与哈希链为准，边界记 `references/07`）。
  4. **语义判据只验形态**：是否真覆盖业务语义由评审判；`语义：不适用` 的理由是否成立也由评审判。
  5. **门签收口规则**（D-109）只对 `M*-G` 生效，不覆盖里程碑内的实现卡。
  6. **历史卡不回溯**：M6 之前的 `done` 卡不补「类型」列与「语义自检」，见下方基线声明；补了就是造假。
  7. **追加签行可被一起伪造**：C3 要求“追加签行 + 对应签文件存在 + 被签对象含 hash 前 8 位”，这只提高伪造成本；同盘同权限下把正文、hash、签文件一起改仍然防不了（与边界 3 同源）。
  9. **preset 没有默认值**：机检只能验“选了、在清单里、写了理由（≥8 字、非套话）”，验不了“选得对不对”——选型是否合适由计划评审判。
