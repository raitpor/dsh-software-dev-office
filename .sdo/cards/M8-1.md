## 意图

把 `explore` 阶段的引用形态固化成**可判红**的检查：需求↔卡↔判据↔测试四向闭合，孤儿与断链必须各自有码、且首条报错点名具体 id。解析放 `skills/sdo-flow/scripts/lib/trace.mjs`（`check` 与 `view` 共用，不许两处各写一份——M6-2 的分叉教训）。

**只对 `status: done` 的卡强制闭合**：open 卡的引用只列不判，否则实现期每张新卡都会红。门卡（`M*-G`）按 done 判。

## 判定

- C1 pass：五行计数（含孤儿需求数/孤儿卡数）与 exit 0 实测（见证据）。
- C2/C3/C4 pass：四码各一真红，首条点名 id/文件。
- C5 pass：done 卡证据行缺失/命令为空真红；空命令只报 `trace_orphan_test`；open 卡不判；M1–M7 基线段不误红。
- C6 pass：单一 `lib/trace.mjs` 解析，`/tmp` 改解析后两处输出同步。
- C7 pass：有文本但不合口径（散文）报 `trace_test_unverifiable`，与 C5 互斥；可复跑命令/脚本:行通过。
- C8 pass：行数/列/去向/不采纳理由均机检；`M8-1 C8` 明确拒绝。

## 评审

- 评审者：`reviewer`（独立席位，只读，非作者）
- 语义自检：四码（C2/C3/C4）与 C1/C5/C7/C8 均用副本 `card.mjs mutation` 真跑出 `expected=red actual=red restored=green`；计数是现扫 `counts` 非硬编码；C6 的单点解析用 `grep -c 'function analyzeTrace' view.mjs check.mjs` = 0/0 且 view/check 仅 import 验证，是结构约束不是可跑红的规则。
- 不可变异确认 C6：单点解析是结构性约束（`analyzeTrace` 只在 lib 一处，view/check 只 import），没有可跑的应红命令；以静态计数与 import 证明。

## 语义自检

C5/C7 是“追溯是否真的连到测试”，结构判据只能证“写了引用”。实测：删/改证据命令可让 `trace_orphan_test`/`trace_test_unverifiable` 红；改 `testRef()` 返回恒真后同一夹具变绿，说明该码确实由测试引用规则驱动。C8 用 C99 与 `M8-1 C8` 两个反例验证去向真实性与自证拒绝；C6 用改解析后的双端同步验证单点解析。

## 已知边界

1. 只认卡面 `references:` 行与「认领需求：」行；正文散文里提到的 `R-xx` 不计入（避免误报）。
2. 测试引用的“存在性”只验文件与行号可解析，不验该测试真的覆盖该判据（这是评审的事）。
3. open 卡的引用只列不判（见「意图」）。
4. C8 明确拒绝 `M8-1 C8` 自证：C8 本身是待收敛的检查器，不能用自己作为“去向已存在”的依据；`M8-2 Cx` 仍要求对应卡与判据真实存在。
5. 基线段只读 `.sdo/milestones/M8.md` 的「测试引用基线段」行（取最后一个冒号后的里程碑号）；计划/正文里提到不算。
