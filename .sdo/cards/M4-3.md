# M4-3 · `view next`（现在能开工什么）

status: open
owner: impl-core
write_scope: [skills/sdo-flow/scripts/view.mjs, skills/sdo-flow/SKILL.md（§11）, README.md]

## 意图
把“下一步做什么”从人翻文件变成一条命令：哪些卡能开工、哪些被依赖卡住、哪些卡/门待签收、哪些台账没关。

## 风险标记

risk_flags：无

## 对齐
- 该做：`view next` 输出五小节（可开工 / 被依赖卡住 / 待签收 / 待签文件 / 未修台账），每节空写「无」。
- 不该做：替人决定优先序、修改任何文件、把“缺读数”说成“已通过”。

## 判据
C1 五小节齐全（缺一节 ⇒ exit 1）；每节空时输出「无」而不是省略。
  反例：删掉「未修台账」节 ⇒ C1 红。
C2 “可开工” = 卡的依赖全部 `status: done` 且该卡 `status: open`；“被依赖卡住” = 依赖未 done，并列出未 done 的依赖 id。
  反例：把依赖未 done 的卡放进“可开工” ⇒ 用夹具验证红。
C3 “待签收” = 卡 `status: done` 但 `.sdo/sign/` 里没有引用该卡号的签字文件；“待签文件” = 计划段 `状态：**待签**` 或读数 `overall` 非 pass 且无门签。
C4 “未修台账” = `status ∈ {open, accepted}`，按 id 排序；不把 `superseded` 算进去。
C5 只读：跑前跑后工作树不变（`git status --porcelain` 相同）。

## 假设
A1：卡号与签字文件里的“被签对象/范围”能对上（签字文件里出现卡号即算签收）。
A2：`status` 只认 `open|in_progress|done|superseded`；未知值 ⇒ 在输出里单列“未知状态”，不猜。

## 预览
预计改：`scripts/view.mjs` 加 `next` 子命令；`SKILL.md` §11、`README.md` 各一行。
验：C1–C5 夹具（一张卡依赖未 done、一份读数缺 overall、一条 open 台账、一张 done 无签收）。
