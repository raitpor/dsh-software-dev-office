## 意图

真实项目里“单文件交付也走全套审签”的往返太重。本卡让 `sign.mjs batch <M>` 一次输出最多三份≤8 行的签字草案（范围 / 被签对象 / 判定 / 已知边界），人一次问答可以签完，但**草案不落盘**，签文件仍逐份写、逐份校验。

## 风险标记

release_touching：`sign.mjs` 是签字链工具，改错会污染签文件格式。

## 对齐（复述）

- 一句话：减少“一问一签”的往返，但不合并签字证据。
- 做：①`sign.mjs batch <M>` 输出 ≤3 份草案、每份 ≤8 行；②草案不写任何文件；③文档写“一次问答最多合并 3 项，每项仍独立成 `S<n>.md`”。
- 不做：不做一次提问签多份的自动化（问答仍由人答）；不改签字三选一与字段。
- 正例：`batch M6` 输出 ≤3 份草案、`git status` 不变 ⇒ exit 0。
- 反例：`batch` 请求 4 个对象 ⇒ exit 2 并提示拆批。

## 预览

预计新增子命令约 90 行；`check.mjs` 只在变异基线签字判定处复用共享 signed-cards 模块（与 sign 同源），不改签字字段。

## 准入

依赖：M6-0。

## 评审

- 评审者：`reviewer`（独立、只读、非作者）
- 判定：可收卡（第 3 轮 delta）
- 语义自检：C4「草案四项非占位」按语义判据对待——范围含卡号、被签对象可解析、判定取自声明、边界去标点后 ≥8 字且不在套话黑名单；机检只能验“形态非占位”，边界写得对不对仍由评审判断。
- 交集：第 1 轮「改完再审」（1 P1 共享判定分叉 + 3 P2）；第 2 轮「改完再审」（1 P1 判词误取历史行 + 2 P2）；第 3 轮「可收卡」（三项全闭合）
- 教训：**两份“恰好一样”的判定就是分叉**，要么共用一份代码、要么承认口径不同；**判词要从声明处取，不要从散文里搜关键词**（历史行永远比判词更像判词）。

## 判定

- C1 pass：4 张 ⇒ exit2、零输出；跨里程碑 ⇒ exit2 点名；变异 max3→4 ⇒ exit0、4 份（已恢复）。
- 共享判定 pass：`signedCardIds` 单文件，sign/check 均 import；选卡与 check 基线签字判定同口径。
- C2 pass：判词取评审段最后一条（M6-0 可收卡、M6-1 可提交）；9 行/缺边界/`待填写` 均 exit2；无判词走 `待人工复核`。
- C3 pass：batch 前后全 `.sdo/` status 均空。
- C4 pass：边界 `无` exit2 点名；无 git 走「无 git」文案 exit0。
- C4 第 2 轮 pass：判定只认评审段最后一条 `- 判定：`；取不到 fallback 文案；历史行在前夹具仍取最后判词。
- 默认选卡 第 2 轮 pass：`SIGN_FILE_RE` 仅在 lib 导出，check/sign 共用；非 `S\d+(-[A-Z])?` 文件不参与已签收。
- 总体：pass（评审复核）。
