# M5-3 · 里程碑归档（文件数与耗时减重）

status: done
owner: impl-core
write_scope: [`skills/sdo-flow/scripts/archive.mjs`, `skills/sdo-flow/scripts/check.mjs`, `skills/sdo-flow/scripts/view.mjs`, `skills/sdo-flow/SKILL.md`（§11）, `README.md`, `.sdo/archive/`]

## 意图
把已收口里程碑的卡/评审/读数/出口表搬进归档目录，用 manifest 锁住字节；检查器只读 manifest、不解析归档正文，使活跃区文件数不随里程碑增长。

## 风险标记

risk_flags：release_touching

## 对齐
- 该做：`archive`/`restore`/`list`；归档索引每行一个里程碑（门签号、被签树、文件数、逐文件 sha256）；`git mv` 搬运、内容不改。
- 不该做：不搬 `sign/` 与 `台账.md`（全局审计脊柱）；不改历史签字；不删任何内容。

## 已知边界
- `restore` 用 `git mv` 搬回，索引会显示反向 rename；要 `git status` 空需在 fixture/收口时提交。C4 证据中的“status 0 行”是 fixture 提交后的读数。
- 归档索引是新增文件；归档动作本身不 commit（由 Lead 收口提交）。
- 门签号/被签树从 `.sdo/sign/` 的签文件标题与「被签对象」提取；没有门签时记 `-`，不阻塞归档。
- 时间测量只作 C5 参考；同机抖动可能让归档后耗时略高（本机 39→42ms），C5 以扫描文件数为准。
- 本卡为 `release_touching`，真实仓库归档等门签后由 Lead 执行；本席只证明脚本与副本。
- `archive`/`restore` 中途 `git mv` 失败可能留下半搬状态；前置校验只覆盖“文件都在、哈希对”，失败后按 `git status` 手工回退（README 维护段同口径）。
