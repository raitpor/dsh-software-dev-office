### M13.6 维修门禁+判据组合（本计划定稿）

> 组合的**定稿位置是计划**（用户 m26484 裁定：定组合不是一张卡，而是计划本身的一部分），因此它随计划签字生效；后续卡只负责把它落成 preset 与文档，不重新设计。

阶段：`diagnose`（定位/复现）→ `fix`（改）→ `verify`（验证）→ `integrate`（交付）。门 id：`G_repair_diagnose` / `G_repair_fix` / `G_repair_verify` / `G_repair_integrate`。

| 门 | 判据（core 三条每门必入，下表不再重复列） | 为什么在这一门 |
|---|---|---|
| `G_repair_diagnose` | `requirement.claimed_or_na`、`scope.present`、`node.acceptance_bound`、`assumption.disposed` | 维修最常见的三种翻车是"没立案就动手、改着改着越界、验收线边修边改"；根因假设必须处置（不能挂着假设就开始改） |
| `G_repair_fix` | `task.complete`、`trace.test_linked`、`agent.mutation_red`、`agent.write_scope_disjoint` | 维修的价值全在"能证明修好了"：测试要绑到卡上、且要能红（不是只写个绿测试）；写域不相交防顺手改别处 |
| `G_repair_verify` | `review.required`、`review.round_bound`、`review.independent`、`agent.reviewer_not_author`、`agent.checker_green`、`agent.findings_disposed`、`agent.evidence_runnable`、`agent.no_self_sign`、`agent.unverified_listed` | 独立评审四件套 + 检查器全绿；`findings_disposed` 处置完才算验完；证据要能原样复跑、不许自签、未验证项必须列出 |
| `G_repair_integrate` | `gate.signed`、`node.integration_listed`、`mandate.revalidated`、`readings.recorded`、`agent.known_limits` | 门签是出口；维修若越出原授权范围必须重授权；集成清单与读数留痕；已知边界要写出来（维修最容易“修了 A 坏了 B 不说”） |

**负面清单（不进维修门的判据与理由）**：

| 判据 | 为什么不进 |
|---|---|
| `stage.requirement_complete`、`intent.restated_consistent`、`alignment.examples_present`、`agent.plan_reviewed`、`redteam.disposed` | 这些都是"从零做一个东西"的门（需求/设计/红队）；维修没有新需求，塞进来只会逼人补假需求文档——这正是"为了过门而造假"的来源 |
| `design.covers_spec`、`design.no_spec_creep`、`design.alternatives_declared`、`design.artifacts_present`、`stage.design_traceable` | 同上：维修不产设计；真有设计变更时，应升级成正常里程碑，而不是把设计门塞进维修 |
| `trace.requirement_covered` | 维修卡通常不关闭需求；需求覆盖由它所属的里程碑负责（`trace.requirement_covered` 留在正常流程） |
| `design.code_matches` | 维修项目**没有设计稿**，这条只能靠写假设计或永远 partial；若改动真涉及设计变更，应升级成正常里程碑（与上表同一理由） |
| `agent.cards_have_negative_cases` | 那是**判据注册**的门槛（每条判据要有正/负夹具），不是每张卡的门槛；维修卡只要 `trace.test_linked` + `agent.mutation_red` |
| `agent.readings_frozen` | 读数冻结属**里程碑门**层（`readings.recorded` + 门签），不是单卡 |
| `intent.explicit_for_risk`、`requirement.baseline_present` | 维修没有新意图、不改需求基线；需求类判据留在正常流程 |
| `test.design_present` | 维修不要求测试设计文档，只要求测试绑到卡上且能红（`trace.test_linked` + `agent.mutation_red`） |
| `trace.card_coverage` | 卡覆盖需求是**里程碑级**的追溯要求，维修单卡不承担 |
| `agent.human_signed` | 维修也要人签，但那是**里程碑门签**层（`gate.signed` + 门签），不是每张卡都签 |

**使用约定（不写清就会被写成假绿）**：

1. **“不适用”怎么写**：`gate.mjs` 的判定列只认 `pass/partial/fail`，没有 N/A 位。维修若没有新增假设（基线假设已由 core 的 `assumption_set.signed` 保证），`assumption.disposed` 填 **pass**，并在说明列写「不适用：本次无新增假设，基线假设见 `assumption_set.signed`」，由门签人签确认——**不许**为了“看起来做了”去编一条假设再处置。**说明列必须带证据锚点**（例如 `git diff <维修前树> -- .sdo/baseline/` 无新增假设节，或基线假设的 `文件:行`），无锚点的“不适用”门签人不得签。
2. **`agent.checker_green` 的口径**：按“**0 错**，且错/警数**不比维修前基线多**”判；WARN 本身不构成 fail（本仓就长期有 1 条历史 WARN），否则维修项目只能靠造假绿通过。
3. **`review.independent` 在维修门里是“对齐正常流程”的保留项**：它的实质要求由 `agent.reviewer_not_author`（身份）与 `agent.no_self_sign`（不代签）覆盖；preset 说明里要写明这层关系，免得维修项目以为要证明三次。

**与 `incremental` 的差异**（口径收紧，避免夸大）：①门数同为 4，但少一组需求/设计类判据（见负面清单；负面清单共 19 条，其中 12 条是与 incremental 的差集）；②`trace.test_linked` **提前**到修复门；③`agent.mutation_red`、`agent.write_scope_disjoint` **不在** `incremental` 的判据表里，是从 `agent-driven` **借入** repair（不是“提前”，原文写错已改）；④新增 `agent.evidence_runnable`、`agent.no_self_sign`、`agent.unverified_listed`、`agent.known_limits` 四条“维修特有”的诚实性判据；⑤`mandate.revalidated` **不是新增**（incremental 也有，用于“越权即停”）。
