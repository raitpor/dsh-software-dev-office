# 判据：注册、负例、门禁与豁免

> **框架坐标**（对齐 [01 理论与边界](01-理论与边界.md)）
>
> - 守的层：**L2**
> - 涉及真源：—
> - 对应命题：命题 2（空集陷阱）· 命题 5（方向不对称）
> - 本文引入/定义的概念：判据、夹具、门禁、baseline

> 判据不是"检查清单"，是**可复算的断言**。一条判据值不值它带来的维护成本，由两个数字回答：**它冤枉过几次人**、**它抓到过几条真缺陷**。

---

## 1. 判据的签名

```ts
type Verdict = 'pass' | 'fail' | 'na'          // 三态；na 必须带理由

type Result = {
  status: Verdict
  code: string                                  // 稳定机读码（'R-12.gaps_mismatch'）
  message: string                               // 一句人话
  remedy: string                                // 可执行修法（空即不许注册）
  evidence: EvidenceRef[]                       // 绑产物指纹与 frontier
  data?: Record<string, unknown>                // 渲染用，不含结论文字
}

type Criterion = (view: Views, params: Params) => Result
```

**fail-closed**：判据**未实现**、**抛异常**、**超时**、**依赖缺失** ⇒ 一律 `fail`，并给出 `code`（不许"查不到就算过"）。

---

## 2. 注册门槛（四条，缺一不许 active）

| 门槛 | 检查方式 |
|---|---|
| 有 `remedy` | `remedy.trim() !== ''` |
| 有**正例**夹具 | `fixture(polarity=positive)` 跑出 `pass` |
| 有**负例**夹具 | `fixture(polarity=negative)` 跑出 `fail`（**不该红的不红**） |
| 有预算 | 单次执行 < 200ms；整组门禁 < 2s（超过就拆/加索引） |

**负例是 v2 相对 v1 最重要的一条升级。** v1 的判据只证明"改坏会红"，从不证明"不该红的不红"，于是 `DEF-158`（逼人灌水才过）这种"判据冤枉人"只能靠评审肉捕。v2 里，**负例红了 ⇒ 判据本身判红**，并且必须在同一个迭代里修。

---

## 3. 判据分组（各自门槛不同）

| 组 | 判什么 | 例子 | 维护者 |
|---|---|---|---|
| `product` | 产品行为（数值/存档/接口） | 离线收益可加、存档往返幂等 | 开发者 |
| `process` | 过程自洽（台账、链条、权限） | `dead_field`、`claim` 无出处、代签、**`metrics.not_gate`（判据读度量值）** | 流程官 |
| `report` | 报告一致（文档、回执、快照） | 回执结论在 `claim` 里找不到 | 流程官 |

分组的意义：**product 组失败是产品坏了；process 组失败是机制坏了；report 组失败是"说法"坏了**。三类修法完全不同，混在一起就会重演 v1 的"79% 缺陷都是机制自己的"。

## 4. 阶段判据组（`process` 组，守《阶段作业单》）

这十八条守的是"每个阶段有没有真的产出"（[13](13-阶段作业单.md)），不是产品功能，分四组：**产出存在**（条款/设计/复述/拆卡，4 条）· **结构完整**（分解树与集成，2 条）· **授权有效**（强度与重验，2 条）· **守门可算**（容器是否真被拦，10 条）。

| 判据 code | 判什么 | remedy | 正例夹具 | 负例夹具 |
|---|---|---|---|---|
| `stage.requirement_complete` | 每条 **`spec(kind='requirement')`** 至少被一条 `criterion` 或一个 `scenario` 消费（`design`/`contract`/`impact` 不适用本判据） | 给条款补判据/场景，或删掉这条条款 | 3 条条款各挂 1 条判据 ⇒ pass | 1 条条款既无判据也无场景 ⇒ fail |
| `stage.design_traceable` | 每条 `spec(kind=design)` 有 consumer | 补 consumer（view/renderer/criterion）或删条款 | 设计条款被 1 条判据消费 ⇒ pass | 设计条款无任何 consumer ⇒ fail |
| `design.covers_spec` | 每条 `kind=requirement` 条款至少被一条设计条款 `inputs` 覆盖 | 补设计条款，或显式声明"该条款不进入本期" | 2 条 requirement 各有设计承接 ⇒ pass | 1 条 requirement 无设计承接 ⇒ fail |
| `design.no_spec_creep` | 每条设计条款必须 `inputs` 指向至少一条 requirement | 删掉凭空条款，或回头补需求条款（走 change） | 设计条款 3 条，均指向 requirement ⇒ pass | 1 条设计条款无任何 requirement 依据 ⇒ fail |
| `intent.restated_consistent` | 存在 `restatement`；`restatement_diff` 无未处置行、无 `defer`；且 `restatement.at < min(spec.at)` | 逐条处置差异；顺序反了则重派复述 | 复述先入库、3 条 diff 全 accept ⇒ pass | 复述晚于条款，或存在 disposition 为空/defer 的 diff ⇒ fail |
| `task.single_criterion` | 一张卡的 `work_unit` 行里 `criterion_id` **唯一**（默认上限 1 条）；且每行 `evidence.criterion_id` 必须等于它 | 拆卡 | 一卡一判据 ⇒ pass | 一卡挂 3 条互不相关判据 ⇒ fail |
| `node.acceptance_bound` | 每个叶 `goal_node` 有 `acceptance_criterion_id`，且该判据有正负例 | 给叶节点补验收判据 | 3 个叶节点各绑一条判据 ⇒ pass | 一个叶节点没有验收判据 ⇒ fail |
| `node.integration_listed` | 父节点的验收含 `integration` 清单，且全部 `connected`，且**至少一行带 `evidence_id`**（父的“整体跑过一次”有证据，不是声明） | 补齐未接上的子块，或标 `dropped` 并说明 | 3 个子块全 connected + 整体跑绿 ⇒ pass | 有子块 pending 就宣布父节点完成 ⇒ fail |
| `intent.explicit_for_risk` | `risk_flags` 非空的条款，其 `intent.strength` 必须是 `explicit` | 让提需求的人显式确认，不靠推断升级 | 高风险条款 intent 为 explicit ⇒ pass | `risk_flags=['payment']` 但 `strength='inferred'` ⇒ fail |
| `mandate.revalidated` | `reopened` 的卡，其 `intent.baseline_hash` 的 gate 在当前 baseline 下仍通过 | 重签或调整范围后重开 | 重开后 gate 仍绿 ⇒ pass | baseline 放宽导致旧授权失效仍续跑 ⇒ fail |
| `provenance.present` | 每条 `task` 与 `spec` 的 `created_by` 非空，且指向已注册 `actor` | 回填建卡人/条款创建者；查不到就找当时的 `spec.defined`/`task.created` 事件 | 3 张卡 2 条条款均有 `created_by` ⇒ pass | 一条条款 `created_by` 为空 ⇒ fail |
| `scope.present` | 需求阶段存在 `scope_decl(stage='requirement')` 且 `paths[]` 非空 | 补一行范围声明（本期允许动的路径前缀） | 有一条 `scope_decl` 且 paths 非空 ⇒ pass | 无 `scope_decl`，或 paths 为空 ⇒ fail |
| `redteam.disposed` | **先按 `spec.risk_flags[]` 找出必须红队的条款**（`payment`/`auth`/`irreversible`/`cross_module`），再看这些条款的 `redteam` 行 `disposition ∈ {accepted, rejected}`；**没有 `redteam` 行 ⇒ fail**（不是空集通过）；`deferred` 必须转成 `block(redteam_deferred)` | 逐条处置红队用例；deferred 记入 gap | 2 条用例均 accepted ⇒ pass | ① 1 条 deferred 未转待决 ⇒ fail；② `risk_flags=['payment']` 但无 `redteam` 行 ⇒ fail |
| `review.round_bound` | 每个 `review` 属于某个 `review_round`；round 的 `baseline_hash`/`frontier` 非空；`pass` 需当轮 finding 全核实 | 补开/补绑 review_round，或先核完 finding | 一轮 3 条 finding 全核实后 pass ⇒ pass | 有 finding 未核实就 pass ⇒ fail |
| `spec_set.signed` | 存在 `decision(decision_kind='spec_set')`，其 `spec_ids[]` 覆盖本期 `kind='requirement'` 条款集合，且绑 frontier | 重新签一次条款集合（`spec_ids[]` 全量） | spec_ids 覆盖全部条款 ⇒ pass | 少一条条款 ⇒ fail |
| `design.code_matches` | 每条 `spec(kind='design'/'contract')` 有 `code_artifact_ref`（`snapshot_id/path/design_sha256`），且**①** `code_artifact_sha256`（**派生列**）== `sha256(按 evidence_id 升序、去重后拼接的 `evidence.artifact_sha256` hex 字符串，无分隔符)`（**产物清单哈希**；排序/去重/拼接格式写死，拆卡实现也成立；不重算构建）；**②** `code_artifact_ref.design_sha256 == design_lock.design_sha256`（设计锁里的只读副本）；**③** 该条款每个 implement `work_unit` 的 `evidence.snapshot_id` 必须是 `code_artifact_ref.snapshot_id` 的**祖先或相等**（内嵌 git 的 commit 图祖先闭包，再用 `snapshot.parent_ids` 交叉校验）——拆卡跨快照成立；**注意**：证明“产物来自祖先快照”，不证明“构建可复现” | 重新生成产物或更新条款版本（走 change） | 3 条设计条款 ①②③ 全对 ⇒ pass | ① 不对 ⇒ `artifact_mismatch`；② 不对 ⇒ `design_version_mismatch`；③ 不是祖先/相等 ⇒ `snapshot_mismatch`——**三种失败分开报** |
| `stage.gate_bound` | 每个 `stage_run` 必须有 `gate_id` + `baseline_hash`，且 `verdict` 与 gate 读数一致（手填即红） | 用 gate 现算重出 verdict | verdict=pass 且 gate 读数全 pass ⇒ pass | verdict 手填 pass、gate 有红 ⇒ fail |
| `task.complete` | 卡的完成：存在 `work_unit` 行，其 `criterion_id` 判据绿、`evidence_id` 指向的证据 `artifact_sha256` 非空 | 补证据或补判据 | 判据绿 + 证据带指纹 ⇒ pass | 判据绿但无证据 ⇒ fail |

> `task.complete` 是**卡的完成判据**；事件仍叫 `task.done`（[02](02-真源-存储事件与折叠.md)「事件类型」）——判据名与事件名分开，避免 `verify` 与检查器混淆。

### 4.1 适用性（`applies_to`）与 `na`

每条判据带 `applies_to`；当前 stage 不在其中 ⇒ 判 **`na`**（不是 pass），并在 `stage_run.criteria[]` 里记 `reason='stage_not_applicable'`。

| 判据 | `applies_to` |
|---|---|
| `stage.requirement_complete` / `intent.restated_consistent` / `scope.present` / `redteam.disposed` / `spec_set.signed` / **`intent.explicit_for_risk`** | requirement |
| `stage.design_traceable` / `design.covers_spec` / `design.no_spec_creep` / **`node.acceptance_bound` / `node.integration_listed`** | design |
| `task.single_criterion` / `task.complete` / **`mandate.revalidated`** | implement（`mandate.revalidated` 也在 deliver 复查） |
| `design.code_matches` | implement / deliver（设计出口只查 consumer，指纹在这里复查） |
| `review.round_bound` | review |
| `provenance.present` / `stage.gate_bound` | 全阶段 |

`assurance.na_stages[]` 记的是"这个 policy 下**不存在**的阶段"（如 `spike` 的 `design`），它与本表**共同**决定哪些判据是 `na`；两者都不要手填，由 policy + `applies_to` 推出。

## 5. baseline 冻结与签名变更

> **公理**：凡是影响判定的东西，**冻结之后只能以「签名变更」的方式改**。
>
> 为什么不是“固定集合”：固定集合挡不住**调阈值**——判据还在、指示灯还是绿的，只是尺子变短了。而“偷改阈值”比“删判据”更隐蔽，效果却一样。

### 5.1 冻结什么（baseline）

```yaml
baseline:
  id: b-001
  frozen_by: u-liang                       # 人签
  engine:  { version: 0.1.0, criteria_manifest_hash: … }
  criteria: [{ id, version, params }]      # 这一版用哪些判据、什么参数
  gates:    [{ id, stage, criteria[], policy, waivable }]
  thresholds: { coverage: 0.8, regression_max_age_days: 7, … }
  assurance: { unbound_gates: [], independence: solo_cooldown(15m),
               db_confidentiality: true, na_stages: [], level: solo }
  hash: sha256(规范化全部字段)              # 内容哈希，不是布尔开关
```

### 5.2 五条规则

1. **每个判定都记 `baseline.hash`**：没有 baseline 的判定无效——判据读数必须能追到“当时用的是哪一版尺子”。
2. **改 baseline = 一次 `change` + 人签**，且**方向不对称**：

   | 方向 | 例 | 何时生效 |
   |---|---|---|
   | **收紧** | 阈值升高、加判据、加门禁 | 可**即时生效**、事后追认（只会让通过更难） |
   | **放松** | 降阈值、删判据、解绑 gate | **必须事前人签**，且要写“这会放行什么” |

3. **引擎升级也算变更**：`criteria_manifest_hash` 变了 ⇒ 走同一套审批。否则“我们升级了”就是合法绕过。
4. **`verify` 每日对账**：重算 baseline hash 与判定记录里的 hash 比较；不一致 ⇒ **仲裁冻结（只读）+ 红**，不许自动“修复”。
5. **唯一硬编码的不可动：core 判据**（防篡改、防代签、防伪造声明）**只能收紧、永不放松**——它保护的是“冻结机制本身”。

### 5.3 可插拔是可以的

| 问题 | 结论 |
|---|---|
| 判据/门禁/阈值可以按项目定吗 | **可以** |
| 靠什么保完整性 | **立项冻结成 baseline + 之后任何改动都是签名变更** |
| 膨胀怎么控 | 不靠禁止，靠**经济约束**：每条判据回答“挡哪条漂移”；判据数量与 `caught`/误报率一起进报告——装饰会被看见 |

“可插拔 + 冻结 + 签名变更”强于“固定集合”，因为它把四种绕过（**加 / 删 / 调阈值 / 换引擎**）统一成同一件事：要改就得签字。

### 5.4 一个陷阱

冻结**不能**是数据库里的 `frozen: true` 字段——那个字段自己也会被改。它必须是**内容哈希**：出现在每个判定里、能离线复算、`verify` 能对账。

## 6. 门禁（gate）

```text
gate = { id, stage, criteria: [criterion_id], policy: all_of | any_of, waivable }
```

- `all_of`：全部 `pass` 或 `na` 才放行；
- **`na` 不算通过，但不算失败**——必须带 `reason` 与"由谁判定"；
- `waivable=false` 的判据不可豁免（安全类、代签类）；
- 每次判定写一条 `gate.judged` 事件，含**每条判据的三态与 data**（不是只写"失败"）。

**放行语义**：`advance` 由 `gate.judged` 驱动；没有 `pass` 的 gate，`advance` 被拒绝（不是"警告"）。

---

## 7. 豁免（waiver）必须是"有价的"

| 规则 | 说明 |
|---|---|
| 只能由人签 | `decision(kind=waiver)`，绑 frontier + 内容哈希 |
| 必须有到期 | 默认 **7 天**（**豁免 TTL**，与授权窗口/分歧 L4/未结案 change 的 7 天无关）；过期自动失效，回到红 |
| 必须写代价 | 表单强制填"豁免了什么风险、谁来承担" |
| 计入读数 | `gaps` 里显示"当前生效豁免 N 项"，超阈值告警 |

**不许"永久豁免"**：v1 的教训是，永久豁免会被正常化，然后没人记得它存在。

---

## 8. 变异自证（判据要证明自己有用）

对每条 `product` 与关键 `process` 判据，要求一组变异：

```text
变异：把实现改坏（一处）→ 判据必须红；复原 → 全绿
自证：脚手架必须报告"字节变了 / 真的写盘了 / 已还原"（不许假变异）
```

v1 的教训（`DEF-166/167`）：变异自证本身可能不可复算——所以 v2 里变异记录写进 `evidence`，绑产物指纹；两次会话读数不一致时，**两次都留，标 `disputed`**，而不是覆盖。

## 9. "这条判据值多少钱"（v1 完全缺失的读数）

| 读数 | 定义 | 用途 |
|---|---|---|
| `caught` | 该判据首次抓到真缺陷的次数（`defect.criterion_id`） | 零的判据进入"退休候选" |
| `false_positive` | 负例夹具红过 / 被人投诉并确认为冤的次数 | >0 必须修判据，不许改成豁免 |
| `cost` | 该判据在最近 30 天的执行总时长 | 排序优化与拆分依据 |

这三个数每轮迭代可见；**没有它们，判据只会继续长，优劣无法判断**。

---

## 10. 不变式

1. 没有负例夹具的判据不可 `active`（DB 约束 + 注册校验）；
2. 判据不得写任何"结论文字"到 `claim` 之外的地方（回执文字由渲染器生成）；
3. 判据不得读文件系统（只读视图）；确需读产物的，必须通过 `evidence` 接口；
4. 不可豁免的判据集合固定（代签、密钥外泄、审计链断裂）；
5. **判定必须绑 `baseline.hash`**；baseline 的冻结与变更规则见「baseline 冻结与签名变更」（唯一家，此处不复述）。

## 11. 验收读数（M1）

- 故意把某个判据的实现改坏 ⇒ 对应负例红；
- 新增一条判据但不给负例 ⇒ 注册被拒（不是警告）；
- 一条判据连续 3 个迭代 `caught=0` ⇒ `gaps` 出现"退休候选"行。
