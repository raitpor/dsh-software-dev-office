# 判据：注册、负例、门禁与豁免

> **框架坐标**（对齐 [01 理论与边界](01-理论与边界.md)）
>
> - 守的层：**L2**
> - 涉及真源：—
> - 对应命题：命题 2（空集陷阱）· 命题 5（方向不对称）
> - 本文引入/定义的概念：判据、夹具、门禁、baseline

> 判据不是"检查清单"，是**可复算的断言**。一条判据值不值它带来的维护成本，由两个数字回答：**它冤枉过几次人**、**它抓到过几条真缺陷**。

---

## 1. 判据的签名

```ts
type Verdict = 'pass' | 'fail' | 'na'          // 三态；na 必须带理由

type Result = {
  status: Verdict
  code: string                                  // 稳定机读码（'R-12.gaps_mismatch'）
  message: string                               // 一句人话
  remedy: string                                // 可执行修法（空即不许注册）
  evidence: EvidenceRef[]                       // 绑产物指纹与 frontier
  data?: Record<string, unknown>                // 渲染用，不含结论文字
}

type Criterion = (view: Views, params: Params) => Result
```

**fail-closed**：判据**未实现**、**抛异常**、**超时**、**依赖缺失** ⇒ 一律 `fail`，并给出 `code`（不许"查不到就算过"）。

---

## 2. 注册门槛（五条，缺一不许 active）

| 门槛 | 检查方式 |
|---|---|
| 有 `remedy` | `remedy.trim() !== ''` |
| 有**正例**夹具 | `fixture(polarity=positive)` 跑出 `pass` |
| 有**负例**夹具 | `fixture(polarity=negative)` 跑出 `fail`（**不该红的不红**） |
| 有预算 | **单次**执行 < 200ms（注册时测）；**整组**门禁 < 2s（门禁判定时测，见下） |
| 有 `guarantee` 声明 | 取值 ∈ `{1,2,3,—}`（§4 的「保证」列）；**不许留空**——留空会让 `guarantee_delta` 漏掉这条判据，于是「新加一条没人管的判据」能悄悄绕过保证等级 |

**两个预算在不同时刻测，别混**：

- **单次 200ms** 是**判据自身的门槛**，在注册时实跑一次测，超 ⇒ `budget_exceeded`、不许 `active`（`03` P1）；
- **整组 2s** 是**门的门槛**，一条判据注册时无从知道整组有多大，只能在 P2 判完一轮后测总耗时。超 ⇒ 记 `data` 里的 `elapsed_ms` 并记一行 `gaps`（修法：拆门/加索引），**不改变 verdict**——慢不等于判错，但必须有读数、必须有人看见。

**负例是 v2 相对 v1 最重要的一条升级。** v1 的判据只证明"改坏会红"，从不证明"不该红的不红"，于是 `DEF-158`（逼人灌水才过）这种"判据冤枉人"只能靠评审肉捕。v2 里，**负例红了 ⇒ 判据本身判红**，并且必须在同一个迭代里修。

## 3. 判据分组（各自门槛不同）

| 组 | 判什么 | 例子 | 维护者 |
|---|---|---|---|
| `product` | 产品行为（数值/存档/接口） | 离线收益可加、存档往返幂等 | 开发者 |
| `process` | 过程自洽（台账、链条、权限） | `dead_field`、`claim` 无出处、代签、**`metrics.not_gate`（判据读度量值）** | 流程官 |
| `report` | 报告一致（文档、回执、快照） | 回执结论在 `claim` 里找不到 | 流程官 |

分组的意义：**product 组失败是产品坏了；process 组失败是机制坏了；report 组失败是"说法"坏了**。三类修法完全不同，混在一起就会重演 v1 的"79% 缺陷都是机制自己的"。

## 4. 阶段判据组（`process` 组，守《阶段作业单》）

这二十四条守的是"每个阶段有没有真的产出、有没有真的对齐"（[13](13-阶段作业单.md)），不是产品功能，分五组：**理解对齐**（例子与反例、假设处置与签字、设计替代方案、返工可见，5 条）· **产出存在**（条款/设计/复述/拆卡，4 条）· **结构完整**（分解树与集成，2 条）· **授权有效**（强度与重验，2 条）· **守门可算**（容器是否真被拦 + 评审门，11 条）。

> 十八 → 二十四不是加码，是**换重心**：前两组（对齐 + 产出）决定"要不要重做"，后三组决定"做完算不算数"。v1 的返工大多来自第一组，而 v1 没有第一组。

> **`保证` 列是 `guarantee_delta` 的唯一来源**：它标“这条判据守的是三条保证里的哪一条”（`—` = **不参与降级判定**：一类守机制完整性（`stage.gate_bound`/`change.rework_counted`），一类是**表约束型**（`work_unit.evidence_consistent`，插入即拦、永远生效，根本绑不到 gate 上）。把表约束挂到保证上会让该保证永远「降级」，所以它必须是 `—`）。冻结时按它**机械算出** delta：某条保证下的判据只要有一条没达到 §6 的**有效绑定**，这条保证就记“降级”，并列出缺的是哪条。工具算，人不能改；**手写的 delta 一律忽略**（以工具算出的为准，签字页显示的就是算出的那份）。

### 4.1 适用性（`applies_to`）与 `na`

每条判据带 `applies_to`；它的取值是**阶段种类**（`kind`），**不是 stage 名**：

`kind ∈ {requirement, design, implement, review, deliver}`

**stage 名由每个项目自取**（`explore`/`harden`/`build`/`verify`…），所以 policy 里每个 stage 必须声明它承担哪些 kind：

```yaml
stages:
  - { id: explore, kinds: [implement], after: [] }
  - { id: harden,  kinds: [requirement, design, implement, review], after: [explore] }
  - { id: deliver, kinds: [deliver], after: [harden] }
```

**`after` 是唯一的先后表达**：`stages[]` 的数组顺序不承载语义（否则"无环"无从校验）；P15 校验每条边指向存在的 stage、图无环、所有 stage 可达。

- 当前 stage 的 `kinds` 与判据的 `applies_to` **不相交** ⇒ 判 **`na`**（不是 pass），`reason='stage_not_applicable'`；
- 相交 ⇒ 该判据**适用**；它在这张卡上是否真的被查，取决于该 stage 的 gate 里有没有它——那是下一层（§6），不能混为一谈；
- 一个 stage 可以承担多个 kind（`harden` 同时固化需求、设计、实现与评审），所以 `kinds` 是**集合**：写成单值会让"harden 起恢复"这类保证无处可落（[08](08-方法论与策略.md) §1 保证表）。

| 判据 | `applies_to`（kind） | 说明 |
|---|---|---|
| `stage.requirement_complete` / `intent.restated_consistent` / `scope.present` / `redteam.disposed` / `spec_set.signed` / `intent.explicit_for_risk` / `alignment.examples_present` | requirement | — |
| `stage.design_traceable` / `design.covers_spec` / `design.no_spec_creep` / `design.alternatives_declared` / `node.acceptance_bound` | design | — |
| `node.integration_listed` | deliver | 清单设计期就写，但"全部 connected + 有 evidence"只有交付前才能验；绑到 design gate 上必然红 |
| `task.complete` / `assumption.disposed` | implement | — |
| `mandate.revalidated` | implement / deliver | 重开的卡在重开时与交付前都要按现行尺子复核 |
| `design.code_matches` | implement / deliver | 设计出口只查 consumer，产物指纹在这里复查 |
| `review.round_bound` | review | — |
| `review.required` | review / implement | `task.complete` 在 implement 收口时要读它（高风险卡），所以它**不是**只在 review 适用 |
| `provenance.present` / `stage.gate_bound` / `change.rework_counted` / `assumption_set.signed` | requirement / design / implement / review / deliver | 全阶段 |

> **这一列是机器解析的**：只允许五个 kind，用 ` / ` 分隔，**不许写括号备注**（备注放第三列）。上一版把 `review.required 也在 implement 收口复查` 写在括号里，R29 解析时按 `（` 截断，implement 就被静默丢掉——这类"人看得懂、机器看不懂"的写法本身就是漂移源。

**`alignment.examples_present` 的 trivial 豁免**：单文件、无外部契约、可逆的小条款可以判 `na`，但必须写 `reason='trivial'`；`risk_flags` 非空的条款**不许**用这个豁免（它会绕开"2 正 1 反"的边界思考）。

`assurance.na_stages[]` 记的是"这个 policy 下**缺哪个 kind**"（一份只做 `build[implement] → deliver[deliver]` 的 policy ⇒ 记 `requirement`、`design`、`review` 三个 kind），它与本表**共同**决定哪些判据是 `na`；**两者都由 policy 的 `stages[]` 里的 `kinds` 与 `applies_to` 推出，禁止手填**（P15 校验，缺/多都拒）。

## 5. baseline 冻结与签名变更

> **公理**：凡是影响判定的东西，**冻结之后只能以「签名变更」的方式改**。
>
> 为什么不是“固定集合”：固定集合挡不住**调阈值**——判据还在、指示灯还是绿的，只是尺子变短了。而“偷改阈值”比“删判据”更隐蔽，效果却一样。

### 5.1 冻结什么（baseline）

```yaml
baseline:
  id: b-001
  frozen_by: u-liang                       # 人签
  engine:  { version: 0.1.0, criteria_manifest_hash: … }
  policy:  { id, preset?, stages[{id, kinds[], after[]}], gates{}, switches, regression, artifact_kinds }   # 生命周期 + 产物类别（[08](08-方法论与策略.md) §1/§2）；**每个 stage 必须带 kinds**（§4.1 的 na 靠它算）；artifact_kinds 决定"原型能否进发布证据"，必须在 hash 内，否则改它不用签字
  criteria: [{ id, version, params, guarantee }]   # 这一版用哪些判据、什么参数、守哪条保证（§4 的「保证」列；delta 靠它算）
  gates:    [{ id, stage, criteria[], policy_mode: all_of | any_of, waivable }]
  thresholds: { coverage: 0.8, regression_max_age_days: 7, … }
  assurance: { unbound_gates: [], independence: solo_cooldown(15m),
               db_confidentiality: true, na_stages: [], level: solo }
  hash: sha256(规范化全部字段)              # 内容哈希，不是布尔开关
```

### 5.2 六条规则

1. **每个判定都记 `baseline.hash`**：没有 baseline 的判定无效——判据读数必须能追到“当时用的是哪一版尺子”。
2. **改 baseline = 一次 `change` + 人签**，且**方向不对称**：

   | 方向 | 例 | 何时生效 |
   |---|---|---|
   | **收紧** | 阈值升高、加判据、加门禁 | 可**即时生效**、事后追认（只会让通过更难） |
   | **放松** | 降阈值、删判据、解绑 gate | **必须事前人签**，且要写“这会放行什么” |

3. **引擎升级也算变更**：`criteria_manifest_hash` 变了 ⇒ 走同一套审批。否则“我们升级了”就是合法绕过。
4. **`verify` 每日对账**：重算 baseline hash 与**该条判定引用的那版** baseline 比较（不是与"当前 baseline"比）；引用的 baseline 必须仍是已冻结、内容可复算的，否则 ⇒ **红**。**合法地换新 baseline 不会让历史判定变红**——否则每次冻结都把整个项目打成只读。
5. **版本语义（换尺子时谁按哪把）**：
   - 判定记录存 **`baseline_id` + `hash`**；它只对"那一版"负责；
   - **在飞的 `stage_run` 继续用旧 baseline 判完**，不强制重判；
   - **release 必须声明 `baseline_hash`**，发布证据只能来自**同一版 baseline** 的判定；旧 baseline 下通过的卡要进新版本 ⇒ **必须在新 baseline 下重判**（否则等于用旧尺子交付新标准）；
   - 这条写进 P15 的"变更"段与 P8 的交付前置。
6. **core 判据只能保留或加强，永不删除或放宽**——"收紧/放松"对二值判据没有意义，别用那个词；它保护的是"冻结机制本身"。**清单按名字钉死，共三条**（不按类别临时解释）：
   - `spec_set.signed` —— 防代签：需求集合必须有人签过，模型不能自增；
   - `assumption_set.signed` —— 防代签：假设集合必须有人签过（含空集），"在什么前提下做"不许静默存在；
   - `provenance.present` —— 防伪造声明：每条 `task`/`spec` 有出处（`created_by` 指向已注册 `actor`），不是凭空出现。

   **"绑了"不等于"查了"，也不等于"绕不过"**：P15 要的是 §6 定义的**有效绑定**五条全满足——判据已注册、某个 gate 的 `criteria[]` 含它、该 gate 的 stage 适用它、该 gate `policy_mode='all_of'`、该 gate `waivable=false`。缺任一条都不算：
   - 绑到 `na` 阶段 ⇒ gate 照样绿（上一轮的假绑定）；
   - 放进 `any_of` 门 ⇒ 别的一条绿了就放行，没人签 `spec_set`；
   - 放进可豁免的 gate ⇒ 一纸 waiver 就过。

   三种都是"绑了没查"，一律 `core_not_effective` 拒冻。

   **core 没有"写降级就放行"的后门**：如果 policy 结构上就没有某条 core 判据需要的 kind（例如 `build[implement] → deliver[deliver]` 这种没有 requirement 的 lite，`spec_set.signed` 无处可绑），**直接拒冻**——不提供"在 `guarantee_delta` 里写一句降级就过"的路径。理由：core 保护的是"冻结机制本身"，允许它被 delta 换掉，等于让人签一句话就把防代签关掉，而签名页上那句话是工具渲染的、人只会看见"降级"三个字。

   **lite 仍然配得出来，代价是少阶段而不是少 core**：把例子改成 `req[requirement] → build[implement] → deliver[deliver]`——它缺 `design/review` 两个 kind，于是 `guarantee_delta` 会算出保证 1（`design.*`）与保证 3（`review.required`）降级，人签的就是这两条降级；但 `spec_set.signed`/`assumption_set.signed`/`provenance.present` 仍在，防代签与防伪造没被关掉。**"lite = 少查"成立的前提是 core 不动**（[08](08-方法论与策略.md) §1 的第三层）。

   **"防篡改"不在这张表里**：篡改检测由 `verify`（hash 链、父链、`event_kind` 闭包）和表约束（`UNIQUE(task_id)`、复合外键）承担——它们**没有开关**、不参与 policy，所以不需要"进 gate 集"，P15 只校验上面三条。把"防篡改"写成判据会让它变成一道可以解绑的配置，正好相反。

### 5.3 可插拔是可以的

| 问题 | 结论 |
|---|---|
| 判据/门禁/阈值可以按项目定吗 | **可以**；生命周期也一样——`policy` 是 baseline 的一段配置，内置 preset（瀑布/原型/增量）只是初始值（[08](08-方法论与策略.md) §1） |
| 靠什么保完整性 | **立项冻结成 baseline + 之后任何改动都是签名变更** |
| 膨胀怎么控 | 不靠禁止，靠**经济约束**：每条判据回答“挡哪条漂移”；判据数量与 `caught`/误报率一起进报告——装饰会被看见 |

“可插拔 + 冻结 + 签名变更”强于“固定集合”，因为它把四种绕过（**加 / 删 / 调阈值 / 换引擎**）统一成同一件事：要改就得签字。

### 5.4 一个陷阱

冻结**不能**是数据库里的 `frozen: true` 字段——那个字段自己也会被改。它必须是**内容哈希**：出现在每个判定里、能离线复算、`verify` 能对账。

## 6. 门禁（gate）

```text
gate = { id, stage, criteria: [criterion_id], policy_mode: all_of | any_of, waivable }
```

- `all_of`：全部 `pass` 或 `na` 才放行；有 `fail` ⇒ `fail`；**空集（一条判据都没绑）⇒ `fail`**——"全部通过"在空集上是真空真，必须显式堵掉（与 `any_of` 空集同罪，见命题 2）；
- `any_of`：**只要有一条 `pass` 就放行**（`pass` 与 `fail` 并存也放行）；**没有任何 `pass`**（全 `fail`/`na`，含空集）⇒ `fail`；
- **`na` 不算通过，但不算失败**——必须带 `reason` 与"由谁判定"；
- **有效绑定**（某条判据算不算真被查）= ① 判据已注册；② 某个 gate 的 `criteria[]` 含它；③ 该 gate 的 stage 与它的 `applies_to` 有交集；④ 该 gate `policy_mode='all_of'`；⑤ 该 gate `waivable=false`。缺任一条都不算——`any_of` 门里"别的一条绿了"就放行，可豁免门一纸 waiver 就过，两者都等于没查（`core_not_effective`）；
- **`waivable` 是 gate 级字段，不是判据级**：`waivable=false` 的**整个 gate** 不可豁免（安全类、代签类都靠它）。旧写法「不可豁免的判据」把粒度写错了——判据没有自己的豁免开关；
- 每次判定写一条 `gate.judged` 事件，含**每条判据的三态与 data**（不是只写"失败"）。

**放行语义**：`advance` 由 `gate.judged` 驱动；没有 `pass` 的 gate，`advance` 被拒绝（不是"警告"）。

---

## 7. 豁免（waiver）必须是"有价的"

| 规则 | 说明 |
|---|---|
| 只能由人签 | `decision(kind=waiver)`，绑 frontier + 内容哈希 |
| 必须有到期 | 默认 **7 天**（**豁免 TTL**，与授权窗口/分歧 L4/未结案 change 的 7 天无关）；过期自动失效，回到红 |
| 必须写代价 | 表单强制填"豁免了什么风险、谁来承担" |
| 计入读数 | `gaps` 里显示"当前生效豁免 N 项"，超阈值告警 |

**不许"永久豁免"**：v1 的教训是，永久豁免会被正常化，然后没人记得它存在。

## 8. 变异自证（判据要证明自己有用）

对每条 `product` 与关键 `process` 判据，要求一组变异：

```text
变异：把实现改坏（一处）→ 判据必须红；复原 → 全绿
自证：脚手架必须报告"字节变了 / 真的写盘了 / 已还原"（不许假变异）
```

v1 的教训（`DEF-166/167`）：变异自证本身可能不可复算——所以 v2 里变异记录写进 `evidence`，绑产物指纹；两次会话读数不一致时，**两次都留，标 `disputed`**，而不是覆盖。

## 9. "这条判据值多少钱"（v1 完全缺失的读数）

| 读数 | 定义 | 用途 |
|---|---|---|
| `caught` | 该判据首次抓到真缺陷的次数（`defect.criterion_id`） | 零的判据进入"退休候选" |
| `false_positive` | 负例夹具红过 / 被人投诉并确认为冤的次数 | >0 必须修判据，不许改成豁免 |
| `cost` | 该判据在最近 30 天的执行总时长 | 排序优化与拆分依据 |

这三个数每轮迭代可见；**没有它们，判据只会继续长，优劣无法判断**。

---

## 10. 不变式

1. 没有负例夹具的判据不可 `active`——由**注册校验**（写入路径）保证，**数据库约束表达不了"至少一正一负"**（[探针](../probe/REPORT.md) 已证：无夹具的判据照样能插入）；**夹具可有多组**：同极性允许多条（`UNIQUE(criterion_id, polarity, input)`，同一输入不许重复），多条负例正是变异自证的材料；
2. 判据不得写任何"结论文字"到 `claim` 之外的地方（回执文字由渲染器生成）；
3. 判据不得读文件系统（只读视图）；确需读产物的，必须通过 `evidence` 接口；
4. 不可豁免的判据集合固定（代签、密钥外泄、审计链断裂）；
5. **判定必须绑 `baseline.hash`**；baseline 的冻结与变更规则见「baseline 冻结与签名变更」（唯一家，此处不复述）。

---

## 11. 验收读数（M1）

- 故意把某个判据的实现改坏 ⇒ 对应负例红；
- 新增一条判据但不给负例 ⇒ 注册被拒（不是警告）；
- 一条判据连续 3 个迭代 `caught=0` ⇒ `gaps` 出现"退休候选"行。
