## 0. 结论（TL;DR）

**结论：0.2.0-rc.1 对 SDO 是显著利好，且包含 2 处必须改设计的破坏性变更。**

| # | 变化 | 对 SDO 的价值 | 设计动作 |
|---|---|---|---|
| 1 | preset 从「文件系统目录 + roots 配置」改为**声明式插件行**（`dsh-agent-preset`） | **消除了设计初稿里最脆弱的一环**（`roots`/`trust`/`!!js baseUrl` 路径把戏）；preset 可作为入口随包以 patch 交付 | **重写 §11.3/§11.4**；新增 `presets/*.patch.yml` |
| 2 | 新增 **Agent Teams**（`ctx.agentTeams` + 9 工具 + 持久 mailbox + CAS 任务板） | **直接替换** §8.3 手搓的派发器与「inbox 单一写者协议」；任务板带依赖 DAG、CAS revision、**文件触及重叠警告** | **重写 §8.3**；RISK-05 缓解措施改为复用原生能力 |
| 3 | 新增 **`dsh-workspace-changes`**（逐轮改动文件 + 逐文件 diff） | 构造/验证阶段的**天然证据源**；Web 已自带「改动文件卡片」 | 新增 §10.4「轮次证据」；接 G5/G6 |
| 4 | 新增 **`dsh-experimental-auto-review`**（逐调用模型审查 + 风险分级） | L3 门禁的**现成参考实现/可选组件** | §9.4 增补；作为 L3 的实现蓝本 |
| 5 | 客户端 UI 扩展点成熟：**`dsh-client-ui-slots` 成为真包**，Team 面板给出投影驱动样例 | Q-06「是否做 Web 面板」的**重路径有官方样板** | §14.2 Q-06 更新 |
| 6 | 新增 **`dsh-hmr`**（代码 + 配置热重载）、`dsh-config-editor`、`dsh-plugin-manager` | 开发体验；插件可**自举安装自己的 preset bundle** | §11.6 更新「必须重启」的旧结论 |
| 7 | 新增 **`dsh-token-meter`** + **`dsh-session-stats`**（逐会话用量与墙钟） | 「成本监视」有了**唯一可信来源**：日志回放、确定、无需模型调用 | **新增设计初稿 §10.6**；但 dsh **无计费概念**，金额须自建单价表并处处标注估算 |
| 8 | **`dsh-session-projection`** + **`dsh-client-ui-slots`** + 官方 client 插件样板 | 「可视化看板」有了标准数据通道与渲染范式 | **新增设计初稿 §10.5**；两步走（文本看板 → Web 面板） |
| 9 | **`dsh-plan-mode`** 的会话级状态范式（仅记日志事件 + 投影 + 命令） | 「入口」有了现成对照组；本项目按 C-07 **只做装配级入口** | 设计初稿 §11.2（preset-only）；会话内开关记为 §14.2 候选 |
| 10 | `dsh-llm` 的 **`llm/stream` waterfall**（模型调用可拦截） | 若将来要做"预算硬停"，接缝在此 | **本轮按 C-08 明确不用**；其拒绝语义未核实（§7 U-9） |

**未变（好消息）**：`dsh-tools` 的**事件集与 `defineTool`/`guard`/`restrict` 签名在两版之间完全一致**——SDO 的工具面与三级门禁设计**可原样移植**。

**仍需接受**：子代理**依旧不支持**按 preset/agentType 指定（逐子代理可配 `persona`/`toolFilter`/`agentOptions`）；preset **仍只能在空会话切换**；teammate **不能**逐成员指定 persona/toolFilter（角色靠 prompt）。

## 2. 六项直接支持 SDO 的新能力

### 2.1 【最重要】preset 声明式化：`dsh-agent-preset` + `dsh-agent-preset-registry`

**机制**（已核实）：

```yaml
# 示意（YAML 方言与字段），不代表 SDO 的最终装配：SDO 只声明一个 preset
# （sdo-office）作为入口。
- id: agent-preset-registry
  name: '@deepseek-ai/dsh-agent-preset-registry'
  config:
    default: standard
- id: preset-sdo-office
  name: '@deepseek-ai/dsh-agent-preset'
  config:
    id: sdo-office             # 稳定标识符，会话保存的就是它
    name: SDO 研发办公室         # 展示名
    order: 10
    plugins: [ ... ]           # 子插件行列表（本插件行 / persona / 工具行 / 提示行 / skill 行）
```

关键事实（逐条引自 README）：

- 「在普通 Cordis YAML 中定义 Agent 的子插件列表。可同时声明多个 preset，由会话选择。」
- 「**注册表不扫描目录，也不接受 preset 路径**。」
- 「新增 preset 或覆盖内置 preset 都是 **bundle 补丁**：插入一行 `@deepseek-ai/dsh-agent-preset`，或按该行 id 写覆盖补丁。」
- 「声明不提供目录、文件复制或文件删除操作。」（旧的「复制目录创作 preset」能力**消失**）
- 「会话日志保存 preset ID 和空白会话的切换记录；重启恢复使用该 ID 的当前定义，**缺失时拒绝恢复**。」
- 激活审计会拒绝：导入失败、缺失服务、向全局 realm 泄漏服务的行；等待 Host 服务的行保持挂载并在 Host 结算后重新审计（**启动顺序不再决定结果**）。

**bundle 侧的真实样例**（`dsh-web-app@0.2.0-rc.1`）：

```json
{
  "dsh": {
    "bundle": {
      "patch": [
        "./cordis.patch.yml",
        "./presets/standard.patch.yml",
        "./presets/ptc.patch.yml",
        "./presets/minimal.patch.yml",
        "./presets/cordis.patch.yml"
      ]
    }
  }
}
```

即：**`dsh.bundle.patch` 现在接受数组**（单文件字符串仍受支持，`dsh-base`/`dsh-acp-app` 仍在用字符串），每个 preset 一个 patch 文件，文件内容是 `- insert: [ {id: preset-*, name: '@deepseek-ai/dsh-agent-preset', config: {id, order, plugins: [...]}} ]`。

**对 SDO 的影响（比 0.1.5 方案好很多）**：

| 方面 | 0.1.5-rc.2 方案（设计初稿 §11.3/§11.4） | 0.2.0-rc.1 方案 |
|---|---|---|
| preset 载体 | 目录（`preset.yml` + `agent.cordis.yml`） | **Cordis 插件行**（纯 YAML，随 patch 交付） |
| 注册方式 | 配 `dsh-agent-presets` 的 `roots: [{path, trust}]` 指向包内目录 | **bundle patch 数组**，无需任何路径配置 |
| 角色卡技能 | `customSkillDirs` + `!!js baseUrl` 相对路径表达式（脆弱、需实测） | 直接用**普通插件行**（`ctx.skills.register` 或 `skill-filesystem` 行）；路径问题消失 |
| 可信度 | `trust: user` 需自行声明 | 由 bundle/patch 层与安装流程承担 |
| 会话切换 | 空会话才能切 | **不变**（同样限制） |

**建议改动**：§11.1 包结构把 `presets/` 从「preset 目录」改为 `presets/*.patch.yml`；§11.4 的 `agent.cordis.yml` 骨架改为 `config.plugins` 行列表；§11.3 的 preset 相关行重写；§2.1 表格中「角色 = 独立装配」一行更新。

> **注**：`presets/` 最终只有**一份** `sdo-office.patch.yml`，作为唯一入口（设计初稿 v0.4 起）。

### 2.2 【最重要】Agent Teams：`ctx.agentTeams` + 9 个团队工具

**能力**（已核实）：

- 会话内的 agent 成为 **Lead**，创建**具名 teammate**（唯一小写名，**名字永久、不复用，含创建失败者**），teammate 可 `fresh`（不带 Lead 记忆）或 `fork`（继承 Lead 已完成轮次）启动。
- **持久消息**（mailbox）：live 成员立即收，离线成员**排队并在恢复后送达**；「消息不会丢失，也不会重复投递」。投递语义 = Steer（运行中在最近步骤边界，非活动则启动/冷恢复轮次）。
- **共享任务板**：`subject`/`description`/**`blockedBy`（依赖 DAG）**/**`writeScopes`（文件触及提示）**；claim/完成/释放/重开；**每次变更 CAS（`expectedRevision`），过期更新被拒绝**；Lead 可分配 owner。
- **写冲突预警**：「当两个 in-progress 任务计划触及重叠路径时，文件提示会产生警告——它们绝不阻止任何操作。」
- roster 状态：`running` / `inactive` / `provisioning` / `failed`，角色 `lead` / `teammate`。
- 权限：**只有 Lead** 可创建/中断；每个服务方法都接收确切的实时调用方 `Agent`。
- 上限（配置项，启动时校验）：`maxMembers 16`、`maxTasks 256`、`maxPendingMessagesPerMember 64`、`maxMessageBytes 65536`、`disposalTimeoutMs 5000`。
- 持久性：**Lead 会话日志是唯一真源**，roster/mailbox/任务每次读取都从其**回放**。
- **前提**：需要持久会话存储（`dsh-session-persistence-jsonl`）。
- **明确不支持**：teammate 独立工作目录、跨进程协调同一团队、任务 owner 自动释放。
- 定位为**实验性**（experimental 名，不承诺稳定性）。

**服务 API**（`ctx.agentTeams`，来自 `lib/types/index.d.ts`）：

```ts
membership(agent): TeamMembership
listMembers(agent): TeamMemberView[]
spawnTeammate(caller, request): Promise<SpawnTeammateResult>
sendMessage(caller, request): Promise<SendTeamMessageResult>
createTask(caller, request): Promise<TeamTaskView>
getTask(caller, id): TeamTaskView
listTasks(caller): TeamTaskView[]
updateTask(caller, request): Promise<TeamTaskView>
waitForChange(caller, timeoutMs, signal): Promise<TeamWaitResult>
interrupt(caller, targetName): { ... }
tryMembership(agent): TeamMembership | undefined
```

**模型面 9 个工具**：`spawn_teammate`、`send_message`、`list_agents`、wait、interrupt、`team_task_create`、`team_task_list`、`team_task_get`、`team_task_update`（每类见 README「九个工具分为四类能力」）。安装后**每个团队成员（含 Lead）都拿到同样 9 个工具与同一份协作策略**；`spawn_teammate` 会在初始任务前插入身份 system-reminder。

**⚠️ 关键限制（决定 SDO 的角色设计）**：

```ts
interface SpawnTeammateRequest {
  readonly name: string
  readonly description: string      // 职责描述（人类/模型可读）
  readonly prompt: ContentBlock[]
  readonly context: 'fresh' | 'fork'
  readonly provider: string
  readonly signal: AbortSignal
}
```

**没有 `persona`、没有 `toolFilter`、没有 `agentOptions`**——teammate 的角色是 **prompt 级**的，无法在装配层强制工具边界。对比 `ctx.subagents.start`（支持 `persona` / `toolFilter` / `agentOptions` / `outputSchema`），两者是**互补而非替代**：

| 机制 | 强项 | 弱项 |
|---|---|---|
| `ctx.agentTeams`（teammate） | 具名 roster、持久 mailbox、**共享任务板 + 依赖 DAG + 写范围警告 + CAS**、崩溃可恢复 | **不能**逐成员收窄工具/persona；单进程、共享 cwd；实验性 |
| `ctx.subagents.start`（子代理） | **可强制的角色边界**（persona + toolFilter + 结构化 outputSchema） | 无共享任务板；协作靠自己编排 |

**建议改动**：

- **§8.3 派发器重写**：编排器优先使用 `ctx.agentTeams`（任务板替代我的 `.sdo/tasks/*.yml` 的"活动视图"，mailbox 替代手写的 `.sdo/inbox/*.json` 单一写者协议）；需要**强制角色边界**的任务改用 `ctx.subagents.start({persona, toolFilter, outputSchema})`。
- **RISK-05（多代理并发写坏状态）**：从"自研 inbox 合并"降级为"复用原生 mailbox + CAS 任务板"，并保留 `.sdo/journal.jsonl` 作 SDO 自己的真源（团队任务板是**协调状态**，不是 SDO 的需求/设计真源——两者职责不同，不应混用）。
- **新增设计约束**：团队启用需持久会话存储；`maxMembers 16` 与 SDO 的 `maxParallelDispatch` 需对齐。
- **注意**：官方 `dsh-experimental-agent-team-profile` 会**禁用** `tool-subagent`/`tool-subagent-fork`/`tool-subagent-control` 并把委派交给团队工具。SDO 若两者都要，**不要复用该 profile 层**，而应在自己的 bundle patch 里只插入 team 两个包、保留 `subagent`/`subagent_fork`（它们与团队工具**不同名**；同名的只有 `send_message`/`list_agents`/interrupt 这类控制工具）。

### 2.3 `dsh-workspace-changes`：逐轮改动证据

**能力**：比较每个顶层轮次开始/结束时的 **git 工作树快照**，并对文件工具编辑的每个文件在**首次编辑前**与**轮次结束时**各复制一份整文件，从而覆盖 git 覆盖不到的文件；无仓库/无 git 时只列文件工具编辑。Session 只收到一条 `workspace/changes` 事件（含轮号），摘要与逐文件 diff 留在 Host；**Web 的「改动文件卡片」渲染它们**。

**对 SDO 的价值**：

- G5（构建门禁）与 G6（验证门禁）的**证据自动可得**：「本轮改动了哪些文件、每个文件多少行、前后内容对比」——这正是"任务完成"与"评审输入"需要的东西。
- 评审员（§8.4 四眼原则）可以直接拿这份 diff 作为评审对象，而不是让调度器自己拼。
- 与 SDO 的 `sdo_task(action=done, evidence=...)` 天然对接：把 `workspace/changes` 作为证据条目登记，避免"证据靠模型自述"。

**建议改动**：新增 §10.4「轮次证据与改动捕获」；在 §9.1 的 `sdo_task` 说明中加入"证据可引用 `workspace/changes`"；§12.1 端到端用例增加一条"任务完成时证据含轮次改动摘要"。

### 2.4 `dsh-experimental-auto-review`：L3 门禁的现成蓝本

**能力**：在每次原生或 PTC inner 工具调用**执行前**，用当前 agent 的 provider/model 评估该动作，并按**实际效果分级**：

- low（普通项目内操作、精确清理本 Session 创建的对象）→ **直接允许**；
- medium（不可逆删除既有对象、生产操作、外部写入、安全控制变更）→ 需要 human/直接父级明确授权（动作、目标、范围）；
- high（跨信任边界泄露敏感信息）→ **始终拒绝**；
- 效果不明确或授权冲突未解决 → 拒绝。

选择 Auto 会设 `ask` 审批策略，被拒调用转为用户审批；**进程内委派 child 固定 `never` 策略，其拒绝是最终结果**；reviewer 响应不合法或技术失败会**使调用失败且从不执行**。默认关闭、实验性，且"可能误放行不安全动作、误拒绝有用操作，并消耗额外 token"。

**对 SDO 的价值**：

1. **它是 SDO §9.4 L3「阶段纪律守卫」的官方同类实现**——证明了"用模型审查工具调用"这条路在 dsh 里是可行的、且已有审批策略（`ask`/`never`）与审计理由的对接方式。
2. 它演示了**与审批栈的正确耦合**：拒绝 → 读 Session 审批策略 → `never` 下最终拒绝 / `ask` 下交给后续 listener → 只有后续都放行才返回 `ask`。SDO 的 L3 若要与审批栈共存，应照此顺序。
3. 它给出**卸载时的迁移义务**（存活 Auto Session 要迁回 Full access、在途 review 要结清）——SDO 启用 L3 时同样需要"切回非 L3"的清理路径。

**建议改动**：§9.4 增补"审批栈耦合顺序"与"模式切换时的迁移义务"；§14.1 增补风险"L3 会误拦合法操作"——参考 auto-review 的分级思路（SDO 的 L3 应按**路径+阶段**分级，而非一刀切）。

### 2.5 客户端 UI 扩展点成熟（Q-06 的重路径有样板）

- **`dsh-client-ui-slots` 现在是独立真包**（0.1.5 中它作为依赖被引用，但 store 里没有自己的目录）。
- `dsh-experimental-client-ui-agent-team` 给出**完整的投影驱动面板样板**：「从共享 Session store 读取 Lead Session 的 `agentTeam` 投影，Host 投影 frame 使其保持最新而无需刷新控件」；它「不扩展稳定 API Proxy、不存储 Team 状态、也不注册面向模型的输入」。

**对 SDO 的价值**：§14.2 Q-06 的两步路径（宿主侧 `ctx.sessionProjections.register` → 客户端小插件消费）现在**有官方同构样例可抄**：SDO 注册 `sdo` 投影（阶段/门禁/追溯覆盖率/开环问题），客户端插件挂到既有 slot 渲染看板。

**建议改动**：§14.2 Q-06 补充"参照 `dsh-experimental-client-ui-agent-team` 的投影 + slot 结构"。

### 2.6 开发期与自举能力：`dsh-hmr`、`dsh-config-editor`、`dsh-plugin-manager`

| 包 | 能力 | 对 SDO 的意义 |
|---|---|---|
| `dsh-hmr` | 「在应用运行期间重载**插件源码和配置**。模块替换、Include 刷新与 profile 配置变更共用一个队列。**包安装在该队列之外执行**。」 | **更新设计初稿 §11.6 的旧结论**：0.1.5 时代"改代码必须重启 dsh"在启用 HMR 后不再成立（未启用时仍"更改在重启后生效"）。开发效率显著提升；但**新增/删除源文件**引起的模块图变化仍需谨慎（见 §6） |
| `dsh-config-editor` | 把插件配置写进当前 profile 的 patch 并立即应用；写入前校验完整候选值，与 profile 更改及 HMR 串行 | SDO 的配置（门禁级别、流程模型、角色开关）可**由用户/agent 就地修改并即刻生效**，不必手改 YAML |

### 2.7 成本与观测三件套：`dsh-token-meter`、`dsh-session-stats`、`dsh-session-projection`

| 包 | 提供 | 对 SDO 的价值 | 关键边界（README 原文要点） |
|---|---|---|---|
| `dsh-token-meter` | `ctx.tokenMeter.measure(session, header?)` → `{totalTokens, surfaceTokens, nodes}`；`estimateMessage()`；会话投影 `tokenUsage`（`uncachedInputTokens`/`outputTokens`/`cacheReadTokens`/`cacheWriteTokens`）、`contextPressure`（`pressureTokens`/`projectedTokens`/`contextWindow`）、`contextBreakdown`（`systemTokens`/`toolsTokens`/`messageTokens`）；`deriveTurnTokenUsage(events)`（逐次尝试/逐轮精确用量，供浏览器消费方） | 「监视 agent 消耗」的**唯一可信来源**：由持久日志回放得出，**确定、无需模型调用** | ⚠️「占用是参考数字，**不是计费记录**」；文本按**每 token 四字符**的固定启发式，会**低估 CJK 与 JSON schema**；提供方用量只在规范 envelope 完全相同时复用。**没有任何"钱"的字段** → 金额必须由 SDO 用**用户单价表**换算 |
| `dsh-session-stats` | `sessionStats` 投影：`turns`/`steps`/`llmMs`/`toolMs`/`ttftMs`/`ttftSteps`/`decodeMs`/`decodeTokens`，**全日志口径**（不受分页与压缩影响） | 看板的"效率"列与"是否卡住"判断（墙钟时间） | 只在组合了投影注册表时挂载（否则键缺失）；计数是**日志口径而非 surface 口径** |
| `dsh-session-projection`（+`-cache`） | `register({key, stateSchema, stateVersion, init, apply, wire?})`；`snapshot(session)` → `{asOfSeq, values}`；`onChanged`；`stateOf(session, key)`；无 `wire` 即 host-only | 看板的**数据通道**：宿主算、客户端读，两侧互不相识 | ⚠️ 单元表是**进程级**的——「key 是否存在**不能**当作逐会话的能力信号」，客户端必须**读值**（`active`）而非看 key；`apply` 必须同步，且无关事件必须返回**同一引用** |

**对 SDO 的直接结论**：看板 = 一个挂在 Lead 会话上的 client-visible 单元（聚合整棵会话树）；成本 = 用户单价表 × `tokenUsage`，并且**必须**处处标注"估算"（设计初稿 NFR-012 / RISK-18）。

**跨 agent 归集的两条硬约束**（读类型定义得出，不是推测）：

1. `SessionStore.get(id)` **只返回存活会话**（`list()` 也只列存活）→ 子代理一结束就取不到用量 → 必须在**结算时刻当场采样**（NFR-014），否则只能记 `unattributed`。
2. 会话树可枚举：`listChildren` / `listDescendants(ctx, sessionId)`，以及父会话的 `subagentCatalog` 投影（`subagent/catalog` 事件）；但子代理的 `subagent/end` 载荷**只带 `stopReason` 与 `lastAssistantMessage`，不含用量**——用量只能来自**子会话自己的**日志/投影。

### 2.8 会话级状态的范式与客户端 UI：`dsh-plan-mode`、`dsh-client-ui-slots`

| 范式 | 事实 | SDO 如何使用 |
|---|---|---|
| 会话级状态（`dsh-plan-mode`） | 用**仅记日志、整值替换**的事件 `plan/mode` 持久化状态（最后一条已记录值即状态）；轮次开启期间变更**待生效**到下一个被接受的轮内 pre-step；激活状态**跨会话恢复与 fork 保留**；未激活时提示段**不贡献任何 token**；`/plan` `/plan off` 切换；投影单元 `plan` 提供 `{active, pending}` | **入口语义的对照组**：SDO 按 C-07 **不做**会话内开关，但"未激活零 token""状态可恢复"这两条纪律照搬。将来若要补会话内开关，这套「事件 + 投影 + 命令」三件套可直接复用（已记为 §14.2 候选） |
| 客户端 UI（`dsh-client-ui-slots`） | 浏览器侧 slot 注册表：`single`/`list`/`keyed`/`chain` 四种 kind、Component Factory、`SlotMap` 由消费方 `declare module` 增补、注册冲突在**加载时**抛错 | M6 交互面板：注册 locale + conversation-header slot，**只读**渲染 `sdo` 投影 |
| 客户端插件形态（`dsh-experimental-client-ui-agent-team`） | `package.json` 的 `dsh.client = { inject: [<客户端包>], platform: 'web' }` + `./client` 导出；host 入口**不执行行为**；面板从 `projectionsBySession[lead].values.agentTeam` **读值**，成员活动来自 Session 状态 | SDO 面板的**照抄样板**，连同三条已知限制一起继承：key 存在 ≠ 有值、**晚启用需刷新页面**、面板只读 |
| 模型调用拦截（`dsh-llm`） | 分发经过 `llm/stream` **waterfall**，可被中间件包裹（README：「…interceptable via the `llm/stream` waterfall」） | **按 C-08 明确不使用**：SDO 不做预算硬停。登记在此只是为了将来若要"停机"时知道接缝在哪，且其**拒绝语义尚未核实**（§7 U-9） |

### 3.1 子代理的新增（不改变结论，但需登记）

- 新增 Host 设置 `maxActiveSubagents`（默认 **8**）：限制**可续接**父子链共享名额的存活子代理数；超额以 `ACTIVATION_LIMIT_REACHED` 拒绝（浏览器侧 `subagent/delivery-unavailable`）；**不排队**。一次性与外部提供方运行不受限。
- 委派设置新增 `maxDepth` 默认 **1**（工具显式指定优先，`provider-managed` 可用）。
- **仍然没有** `preset`/`agentType` 参数——逐子代理可配的仍只有 `persona` / `toolFilter` / `agentOptions` / `maxDepth`。

**对 SDO 的约束**：`maxParallelDispatch`（设计初稿 §11.2 写 4）与 `maxActiveSubagents=8` 需一并考虑；**可续接**子代理会占名额且不排队，所以 SDO 的编排器必须在派发前做容量预算，而不是"发出去等报错"。

## 6. 目标版本线：**已定 `0.2.0-rc.1`**（不再选型）

**决策（2026-09-29）**：本项目**直接基于 `dsh 0.2.0` 开发，不考虑 `0.1.5`**——不做双版本适配、不做迁移桥。本节保留原选型对照的**结论性内容**，作为"为什么是 0.2.0"的记录；`0.1.5` 列至此仅为历史对照。

| 维度 | 0.2.0-rc.1 提供 | 对 SDO 的意义 |
|---|---|---|
| preset 交付 | 声明式 patch 行（`@deepseek-ai/dsh-agent-preset` 的 `config.plugins`） | 消除初稿里最脆弱的一环（目录 + `roots` + `trust` + `!!js baseUrl` 路径把戏） |
| 多代理协调 | 原生任务板（CAS revision + 依赖 DAG）、持久 mailbox、写范围重叠警告 | 直接替换手搓派发器与 `.sdo/inbox` 单一写者协议 |
| 改动证据 | `workspace/changes`：每轮改动的文件与逐文件 diff（宿主侧原生记录） | G5/G6 有了不依赖模型自述的证据源 |
| 开发效率 | `dsh-hmr`：源码与 profile 配置热重载（未启用时仍重启生效） | 缩短"改—验"回路 |
| 门禁参考实现 | `dsh-experimental-auto-review`：逐调用模型审查 + low/medium/high 分级 | 提供分级审查思路与审批栈耦合顺序的既有实现 |
| 稳定性代价 | 版本线为 `rc`，且 Teams 等为**实验性、不承诺稳定性** | **必须**把实验性 API 封在适配层之后并保留降级路径 |
| 生态 | `dsh-agent-presets` 已被移除，社区包会陆续跟进 0.2.0 | 跟随主线，不做落后版本兼容 |

**已落实的隔离要求**（对应设计初稿 C-06 / §8.3 / RISK-11）：

- `ctx.agentTeams`（实验性）封装在 SDO 内部 `src/integration/` 的 `TeamOrchestrator` 适配层之后，**领域逻辑只依赖 SDO 自己的接口**，不直接散落调用实验性 API；
- 配置保留 `orchestrator: native-team | subagent | inline` 三档，**原生团队不可用时自动降级**到 `subagent`；
- 该依赖与降级策略已登记为设计初稿 §14.1 的 **RISK-11**，并写入 §14.3 能力边界第 6/8 条。
