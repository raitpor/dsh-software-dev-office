# 变更与影响链

> 这一篇回答两个问题：**改一处，哪些地方会跟着失效**（影响链），以及**工具凭什么替你做这件事**（两段式写协议）。
> 前提：所有写都必须经过工具，所以工具可以在同一个动作里既改内容、又维护影响链。**模型不负责找影响面，只负责决定改不改。**

## 1. 派生图：节点与边

节点 = 任何有身份的东西：`intent / spec / scenario / criterion / design / task / evidence / claim / defect / release`。

边 = **消费关系**，并且**边上带版本**：

```json
{"kind":"task","id":"TASK-261",
 "inputs":[{"kind":"spec","id":"S-12","hash":"sha256:aa…"},
           {"kind":"design","id":"D-03","hash":"sha256:bb…"}]}
```

**只记“消费了谁”不够**——必须记“消费的是哪一版”。有了 `inputs`（含 hash），影响链才是可计算的：某节点 hash 变了 ⇒ 所有 `inputs` 里引用旧 hash 的节点**立刻可判定为 stale**。

**硬约束**：参与结论的节点（claim / criterion / evidence / task / spec）必须显式声明 `inputs`，**不声明不许创建**。纯说明性内容（narration、文档片段）不强制。这条把“影响链完整性”变成**创建时的不变式**，而不是事后补。

**存储形态**：`inputs` 是真源，`node` / `edge` 是**同一事务里重建的物化索引**（任何代码不得直接写 `edge`）；表结构与遍历契约见 [03](03-真源-存储事件与折叠.md) 的「图模型」一节。**不引入图数据库**——理由同样在那里（约束即判据、聚合视图、缺省形态）。

## 2. 三类变更

| 变更 | 例子 | 下游处置 |
|---|---|---|
| **内容变**（hash 变） | 条款改写、设计换方案 | 标 `stale`；**失效但不删除**；重派生要落**新**节点 |
| **作废 / 取代** | 条款废弃、设计推翻 | 下游必须**重新绑定或一并作废**；不许挂着旧上游 |
| **范围变**（release in/out） | 某缺陷顺手进本版 | 不重算，只改 claim 的“有效归属” |

## 3. 复位动作表（工具自动做的部分）

| 节点 | 自动复位 | 留下什么给重做 |
|---|---|---|
| `claim` | 标 `stale` 并按新上游重派生一次 | 重派生后仍不成立的前提 |
| `evidence` | 标 `invalid`（它绑的是旧产物指纹） | 重跑命令产出新证据 |
| `criterion` | 标 `retired_pending_reregister`（**不自动改判据逻辑**） | 重新注册（新版本 + 重跑正负例夹具） |
| `scenario` | 标 `stale` | 人确认场景是否还成立 |
| `design`（派生文档） | **自动重渲染** | 手写散文部分要人改 |
| `task`（未开工） | 标 `stale`，回 `ready` 但被阻断 | 重新读新条款 |
| `task`（在飞） | `blocked(upstream_changed)`，**保留工作副本** | 续做还是丢弃（保留 diff） |
| `task`（已完成） | `reopened(upstream_changed)`，旧证据留作历史 | 重新举证 |
| `release` 项 | `blocked`，冻结前必须处理 | 决定进/出本版 |

**“完成”是可被上游推翻的断言**，不是永久状态——否则影响链会在“已完成的卡”那里断掉，而这是最常见的一种（需求改了，卡还显示已完成）。

## 4. 传播三条规则

**① 只标记，不重建。** 传播的产物是 `stale(upstream=…, since=frontier)`；重建必须是**显式的新派生**（新 claim，旧的标 `superseded`）。自动重建会造出“拿旧证据算新结论”的 L1 漂移。

**② 阻断与告警必须分开。**

| 级别 | 判定 | 后果 |
|---|---|---|
| 阻断 | stale 节点参与结论（claim、判据输入、release 证据） | 卡不能 done、版本不能冻结 |
| 告警 | 只影响说明性内容（narration、文档片段） | 只提示 |

不分级别的后果 v1 已经演过：一次需求变更让整个项目全红 ⇒ 所有人学会忽略红色。

**③ 唯一例外通道：`pin`。** 允许在**边**上显式声明“我就是要基于那个旧版本”，但必须带理由 + 人签，且永久可审计。没有 pin，影响链会逼着所有人“假装没变”；有了 pin，例外就变成可计数的负债。

## 5. change set

一次变更 + 受影响集合 + 处置结果，落成一条记录：

```text
change C-17: spec S-12 hash 变
  impact: spec×3 design×2 task×11 criterion×4 claim×9
  applied: claim×2 stale / evidence×1 invalid / task×3 blocked|reopened / design×1 re-rendered
  pins: 1（理由 + 签字）
```

它有两个消费方：**审计**（这次变更后来真的落地了吗）与**签字页**（“差异/后果”两格的来源）。

**未结案的 change 进 `v_gaps`**：标了 stale 不等于解决，默认 **7 天**（**change 结案 TTL**，与豁免/授权窗口/分歧 L4 的 7 天无关），逾期升级为阻断。

## 6. 两条边界

**① 连坐到底。** 传播沿反向边递归进行，直到没有下游。只到第一层会留下“上游 stale、下游自以为有效”的假象，而那个假象正是 L2 漂移。

**② 已冻结的 release 不可被穿透。** 影响面里若有“已冻结版本的证据”，`change` 必须**拒绝**（或要求先开新版本）。否则一次需求修改会悄悄改掉已发布版本的事实。

## 7. 两段式写协议（所有带影响面的动作通用）

```text
① sdo_act(action, payload)      → {preview_id, will_change, requires, expires_at}
② sdo_act(confirm, preview_id)  → {change_id, applied: […]}          # 原子提交
③ sdo_act(cancel,  preview_id)  → {cancelled: true}                  # 留痕
```

**关键语义**：

1. **preview 是视图，每次现算**，与 confirm 使用**同一份计算**。不做“轻量摘要”——否则所见非所改。
2. 回执字段叫 `will_change`（**不是 todo**）：语义是“**如果你 confirm，这些就变成这样**”，逐节点给 `from → to` 与原因。**它不是给模型的待办**。
3. 职责划分一句话：**工具决定“改什么”，模型只决定“改不改”。**

`will_change` 的形状：

```text
criterion R-12   → retired_pending_reregister   因 spec S-12 hash 变
claim     C-9    → stale（重派生后 value=false）
evidence  E-31   → invalid（旧产物）
task      261    → blocked(upstream_changed)，工作副本保留
task      248    → reopened(upstream_changed)
design    D-03   → re-rendered（摘要与索引两节变化）
```

## 8. 哪些动作必须两段式

| 类别 | 例子 | 形态 |
|---|---|---|
| 会改变他人有效性 | 改内容、作废、冻结 release、注册判据、reopen、改 policy | **必须两段式** |
| 纯追加、不使他人失效 | 认领、附证据、narration、加锁、记缺陷 | 单步 |
| 本身是决策 | 签字、豁免 | 两段式，且第二段必须人签 |

判断标准一句话：**这个动作会不会让别的节点的“有效性”改变？**

## 9. 三个校验（缺一个协议就有洞）

| 校验 | 防的是 |
|---|---|
| **payload hash** | 预览 A、提交 B（confirm 必须带与 preview 相同的 payload 摘要） |
| **frontier** | 预览之后世界变了 ⇒ 409，要求重新 preview |
| **grant / scope** | 被 [09](09-协作-权限-并行与子代理.md) 的 grant 覆盖 ⇒ `requires: delegated`（进待审计队列）；未覆盖或影响面超 `max_impact` ⇒ `requires: human_sign`，模型 confirm 也提交不了 |
| **baseline 方向** | 变更**放松**了判定（降阈值 / 删判据 / 解绑 gate / 换引擎）⇒ `requires: human_sign` 且不可 delegated；变更**收紧**了判定 ⇒ 可即时生效、事后追认 |

第三条把“权限升级”的触发条件从“动作类型”改成“**这次的影响面**”——影响越大越不能自决。

## 10. cancel 是数据，不是垃圾

`cancel` 落 `act.cancelled`，与 preview 的影响集一起统计。**某类动作的 cancel 率异常高 ⇒ 说明这一类的影响面设计得过大**，是设计信号，不是模型偷懒。不强制填理由（强制会逼出编造的理由）。

## 11. 不变式

1. 参与结论的节点没有 `inputs` ⇒ 不许创建；
2. 传播只标记不改写；重建必落新节点；
3. 阻断类 stale 未处置 ⇒ 卡不能 done、版本不能冻结；
4. 冻结后 release 的证据不可被 change 穿透；
5. confirm 的 `will_change` 必须与 preview 逐条一致（否则视为实现缺陷）；
6. 同一 `preview_id` confirm 两次返回首次结果（幂等）；
7. pin 必须带理由 + 人签，且计入负债读数。

## 12. 验收读数

- 改一条被 3 个 spec、11 张卡引用的条款：**一次 confirm** 后，所有下游状态已自动复位，模型没有逐条操作；
- 把 preview 的影响面与 confirm 的实际改动逐条 diff ⇒ **0 处不一致**；
- 预览之后偷偷改上游再 confirm ⇒ **409**；
- 构造“已冻结 release 的证据”在影响面里 ⇒ `change` **拒绝**，并点名是哪条冻结证据；
- 在飞卡被复位后，工作副本仍在、diff 未丢（不是静默回滚）；
- cancel 后库里**没有任何**节点状态变化（只多一条 `act.cancelled`）。
