## 四、这次实战暴露的**类**问题（比单条缺陷更重要）

| 类别 | 实例 | 以后怎么防（已落实） |
|---|---|---|
| **语义不统一** | `dropped` 卡被当"未完成"算进完成率、被成对写范围误报、完成的卡永久占写范围 | 统一口径为"只有**未放弃**的卡参与判定"；`done`/`verified` 释放写范围 |
| **口径没写进 schema** | 契约"口径"未声明 → 按自然语义理解会算成 0/17 覆盖 | 口径成为字段并进 schema；`producer → consumer` 方向明确 |
| **判据名不符实** | `tests.passed` 曾只查用例数，不查 must 覆盖 | 改为真的校验"每条 must 需求都有通过的用例" |
| **展示层口径与真源不一致** | 「最近判定」按文件名字典序取 → 回执与实际不符 | 按 journal `seq` 排序（时间真源） |
| **平台假设** | 权限位断言、`join()` 反斜杠 → Windows 5 红 | POSIX 权限断言加平台守卫；`store.path()` 归一化正斜杠 |
| **验证方法假绿** | 我多次用"靠父目录/兄弟包兜底"的环境验证通过 ✗ | 只认**与生产同款判据**（CI 命令、隔离 PATH、显式文件列表） |

## 六、结论

- **能用了**：在 dsh 0.2.0 上把"一个人的研发办公室"跑成闭环 —— 立项到交付、门禁全过、交付物带 sha256 与回滚点，且**全程单会话 + 子代理**。
- **值得信的地方**：门禁是机械的（不靠模型自评 ✓）、证据是落盘的（`journal.jsonl` 611 事件 ✓）、文案是双语可切的 ✓、安装包是离线可用的 ✓、CI 是双平台绿的 ✓。
- **别指望的地方**：它不会替你自动开子代理（第 1 条限制 ✗），也没有图形面板（第 3 条 ✗）；成本数字只是估算而非账单（设计如此 ✓）。
- **最值钱的产物其实是这次实战的缺陷账**：42 条缺陷 + 6 类模式化问题，把"看起来能跑"和"真能跑"之间的差距标了出来 ✓。
