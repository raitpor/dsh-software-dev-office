|---|---|

## 1. Q-08：`dsh.bundle.patch` 数组内的顺序语义

### 装置

`pkgs/sdo-verify-bundle/package.json`：

```json
{ "name": "sdo-verify-bundle", "type": "module",
  "dsh": { "bundle": { "patch": ["./zz-first-in-array.yml", "./aa-second-in-array.yml"] } } }
```

**文件名顺序与数组顺序故意相反**（`aa-` 字母序在前）：

- `zz-first-in-array.yml`（数组第 0 位）：`insert` 行 `q08-row`（`tag: FROM-ZZ-FIRST`）+ 行 `q08-override-target`（`stage: ZZ`）
- `aa-second-in-array.yml`（数组第 1 位）：`insert` 行 `q08-row`（`tag: FROM-AA-SECOND`）+ **id 定向**覆盖 `q08-override-target`（`stage: AA`）

### 原始证据（`out/dump.yml`，`dsh --profile probe --dump-config`）

```text
# == sdo-verify-bundle
- id: q08-row
  name: sdo-verify-third-party
  config:
    tag: FROM-ZZ-FIRST          ← 数组第 0 位文件的内容先出现
- id: q08-override-target
  name: sdo-verify-third-party
  config:
    stage: AA                   ← 被后面的 id 定向补丁整体替换
- id: q08-row
  name: sdo-verify-third-party
  config:
    tag: FROM-AA-SECOND
```

挂载标记（`out/mount-markers.jsonl`，真实挂载一次）：

```json
{"config":{"tag":"FROM-AA-SECOND"}}
{"config":{"stage":"AA"}}
```

### 结论

1. **数组顺序被严格遵守**（若按文件名序，`aa-` 的内容会先出现；事实相反）。
2. 后列文件可按**行 id 覆盖**前列，且 `config` 是**整体替换**（`ZZ` → `AA`）。
3. **同 id 用 `insert` 重复插入不会覆盖**：组合树里留下**两行**，挂载只发生一次且**取后者**。
   → 实践含义：**覆盖必须用 id 定向补丁**（`- id: xxx` + `config:`，不带 `insert`），这正是设计文档 §11.2 给用户的写法。

## 2. Q-09：同一 preset 内同时挂 `tool-subagent` 与 team 工具

### 装置

`hprobe`（headless profile）的补丁层手工插入 preset 注册表 + 两个声明：

- 控制组 `sdo-verify9-ctl`：`@deepseek-ai/dsh-tool-subagent`、`@deepseek-ai/dsh-tool-subagent-control`、工具面探针
- 实验组 `sdo-verify9`：上面两行 **加上** `cordis:group`（`isolate: {agentTeams: true}`）内的 `dsh-session-persistence-jsonl`、`dsh-experimental-agent-team`、`dsh-experimental-tool-agent-team`，再挂工具面探针

### 原始证据（`out/tool-surface.jsonl`）

```text
marker=CTL-subagent-only   from=registry-scope via=noarg count=24 dups=[]
marker=EXP-subagent+teams  from=registry-scope via=noarg count=24 dups=[]
```

两组工具面**完全一致、零重名**，且两个声明都在同一次运行里被挂载 → **同装不报错、无激活审计拒绝**。

团队工具**没有**出现在该工具面里 → 它们是**按成员作用域懒安装**的（`TeamService.tryMembership` 那一路），所以叠加发生在运行期。

**官方如何处理**（`dsh-experimental-agent-team-profile/cordis.patch.yml` 原文）：

```yaml
- id: tool-subagent-control
  disabled: true
- id: tool-subagent-list-agents
  disabled: true
- id: tool-subagent
  disabled: true
- id: tool-subagent-fork
  disabled: true
```

### 结论

**能同装，但不能混用。** 同名/同语义重叠：

| 工具名 | `tool-subagent-control` | `tool-agent-team` |
|---|---|---|
| `send_message` | ✅ | ✅ **同名** |
| `interrupt_agent` | ✅ | ✅ **同名** |
| `list_agents` | ✅ | ✅ **同名** |
| `subagent` / `subagent_fork` | ✅ | 由 `spawn_teammate` / `wait_agent` / `team_task_*` 取代 |

→ **每个 preset 二选一**，按官方做法用 `disabled: true` 关掉另一套。设计文档 §8.2 已据此把"三个后端可混用"改为"装配层二选一"。

### 未验部分（已转为测试项）

**运行期 agent 作用域叠加**（同名工具谁生效）**未验**：本环境无凭据，`MISSING_CREDENTIAL` 在**会话/agent 创建之前**就拦下运行——顶层挂了 `session/created`、`agent/created`、`agent/pre-step`、`agent/request` 四个监听，**零事件**。已在设计文档 §12.1 登记为测试项"委派工具同名叠加"。

## 3. Q-10：preset 的 `config.plugins` 内以包名引用第三方插件行

### 装置

`hprobe` 补丁层：

```yaml
- insert:
    - id: agent-preset-registry
      name: '@deepseek-ai/dsh-agent-preset-registry'
      config: { default: sdo-verify }
    - id: preset-sdo-verify
      name: '@deepseek-ai/dsh-agent-preset'
      config:
        id: sdo-verify
        order: 1
        plugins:
          - id: verify-third-party
            name: 'sdo-verify-third-party'      # ← 非 @deepseek-ai 的第三方包
            config: { marker: Q10-BIND }
```

第三方包只做一件事：在 `apply()` 里把收到的 config 追加到 `out/mount-markers.jsonl`。
解析方式：`profiles/hprobe/node_modules/sdo-verify-third-party` → 软链到工作区内的探针包（**未走 pnpm**）。

### 原始证据

命令与输出：

```console
$ DSH_HOME=…/.sdo-verify/home dsh --profile hprobe "q10 bind probe"
dsh: MISSING_CREDENTIAL: llm-deepseek: no API key for provider route "deepseek-official" …   [exit=1]

$ cat out/mount-markers.jsonl
{"at":"2026-09-29T07:26:04.659Z","pid":23,"argv":["…/lib/bin.js","--profile"],
 "config":{"marker":"Q10-BIND"}}
```

### 结论

**通过** ✅：preset 的 `config.plugins` 里以**包名**引用第三方包**可被解析并挂载**，且插件拿到的正是 preset 传给它的 config。

**且发生在任何模型调用之前**——随后才因无凭据退出，本次验证**零 token 消耗**。

→ **RISK-15 关闭**；M0 的"入口假设"成立（M0 仍未开工，剩下的是包骨架与 store/journal 等）。

## 4. 附带发现：preset 机制只由 `dsh-web-app` 提供

```console
# 全实例所有随包 patch 文件（cordis.patch.yml / presets/*.patch.yml）里找注册表行
✔ dsh-web-app/node_modules/@deepseek-ai/dsh-web-app/cordis.patch.yml
（其余 app bundle 均为 0 处）

# web-app 内位置
cordis.patch.yml:562:    - id: agent-preset-registry
cordis.patch.yml:563:      name: '@deepseek-ai/dsh-agent-preset-registry'

# headless 组合树（379 行）里 preset 相关匹配
仅 '@deepseek-ai/dsh-permission-presets'（权限预设，与 agent preset 无关）
```

**推论**：`dsh-headless` / `dsh-acp-app` / `dsh-sdk-app` 里**没有 preset**，本插件在这些 profile 里没有入口 → 设计文档按用户决策标注 **SDO 先 Web-only**，非 web profile 的入口登记为 **Q-21**；Q-18 / Q-20 / RISK-22 / §14.3 第 14 条标注"本期不可达"。

## 5. 复现步骤

```bash
WS=<包根>; H=<实例>/dsh/node_modules/.bin/dsh; V="$WS/node_modules/.sdo-verify"
rm -rf "$V"; mkdir -p "$V/home/profiles" "$V/pkgs"
cp -a <实例>/home/profiles/web "$V/home/profiles/probe"     # 含 preset 注册表
# 造探针包（bundle / third-party / toolprobe），软链进 profile 的 node_modules/，改 package.json 的 bundles
DSH_HOME="$V/home" "$H" --profile probe  --dump-config      # Q-08
DSH_HOME="$V/home" "$H" hprobe --from-default-profile headless
DSH_HOME="$V/home" "$H" --profile hprobe "bind probe"       # Q-09 / Q-10（无凭据即止，零 token）
```

验证台可整目录删除：`rm -rf node_modules/.sdo-verify`（不影响真实 profile 与仓库）。
