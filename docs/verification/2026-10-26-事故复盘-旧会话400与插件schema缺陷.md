## 3 被证据排除的假设

1. **「上下文超窗」**（交接文档 §1 的推断）：**不成立/至少不被支持**。最后一次成功请求 ≈ 502 k tokens（窗口 1 M），而同一会话在 turn 96 曾有 661 k tokens 的请求**成功**；失败期间窗口配置未变。
2. **「工具 schema 变了」**：不成立。失败 4 小时内的 5 份 header 工具集哈希一致。
3. **「插件回执把上下文撑爆」**：方向不对。`tool/result` 只占 8.4 MB（总量 102.6 MB 的 **8%**）；最大头是 assistant 消息（61.5 MB，含 reasoning）。插件的另一份自造内容是**每轮注入的状态块**（15.8 MB / 2 282 次），合计约 **23%** —— 是可优化项，但不是主因。
4. **本地校验器的拒绝**：不成立。适配器里那几条 `INVALID_REQUEST`（tool 结果无对应调用、历史以未结算工具结尾等）都会带自己的句子；实际文案是兜底句 `request failed (400)` ⇒ 是**服务端**拒绝。

## 4 可归因的插件缺陷（已记）

**`DEF-257` / `TASK-288`**：工具声明里的 `items: { type: 'json' }` 不是合法 JSON Schema（`type` 只允许七种），落点 `src/interface/tools.ts:39` 与 `src/domain/releaseTool.ts:1320-1336`。
- 该会话 10-14 两次 400 的响应体与本行代码**逐字对应**（`type` 元 schema 的 anyOf 在验证值 `json`）。
- 今天没炸，是因为宿主在发送前把 `items` 洗成 `{}`（header 实测），**合法性依赖宿主归一化**；插件侧没有任何守卫断言「我们发出的 schema 合法」。
- 处置：`items: {}` + 一格 schema 合法性守卫（含反向对照），卡面见 `TASK-288`。

## 5 不能归因的部分：致命 400 的真因**未知**

- 宿主 `providerError()` 在响应体没有 `error.message` 时用兜底文案，**原始响应体被丢弃**（`dsh-llm-deepseek` 适配器 `providerError`）。20 次失败没有留下任何可判读的原因。
- 请求体本身不落盘（只落 header），因此无法事后重放。
- 可确认的是：**同一份历史既让普通请求失败，也让压缩请求失败** ⇒ 只要历史里存在一个被服务端拒绝的成分，压缩这条唯一恢复路径也会被同一原因挡住（死锁）。这与「换一个模型/清空历史才能恢复」的表现一致。

### 上游（宿主）两条应上报的问题

1. **400 的响应体必须透传**（截断到合理长度即可）：否则 `(400)` 这类文案会永久掩盖真因——本次复盘绕了 94 份 header 才能排除三个假设。
2. **压缩不能与故障共用同一条被拒路径**：压缩请求应能在「历史被认为非法」时降级（砍最旧工具回执/最旧对话段、分块 map-reduce），先保命再谈质量。

## 6 对插件侧的建议（不新开缺陷，已有跟踪）

- **状态块体积**（15.8 MB / 2 282 次，最大 17.5 KB）：与 `TASK-219`（紧凑只读视图）同向；建议在 `TASK-219` 的 DoD 里补一句「状态块自身有体积预算与折叠」。
- **回执体积**：`DEF-212`（open）已在跟；`TASK-280` 的 WIP 在做 `sdo_plan next` 回执的结构性有界（未提交、未评审）。
- **会话累计体量读数**：插件目前**没有**任何「本会话已注入多少字节」的读数（它看不到宿主会话日志，但能数自己发出的状态块与回执）。是否值得做，取决于是否接受「事故后无法回答插件占多少」——本次实测答案是**占 23%**。
