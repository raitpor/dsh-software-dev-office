# 上游问题报告：Web 客户端不渲染"轮次之外"的斜杠命令结果

- 报告日期：2026-09-29
- 环境：dsh `0.2.0-rc.1`（本地实例 `~/.local/share/hdsl/instances/0.2.0-rc.1`），profile `web`，浏览器 GUI `http://127.0.0.1:3785`
- 插件：`dsh-software-dev-office`（第三方 Cordis 插件，注册 10 个斜杠命令）
- 会话证据：`$DSH_HOME/sessions/--home-raiptor-gitrepo-dsh-plugins-dsh-plugins-packages-dsh-software-dev-office--/session-fa33a1c3-7c72-4bd9-b691-ecbb45f649d3/session.v4.jsonl.zstd`

## 现象

1. 在 Web GUI 输入 `/sdo-status` 并回车：**界面没有任何反应**（无输出、无错误、无提示），输入内容被清空。
2. 该会话离开后再回来：**会话消失**（列表里找不到），行为与空白会话一致。
3. 同一会话里改用自然语言发言（"你好"）后，模型正常产出内容；工具调用结果渲染正常。
4. 重启 dsh 后重复上述操作，现象不变。

## 已排除：插件侧没有问题

从会话记录解压出的真源事件（`zstd -dc <session>.zstd`）里，6 次回车各自留下完整的一对事件：

```json
{"type":"command/run","seq":4,"data":{"commandId":"cmd-b8a03970-1","name":"sdo-status","args":"","source":{"kind":"user"}}}
{"type":"command/done","seq":5,"data":{"commandId":"cmd-b8a03970-1","kind":"success",
  "text":"SDO 状态\n- 尚未初始化：当前工作目录下没有 `.sdo/`。\n- 下一步：调用 `sdo_init`（项目名/流程/规模）。"}}
```

即：**命令确实被执行、handler 返回成功、文本非空**。返回值形状与 `@deepseek-ai/dsh-commands` 的类型定义一致：

```ts
export type CommandResult = { readonly kind: 'success'; readonly text?: string; readonly sourceEventSeq?: SessionSeq }
                        | { readonly kind: 'error'; readonly text: string }
```

## 定位：客户端有渲染路径，但命令落在"轮次之外"

`@deepseek-ai/dsh-client-ui-chat@0.2.0-rc.1/lib/client.js` 里存在命令节点的完整渲染定义：

```js
const commandDefinition = {
  kind: 'command',
  target: 'chat',
  match: (event) => event.type === 'command/run'  ? { id: String(event.data.commandId), role: 'start' }
                  : event.type === 'command/done' ? { id: String(event.data.commandId), role: 'update' }
                  : null,
  start:  (_context, match) => ({ command: commandFromRun(match) }),
  update: (context, match) => ({ ...context.state, command: commandFromDone(match, context.state.command) }),
  buildViewNode: (context) => {
    const state = context.state ?? fallbackState(context)
    if (state === undefined) return null
    if (state.command.name !== 'compact') return chatNode(context, 'command', state.command.seq, state.command)
    ...
  },
}
```

`commandFromDone` 会把结果文本放进 `outcome: { kind, text }`；`command` 也是视图分派里的一个 `case`。**因此"没有实现渲染"可以排除。**

会话里的事件顺序揭示了真正的差异：

| 事件 | seq |
|---|---|
| `command/run` / `command/done`（6 对） | 4–15 |
| 第一个 `turn/start`（用户发言"你好"那一轮） | 18 之后 |

**6 次命令都是在"任何 turn 之外"执行的**：`turn/start` 直到用户发出第一条普通消息才出现。
Web 客户端按"轮次（turn）"投影对话；落在轮次之外的命令节点没有被投影出来，于是界面空白；而该会话在被投影时也没有任何消息内容，因此离开后被当作空白会话丢弃。

## 建议

1. **客户端侧**：让 `command/run` / `command/done` 的节点不依赖 turn 归属（或在分发命令时开一个"仅命令的 turn"），使交互式适配器里命令结果一定可见。
2. 顺带：**只有命令事件的会话不应被当作空白会话丢弃**（用户会以为会话丢了，且这会让"用命令初始化项目"变成不可能）。
3. 若第 1 条短期不便修：希望客户端至少在命令执行后给出一个可见回执（哪怕只是一行 toast），否则"回车无反应"与"命令不存在"对用户不可区分。

## 复现步骤（最小）

1. 用任意第三方插件（或内置插件）在 Web profile 下注册一个命令，handler 返回 `{ kind: 'success', text: 'hello' }`。
2. 新建会话（该会话尚无任何普通消息）。
3. 输入该命令并回车 → 界面无反应。
4. 检查会话真源：`command/run`、`command/done`（`kind: success`，`text` 正确）都在，但 `turn/start` 出现在其后。
5. 在该会话里发一条普通消息后再看 → 之前的命令结果依然不显示。

## 实测补充（2026-09-29，真机验证）

插件改用 `agent.followup()` 注入命令结果后，**界面正常渲染出该消息，且不触发模型回复**（用户实测）。
即：

- 命令结果的用户可见性可以通过 `followup` 实现，**代价不是"多一轮模型消息"**；
- 因此这条路径**不违反**"命令不产生模型消息"的设计意图，只是绕开了"客户端不渲染命令节点"这一缺陷；
- 本报告的严重度可降级：**不影响第三方插件可用性**（有干净绕行），但"零消息会话被丢弃"仍会影响
  "用命令初始化项目"的体验——建议仍按上文第 1、2 条修客户端。

```text
   index 2  tool-call-chunks  technique_save   args: [""]
   index 3  tool-call-chunks  technique_save   args: [""]
   index 4  tool-call-chunks  technique_apply  args: [""]
   index 5  tool-call-chunks  memory_save      args: [""]
```

**结论（责任划分）**：失败的 4 个调用全是**记忆层插件**的工具（`technique_save` ×2 / `technique_apply` / `memory_save`），**整步没有任何 `sdo_*` 调用** —— 本次失败与 dsh-software-dev-office 无关。

**可疑触发条件**：一个 step 内**并排发出多个大参数工具调用**（记忆层工具字段多、正文长），参数流在 provider 侧拼装时损坏；`args` 全是空串说明参数**从未完整到达**。

**上游期望（健壮性缺口）**：
1. 参数 JSON 损坏时**不应整轮失败**——至少应把该 step 标记为"工具调用丢弃"，让模型有机会重发；
2. 或者对**多工具并排**的场景做产物校验，损坏即整 step 重试（当前直接 `MALFORMED_RESPONSE` 终止本轮，用户侧表现为"本轮运行失败"）；
3. 客户端可考虑把该错误呈现为**可重试**提示，而不是静默结束回合。
