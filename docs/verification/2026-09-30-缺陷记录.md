# SDO 缺陷记录（真机实测驱动）

> 只记**在真实会话里发生过**的缺陷：症状 → 证据 → 根因 → 修复 → 复验。
> 证据一律给到可复跑的东西（会话 id、事件 seq、命令、测试名）。

## DEF-01 跨会话串工作区（工作区定位用到别的会话/外部目录）

- **症状**：新会话 + 新工作区调用 `sdo_status`，显示**别的项目**（`PRJ-001 raiptor`）。
- **证据**：会话 `session-ccda9900` / `session-9b4bfe2c` / `session-8a85fe68` 的 `command/done` 均返回同一项目；`$HOME/.sdo` 存在一个游离项目。
- **根因（两层）**：① `workspaceFor` 在拿不到会话 cwd 时回退"最近活跃会话的 cwd"；② 又加了"从 `process.cwd()` 向上查找含 `.sdo/` 的目录"——命中了上层目录里的游离 `.sdo/`。
- **修复**：删除两处兜底；定位只用「显式 → agent 会话 cwd → 本会话记录 → 无」；**取不到就明确报错/降级，绝不猜**。
- **复验**：`test/office.test.ts` 的「DEF：新会话 + 新工作区不得显示别的会话的项目」「DEF：定位只看本层」。

## DEF-02 向用户建议"开新会话继续"（违反单会话原则 C-09）

- **症状**：架构阶段被阻塞时，回执让用户"新建一个选择 sdo-office 的会话接续"。
- **根因**：Q-20 阻塞分支的 remedy 文案写错；且当时 **preset 没装配 plan mode**，导致该分支必然触发。
- **修复**：文案改为"不要另开会话，在当前会话内接入评审通道或向用户说明计划后确认"；不允许用换会话绕过。
- **复验**：`grep -c "不要另开会话" src/index.ts` = 1。

## DEF-03 preset 里引用解析不到的插件行 → 整个 preset 注册失败（选不到 sdo-office）

- **症状**：重启后会话里**选不到** `sdo-office` preset。
- **证据**：profile 下 `@deepseek-ai/dsh-plan-mode` 不存在；组合树里 `dsh-plan-mode` 的 4 处全来自官方 bundle，我自己的层里那一处就是元凶。
- **根因**：该包只随 `dsh-web-app` bundle 解析；外部包的 preset 引用它 → 解析失败 → preset 注册整体失败。
- **修复**：移除该行并在 preset 里写明原因；Q-17 的"两道评审"改由已装配的提问通道承担。
- **守卫**：`test/m7.test.ts` 增加 preset 行白名单测试——新增 `@deepseek-ai/*` 行必须先更新白名单（强制"加行前先想清楚能否解析"）。

## DEF-04 工作区未知时**抛错**，而不是友好提示

- **症状**：`/sdo-status` 在未立项会话里报错（会话报错），而不是"尚未初始化"。
- **根因**：DEF-01 修复时把"取不到工作区"直接变成 `requireWorkspace` 抛错，**读路径**也一起抛了。
- **修复**：读路径友好降级（`StatusSnapshot.workspaceUnknown` + 明确文案），写路径仍拒绝；不读外部目录。
- **复验**：`test/office.test.ts` 的「DEF：工作区未知时明确报错，绝不使用外部目录兜底」（读=降级、写=拒绝）。

## DEF-05 会话工作目录读错字段（**时序依赖**的根因）

- **症状**：`sdo_status` 抛「无法确定本会话的工作区」；重启后偶发恢复（因为 `session/created` 被重新宣布，映射才补上）。
- **证据**：`dsh-agent 0.2.0-rc.1` 的 `Agent` **没有** `cwd` / `workspace.cwd` / `session.cwd`；真实位置是 **`agent.session.header.cwd`**（诊断报告：`plugins-test/sdo-test/SDO-工作区定位缺陷诊断.md` §4.2）。
- **修复**：`callOf`（工具与命令）优先读 `agent.session.header.cwd`；注入路径另用 `sessions.get(sessionId).header.cwd` 兜（诊断建议 A）。
- **复验**：`test/office.test.ts` 的「全链路：agent 形状的调用（session.header.cwd）」+ `test/m7.test.ts` 的 `callOf` 断言。

## DEF-06 允许 agent 自行"发明需求"（无来源即可落账）

- **症状**：用户只说了"做房间预定系统"，agent 自行 `capture` 了 6 条需求并往下推。
- **证据**：会话（酒店系统）里 6 条 `sdo_requirement action=capture` 的陈述/范围/术语表均非用户原话。
- **修复**：`captureRequirement` 加**来源硬约束**（`sourceRaw` / `sourceStakeholder` / 原型回填 三者之一），否则拒绝并提示先问用户。
- **复验**：执行自证「无来源被拒 / 带用户原话可落账」；回归测试见 `test/m3.test.ts`。

## DEF-07 允许"自问自答"（assume 无用户授权）

- **症状**：审讯问题由 agent 自己按默认答案落账，grill 退化为自问自答。
- **修复**：`answerQuestion` 的 `assume` 必须带 `authorizedByUser: true`；未授权假设在 DoR 里**仍算未决**（`isEffectivelyOpen`）。
- **复验**：执行自证「自问自答被拒」；`isEffectivelyOpen` 单元断言。

## DEF-08 红队 `limit` 被当成"每条需求问几个角度" → 一次生成 60 问

- **症状**：`sdo_redteam attack limit=6` 生成 **60** 个 P0 问题（10 条需求 × 6 角度），灌爆上下文与问题账本。
- **证据**：会话 `session-ccda9900` 的 `sdo_redteam` 回执「生成 60 个 P0 问题」。
- **修复**：`limit` = **本次调用总问题数上限**（默认 4，硬顶 12）+ 按目标**轮转分配**。
- **复验**：`test/m4.test.ts`「redTeamAttack 的 limit 是总问题数上限」→ 现在 `limit=6` 出 6 问 / 6 目标 / 6 议题。

## DEF-09 测试把缺陷固化成期望行为

- **症状**：诊断报告指出 `test/office.test.ts` 只覆盖"映射为空就抛错"，等于把 DEF-05 固化为期望。
- **修复**：新增全链路正例（agent 形状 → 定位 → 立项 → 状态可读），并保留"完全无信息时拒绝"的负例。
- **教训**：**负例不能替代正例**；只测失败路径会把 bug 写进规格。

## 通用教训（三次回归的共同模式）

1. **不许外部兜底**：定位、推进、成本缓存都只认当前工作区；取不到就明说。
2. **不许换会话**：单会话原则下，"换会话"永远不是 remedy。
3. **加行先验证**：preset 新增插件行后，必须实测"能否选中该 preset"——`--dump-config` 只能证明补丁被应用，**证明不了插件可解析**。
4. **先看代码再改**：本轮有 4 次因锚点想当然而静默失败；现在改成每次替换都打印匹配计数。

## 迁移尝试记录：lang 抽取不能"盲抽字面量"

- **做法**：写 `scripts/extract-lang.mjs`，把面向用户模块里的中文单引号字面量机械抽成 `t('ui.<模块>.<序号>', '<原文>')` 并登记到 `zh-CN.yml`。先跑 `inject.ts`(10) + `board/render.ts`(18)。
- **结果**：`tsc` 0，但**测试挂 4 个**（`五视图：齐备性检查`、`设计元素：DependsOn 边驱动契约完整性`、`G3 全绿`、`架构阶段的证据`）——说明这两个模块里存在**把中文串当数据/键/比对值**的用法，按字面量改写会改语义。
- **处置**：回退两个文件与 `ui:` 段，构建与测试恢复全绿；脚本保留在 `scripts/`（幂等 + 自动备份 `.lang-bak`）。
- **结论**：迁移必须**逐处判定**（文案 vs 数据），不能全局正则替换。`test/m7.test.ts` 的棘轮守卫继续作为"不许新增硬编码"的约束；下一批迁移应先按"字符串是否出现在比较/索引/键位"筛查，再人工过一遍。

## 迁移尝试记录（第二次）：脚本对 YAML 的插入不幂等

- **现象**：逐文件试跑（6 个模块各自 tsc+测试，失败即回退）全部回退，但最终测试仍有 4 个失败。
- **根因**：`extract-lang.mjs` 用 `replace(/^ui:\n/mu, ...)` 追加键，**不幂等**——反复运行把 `ui:` 段层层嵌套，`zh-CN.yml` 解析失败 → 枚举标签读空 → 视图/契约/G3/证据 4 个用例挂。**代码其实已全部回退，坏的是数据文件。**
- **处置**：移除所有 `ui:` 段，`zh-CN.yml` 恢复可解析；测试回到全绿。
- **教训**：任何"批量改写数据文件"的工具必须**幂等**，且运行前备份原文件；校验手段不能只看 `tsc`，要看**运行时读该数据的测试**。

## DEF-10 红队质询"同一句模板复制 N 份"（问题不来自需求内容）

- **症状**：sdo-test 会话里模型如实反馈——6 个议题是同一句模板（"谁会被这个功能伤害？谁的操作会因此变多？"）逐条复制，没有针对需求内容。
- **根因**：`RED_TEAM_ANGLES` 的 7 条模板 `text` 是**写死**的，套到任何需求上文字都一样；我先前只加了"针对 REQ-00X"前缀，看起来仍是复制。
- **修复**：红队问题改为**由需求自身派生**——标题 + 该需求歧义评分为 0 的维度；角度按"是否正对薄弱维度"排序，因此每条需求拿到的问题不同；正对薄弱维度时额外标注「本问聚焦：<维度>」。
- **复验**：`test/m3.test.ts`「DEF-10：红队问题必须由需求内容派生」——两条不同需求的问题文字必须不同且各含自己的标题；薄弱维度为 data 的需求，其问题须提到"数据"。

## DEF-10 后续：方案 B（模型生成红队质询 + 插件校验）

- **做法**：新增 `sdo_redteam action=propose`（把需求**原文**与薄弱维度交给模型，并给出产出格式与校验规则）与 `action=file`（回填模型生成的问题）。

- **复验**：`test/m3.test.ts`「方案B：红队质询由模型生成、插件校验」；实例校验含 propose/file/校验闸门。

## 迁移范式（第三批：inject.ts 成功，可照抄）

**踩过的两个坑（都已验证）：**

1. **`t()` 只支持两层键**：`t('status.title')` ✅；`t('statusTitle')` ❌ —— 没有点号时 `section='statusTitle'`、`id=''`，函数返回**空串**（不是 key），于是整块状态文案消失。键必须形如 `section.key`。
2. **数据位不能抽**：出现在对象键位、索引、`===`/`includes` 参数、`kind|status|role|process|gate…` 取值位的字符串是**数据**，语义会被改写（前两批自动抽取因此在 `board/render.ts`/`describe.ts` 失败 4 个视图类用例）。

**可照抄的迁移步骤（每批一个模块）：**

1. 读全文，逐条判定"文案 vs 数据"；只动文案。
2. 文案写进 `zh-CN.yml` 的**两层扁平键**（`status.title` 这种），带 `{占位符}`；占位符用 `fmt('status.title', {…})` 填充。
3. 代码里删掉中文字面量（**不保留 fallback 中文**，否则中文仍在代码里，棘轮也不会下降）。
4. 跑 `tsc + 全量测试`，并**目视渲染结果与迁移前逐字一致**（inject.ts 已以此验证）。
5. 用实测值下调 `test/m7.test.ts` 的棘轮基线。
6. 全部批次做完后**只同步一次**。

## 迁移第四批：commands.ts + tools.ts 兜底（含第三次 YAML 事故）

- **做成**：11 条斜杠命令说明 + 1 条错误信息 → `zh-CN.yml` 的 `command` 段（两层键）；`tools.ts` 里 84 处 `t('param.x', '英文兜底')` 去掉兜底，改由 lang 供中文（其中 78 键本已存在，**参数说明因此从英文变中文**）。
- **棘轮**：`inject.ts` 12→4、`commands.ts` 25→13、`tools.ts` 22（余下为非 `t()` 文案，下一批处理）。
- **第三次 YAML 事故（同一类，已定位规则）**：本插件的 YAML 子集解析器**不支持带引号的键**（`"sdo-init": …` → "期望 `键: 值`，但看到的是标量"）。**规则：键一律不加引号**（含连字符也合法），只有**值**需要引号。
- **新增守卫（长期看住）**：`test/m7.test.ts` 的「lang 守卫」——① 关键节必须取到中文；② 扫描源码里所有 `t('…')` 引用，逐键校验在 `zh-CN.yml` 里有值。本批它当场抓出 6 个缺失键（`param.sourceStakeholder/sourceRaw/pickedOption/ids/context` + 一个三层键误用），已全部修好。
- **教训**：删兜底前必须确认 key 存在——守卫就是为此而生；`t()` 的两层键约束与"键不加引号"是本插件语言包的两条硬规则。

## 迁移第六批（v5 递归抽取）：未落地，但换来两条流水线教训

**目标**：把模板字符串 `${…}` **表达式内部**的中文文案也迁进 lang（真实剩余 142 处中约 8 成属此类，如 `` `${x ?? '（无记录）'}` ``）。

**结果**：四个文件（describe/index/board/commands）**全部回退**，未落地。

**两条教训（比这一批本身更重要）**：

1. **回退必须连数据一起回退**。抽取器每次运行都会改写 `zh-CN.yml`，而我的"失败即回退"只回退了**代码**，语言包里的半成品段落留了下来 → 后续测试在"代码已回退"的状态下继续失败，一度以为检查点也坏了。**正确做法：每次运行前备份 `zh-CN.yml`，回退时一并恢复**（本轮末尾已用"从实例取回上一轮全绿的语言包"完成恢复，126/126 复绿）。
2. **递归进入 `${}` 后，数据位判定必须一起带进去**。外层我用 `isData()` 跳过了对象键位/索引/比较等**数据位**，但递归处理表达式内部时**没有**再做这个判定，于是把索引/键位里的中文也包成了 `t()` → 语义被改写、内容类用例失败（M6-02 看板幂等、status 等）。**修正方向**：对表达式内部的字面量同样施加"前面是 `[`/后面是 `:`/前面是 `:=` 枚举取值"等跳过规则。

**计数器已换成状态机**（`src/domain/langScan.ts`）：此前用正则在含英文撇号（如 `user's`）的注释处**引号配对错位**，把真实 142 处算成 400+；现在抽取器与守卫**共用同一套状态机**，数字可信。

**当前真实剩余**：`describe 98 ｜ index 28 ｜ board 12 ｜ commands 4`（`tools`/`inject` 已 0），合计 **142**。

## 迁移第七批：v5 落地 commands.ts（并修掉"转义序列"这个致命小 bug）

**落地**：`commands.ts` 4 → **0**（斜杠命令回显与 --choice 缺失提示全部走 lang），检查点保持 126/126 全绿。

**关键 bug（解释了前两轮四个文件为何全挂）**：抽取模板字符串时我把 **TS 转义序列原样搬进 YAML** —— `` `（SDO 命令 \`${name}\` 的结果…` `` 里的 `` \` `` 变成"反斜杠 + 反引号"两个字面字符，`fmt()` 渲染出来就多一个反斜杠，回显消息的断言（`/SDO 命令 `sdo-status` 的结果/`）随之失败。**修法：抽取时对字面量做 `unescape`**（`\n \t \r \\ \` \' \" \xNN \uNNNN`），把**真实字符**写进 YAML。
- 现象特征（可复用）：迁移后文本出现"多一个反斜杠"或断言里看到 `\\`` → 就是没解转义。

**仍未落地**：`board/render.ts` 12、`index.ts` 28、`describe.ts` 98 —— 需逐文件看测试失败点（下一个诊断入口：先单文件跑并在失败时打印"哪条断言 + 实际文本"）。

## 迁移第八批：三元冒号误判修复 → 396 处降到 31 处（−92%）

**关键 bug（剩余项的主因）**：我的"对象键位"判定把**三元表达式的冒号**当成了键位分隔符 —— `enabled ? '启用' : '停用'` 里的 `'启用'` 后面紧跟 `:`，于是被当成"对象键"跳过。
**修法**：只有"最近的分隔符（`?`/`{`/`,`/`(`）之后**没有 `?`**"时才算键位；有 `?` 说明处在三元真值分支，属正常文案。
**效果**：`describe 43→15`、`index 22→16`、`board 5→0`，合计 **70 → 31**。

**剩余 31 处的真实形态（下一轮）**：绝大多数是**嵌套模板字符串**（`` `${c ? `中文 ${x}` : '中文'}` ``）——抽取器的 `fixExpr` 目前只处理表达式里的**单引号**字面量，**没有递归处理嵌套的反引号模板**。少数是注释邻近项与真数据位。

**同步状态**：重启后实例恢复可写，本轮已一次性同步（`lib/` + `zh-CN.yml`，32 节）。

## 事故记录（真正根因）：`cp -r` 断了硬链 → 实例副本缺依赖 → 插件加载失败 → preset 消失

- **现象**：重启后 **sdo-office preset 从会话列表消失**（`--dump-config` 里仍在）。
- **决定性证据**：
  ```text
  实例副本 <profile>/node_modules/dsh-software-dev-office/lib/src/index.js  inode 1833748（链接数 1 = 真实文件）
  仓库     <repo>/lib/src/index.js                                        inode 2036869
  从实例副本 import 我的插件 → ERR_MODULE_NOT_FOUND: Cannot find package '@deepseek-ai/cordis'
  从仓库位置 import        → 可加载
  ```
- **机制**：`file:` 依赖原本是**硬链接**：文件 realpath 指向仓库 → 依赖从**仓库的 node_modules** 解析。我用 `cp -r` 同步时**把硬链接换成了真实副本**（inode 变了、链接数 1），于是 realpath 变成 profile 副本 → 改为从**副本自己的 node_modules** 解析；而副本里只有我后来复制的那几个包，**缺 `cordis`/`dsh-llm`/`dsh-tools` 等** → 插件模块加载即失败 → bundle 注册失败 → **preset 不注册**。

- **教训（与既有硬链规矩合并）**：
  1. `file:` 依赖改动**只能用 `cp`（保硬链接）**，**不要用 `cp -r`**；用 `cp -r -p` 也会断链；
  2. 一旦断了链，实例副本就必须拥有**自己的完整依赖闭包**，否则插件加载失败会让 **preset 消失**（症状离根因很远，极易误判为"preset 文件坏了"）；

## preset 消失：最终根因与设计规则（可复用）

**最终根因**：我在 `src/index.ts` 顶部加了**静态** `import PlanModeController from '@deepseek-ai/dsh-plan-mode'`（以及 session-projection）。这个包在宿主侧的解析路径上**取不到**（副本的 `node_modules` 里没有它需要的 `@deepseek-ai/cordis` 等）→ **整个插件模块 import 失败** → bundle 注册失败 → **sdo-office preset 从会话列表消失**。`--dump-config` 仍显示 preset（组合树是静态的），所以症状与根因离得很远。

**触发条件叠加**（两个我自己的动作）：
1. 用 `cp -r` 同步代码 → **把 `file:` 依赖的硬链接换成真实副本**（inode 变化、链接数变 1）→ 副本开始按**自己的** `node_modules` 解析；
2. 顶部静态 import 一个**可选**依赖 → 该依赖在副本里解析不到 → 插件加载即失败。

**修复（根治性，按构造消除）**：可选依赖一律**动态 `import()` + try/catch**，缺包只记录原因、**绝不让插件模块加载失败**：

```ts
void (async () => {
  try { const mod = await import('@deepseek-ai/dsh-session-projection'); ctx.plugin(mod.default ?? mod, {}) }
  catch (e) { planModeLoadError = 'sessionProjections: ' + msg }
  if (planModeLoadError === undefined) {
    try { const mod = await import('@deepseek-ai/dsh-plan-mode'); ctx.plugin(mod.default ?? mod, { section: t('planMode.section') }) }
    catch (e) { planModeLoadError = 'plan-mode: ' + msg }
  }
})()
```

**验证**：`node --input-type=module -e "await import('<实例副本>/lib/src/index.js')"` → **✓ 可加载**；`tsc` 0；129/129。

**设计规则（写进规矩）**：
1. **可选能力一律懒加载**（动态 import + try/catch），**禁止**用顶层静态 import 引可选依赖——否则一个取不到的包会连带整包、乃至 preset 一起失效；
2. `file:` 依赖的同步**只能 `cp`（保硬链接）**，不要 `cp -r`；一旦断链，副本就必须自带完整依赖闭包；
3. 判定"插件能否加载"要用 **`import()` 从目标位置实测**，不要只看文件存在或 `--dump-config`。

## DEF-41/42：语言包覆盖率读数不可能 + 注入块解析不出工作区（sdo-test 会话新报）

**DEF-41（G-08）语言包覆盖率出现 `980 of 951`**
- 现象：切到 en 后 `/sdo-lang` 回执写 "provides **980** of **951** keys" —— 分子大于分母，句子前提不成立。
- 根因：回执的分子用 `translatedKeys()`（**目标语言包有多少键**），分母用 `baseKeyCount()`（**基准语言键数**）。非基准语言包可以带**专属键**：`criterion.C-01…C-92` 这 29 条在中文下取自**流程数据**（中文），英文包必须自带 → 980 > 951。
- 修复：新增 `coveredBaseKeys()`（**目标语言覆盖了多少个基准键**，≤ 总数）与 `extraKeys()`（专属键数），回执改为「覆盖 {p1}/{p2} 个基准键」+ 如实说明「其中 {p1} 个是专属键」。
- 判别性测试：`covered ≤ total`、`covered > 0`、`extra > 0`；基准语言下覆盖率**恒为 100%**。

**DEF-42（G-07 新变体）注入块说"工作区未能确定"，而同一轮的工具调用正常读出项目**
- 根因（**这次是确定性的**）：`systemPrompt.context({ text })` 回调只拿到 `AssembleContext.scope`，它是 `@deepseek-ai/dsh-scope` 的 `ScopeKey`（`type ScopeKey = object`）；`dsh-agent` 用 `scopeTarget(agent, agent)` 建键 —— **键就是 agent 对象本身**。旧实现 `String(scope)` 得到 `"[object Object]"`，与 `session/created` 记下的会话 id 永不相等 → `callForScope` 返回 `{}`（连 sessionId 都丢）→ 后面的 `sessionsService` 兜底因 `sessionId === undefined` **根本不执行** → 工作区未知。
- 修复：新增 `src/interface/scope.ts` 的 `resolveScopeCall(scope, sources)`，解析顺序 —— ① scope 即 agent（鸭子类型 `session.header.cwd`）② 裸 id ③ scope 上 `sessionId`/`id`/`session.id` 候选 ④ 每个候选依次问本插件会话表 → 宿主 sessions 服务；全失败**诚实降级为空**（绝不猜别的项目）。注入路径与工具路径共用它。
- 判别性测试：agent 形态（真机形态）、带 id 的 agent、裸 id 走会话表、裸 id 走 sessions 服务、以及 `{}`/`undefined` 必须降级为空。
- **待真机确认**：重启后注入块应显示项目（而不是"工作区未能确定"）；本地无法复现宿主装配。
