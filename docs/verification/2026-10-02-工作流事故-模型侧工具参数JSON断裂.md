# 工作流事故：模型侧工具参数 JSON 断裂（MALFORMED_RESPONSE）

- **日期**：2026-10-02
- **性质**：**模型侧作业事故**（不是 SDO 产品缺陷；SDO 与工作区均未受损）
- **症状**：一轮里核实与修复**全部做完了**，但**最终汇报没有发出** —— 用户看到的是「上轮失败了」

## 1. 证据（可复跑）

解压会话记录 `$DSH_HOME/sessions/<项目 slug>/<session-id>/session.v4.jsonl.zstd`，看该轮 `turn/end` 的 `reason`：

```json
{"turn":33,"reason":{"kind":"error","error":{"message":"DeepSeek Messages stream: tool input is invalid JSON","code":"MALFORMED_RESPONSE"}}}
```

同轮最后一个 `assistant/attempt`：`step 56`、`stream` 只有 **8** 个 chunk（正常步都是几十上百）⇒ 在**刚起步发那次工具调用时**流就断了。
该轮前面 55 次调用都是 `bash`（参数 0.3–3.7 KB，全部正常执行）。

## 2. 根因

出错那一步在发一个**参数里含长段中文散文**的工具调用（知识库记账类，`evidence` 字段写成了一整段中文）。
流式 tool-call 的 `arguments` 是**按 chunk 拼接出来的 JSON 字符串**：中文散文越长、越夹带引号与换行，拼接出的 JSON 越容易失效 → 宿主判定 `tool input is invalid JSON` → **整轮中止**，后面的正文汇报一起丢。

同源历史（都在本仓库/本机有据）：

- 本会话更早两次同样的 `MALFORMED_RESPONSE`（均发生在发出「长中文参数的记账调用」时）；
- `fa_fcb5532e`：`sdo_adr` 的 JSON 参数用**单引号**当 JSON 引号 → `invalid arguments: "consequences" must be a string`。

## 3. 正确做法（下次照做）

1. **工具参数保持短**：记账类调用（知识卡/记忆/回执）的 `evidence`、`summary`、`steps` 只写**一句可核对的话**（带数字或路径，例如 `408/408 pass`、`presets diff 0`）。细节写进**最终回复** —— 回复是纯文本流，不经过 JSON 解析。
2. **先汇报，再记账**：一轮的核实/修改做完后，**先把用户可见的汇报发出去**；`technique_apply` / `memory_save` / `technique_save` 这类记账调用放到汇报之后（或本轮更早的位置），别让它们挡在汇报前面。
3. **中文参数里不用 ASCII 引号**：需要引号一律用「」或反引号；不要把多个长中文段落塞进同一个调用。
4. **已经做完的工作不会因为中止而丢失**（工具结果已落盘/入账）。恢复时先**复核状态**（`tsc`、全量测试、`git status`、实例 diff），**只补发汇报**，不要重跑一遍。
