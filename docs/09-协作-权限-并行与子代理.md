# 协作：权限、并行写与子代理约束

> 本篇合并自「协作-角色与权限」+「并行写-工作副本与复用」，并新增「子代理约束」（合并目的：一个事实只有一处，防漂移）。

> 多人协作要解决的不是"登录"，而是三件事：**谁有权决定什么**、**谁改了同一处**、**分歧在哪里可见**。
> 登录系统只是这三件事的外壳。

---

## 1. 三个概念

```text
actor  ──membership──▶  scope  ◀──right──  action
```

| 概念 | 说明 |
|---|---|
| `actor` | 人 / agent 会话 / 服务。`kind ∈ {human, agent, service}`；agent 的 `actor` 唯一标识一个子会话（不是"developer"这个角色） |
| `scope` | 作用域：`module:<path>`（代码域）、`domain:<name>`（需求域）、`release:<id>` |
| `right` | 动作权：`read` / `write` / `review` / `decide` / `sign` / `admin` |

**关键区别**：v1 用"角色"（developer / reviewer / office）做全局判断，导致"角色对但域不对"也能操作；v2 把**权绑到 scope**，一个 actor 在 A 模块是 reviewer、在 B 模块是 writer。

---

## 2. 决策权矩阵（缺省值，可按项目改）

| 动作 | 需要什么权 | 是否可自签 | 是否可双人 |
|---|---|---|---|
| 建卡 / 认领 / 阻塞 | `write@module` | — | 否 |
| 评审（记发现） | `review@module` | **不能评审自己产出的卡** | 否 |
| 核实发现 / 采纳评审 | `review@module` | 不能核实自己提的发现 | 否 |
| 冻结版本 / 豁免 | `decide@release` + `sign` | 不能 | **必须 2 人**（可配置） |
| 改意图 / 改条款 | `decide@domain` + `sign` | 不能 | 可配置 |
| 撤签 / 撤销决策 | `admin@domain` + `sign` | 不能 | 必须 2 人 |

**"不能自签"由判据守**：`decision.signer ≠ producer`，`producer` 是产生该命题的 actor（或该卡的认领者）。

---

## 3. 角色去哪了：四张角色卡的处置

v1 用四张角色卡（office / developer / tester / reviewer）同时表达四件事：**职责、权限、工具面、方法**。v2 把四件事拆开，于是“角色”不再是身份，而是**权 + 工作类型 + policy**。

| v1 角色 | v2 的形态 | 判断 |
|---|---|---|
| **office（流程官）** | **解散**：记账归引擎、规划是 `write@plan` 权、决策是人的 `decide`/`sign` | 它把四件事塞进一个身份，正是“角色不参与判定”的根因 |
| **developer** | **降级为工作类型**：任何持 `write@module` 的 actor 都可认领实现卡 | 指导性内容（DoD/红线）留作 skill 文档 |
| **tester** | **降级**：拆成“定义判据与夹具”（归 `review` 侧）与“跑适配器”（机器做） | 中间没有“tester 这个人”的位置 |
| **reviewer** | **升级为强制权限** `review@scope` + 职责分离（不得是 producer） | v1 里 187 条缺陷有 72 条是评审发现的，最不该丢的一条 |

**原则**：v2 不需要“角色”，需要**权限 + 职责分离 + 可判据化的清单**。角色卡里能机械检查的条目（不得自审、不得代签、完成必须有证据）提升为判据；查不了的留作文档，不作为身份依据。

## 4. 预授权 grant（委托）：让人签从瓶颈变成杠杆

v2 的默认是“只有人能签”。单人项目里这条会变成死结：要么全卡住，要么签字变成橡皮章——两个结果都毁掉“不可否认”。**grant 是唯一的解**：人预签一次策略，agent 在策略内自己决定，事后审、随时撤。

**它不是“放权”，是“有界授权”**——边界三条，缺一条就变成“agent 自己说了算”。

### ① 可授哪些决策：按影响面分，不按信任度分

| 不可授（永远要人签） | 理由 |
|---|---|
| 意图变更、release 冻结、豁免 | 这是“不可否认”的落点，代劳即失效 |
| 撤销签字、密钥与身份操作 | 撤销本身不能代劳 |
| 任何**不可豁免判据**的红 | 安全底线 |

| 可授（默认只在窄范围） | 例 |
|---|---|
| 文档类变更 | 只改 `docs/**`、不动 release 集合 |
| 证据补充 / claim 重派生 | 上游变更后的自动重算 |
| 卡的重排与优先级 | 只改先后，不改“做什么” |
| 已签 intent 之下的建卡/拆卡 | 落实已签意图，**不新增意图** |

判定不靠感觉，靠**读数**：grant 写死 `max_impact {blocking, advisory}`、`paths`、`forbidden[]`；影响面超限 ⇒ **自动升级为人签**（不是“先做再说”）。

### ② 审计窗口：先执行、后复核，但复核前**不算已签事实**

```text
grant 生效
  → agent 在授权内决策，落 decision(kind=delegated, status=pending_audit)
  → 可推进工作，但**不能作为发布证据**（[11](11-交付与版本.md)）
  → 窗口内人审：确认（转正）/ 推翻（触发级联复位，见 [14](14-变更与影响链.md)）
  → 到期未审：仍 pending；release 冻结被阻断；进 v_gaps 并升级提醒
```

**授权 ≠ 免审**。授权内做的事在审计完成前只是“临时有效”，不能变成“发布依据”；否则窗口会自动变成“默认通过”。

### ③ 撤销：不删历史、要理由、不能转授

| 方式 | 效果 |
|---|---|
| 逐条推翻 | 该 delegated 决策失效并触发级联复位 |
| 整体撤回 | grant 立即失效；已发生的决策保留、仍在待审计队列 |
| 到期失效 | 默认 **7 天**（**授权窗口**，与分歧 L4 的 7 天无关）或“一个 release 周期”，续期需人重签 |

三条铁律：**不删历史**（标 `authority_revoked_after`）、**撤销要理由**（不许空）、**不能转授**（agent 不得把 grant 再授给别的 agent）。

### 数据形状

```yaml
grant:
  id: g-001
  granted_by: u-liang                     # 人签
  grantee: { kind: agent, session: "…" }  # 或按 scope 而非按人
  decisions: [doc_change, evidence_attach, claim_rederive]
  constraints:
    paths: ["docs/**"]
    max_impact: { blocking: 0, advisory: 20 }
    forbidden: [release_freeze, waiver, intent_change]
  window: { starts: …, expires: … }       # 默认 7 天
  audit:  { mode: post_hoc, deadline: 24h }
  revoked_at: null
```

### 与其它机制的接入

| 机制 | 接入点 |
|---|---|
| 两段式写协议（[14](14-变更与影响链.md)） | preview 的 `requires`：被 grant 覆盖 ⇒ `delegated`；否则 `human_sign` |
| 影响链（[14](14-变更与影响链.md)） | 影响面超 `max_impact` ⇒ **自动拒绝** |
| 待审队列（[07](07-交互-界面与待审队列.md)） | 审计项进同一队列，标 `delegated`（行类型见该篇） |
| 交付（[11](11-交付与版本.md)） | `pending_audit` 的决策不能进发布证据 |
| 双人签 | **不能**用授权满足——冻结仍需两个真人 |

### 不变式

1. grant 只能由人签发，且必须绑定 `decisions` 白名单与 `max_impact`；
2. `forbidden` 里的决策类型**任何 grant 都授不出**（配置层面禁止，不是策略问题）；
3. `pending_audit` 的决策不得作为发布证据；
4. 撤销不删除任何历史；撤销必须有理由；
5. grant 不可链式转授；到期不自动续。

### 起步授权（默认只开这一条）

> **只改 `docs/**`、不动 release 集合、影响面 `blocking=0` 的决策，agent 可代决；24 小时内人审一遍；授权窗口 7 天，续期需人重签。**

边界清楚：它不允许任何会阻塞卡或影响发布的东西——即使漏审，最坏结果是文档写错，**不会污染发布事实**。

## 5. 冲突可见与分歧裁定

### 5.1 `disputed` 不是并发冲突

真源单写 + `expected_version`（CAS）保证**并发写只有一个成功**，另一个拿 409 去重读。所以：

> **并发写不会产生 `disputed`。`disputed` 是语义分歧**：两个 actor 在**同一份输入**上得出相反结论，或后一个推翻了前一个。

这个区分决定了治法：**并发靠数据库，分歧靠人。**

同一对象被两个 actor 写下相反结论时：

```text
conflicts view:
  subject=TASK-261 | u-liang: finished-only @16:20（inputs spec S-12@aa…）
                   | u-wang:  any-idle    @16:22（inputs spec S-12@aa…）
  state=disputed | 裁定权：decide@domain:pool
```

- **不静默后写覆盖**；
- `disputed` 的对象**不能 done**（判据红），也**不能进发布证据**。

### 5.2 先把“假分歧”摘出去

若 A 的结论基于 `S@hash1`，而 B 已产出 `S@hash2`（因果更晚），A 标 **`stale`**，**不是** disputed。
**只有同一 frontier 上的两个相反结论才算分歧**——否则每一次上游变更都会伪造出一堆“争议”。

### 5.3 四级升级阶梯

| 级 | 触发 | 处置 |
|---|---|---|
| **L1 同 actor 前后相反** | 同一 actor 两次相反结论 | **不算分歧**：后者 `supersede` 前者 |
| **L2 跨 actor 相反** | 不同 actor 在同一输入上相反 | `disputed`，进待审队列；由持 `decide@scope` 的人裁定 |
| **L3 超时未裁（48h）** | 仍在 disputed | 升级 P0：**该 scope 下所有卡不能 done** |
| **L4 长期未裁（7 天）** | 仍未裁 | **阻断 release**，并记一条**流程缺陷**（说明决策机制卡住了，不是技术缺陷） |

### 5.4 裁定必须带“被否掉的主张”

```json
{"kind":"resolution","dispute":"d-7f21","chosen":"right",
 "claim_kept":"C-9","claim_rejected":"C-12",
 "rationale":"右案保留了并发上限，左案在 100 并发下会重复入账",
 "signer":"u-liang","frontier":"f:9c1e"}
```

只写“选了 B”不够——**必须写清 A 为什么错**，否则三个月后会被翻出来重吵。

### 5.5 与 grant 联动：授权质量是读出来的

- delegated 决策被推翻 = 一次 resolution，记 `authority_revoked_after`；
- **同一 grant 下连续 3 次被推翻 ⇒ 该 grant 自动收紧为“只能提案、不能代决”**；
- 争议的一方**不能自裁**（与“不得自审”同源）；提出者可撤回（`resolution(chosen=kept)`）。

### 5.6 分歧多说明判据不清

若 agent 之间频繁分歧，问题通常不是机制，而是**判据写得不够具体**。所以分歧率要进 `v_gaps`，作为“该补判据了”的信号——**不要把分歧当噪声压掉**。

## 6. 双人签（关键决策）

| 场景 | 规则 |
|---|---|
| 版本冻结 | 至少 2 个不同 `human` 的 `decision`，且 frontier 相同 |
| 豁免安全类判据 | 禁止（不可豁免） |
| 撤签 | 至少 2 人，其中一人有 `admin` |

实现：`decision.group_id` 把多条签字聚成一个决策；`gate` 判据检查 `count(distinct signer) >= 2`。

## 7. 成员与作用域管理

- 加入项目 = 由有 `admin` 的人签发 `membership(actor, scope, rights)`；
- 离开项目 = 撤销 membership，**不删历史签字**（审计需要）；
- 外部贡献者：只给 `read + write@module`，不给 `decide`；
- agent 的 `actor` 与会话绑定：会话结束 ⇒ agent 的 `write` 权自动失效（不需要人工清理）。

---

## 8. T0 / T1 / T2 的差异

| 形态 | 身份来源 | 说明 |
|---|---|---|
| **T0 单人** | 本机登录（1 个 human + N 个 agent） | 权限矩阵仍生效（agent 不能签、不能决定）；只是 human 只有一个 |
| **T1 同机多人** | 本机账号（每个 human 一个 actor） | 同一 DB、同一 signerd；需要注意"谁在用哪台机器"的审计 |
| **T2 远程** | 服务端账号 + HTTPS | 需要会话 token、限速、审计日志外送 |

**T0 也保留权限**——这是 v1 的教训：单人项目里 agent 直接代签，等于没有签字。

---

## 9. 不变式（协作侧）

1. 任何 `decision` 的 `signer` 必须是有 `sign@scope` 的 `human`；
2. agent 永远没有 `sign` 权（即使临时授予也会被 signerd 拒绝）；
3. `disputed` 的对象不能 `done`；
4. membership 撤销后，历史签字仍可验证（公钥不删）；
5. 权限变更本身落事件（谁在什么时候给了谁什么权）。

---

## 10. 验收读数（M3）

- 让 agent 尝试签一张卡 ⇒ 拒绝并告警（`auth.failed(reason='agent_attempt')`）；
- 两人同时改同一字段 ⇒ `conflicts` 出现一行 `disputed`，且该卡 `done` 被判红；
- 撤销某人的 `decide@release` ⇒ 他的待审项从 `review_queue` 消失（不是隐藏错误，而是明确"无权限 + 申请入口"）；
- 版本冻结时只有 1 个签字 ⇒ 门禁红，且提示"需要 2 人"。

> v1 在这两件事上长期做不成，根因不是"轻量 git 不够轻"，而是**没有权威的序列化点**：写范围靠字符串比前缀，复用靠"猜会话还活着"。
> v2 把两者都变成**数据库里的一行**。

## 11. 工作副本（worktree）

```text
<repo>/.worktrees/<card-id>/          # 仓库内，gitignore
branch: card/<card-id>                # 从当前基线 fork
```

| 阶段 | 动作 | 落事件 |
|---|---|---|
| 认领 | 建 worktree + 分支；若有同前缀锁 → 拒绝 | `task.claimed` + `worktree.created` |
| 工作 | 子代理只在该 worktree 内写；路径越界由沙箱拒 | — |
| 完成 | `merge --no-ff` 回基线；冲突 → 人审 | `task.done` 或 `block(merge_conflict)` |
| 收尾 | 删除 worktree + 分支（保留 commit） | `worktree.removed` |

**为什么放仓库内**：放到仓库外时，`node_modules`、`tsconfig` 路径与工具链会对不上；放仓库内只需在 `.gitignore` 里忽略 `.worktrees/`，且 IDE 能索引到。（v1 的 `DEF-*` 就是"副本根在 `dirname(repo)` 导致相对路径全错"。）

## 12. 锁：路径前缀表

```sql
CREATE TABLE lock (
  path_prefix TEXT PRIMARY KEY,      -- 例：src/domain/plan.ts、src/domain/、docs/
  card_id     TEXT NOT NULL,
  actor       TEXT NOT NULL,
  acquired_at TEXT NOT NULL,
  expires_at  TEXT NOT NULL          -- 默认 2h；到期需续，不自动续
);
```

- **加锁**：`INSERT`；冲突（`PRIMARY KEY`）⇒ 409，并返回"被谁持有、到期时间"；
- **粒度**：文件级为主，目录级只在"整块重写"时用；**不许**用"整个 `src/`"；
- **公共面**（登记表、索引、语言包）不锁，走"单写者队列"：`public_face` 只有一个写者（[03](03-真源-存储事件与折叠.md)），其他卡**申请**而非直接改。

> v1 的 `DEF-168`（拆卡时写范围系统性漏掉守卫/棘轮/判据注册面）在 v2 里由"公共面单写者"从结构上消掉：卡不需要写范围覆盖公共面，它只需要**申请**。

## 13. 合并与冲突

| 情形 | 处理 |
|---|---|
| 两卡改不同文件 | 自动合并（`merge --no-ff`），无冲突 |
| 两卡改同一文件（锁已保证不会并发） | 后完成者必须 rebase 到新基线，冲突重跑判据 |
| 合并后判据红 | 视为"集成回归"，落 `defect(kind=integration)`，**不许**跳过 |
| 冲突无法自动解 | `block(merge_conflict)` + 人审；人审结论也是一次签字 |

**合并只在代码层发生**。台账（真源）永不合并——它是服务（[01](01-理论支撑.md)）。

## 14. 复用：把"为什么新起"变成可执行动作

```ts
type ReuseDecision =
  | { ok: true,  session: SessionId }
  | { ok: false, reason: ReasonCode, action: 'spawn_new' | 'wait' | 'retry', detail: string }

type ReasonCode =
  | 'mask_version_changed'   // 会话的工具面与当前角色不匹配
  | 'has_inflight_card'      // 手上还有在飞卡
  | 'idle_unknown'           // 不知道是否空闲（TTL 到期未观测）
  | 'host_rejected'          // 宿主拒绝复用
  | 'retired'                // 已退役
```

**规则**：

1. 每次派发**最多写 1 条** `reuse.skipped`（聚合：`{reason_counts}`），不是每候选一条；
2. `idle_unknown` 时**不许**自动判空闲（v1 的 `DEF-*`：TTL 一过就当空闲，导致两卡互踩）；
3. 连续新起 N 次（默认 3）落一条告警，进 `v_gaps`；
4. 退役（`retired`）是**一次性动作**：写一条事件，把会话移出候选集，此后不再评估。

**这四条合起来把 v1 的"一次派发刷 83 条 skip 事件"变成"一次派发最多 1 条"**。

## 15. 容量与预算

| 参数 | 缺省 | 说明 |
|---|---|---|
| 并发在飞卡 | 3 | 超过则排队；不是硬上限，由人调 |
| 单 card worktree 时长 | 2h | 到期需续，防止僵尸副本 |
| 回执 / 注入预算 | 见 [06](06-观测-视图工具与预算.md)「预算常量」 | 超限结构化截断 + 指针 |

## 16. 不变式（并行侧）

1. 同一 `path_prefix` 同时只有一个持有者；
2. 一个会话最多持有一张在飞卡（`has_inflight_card` 时不许再派）；
3. worktree 必须可删（无未提交改动）才能回收；否则落 `block(dirty_worktree)`；
4. 公共面修改必须经单写者，卡不得直接写；
5. 复用失败必须带 `reason` 与 `action`（不许静默新起）。

---

## 17. 验收读数（M4）

- 两张卡同时改同一个文件：**一张成功、一张 409**（含持有者与到期时间）；
- 一次派发写出的 `reuse.skipped` 事件数 **≤ 1**（v1 是 83）；
- 连续 3 次新起会话 ⇒ `v_gaps` 出现告警行；
- 合并后判据红 ⇒ 落 `defect(integration)`，卡不能 `done`。

## 18. 子代理约束：假设它会越界

> v2 **不对宿主提任何要求**（宿主所有权不在使用者手里）。因此不承诺"阻止越界"，承诺"**越界会被发现、被定价、被拒绝准入**"。

### 四层

| 层 | v2 做什么 | 依赖宿主吗 |
|---|---|---|
| **预防** | 能力票据、工具面最小、`claim` 不可写、`sign` 不可及、TTL 收尸 | 否（只针对 v2 自己的工具面与接口） |
| **检测** | 派发打点（base commit + 授权范围 + 副本）、副本与主树比对、DB hash 链 `verify` | 否 |
| **准入** | 只有 `diff ⊆ 授权范围`、锁已持有、判据重跑全绿，才允许合入基线（上游变更导致的级联复位见 [14](14-变更与影响链.md)） | 否 |
| **计价** | `boundary.violation` / `admission.rejected` / `orphan.expired` 三条事件 + 自动降权 | 否 |

### 能力票据（不是角色）

```json
{"actor":"a-dev-7f3a","task":"TASK-261","expires":"…",
 "tools":["sdo_query","sdo_act","sdo_check","edit"],
 "scopes":["write:module:src/domain/pool.ts"],
 "budget":{"calls":400,"bytes_out":200000,"wall_ms":7200000,"files":12},
 "issued_by":"dispatch#4821","sig":"…"}
```

规则：**默认拒绝**（工具不在票据里 ⇒ 不出现在 schema 里，而不是"调用被拒"）；**不可自我续期、不可转授**；子代理**没有 `subagents` 工具**（不能无限套娃）。

### 准入流程（防过程做不到，就防结果）

```text
dispatch → 记录 base_commit + 授权范围 + 建副本 .sdo-worktrees/<card>
child    → 随便干（可能越界，v2 不阻止）
admission→ diff ⊆ scopes ? 锁持有 ? 判据重跑绿 ?
           ├─ 是 → 合入基线
           └─ 否 → 拒绝准入 + boundary.violation + 要求还原
```

**"能写不能进"** 比"写不进去"更好查：一旦越界，`git diff` 就是证据，而子代理的自述在结构上**无效**（`claim` 不可写，见 [04](04-链条-意图到声明.md)）。

### 真源：tamper-evident，不承诺 tamper-proof

| 机制 | 作用 |
|---|---|
| 事件 hash 链 + `verify`（每日 + 发布前） | 改一行即断链，断点定位到事件 id |
| 事件数与快照对账 | 删事件也能发现 |
| 关键表只追加 + `expected_version` | 覆盖写被 CAS 拒绝 |
| 断链 ⇒ **隔离模式**（只读 + 报警） | 不自动"修复"（自动修等于帮篡改者抹痕） |

### 计价与降权

| 事件 | 内容 | 后果 |
|---|---|---|
| `boundary.violation` | 哪个文件、超出哪条范围、哪张卡、哪个 actor | 累计 ≥3 次 ⇒ actor 降权（只能查不能写） |
| `admission.rejected` | 缺锁 / diff 越界 / 判据红 | 卡阻塞，人决定还原还是扩范围 |
| `orphan.expired` | 父会话死亡 / 超 TTL 未收尾 | 卡 `blocked(orphan)`，进 `v_gaps` |

### 零宿主契约

**最低要求（任何插件环境都成立）**：能读写工作区、能起子会话、能注册工具、能访问自己的数据库文件。

**可选增强（有则更强，没有不影响正确性）**：子会话工具调用日志（更精确归因）、OS 级隔离（检测升级为阻止）、子会话生命周期事件（收尸更及时）。

**永远不要求**：移除 `bash`、改宿主压缩策略、改宿主上下文预算。v2 只用"少给自己工具、少给自己预算"来适配。

### 验收读数

- 在副本里乱改 ⇒ 准入 `diff ⊄ scopes` ⇒ `admission.rejected` + `boundary.violation`，卡不能 done；
- 直接改主树 ⇒ 准入时主树 `git status` 非空 ⇒ 同样违规（证据是 git，不是自述）；
- 写 `claim` / 尝试签字 ⇒ 接口层拒绝 + 安全告警；
- 父会话被杀 ⇒ 子代理 TTL 到期失效，卡 `blocked(orphan)`，`v_gaps` 出现一行；
- 手工篡改 DB 一行 ⇒ 次日 `verify` 报断点，进入隔离模式。
