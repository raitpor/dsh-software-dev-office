# 代理池与生命周期

> **框架坐标**（对齐 [01 理论与边界](01-理论与边界.md)）
>
> - 守的层：**L1**
> - 涉及真源：过程
> - 对应命题：注意力预算
> - 本文引入/定义的概念：代理状态、lease、复用、压缩闸

> 子代理是**资源**，不是一次性的执行者。目标是三件事：**能复用**（不重读项目代码）、**能自压缩**（不因上下文耗尽就新起）、**只在无法唤醒时退役**。
>
> **边界（与 01 的非目标一致）**：SDO **不实现**会话创建与上下文压缩（调用宿主 API），但**派发决定归它**：`sdo_dispatch` 是唯一入口，复用由代码强制，`new_reason` 必须可机器复算。它做三件事——**决定 + 记账 + 读数**。
> v1 的反面证据：160 个子会话、一次派发刷 82 条 skip 事件、复用靠"猜会话还活着"、代码变动就整库重读。

## 1. 状态机

```text
        ┌──────── wake ────────┐
        ▼                      │
   idle ──claim──▶ busy ──release──▶ idle
     │                │
     │                └─watermark≥70%─▶ compacting ──▶ idle
     ├── idle_too_long / over_pool ──────────────────────▶ parked
     └── probe_failed×3 ─────────────────────────────────▶ dead
```

| 状态 | 含义 | 可分配 |
|---|---|---|
| `idle` | 空闲、能力匹配、可接活 | ✅ |
| `busy` | 手上有在飞卡 | ❌（直到 release） |
| `compacting` | 正在自压缩，暂不接活 | ❌（短暂） |
| **`parked`** | **暂时不可分配**（空闲太久 / 超池上限） | ❌，但**可唤醒** |
| **`dead`** | **无法唤醒**——唯一的退役形态 | — |

> **`parked` 不是退役。** 而 v1 特有的那条"掩码指纹变了 ⇒ 退役"在 v2 **根本不存在**：v2 不做能力面匹配（见下），所以"工具变了"不构成任何状态迁移。

## 2. 表

```sql
CREATE TABLE agent (
  id                 TEXT PRIMARY KEY,     -- 子会话 id
  actor_id           TEXT NOT NULL,        -- 台账身份：它的 rights × scope 决定能接什么卡
  project_snapshot   TEXT NOT NULL,        -- 绑定的 project frontier + commit
  state              TEXT NOT NULL,        -- idle | busy | compacting | parked | dead
  context_watermark  REAL NOT NULL,        -- 0..1，最近一次读到的用量
  last_active        TEXT NOT NULL,
  probe_failures     INTEGER NOT NULL DEFAULT 0,
  reuse_count        INTEGER NOT NULL DEFAULT 0,
  parked_reason      TEXT
);
CREATE TABLE agent_probe ( agent_id, at, ok, detail );          -- 生存探测记录
CREATE TABLE agent_compaction ( agent_id, at, before_tokens, after_tokens, kept TEXT );
```

## 3. 派发：唯一入口，复用是默认（不是建议）

> 只给"建议"等于没写：模型会遗忘、或随口说"上下文不相关"就新起——v1 的复用失败率就是这么来的。所以**决定权收回代码**。

**卡的认领只能通过派发**：`sdo_dispatch(card)` 产出 `lease`（绑 actor + card + scope + frontier + TTL），`claim` 必须持 `lease`。模型自己开新会话也拿不到 `lease` ⇒ **绕过派发没有意义**（拿不到 lease 就认领不了卡，也就写不了台账）。

**预占与收回（PM 的手，不是第二套授权）**：PM 可以先落 `task.assigned(task, actor, expires_at)` 把"可领"收窄到某个 actor——**预占不是授权**，它不授予写权，也不改 `task.status`；写权仍只来自 `lease`。反过来，PM 用 `revoke` 落 `lease.revoked` 收回租约：在飞的卡先 `blocked(lease_revoked)` 再回 `ready`，工作副本不删（证据还在），但不能再写。**再平衡 = 收回 + 预占**，没有第三个动作。

派发内部顺序（代码决定，不看模型意愿）：

| 步 | 判定 | 结果 |
|---|---|---|
| 1 | 硬条件：存活 / `state='idle'` / `rights × scope ⊇ 卡` / `watermark < 限值` / **评审卡（`task.kind='review'`）还要求 `actor ≠ producer(task.subject_id)`**（`subject_id` 指向被评对象；不是评审卡自己的 `owner`） | 筛出候选集 |
| 2 | 候选集**非空** | **必须复用**（按上下文相关性排序取第一） |
| 3 | 候选集**为空** | 才允许新起，`new_reason` ∈ {`no_idle_capable`, `context_irrelevant`, `watermark_exhausted`} |
| 4 | 给了其它原因，或原因校验不过 | **拒绝派发** |
| 5 | 成功 | 落 `agent.reused` / `agent.spawned(reason)` + `lease.issued` |

三条 `new_reason` 都必须**可机器复算**（不接受自述）：

| 原因 | 校验方式 |
|---|---|
| `no_idle_capable` | 候选集为空（按步 1 复算） |
| `context_irrelevant` | 所有候选的 `last_task.files ∩ card.scope.files = ∅`（可计算） |
| `watermark_exhausted` | 候选全部 `watermark ≥ 限值`，且已有 `agent.compaction_attempted` |

**上下文相关性的用法**：候选按"文件交集大小"排序取第一——刚做完 A 模块的代理不会因为"能力够"就被硬塞 B 模块的卡，但**只要还有相关候选，就必须复用**。

**项目快照过期不阻止复用**：注入增量（`diff --stat` + 改动文件清单），**不重读全库**。

> 工具面不参与判定——写进项目过 工作副本 + 准入，写台账过 scope + 判据 + 签字（见 [10](10-语言与平台.md)「为什么不治理工具面」）。

## 4. 自压缩：不压就接不到活

- **闸**：`watermark ≥ 限值（70%）` 的代理**不进入候选集**（第 3 节的硬条件）——它不是"被提醒"，是"派不出去"；
- **执行**：压缩仍由**子代理自己或宿主**完成（那是上下文能力，不在 SDO 手里）；
- **记账**：压完调用 `agent.report_compaction { before_tokens, after_tokens, kept[] }`，**校验 `after < before` 且 `kept[]` 含四类**，否则记账被拒；
- **必留四类**（约定，便于人复核）：任务目标 / 已改文件与 diff 摘要 / 未决问题 / 最近一次验证读数；
- **绝不动 DB 里的事实**：`claim`、证据、读数都在库里，压缩的只是对话。

> 这是"避免上下文耗尽就新起"的关键：**耗尽前压缩，而不是耗尽后新建**。

## 5. 退役：唯一条件是"无法唤醒"

| 触发 | 判定 |
|---|---|
| 连续 **3 次**探测失败（间隔 30s） | `dead` |
| 宿主明确返回"会话不存在" | `dead` |
| 空闲超阈值 / 超池上限 | **`parked`**（可唤醒），**不退役** |

退役必须落 `agent.retired` 事件 + 探测记录（证据），并进 `gaps` 供人复核——**退役是一条需要解释的事**。

## 6. 池容量

| 参数 | 缺省 | 超限行为 |
|---|---|---|
| 活跃（idle+busy） | **8**（部署配置 `max_members`） | 新建前先 `parked` 最久未用的 idle |
| `parked` 数量 | **不设硬上限** | 超过 7 天标 `stale`（进 `gaps`），**不杀也不唤醒**；只有探测失败才 `dead` |

**不因池满而杀活跃代理**；只 parked，必要时才退役。

### 6.1 借鉴：部署上限（旋钮，不是尺子）

宿主团队插件把"人数、队列、单条消息、清理"都做成了**启动时校验的上限**；SDO 需要同样的旋钮，但它**不是尺子**：上限只调配额，不参与任何判定，因此**不进 baseline、不进 hash**，改它不用重冻。

| SDO 的上限 | 缺省 | 超限行为 |
|---|---|---|
| 活跃成员（idle+busy） | 8 | 新建前 `parked` 最久未用的 idle（同 §6） |
| 每 actor 的未答 `attention` | 16 | 按 `attention` 的 `asked_of` 列计数；超限拒绝新 `attention`（`attention_overflow`），先清旧的——**不许静默排队** |
| 单条 `payload` 大小 | 64 KiB | 拒绝并提示拆成多条 |
| 释放/清理超时 | 5 s | 超时即标 `stale` 进 `gaps`，不阻塞调用方 |

**载体只有一张表**（[02](02-真源-存储事件与折叠.md)「运维」）：

```sql
CREATE TABLE config (              -- 部署配置：唯一载体，不进 baseline
  key        TEXT PRIMARY KEY,     -- limits.max_members | limits.max_pending_attention
                                   -- | limits.max_payload_bytes | limits.cleanup_timeout_s
  value      INTEGER NOT NULL,
  updated_by TEXT NOT NULL,        -- 最近一次改动的 admin
  updated_at TEXT NOT NULL
);
```

- **写入只走一个动作** `config` 动作（`admin@domain`，[07](07-协作-权限-并行与子代理.md) §2）；写入时校验：键在白名单、`value` 是整数且 `≥1`、`max_payload_bytes ≥ 1024`，否则拒（`config_invalid`），无权 ⇒ `no_permission`。成功写 `config.changed{key, before, after, actor}`，`updated_by/updated_at` 由该事件投影。
- **初始化**：迁移时写四条 `config.changed`（`actor='migration'`、`before=NULL`、`after` 为缺省 8 / 16 / 65536 / 5），表行由事件投影；迁移 actor 免 admin 校验、免 payload 上限（只此例外，否则自举死锁）。因此**读不到键 = 库坏了**；运行期按 `config_missing` 失败关闭（拒绝 `dispatch`/`attention.raised`），不临时猜缺省。
- **执行点**：成员上限在进入**候选集之前**（与 `design/03` P5 同一处：先 `parked` 最久 idle，全 busy 才拒 `member_capacity`）、attention 上限在 `attention.raised` 时、payload 上限在落库前、清理超时在 `revoke`/`workcopy.removed` 时。写入处与使用处都校验：写入拒非法值；使用处再断言一次（绕库直改会被 `verify` 抓）。
- **不进 P15**：P15 校验的是尺子（判据/门禁/engine）；部署配置不合法不该产出 `baseline.rejected`，它只该被 `config` 动作 拒或在启动时失败关闭。

### 6.2 等待：有 wait 就用，没有就退化

**SDO 不提供 `wait`，也不要求宿主提供**（[01](01-理论与边界.md)「不对宿主提要求」）。所以等待写成两条路径：

| 宿主能力 | PM 怎么做 |
|---|---|
| 提供 wait（如宿主团队插件的 `wait_agent`） | **用 wait，不轮询**：它只观察调用之后的变化；没有别的成员在跑就立刻 `noProgress`；醒来先重列 `pm_queue` 再判断 |
| 不提供 wait | **允许有界轮询**：带退避（如 30s→2min→5min 封顶）、单次只读 `pm_queue`、连续两次读到的 `pm_queue` 与上次相同（这就是轮询下的 `noProgress`）就停手，去升级或等下一次外部触发（不空转） |

**无论哪条路径，判断都只看 `pm_queue` 重读后的结果**，不拿旧快照做决定。轮询本身不是问题，"没有新信息还反复读"才是。

## 7. 视图与度量

`agents`：`id, actor_id, state, watermark, project_snapshot, last_task, last_compaction, reuse_count, parked_reason`。

| 指标 | 用途 |
|---|---|
| **可复用而未复用 / 总派发** | 核心读数，**应为 0**（强制派发后不存在“建议不被采纳”） |
| **强制复用导致的返工/污染率** | 复用错对象（上下文不相关）会返工；上升说明相关性排序权重不对 |
| 平均水位 | 长期 > 80% 说明压缩太晚 |
| 压缩次数 / 代理 | 过低 = 没在自管理；过高 = 任务切得太碎 |
| **僵尸数**（`parked` > 7 天） | 应为 0；不为 0 说明没人清理 |
| **退役数** | 应趋近 0（只有真的唤不醒才退役） |

## 8. 不变式

1. **派发唯一入口**：卡只能由 `sdo_dispatch` 发出 `lease` 后被认领；复用是默认，新起必须给**可机器复算**的原因（机检形态见 [02](02-真源-存储事件与折叠.md)「不变式」第 5、6 条）；
2. **退役只由 `unwakeable` 触发**；其它情形一律 `parked`；
3. 复用前必须过三项硬条件（存活 / 空闲 / 权限覆盖）；软条件只影响选择；
4. 压缩不得丢弃任何 DB 事实的引用（由记账的 `kept[]` 声明，可抽查）；
5. 池满只 `parked`，不杀活跃代理；
6. 一次派发只写 **1 条**聚合事件（复用命中 / 新起 + 原因），不逐候选刷事件。

## 9. 验收读数

- 同一 `rights × scope` 连续派两张卡 ⇒ **第二次强制复用同一会话**（不是建议），注入增量（`diff --stat`）而非全库重读；
- 无候选时给 `new_reason=context_irrelevant` 但两个模块文件有交集 ⇒ **派发被拒**（原因校验不过）；
- 绕过 `sdo_dispatch` 直接 `claim` ⇒ 因无 `lease` 被拒；
- 权限不覆盖（例：`review@scope` 的代理收到实现卡）⇒ **不复用**，新建；
- 水位打到 70% ⇒ 该代理**派不出卡**；压缩并 `report_compaction`（`after < before`）后恢复接活；
- 宿主删掉会话 ⇒ 3 次探测失败 ⇒ `dead`，有事件 + 证据；
- 连续派 100 张卡：活跃 ≤ 8，`parked` 只增不杀、`stale` 可见，**可复用而未复用 = 0**，且复用后的返工/污染率不上升。
