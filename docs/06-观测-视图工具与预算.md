# 观测：视图、工具与预算

> 本篇合并自「工具面-视图与查询」；预算常量统一在此定义（合并目的：一个事实只有一处，防漂移）。

> 状态在数据库里、数据库不在 agent 可读路径上 ⇒ **绕路在物理上不存在**。
> 于是"取不到的状态"不再是 agent 的失败，而是**产品的缺陷**（`query_miss` → `v_gaps`）。

---

## 1. 三个工具（上限，不再增加）

| 工具 | 作用 | 写/读 |
|---|---|---|
| `sdo_query` | 读视图：`{ view, where, select, order, limit, cursor, as_of }` | 只读 |
| `sdo_act` | 写动作：`{ action, subject, expected_version, payload, request_id }`；**带影响面的动作走两段式**（preview → confirm/cancel，见 [14](14-变更与影响链.md)） | 写 |
| `sdo_check` | 现算判据：`{ gate }` 或 `{ criterion }` | 只读（失败时落 `gate.judged`） |

**关于签字**：模型只有一个动作 `sdo_act(action=request_sign)` 与一个只读字段（`decision.status` / `reason_code`）。**没有“验签”工具**——校验由插件在写入与 `verify` 两处完成（[08](08-签字-身份与免密.md)「模型不在信任链上」）。

**为什么不按业务拆 N 个工具**：每缺一个视图就长一个工具，会重演 v1 的 68 条判据——工具越多，越没人知道该用哪个，agent 又会回去读源码猜。**视图是数据，工具是解释器**。

---

## 2. 视图是数据（`view_catalog`）

```sql
CREATE TABLE view_catalog (
  name        TEXT PRIMARY KEY,
  sql         TEXT NOT NULL,          -- 只允许 SELECT；服务端静态校验
  columns     TEXT NOT NULL,          -- JSON：列名、人话名、单位、类型
  doc         TEXT NOT NULL,          -- 这个视图回答什么问题
  min_right   TEXT NOT NULL,          -- reader | reviewer | decider | signer
  row_budget  INTEGER NOT NULL        -- 默认返回行数上限
);
```

`sdo_query({view:'list'})` 返回目录本身：**视图自描述**。agent 先看目录再查，而不是猜名字。

**新增视图不改代码**：写一条 `INSERT INTO view_catalog`（经迁移脚本），下一次查询即可用。

## 3. 首批 8 个视图

| view | 回答什么 | 关键列 | 最低权限 |
|---|---|---|---|
| `overview` | 现在在哪个阶段、在飞几张、健康度 | `stage, in_flight, blocked, open_defects, health` | reader |
| `review_queue` | **待我决策的项**（一项一行） | `item_id, proposition, evidence_refs, impact, options` | decider |
| `board` | 每张卡：阶段/谁/上一步/阻塞原因码 | `task_id, title, status, owner, last_action, block_code` | reader |
| `plan` | 待办、计划、依赖链 | `task_id, status, blocked_by[], scope` | reader |
| `evidence` | 每条声明 → 证据 → 产物指纹 | `claim_id, criterion_id, artifact_sha256, at` | reader |
| `defects` | 分布、复发族、未修清单 | `defect_id, family, status, severity, criterion_id` | reader |
| `team` | 谁在做什么、谁能决策哪个域 | `actor_id, kind, scopes[], rights` | reader |
| `gaps` | `query_miss` 聚合 + 退休候选判据 + 生效豁免 | `kind, subject, count, last_seen` | reviewer |

**`review_queue` 是产品核心**（[07](07-交互-界面与待审队列.md)）：一行三样——可反驳的命题、可点开的证据、不签的后果。

## 4. 输出契约（预算与游标）

```ts
type QueryResult = {
  rows: Row[]                 // 已按 select 裁剪
  bytes: number               // 本次返回的字节数（服务端计算）
  truncated: boolean          // 是否截断
  next_cursor?: string        // 截断时给游标，绝不静默丢
  as_of: Frontier             // 这批数据对应的事件 frontier
  view: string                // 视图名 + 版本
  miss?: { reason: string }   // 视图/列不存在时的结构化说明（同时落 query_miss）
}
```

硬规则：

1. **每次返回必带 `as_of`**——读数是"到哪一组事件为止"，不是"现在"；
2. **超预算必截断且给游标**，不许静默；
3. **列名是人话 + 单位**（`count_7d` 显示为"近 7 天数量"），编号只作次要标识（[07](07-交互-界面与待审队列.md)）；
4. 同一 `(view, args, as_of)` 的结果**确定性**（用于对账与快照）。

## 5. `query_miss`：缺工具由使用记录决定

```json
{ "kind": "query_miss", "payload": { "view": "release_gaps_by_owner", "reason": "view_not_found",
  "hint": "想按负责人看顺延缺口", "task": "TASK-280", "actor": "a-dev-7f3a" } }
```

- **何时落**：视图不存在 / 列不存在 / 行被权限裁掉（后两者带 `reason`）；
- **怎么用**：`v_gaps` 按 `(kind, subject)` 聚合，显示"最常被问却答不上的前 N 项"；
- **怎么关**：补一个视图或列 ⇒ 该聚合行自然消失（不是手动标记"已处理"）。

这条闭环让工具面**按需求长**，且每个新增视图都有原始诉求可查。

---

## 6. 权限裁剪（读也要最小权限）

- `min_right` 由 `view_catalog` 声明；`sdo_act` 的每个 action 有自己的 `right`；
- **列级裁剪**：agent 视图不含 `human_only` 列（如"别人的签章状态"）；
- 裁剪**要留痕**：`query_miss(reason='filtered_by_permission')`，否则 agent 会以为"没有数据"。

---

## 7. 不变式

1. 工具参数与返回值**永不含**口令、密钥、token（类型层面禁止该字段）；
2. 视图 SQL 只允许 `SELECT`（服务端静态校验 + 迁移期审核）；
3. 任何 `truncated=true` 必须带 `next_cursor`；
4. `sdo_act` 的任何写都必须给 `expected_version`（除 `create`）；
5. `query_miss` 是**唯一**允许 agent 写入的"观测类"事件。

---

## 8. 验收读数（M0–M1）

- `sdo_query({view:'list'})` 返回 8 个视图，每个含列的中文名与单位；
- 人为删掉 `review_queue` 视图 → agent 查询得 `miss.reason='view_not_found'`，`v_gaps` 出现该行；
- 视图返回 10 万行时：`truncated=true` 且 `next_cursor` 可用（两次请求拼出完整结果）；
- 同一 `as_of` 两次查询结果**逐字节相同**。

## 9. 预算常量（**唯一定义处**，别处只许引用）

| 面 | 预算 | 超限行为 |
|---|---|---|
| 单次工具返回 | **≤ 8 KB** | 结构化截断 + `next_cursor`（不静默） |
| 每轮注入 | **≤ 1500 字符** | 折叠成摘要 + 指针 |
| 单次查询行数 | **≤ 500**（可调） | 截断 + 游标 |
| `sdo_query` P95 | 见 [03](03-真源-存储事件与折叠.md)「三条预算线」 | 判据红 |

三条**反模式判据**（出现即红）：`perf.n_plus_one`（同请求内重复查同一表 ≥3 次）、`perf.unbounded_select`（无 `LIMIT`）、`perf.ui_compute`（界面层做聚合/排序）。
