# 方法论与策略（policy）

> 结论：**方法论依然适用，但必须从"产品内置的流程"降级为"策略数据 + 可机械检查的时序断言"。**
> v1 的教训：4 套 process + 方法包 + 构造 profile + 八维评分，把"人的思考方式"编码进产品 ⇒ 每种组合都要维护判据与必产项 ⇒ 79% 的缺陷来自机制自己。

---

## 1. 生命周期：三份 policy，不是三份代码

| policy | stage DAG | gate 绑定 | 用途 |
|---|---|---|---|
| `linear` | `req → design → build → verify → deliver` | 每个 stage 出口一 gate | 需求明确、变更昂贵 |
| `spike` | `explore → harden → deliver` | explore 出口只判"可观察"，harden 全量 | 先做原型再决定 |
| `incremental` | 多 lane，每 lane `build → verify` + 全局 `integrate` | lane 出口 + 集成 gate | 多条线并行 |

**同一套 engine**：gate 判定、判据、证据、签字机制完全共享；policy 只换"绑哪个 gate 到哪个 stage"。

```yaml
policy:
  id: spike
  stages: [explore, harden, deliver]
  gates:  { explore: [G1], harden: [G2, G3], deliver: [G6] }
  artifact_kinds: { prototype: throwaway, product: releaseable }
  switches:
    tdd:           { enabled: true }
    contract_first: true
    boundary_matrix: true        # 数值参数必须覆盖 min-1/min/max/max+1
    coverage_trend: non_decreasing
  regression: { mode: impact_set, max_age_days: 7 }
```

**铁律：加一种 policy，判据总数不许增加。**（验收读数）

---

## 2. 原型的"转正"必须是一次签字

`artifact.kind` 是所有产物的一等属性：

| kind | 能进发布证据 | 转换 |
|---|---|---|
| `prototype` | **不能** | 必须 `decision(graduate)`：引用原型产物 + 新 frontier，重新绑定证据 |
| `product` | 能 | — |
| `throwaway` | 不能 | 只能被引用，不能被交付 |

v1 真正的病不是"写原型"，而是**原型代码悄悄转正、没人签字**。这条只有数据模型能守。

---

## 3. 开发阶段方法论：只留"能变成时序断言"的

| 条目 | v2 处置 | 判据形态 |
|---|---|---|
| 需求工程 | 保留，但用"**每条条款必须被一条判据或一个场景消费**"替代歧义打分 | `spec` 无消费者 ⇒ 红 |
| 设计方法（结构化/OO/演进式/移植） | **不进引擎**（对人有用、对执行面无判据） | 只留两条：设计产物与代码一致（指纹）、跨模块承诺有 consumer |
| TDD | 策略开关 + **事件序判据** | `evidence(红) → evidence(绿) → task.done`，顺序反了即红 |
| 契约先行 | 策略开关 | `contract.defined` 必须在第一次代码写事件之前 |
| 构造 profile（5 选 1）、八维评分、审讯提问模板 | **退休** | 理由：代理指标，Goodhart 温床（v1 曾逼人给已否决需求灌水） |

**TDD 的可判形态**（v2 相对 v1 的升级）：

```text
要求：同一卡上存在事件序列
  ev(evidence, label='red',   ref=commit_a)   ← 先失败
  ev(evidence, label='green', ref=commit_b)   ← 后通过，且 a 是 b 的祖先
  ev(task.done)
缺 red 或顺序错 ⇒ 判红。v1 只在手册里写"要 TDD"，没人能验。
```

## 4. 测试方法论：分配"谁消费它"

| 方法 | v2 位置 | 可机械的部分 |
|---|---|---|
| 黑盒（等价类/边界/决策表） | `scenario` 的参数化夹具 | **边界矩阵**：数值参数必须有 min−1/min/max/max+1 四格 |
| 白盒（语句/分支覆盖） | **证据**，不是判据 | 覆盖率趋势不得下降（防删测试过门禁） |
| 集成 | `contract` + 集成 gate | 跨 lane 的承诺必须有 consumer 且被验证 |
| **回归** | **重点强化** | `regression_set(change)` = 受影响的 criterion 集合（由 claim 依赖图算），合并后必须重跑并更新 frontier |
| 变异 | 保留 | 变异记录落 `evidence`，绑 frontier；两次读数不一致 ⇒ 都留、标 `disputed` |
| 探索式 / 可用性 | 人审 `scenario` + 签字 | 无机械面，不硬编判据 |

**回归集为什么是重点**：v1 只有"跑全量"这一招——慢，且挡不住"改 A 坏 B"。v2 用 frontier + 依赖图算出**受影响的判据子集**，既快又准，因为它绑的是"哪条声明受影响"，不是"哪个测试文件被改"。

## 5. 退休清单（明确不搬）

| v1 的东西 | 处置 | 理由 |
|---|---|---|
| 4 套 process yml | 合成 3 份 policy 数据 | 代码不变，只换数据 |
| 方法包（structured/oo/evolutionary/porting/none） | 退休 | 无机械判据，只制造必产项 |
| 构造 profile + 最小必产项 | 退休 | v1 膨胀源 |
| 八维歧义评分 / 审讯提问模板 | 退休 | 代理指标，逼灌水 |
| 每轮状态块注入 | 退休 | 由 UI + 视图取代（[07](07-交互-界面与待审队列.md)） |

**保留并升级**：TDD（→ 事件序）、契约先行（→ 时序）、变异自证（→ 绑 frontier）、覆盖率消费（→ 趋势判据）。

---

## 6. 不变式

1. policy 只声明"绑哪个 gate、要哪种产物、开哪个开关"，**不声明"怎么做"**；
2. 新增 policy 不得引入新判据（只能复用既有判据）；
3. `prototype` / `throwaway` 产物不得出现在发布证据集；
4. 策略开关必须在卡上可查（哪张卡按哪个 policy 走的）；
5. 退休清单里的条目若被重新引入，视同新需求，需要 intent + 判据 + 负例。

---

## 7. 验收读数（M1）

- 同一份代码分别用 `linear` 与 `spike` 跑：**判据数量相同**，只有 gate 绑定不同；
- 一张卡缺"红"证据却标 `tdd` ⇒ 门禁红并指出缺哪条事件；
- 原型产物被塞进发布证据集 ⇒ 红；
- 数值参数只测 min/max、漏 min−1/max+1 ⇒ 边界矩阵红。
