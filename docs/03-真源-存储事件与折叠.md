# 真源：存储、事件、折叠与性能

> 本篇合并自「真源-存储与并发」+「事件协议与折叠」+「性能与预算」（合并目的：一个事实只有一处，防漂移）。

> 结论先行：**真源是数据库里的服务，不是仓库里的文件。** 台账不进 git；git 只放代码与"审计快照"。
> 依据：两个真相相加不会得到真相（见 [01](01-理论支撑.md)）。

---

## 1. 为什么是数据库（四条，按重要性）

| 理由 | 说明 |
|---|---|
| **约束即判据** | 外键挡悬空引用、`UNIQUE` 挡重复登记、`CHECK` 挡非法状态。v1 里靠判据事后抓的东西，这里**写不进去**。 |
| **事务即串行化点** | 认领、加锁、签字都要"读-判-写"原子。v1 用 CAS + 文件，永远有窗口期；这里一条 `UPDATE ... WHERE version = ?` 就够。 |
| **视图即唯一出口** | 派生状态是 SQL 视图/物化表，没有"第二份实现"，从结构上消灭 `声明≠真源`。 |
| **并发即能力** | 多 agent 并行写、多人协作，前提是有一个权威的序列化点。文件没有，数据库有。 |

**代价（必须写在前面）**：不能进 git（不能 diff / 不能 code review）；单点；迁移要版本化；大对象不能进库。

## 2. 部署形态与配置

| 形态 | driver | 并发语义 | 适用 |
|---|---|---|---|
| T0 | `sqlite`（单文件） | WAL + `BEGIN IMMEDIATE` | 单人，装完即用 |
| T1 | `sqlite`（同机/同卷） | 文件锁 + 事务；**不支持网络卷** | 2–5 人同机 |
| T2 | `postgres` | 行锁 / 可串行化 | 多人多地 |

```yaml
store:
  driver: sqlite                     # 缺省
  url: ~/.local/share/sdo/<project>.db
  # postgres 示例：url: postgres://sdo@db.internal/sdo
```

**硬规则**：

1. **数据库文件不在 agent 可读路径上**（v1 的 `.sdo/` 在工作区内，agent 能用 bash 读；v2 必须挪出去）——这是"观测只能走视图"的物理前提（[06](06-观测-视图工具与预算.md)）。
2. **只允许一个写者进程**（T0/T1）或多个连接上的事务（T2）；不存在"两个真源"。
3. **schema 版本化**：`schema_version` 表 + 前进迁移脚本；禁止手工改表。

## 3. 并发写：拒绝，不合并

```text
act(action, subject, expected_version, payload)
  ├─ version 不符        → 409 conflict（附：谁改的、改了什么、当前 version）
  ├─ 违反约束（FK/UNIQUE）→ 422（附：哪个约束、哪一行）
  └─ 成功               → 事件追加 + 物化表更新（同一事务）
```

- **不做自动合并**：人可以"基于最新版重做"，但那是**一次新的写**，留两条事件。
- **冲突可见**：同一对象两人并发写时，`conflicts` 视图列出"谁在什么时候不同意"，而不是后写覆盖。
- **幂等**：每个写请求带 `request_id`；重放同 `request_id` 返回首次结果（网络重试不会双写）。

## 5. 备份、恢复与审计（运维侧）

| 动作 | 频率 | 说明 |
|---|---|---|
| 全量备份 | 每日 | `sqlite3 .backup` / `pg_dump` |
| WAL 归档 | 持续（T1/T2） | 支持时间点恢复 |
| **恢复演练** | 每月 | 恢复到一个临时库，跑 `sdo_ledger verify`（重放 hash 链，对账事件数与最新 frontier） |
| **审计快照** | 每次发布/里程碑 | `sdo_ledger export --at <frontier>` → 确定性 JSONL（排序 + hash 链）**进 git**，作为发布物 |

**"台账进 git"被替换成"审计快照进 git"**：前者要求可合并（做不到），后者只要求可复算（做得到）。

审计者验证三件事：① 快照 hash 链自洽；② 快照里的 claim 都能在事件里找到出处；③ `decision` 的签名可验（公钥随快照发布）。

## 6. 风险与对策

| 风险 | 对策 |
|---|---|
| 单点故障 | 每日备份 + 恢复演练；T2 上只读副本；文档写明 RPO/RTO |
| CI 拿不到台账 | 三选一：CI 用只读凭据连 T2 / CI 只跑代码测试 / CI 校验发布快照自洽 |
| code review 看不到台账变更 | PR 里贴 `sdo_ledger diff --from <frontier> --to <frontier>`；发布快照进 git |
| 大对象撑爆库 | 大对象（日志、截图、构建产物）进文件/对象存储，库里只存 `artifact(sha256, uri, bytes, media_type)` |
| 迁移破坏数据 | 迁移脚本只前进、每次迁移前自动备份、迁移后跑 `verify` |

## 7. 验收读数（M0）· 存储侧

1. 一次 `status` 视图查询中，`event` 表被读 **1 次**（日志可证）；
2. 并发两个写请求打开同一张卡：**一个成功、一个 409**，且 409 里含"谁赢了"；
3. `sdo_ledger verify` 在导入后的库上通过（hash 链连续、无悬空引用）；
4. agent 侧无法用 `bash`/`read` 触达 DB 文件（沙箱路径检查）。

> 事件表是**唯一真源**；`fold` 是唯一允许读它的代码；所有消费者读投影，不读事件。
> 依据：单一出口（[01](01-理论支撑.md) P1）。

## 8. 图模型：node / edge / 遍历契约

**决策：不引入图数据库，但数据模型按图建。** 理由三条：

| 理由 | 说明 |
|---|---|
| 约束即判据 | 我们靠外键/UNIQUE/CHECK 让非法状态“写不进去”；图库只有唯一性/存在性约束，等于把门禁退回代码 |
| 视图与聚合 | 8 个视图全是 `JOIN + GROUP BY + LIMIT/游标`；图库做表格聚合与分页很别扭 |
| 缺省形态 | v2 承诺“缺省 sqlite、装完即用”；内嵌图库的成熟度、备份与迁移工具都撑不起这条 |

### 8.1 两张表

```sql
CREATE TABLE node (kind TEXT, id TEXT, hash TEXT, at TEXT,
                   PRIMARY KEY (kind, id, hash));
CREATE TABLE edge (
  src_kind TEXT, src_id TEXT, src_hash TEXT,   -- 消费方，以及它消费的版本
  dst_kind TEXT, dst_id TEXT, dst_hash TEXT,   -- 被消费方，以及被消费的那一版
  edge_kind TEXT NOT NULL,                      -- derives | verifies | locks | grants
  PRIMARY KEY (src_kind, src_id, src_hash, dst_kind, dst_id, dst_hash, edge_kind)
);
CREATE INDEX edge_by_dst ON edge (dst_kind, dst_id, dst_hash);
```

- **主键里带 hash**：同一对节点的新旧两版是两条边，天然区分“基于哪一版”；
- **单一出口**：`inputs`（节点上的 `{kind,id,hash}`）是**真源**，`edge` 是**同一事务里重建的物化索引**，任何代码不得直接写 `edge`；
- 影响查询 = 一条 `WITH RECURSIVE`，从 `dst=(kind,id,oldhash)` 沿 `src` 反向走到无下游。

### 8.2 遍历契约

```ts
impact(seed: NodeRef, opts: { maxDepth?: number; budget: number })
  → Array<{ node: NodeRef; path: NodeRef[]; depth: number; level: 'blocking' | 'advisory' }>
```

三条硬规则：

1. **DAG**：派生图必须无环——建边时做可达性检查，**成环即拒绝**（不是告警）；
2. **预算**：深度上限、行数上限 + 游标、`visited` 集防重复；超出返回 `truncated` 与游标，绝不静默；
3. **路径即证据**：每条结果带 `path`（`spec S-12 → design D-03 → task 261`），否则用户看到“11 张卡失效”却不知道为什么。

### 8.3 memo 的键必须含 frontier

遍历可以缓存，但键是 `(seed.hash, frontier)`——这是**纯函数结果缓存**，不是陈旧副本：同一输入必得同一输出。**禁止**用“5 分钟过期”作为失效条件（见本部分「不变式（可机械检查）」第 5 条）。

### 8.4 规模与可选升级

50k 节点 / 200k 边：Postgres 与 sqlite 的递归 CTE 都是**毫秒级**，不需要图引擎。
若 T2 之后确实偏好 Cypher：Postgres 上挂 `apache-age` 扩展——**同一个库、同一套事务与外键**，一个数据库两种查询语言；比引入独立图库划算。

`verify` 增两行：`edge` 由 `inputs` 重建后与库中逐条一致；`edge` 无环。

## 9. 事件长什么样

```json
{
  "id": "e-7f3a-0042",
  "at": "2026-10-26T08:43:06Z",
  "actor": "u-liang",
  "kind": "task.blocked",
  "subject": "TASK-280",
  "payload": { "reason_code": "awaiting_review", "note": "…" },
  "caused_by": ["e-7f3a-0041"],
  "request_id": "r-81c2",
  "prev": "sha256:…",
  "hash": "sha256:…"
}
```

| 字段 | 规则 |
|---|---|
| `id` | `e-<actor短id>-<该actor内递增>`，全局唯一，与物理顺序无关 |
| `at` | 事件时间（UTC）；**不作为排序依据**（时钟不可信） |
| `actor` | 已登记的 `actor`（人 / agent 会话 / 服务） |
| `kind` | 见 §2，**枚举**，schema 校验 |
| `subject` | 作用对象 id（`TASK-…` / `REQ-…` / `d-…`），外键 |
| `payload` | 每 kind 有 schema；**只存状态变更所需的最小字段** |
| `caused_by` | 因果边（哪些事件导致它）——判据需要的是因果，不是序号 |
| `request_id` | 幂等键：同 id 重放返回首次结果 |
| `prev` / `hash` | 链自证；`hash = sha256(规范化(event 去掉 hash) + prev)` |

**排序**：`ORDER BY at, id` 只用于**展示**；判据与 fold 一律按 `caused_by` 的拓扑序 + 事务提交序。

## 10. 事件类型（12 种，上限）

| 域 | kind | 何时写 |
|---|---|---|
| 意图 | `intent.proposed` / `intent.signed` | 有人提出意图 / 有人签字 |
| 条款 | `spec.defined` / `spec.revised` | 条款落地 / 修改（必须带理由） |
| 过程 | `task.created` / `task.claimed` / `task.blocked` / `task.done` / `task.dropped` | 卡的生命周期（**只记状态变更**） |
| 证据 | `evidence.attached` | 绑产物指纹（大对象存 uri） |
| 评审 | `review.recorded` / `review.finding_verified` | 评审落盘 / 逐条核实 |
| 判据 | `gate.judged` | 一次门禁现算的结论（含每条判据三态） |
| 发布 | `release.frozen` | 版本冻结（含范围集合与签字） |
| 签字 | `decision.signed` / `decision.revoked` | 密码学签字 / 撤销 |
| 身份 | `actor.enrolled` / `auth.login` / `auth.unlock` / `auth.failed` | 身份与凭据（不含口令） |
| 观测 | `query_miss` | 想查却查不到（产品缺陷的输入，见 [06](06-观测-视图工具与预算.md)） |
| 运维 | `schema.migrated` / `backup.taken` / `verify.passed` | 库自身的变化 |
| 并行 | `lock.acquired` / `lock.released` / `worktree.created` / `reuse.skipped` | 见 [09](09-协作-权限-并行与子代理.md) |
| 变更 | `change.proposed` / `change.applied` / `node.reset` / `act.cancelled` | 见 [14](14-变更与影响链.md) |
| 冻结 | `baseline.frozen` / `baseline.amended` / `baseline.loosened` | 见 [05](05-判据-门禁与负例.md)「baseline」 |

**明确不许进事件流的**：

- 逐候选诊断（v1 的 `reuse-skipped` 一天写 1942 条）——聚合后写一条，或写 `metrics` sidecar；
- 心跳、进度百分比、逐帧日志——这些是 sidecar，可丢；
- 任何口令、密钥、token 的明文或哈希。

> 判断标准：**这条事件改变了哪个对象的状态？** 没有，就不要写。

## 11. 折叠（fold）

```ts
type Fold = (prev: State, events: Event[]) => State   // 纯函数，无 I/O，可重放
```

- 物化表由 fold 维护；启动时若物化表缺失/落后，从事件重放补齐；
- **增量**：`fold(prev, events.slice(sinceIdx))`；`sinceIdx` 由 `state.cursor` 记录；
- **确定性**：同一组事件、同一排序 ⇒ 同一状态（用 `verify` 复算，见 §5）；
- **不可变**：fold 不改事件，只产出新状态。

**只有 fold 能读 `event` 表**。这条用一条 lint 判据守：

```text
规则：`SELECT … FROM event` 只允许出现在 fold 模块（路径白名单）
违例：判红，附违例文件与行号
```

同一条规则把 v1 的"1124 次解析"这类问题从结构上消灭。

## 12. frontier：取代"第几条"

```ts
type Frontier = readonly EventId[]   // 一组事件 id（因果闭包）
```

- `claim.as_of_frontier`：这条声明"成立到哪一组事件为止"；
- 签字对象里包含 frontier 哈希；**frontier 变了，签字失效**（[08](08-签字-身份与免密.md)）；
- 展示时给人看"对应第几条之前"是允许的（派生视图），但**判据与签字只认 frontier**。

为什么不用 seq：真源是单写服务，seq 看似稳定；但一旦导出快照、跨库导入、或分库，seq 就不可比。frontier 是唯一在各形态下都成立的"有效期"表述。

## 13. 一致性检查（`sdo_ledger verify`）

| 检查 | 失败含义 |
|---|---|
| hash 链连续 | 事件被改过或缺失 |
| `prev` 指向存在 | 链断裂 |
| 所有 `subject` 外键可解析 | 悬空引用 |
| 所有 `claim.derived_by` 是已注册 renderer | 手拼声明 |
| 所有 `criterion` 有正例与负例夹具 | 判据不合格 |
| `state.cursor` 与事件数一致 | fold 落后 |
| 判定记录的 `baseline.hash` 与当前 baseline 一致（或变更已签字） | 尺子被偷换 |
| `decision.signature` 可验且 `signer ≠ producer` | 代签或坏签 |

`verify` 是**运维动作**也是**发布动作**：发布快照前必须跑通。

---

## 14. 不变式（可机械检查）

1. 事件只增不改（DB 层禁 `UPDATE/DELETE`，只允许 append 权限）；
2. 每条事件都能被某个 fold 消费者解释（无"死事件"）；无法解释的 kind ⇒ schema 迁移没做完；
3. 任何 `claim` 必须指向一个存在的 frontier，且 `derived_by` 已注册；
4. 任何 `decision` 必须指向一个存在的 frontier，且签名可验。

## 15. 验收读数（M0）· 事件侧

- 一次 `status` 查询的事件表读取次数 = **1**；
- 重放 10 万条事件，两次 fold 的结果**逐字节相同**；
- `verify` 在故意删一条事件的库上**报出断点 id**（不是"失败"两个字）。

> v1 的教训很具体：一次状态查询解析台账 **1124 次**、耗时 **15.9 秒**；一次会话涨到 **132 MB** 后 400 死锁。
> 根因不是"代码慢"，而是**没有把成本当成契约**。v2 把延迟、体量、行数都变成**有预算、有判据、有基准**的东西。

## 16. 三条预算线

| 线 | 指标 | 预算 | 超限行为 |
|---|---|---|---|
| **读** | 一次 `sdo_query` 的 P95 | **< 50 ms**（100 万事件库） | 判据红 + 建议加索引/加视图 |
| **写** | 一次 `sdo_act` 的 P95 | **< 10 ms** | 同上 |
| **折叠** | 全量 `fold` 重建（100 万事件） | **< 5 s** | 同上 |
| **回执 / 注入 / 行数** | 见 [06](06-观测-视图工具与预算.md)「预算常量」 | — |

**本节只定义存储侧门槛**（读/写/折叠）；输出面预算（单次回执、每轮注入、查询行数）**唯一定义在** [06](06-观测-视图工具与预算.md)「预算常量」，此处只引用、不复述数值与理由。预算不是建议值，是**类型化的参数**：渲染函数签名里就有 `budget`，不传编不过。

## 17. 性能的结构性前提（不满足就别谈优化）

1. **一次查询只读一次事件**：视图是物化表/SQL 视图，禁止"N 个实体各扫一遍事件"（v1 的 1124 次就是这么来的）。
2. **禁止 N+1**：取列表时一次性 join 出所需字段；对同一实体的重复访问必须走缓存（按 `frontier` 失效）。
3. **增量折叠**：`fold(prev, newEvents)`，`state.cursor` 记录处理到哪；全量重建只用于 `verify` 与迁移。
4. **禁 `SELECT *`**：视图显式列；列数纳入评审（列越多，越容易顺手把大字段带出来）。
5. **界面零计算**：UI 只格式化（[07](07-交互-界面与待审队列.md)），所有聚合在 SQL 里。

## 18. 索引策略（按访问路径反推）

| 访问路径 | 索引 |
|---|---|
| 按对象查事件（`subject`） | `event(subject, kind, at)` |
| 按 kind 扫描（判据归因） | `event(kind, at)` |
| claim 有效性（frontier） | `claim(subject, predicate, as_of_frontier)` |
| 待审队列 | `decision(status, scope)` / `review_queue` 物化 |
| 卡与锁 | `task(status, module)`、`lock(path_prefix)` |
| 视图分页 | 视图自带排序键（`at DESC, id`） |

**强制**：每条视图在 `view_catalog` 里声明 `est_rows` 与 `explain`（最近一次 `EXPLAIN QUERY PLAN` 的摘要）；`est_rows` 与实测差 10 倍以上 ⇒ 告警（说明统计过期或索引没走对）。

---

## 19. 体量增长与归档

| 项 | 策略 |
|---|---|
| 事件表 | 单库上限（默认 100 万事件 / 2 GB）；超限必须**归档**到 `event_archive`（同 hash 链、只读、按 `as_of` 可查） |
| 大对象 | 不进库：`artifact(uri, sha256, bytes)`，文件/对象存储 |
| 日志 | 只存 `log_excerpt`（引用 + 摘要），不存全文 |
| 快照 | 发布快照压缩存储（zstd），进 git 的只有快照 |
| 体量可见 | `v_gaps` 常驻显示"事件数 / 库大小 / 归档段数"，超阈值进待审 |

**硬规则**：任何"无上限"的增长都不允许——v1 的 `.sdo/journal.jsonl` 从 0 长到 1 万条事件、6.9 MB，全程无人管。

## 20. 退化与背压

| 情形 | 行为 |
|---|---|
| 写突发 | 队列 + `429` + `Retry-After`；**读永不因写阻塞**（WAL） |
| 库锁等待 | 3 s 超时 ⇒ 明确报"谁持有锁、何时到期"，不无限等 |
| 缓存失效 | 一级缓存按 `frontier` 失效（内容变即失效，不会读旧数） |
| 视图未物化 | 首次查询触发物化；物化中返回 202 + 任务 id（不静默等 10 s） |
| 归档后查询 | 透明路由到 `event_archive`，返回带 `archive=true` 标记 |

## 21. 基准与判据（每次发布跑）

```bash
sdo bench --events 1e6 --mixed        # 生成合成事件 + 读写混合压测
```

| 基准 | 门槛 |
|---|---|
| `bench.read_status` / `bench.write_event` / `bench.fold_rebuild` | **见「三条预算线」**（不在此复述数值） |
| `bench.review_queue` | P95 < 80 ms（含物化）——**本表唯一定义** |
| `bench.export_snapshot` | < 30 s @ 1M——**本表唯一定义** |

三条**反模式判据**（出现即红）：

- `perf.n_plus_one`：同一请求内对同一表重复查询 ≥ 3 次；
- `perf.unbounded_select`：无 `LIMIT` 的列表查询；
- `perf.ui_compute`：界面层出现聚合/排序计算（静态检查）。

## 22. 容量估算（给运维）

| 规模 | 事件数 | 库大小（估） | 备注 |
|---|---|---|---|
| 单人小项目 | 1 万 | ~10 MB | sqlite 单文件毫无压力 |
| 团队一年 | 100 万 | ~1–2 GB | T1 sqlite 仍可用；开归档 |
| 更大 | > 100 万 | — | 转 T2（postgres）+ 归档 |

**注**：v1 的"132 MB 会话"是**宿主上下文**问题，不是库的问题；v2 的库按事件数增长，与"会话体量"解耦（这也是把真源移出会话上下文的好处）。

## 23. 不变式

1. 任何读路径的单次事件表扫描 ≤ 1；
2. 任何列表接口必须带 `LIMIT` 与游标；
3. 任何输出面必须带 `bytes` 与 `truncated`；
4. 任何增长必须可见（`v_gaps` 里有体量行）；
5. 缓存必须能按 `frontier` 失效，禁止"时间过期"作为唯一失效条件。

## 24. 验收读数（M0–M1）

- 100 万事件的合成库上：`read_status` 与 `fold_rebuild` **达到「三条预算线」的门槛**（不在本节复述数值）；
- 一次状态查询的事件表读取次数 **= 1**（v1 是 1124）；
- 单次回执超过「输出面预算」（见 [06](06-观测-视图工具与预算.md)）⇒ `truncated=true` 且游标可用；
- 连续写 1000 条事件期间，读查询 P95 不劣化超过 20%（WAL 生效）；
- 故意写一条无 `LIMIT` 的列表查询 ⇒ `perf.unbounded_select` 红。
