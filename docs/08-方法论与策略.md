## 1. 生命周期：policy 是 preset，不是模式分支

**policy = 一份配置**（阶段 DAG + gate 绑定 + 开关 + 回归策略）。所谓"瀑布 / 快速原型 / 增量"只是**三个内置 preset**，不是三种代码路径，也不是三种引擎行为。

| preset | 等价说法 | stage DAG（`id`[`kinds`]） | gate 绑定 | 典型用途 |
|---|---|---|---|---|
| `waterfall` | 瀑布 / `linear` | `req[requirement] → design[design] → build[implement] → verify[review] → deliver[deliver]` | 每个 stage 出口一 gate | 需求明确、变更昂贵 |
| `prototype` | 快速原型 / `spike` | `explore[implement] → harden[requirement, design, implement, review] → deliver[deliver]` | explore 出口只判"可观察"，harden 全量（含评审） | 先做原型再决定 |
| `incremental` | 增量 | `req_design[requirement, design] → build[implement] → verify[review] → integrate[deliver]` | lane 出口 + 集成 gate | 多条线并行（**lane 在 task/派发层**，不进 policy） |

**`kinds` 是 stage 与判据词表的唯一接缝**：判据的 `applies_to` 只认五个 kind（[04](04-判据-门禁与负例.md) §4.1），而 stage 名是项目自取的（`explore`/`harden`/`build`…）。没有 `kinds`，`na` 就没法算、"`harden` 起恢复"也无处落。**一个 stage 可以承担多个 kind**（`harden` 同时固化需求、设计、实现与评审），所以要写成集合；写成单值就必然要把 `harden` 拆成三段，等于用配置掩盖语义。

**`after` 是唯一的先后表达**：`stages[]` 的数组顺序**不承载语义**——否则 P15 的"DAG 无环"就是空转（列表天生无环）。每段用 `after: [stage_id]` 声明依赖，P15 校验每条边指向存在的 stage、图无环、所有 stage 从入口可达。**多 lane 不是 policy 的事**：`incremental` 的并行是同一 stage 下多张卡在派发层并行，policy 只描述阶段顺序；把并发塞进 policy 会让"阶段先后"与"同时跑几个"混成一个字段。

**自定义 policy 走同一份 schema**：用户（或项目模板）写一份 `policy` 数据，冻结进 baseline 即可；引擎不认识"preset 名"，只认识字段。preset 只是 bootstrap 时帮你把字段填好的一组默认值。

```yaml
policy:                          # 属于 baseline，冻结后随 baseline 一起签
  id: my-lite                    # 名字自取；preset 只影响初始值
  preset: prototype              # 可选：记录"从哪个 preset 起手"，便于解释
  stages:
    - { id: explore, kinds: [implement], after: [] }
    - { id: harden,  kinds: [requirement, design, implement, review], after: [explore] }
    - { id: deliver, kinds: [deliver], after: [harden] }
  gates:  { explore: [G_explore_exit], harden: [G_harden_exit], deliver: [G_deliver_exit] }   # gate 的 criteria 见 §1.1
  artifact_kinds: { prototype: throwaway, product: releaseable, throwaway: throwaway }
  switches:
    tdd:           { enabled: false }   # lite：关掉 TDD 事件序
    contract_first: false
    boundary_matrix: false
    coverage_trend: off
  regression: { mode: impact_set, max_age_days: 7 }
  review:     { sample_every: 5, sample_seed: 7 }   # 按单调卡序号取模（只对 kind≠review 的卡）：连续 N 张恰好抽 1 张；N∈[2,20]，不许 0/超大 N
```

> `stages[]` 里的 `kinds` 与 `after`、连同 `gates{}` 一起进 baseline 的 hash：改 stage 语义或先后顺序等于换算尺子，不能绕开签字。

### 1.1 三个 preset 的 gate 目录

**只有 stage 名的 preset 冻不了**：P15 要求每个 stage 至少一个 gate、每个 gate 至少一条已注册判据。下面三份目录就是 preset 的实体，`guarantee_delta` 与保证表都由它推出来（改这里等于换算尺子，必须签字）。

```yaml
# waterfall：五段各一个出口 gate，全部 all_of 且不可豁免
# 全局 core（spec_set.signed / provenance.present / assumption_set.signed）每个出口都判
G_req_exit:     { stage: req,     policy_mode: all_of, waivable: false,
                  criteria: [stage.requirement_complete, intent.restated_consistent,
                             alignment.examples_present, spec_set.signed, scope.present,
                             intent.explicit_for_risk, redteam.disposed,
                             provenance.present, assumption_set.signed] }
G_design_exit:  { stage: design,  policy_mode: all_of, waivable: false,
                  criteria: [stage.design_traceable, design.covers_spec, design.no_spec_creep,
                             design.alternatives_declared, node.acceptance_bound,
                             spec_set.signed, provenance.present, assumption_set.signed] }
G_build_exit:   { stage: build,   policy_mode: all_of, waivable: false,
                  criteria: [task.complete, assumption.disposed, mandate.revalidated,
                             spec_set.signed, provenance.present, assumption_set.signed] }
G_verify_exit:  { stage: verify,  policy_mode: all_of, waivable: false,
                  criteria: [review.round_bound, review.required,
                             spec_set.signed, provenance.present, assumption_set.signed] }
G_deliver_exit: { stage: deliver, policy_mode: all_of, waivable: false,
                  criteria: [design.code_matches, node.integration_listed, mandate.revalidated,
                             spec_set.signed, provenance.present, assumption_set.signed] }
```

```yaml
# prototype：explore 只判"东西真的跑起来过"，harden 全量（含评审）
G_explore_exit: { stage: explore, policy_mode: all_of, waivable: false,
                  criteria: [task.complete, spec_set.signed, provenance.present,
                             assumption_set.signed] }
G_harden_exit:  { stage: harden,  policy_mode: all_of, waivable: false,
                  criteria: [stage.requirement_complete, intent.restated_consistent,
                             alignment.examples_present, spec_set.signed, scope.present,
                             intent.explicit_for_risk, redteam.disposed, assumption_set.signed,
                             stage.design_traceable, design.covers_spec, design.no_spec_creep,
                             design.alternatives_declared, node.acceptance_bound,
                             task.complete, assumption.disposed, mandate.revalidated,
                             review.round_bound, review.required, provenance.present] }
G_deliver_exit: { stage: deliver, policy_mode: all_of, waivable: false,
                  criteria: [design.code_matches, node.integration_listed, mandate.revalidated,
                             spec_set.signed, provenance.present, assumption_set.signed] }
```

> **prototype 的 explore 只承接低风险卡**：它的 gate 只有 `task.complete` 与三条全局 core；`task.complete` 对"必须评审"类卡（`risk_flags` 非空 / 实现设计条款 / 与 release 相关 / 被抽样命中）要求 `review.required` 也 pass，而后者在 `implement` 适用、explore 的 gate 里没有它。所以**高风险卡与抽样命中的卡都不许停在 explore**，必须在 `harden` 收口——这是"explore 只判可观察"的边界，不是漏洞。

```yaml
# incremental：需求/设计在 lane 外做一次；lane 的并行属于派发层，不在这里
G_req_design:   { stage: req_design, policy_mode: all_of, waivable: false,
                  criteria: [stage.requirement_complete, intent.restated_consistent,
                             alignment.examples_present, spec_set.signed, scope.present,
                             intent.explicit_for_risk, redteam.disposed, assumption_set.signed,
                             provenance.present,
                             stage.design_traceable, design.covers_spec, design.no_spec_creep,
                             design.alternatives_declared, node.acceptance_bound] }
G_build_exit:   { stage: build,     policy_mode: all_of, waivable: false,
                  criteria: [task.complete, assumption.disposed, mandate.revalidated,
                             spec_set.signed, provenance.present, assumption_set.signed] }
G_verify_exit:  { stage: verify,    policy_mode: all_of, waivable: false,
                  criteria: [review.round_bound, review.required,
                             spec_set.signed, provenance.present, assumption_set.signed] }
G_integrate:    { stage: integrate, policy_mode: all_of, waivable: false,
                  criteria: [node.integration_listed, design.code_matches, mandate.revalidated,
                             spec_set.signed, provenance.present, assumption_set.signed] }
```

> **三份目录都要能冻出"三条保证全部保持"**（这是它们叫 `waterfall`/`prototype`/`incremental` 的最低条件）：上面每份都覆盖了保证 1/2/3 的全部判据，且 core 三条都在 `all_of`、不可豁免的 gate 里。自定义 policy 可以更少——少到哪条保证降级，`guarantee_delta` 会算出来给人签。

**什么时候配、谁来配**：

1. **立项时配一次**：选 preset（或直接写自定义 policy）→ 与判据/门禁/阈值一起组成 baseline → **人签冻结**；
2. 运行期**不换**：`stage_run` 记 `baseline_hash`，卡按当次 baseline 判——同一项目里不允许两张卡用两套 policy（否则读数不可比，`stage.gate_bound` 也失去意义）；
3. 要换 ⇒ **新 baseline**（走 `docs/04` §5.2 的方向不对称：收紧可即时，放宽必须事前签）。

**lite 档就是一份 policy + baseline**：少几个 stage、少绑几个 gate、关掉几个开关、判据参数放低——不需要新机制，也不需要新档位概念。

**但配置面必须让人看见"lite 放弃了哪条保证"**（[01](01-理论与边界.md) §1 的三条）：

| 配置 | 保证 1（记录忠实 + 做对） | 保证 2（没说清楚必须处置） | 保证 3（能证明做对） |
|---|---|---|---|
| `waterfall` | 强（复述 + 2 正 1 反 + spec_set 人签） | 强（assumption + 双向门） | 强（review.required + 证据 + verify） |
| `prototype` | explore 段 **`na`**（该 stage 只承担 `implement` kind）；`harden` 承担 `requirement/design/implement/review`，从那里起恢复 | explore 里可以记假设、开工不受阻；但**出 explore 前必须签 `assumption_set`**（core 检查点覆盖每个 stage 出口） | explore 段只判「可观察」；`harden` 起恢复（harden 承担 `review` kind） |
| `incremental` | lane 内强；跨 lane 靠集成清单 | lane 内强 | lane 内强；集成 gate 必过 |
| 自定义 / lite | **取决于你绑了哪些 gate**：不绑 `alignment.examples_present` ⇒ 保证 1 降级 | 不绑 `assumption.disposed` ⇒ 保证 2 降级（**签名集合仍由 core 的 `assumption_set.signed` 保**） | 不绑 `review.required` ⇒ 保证 3 降级 |

> **这张表是 preset 的"结果"，不是规则**：真正判定"某条保证有没有降级"的是 [04](04-判据-门禁与负例.md) §4 的「保证」列——逐条看该保证下的判据有没有达到 §6 的**有效绑定**（`all_of` + 不可豁免 + stage 适用），工具机械算出 `guarantee_delta`；人只能看，不能改（改了也对不上）。

> **"不能省"与"可以降级"说的不是同一层，别混**：
>
> - **机制不能省**（事件必须记）：`restatement`、`assumption`（含 `blast_radius`/状态）、`evidence`、`verify`、`baseline` 本身——这是三条保证的底座，删了就不是 SDO 了；
> - **判据绑定可以降**（可以 `na`/不查）：`alignment.examples_present`、`assumption.disposed`、`design.alternatives_declared`、`review.required` 等**非 core** 判据可以不绑，代价是那张"保证等级表"里对应的保证降级；
> - **core 判据只能保留或加强，永不删除或放宽**（"收紧/放松"对二值判据没意义）：清单按名字钉死，**共三条**——`spec_set.signed`、`assumption_set.signed`、`provenance.present`（[04](04-判据-门禁与负例.md) §5.2 第 6 条）；**每个 policy 的 gate 集都必须包含，且凡是适用的 stage 出口都要有效绑定**（`all_of` + 不可豁免 + stage 适用）——绑在「这条判据是 `na`」的 stage 上、放进 `any_of`/可豁免的 gate、或**只在某一个 stage 绑过**，都等于没查，P15 直接拒冻；policy 结构上缺该 kind 也拒冻，**没有「写降级就过」的后门**（lite 必须留着绑 core 的那个 kind）。"防篡改"由 `verify`（hash 链/父链/kind 闭包）与表约束承担，没有开关、不参与 policy，所以不算判据、也不需要进 gate 集。
>
> 所以"lite = 少查"成立的前提是：**记还是要记，只是不拿更多判据去查**；而 core 判据一条都不能少。

**阶段出口必须有 gate**：policy 的 `gates` 配置里每个 stage 至少绑一个 gate（`stage_exit` 类），`stage_run(gate_id, baseline_hash, criteria[])` 记录当次读数，`stage.exited.verdict` **由 gate 读数算出，不能手填**（判据 `stage.gate_bound` 守这条）。没有绑定 gate 的 stage ⇒ 该阶段无法“算完”，`verify` 判红。

**铁律：加一种 policy，判据总数不许增加。**（验收读数）

## 2. 原型的"转正"必须是一次签字

`artifact.kind` 是所有产物的一等属性：

| kind | 能进发布证据 | 转换 |
|---|---|---|
| `prototype` | **不能** | 必须 `decision(graduate)`：引用原型产物 + 新 frontier，重新绑定证据 |
| `product` | 能 | — |
| `throwaway` | 不能 | 只能被引用，不能被交付 |

v1 真正的病不是"写原型"，而是**原型代码悄悄转正、没人签字**。这条只有数据模型能守。

## 3. 开发阶段方法论：只留"能变成时序断言"的

| 条目 | v2 处置 | 判据形态 |
|---|---|---|
| 需求工程 | 保留，但用"**每条条款必须被一条判据或一个场景消费**"替代歧义打分 | `spec` 无消费者 ⇒ 红 |
| 设计方法（结构化/OO/演进式/移植） | **不进引擎**（对人有用、对执行面无判据） | 只留两条：设计产物与代码一致（指纹）、跨模块承诺有 consumer |
| TDD | 策略开关 + **事件序判据** | `evidence(红) → evidence(绿) → task.done`，顺序反了即红 |
| 契约先行 | 策略开关 | `contract.defined`（即 `spec.kind='contract'`）必须在第一次代码写事件之前 |
| 构造 profile（5 选 1）、八维评分、审讯提问模板 | **退休** | 理由：代理指标，Goodhart 温床（v1 曾逼人给已否决需求灌水） |

**TDD 的可判形态**（v2 相对 v1 的升级）：

```text
要求：同一卡上存在事件序列
  ev(evidence, label='red',   ref=commit_a)   ← 先失败
  ev(evidence, label='green', ref=commit_b)   ← 后通过，且 a 是 b 的祖先
  ev(task.done)
缺 red 或顺序错 ⇒ 判红。v1 只在手册里写"要 TDD"，没人能验。
```

## 4. 测试方法论：分配"谁消费它"

| 方法 | v2 位置 | 可机械的部分 |
|---|---|---|
| 黑盒（等价类/边界/决策表） | `scenario` 的参数化夹具 | **边界矩阵**：数值参数必须有 min−1/min/max/max+1 四格 |
| 白盒（语句/分支覆盖） | **证据**，不是判据 | 覆盖率趋势不得下降（防删测试过门禁） |
| 集成 | `contract` + 集成 gate | 跨 lane 的承诺必须有 consumer 且被验证 |
| **回归** | **重点强化** | `regression_set(change)` = 受影响的 criterion 集合（由 claim 依赖图算），合并后必须重跑并更新 frontier |
| 变异 | 保留 | 变异记录落 `evidence`，绑 frontier；两次读数不一致 ⇒ 都留、标 `disputed` |
| 探索式 / 可用性 | 人审 `scenario` + 签字 | 无机械面，不硬编判据 |

**回归集为什么是重点**：v1 只有"跑全量"这一招——慢，且挡不住"改 A 坏 B"。v2 用 frontier + 依赖图算出**受影响的判据子集**，既快又准，因为它绑的是"哪条声明受影响"，不是"哪个测试文件被改"。

## 5. 退休清单（明确不搬）

| v1 的东西 | 处置 | 理由 |
|---|---|---|
| 4 套 process yml | 合成 3 份 policy 数据 | 代码不变，只换数据 |
| 方法包（structured/oo/evolutionary/porting/none） | 退休 | 无机械判据，只制造必产项 |
| 构造 profile + 最小必产项 | 退休 | v1 膨胀源 |
| 八维歧义评分 / 审讯提问模板 | 退休 | 代理指标，逼灌水 |
| 每轮状态块注入 | 退休 | 由 UI + 视图取代（[05](05-观测与交互.md)） |

**保留并升级**：TDD（→ 事件序）、契约先行（→ 时序）、变异自证（→ 绑 frontier）、覆盖率消费（→ 趋势判据）。

## 6. 不变式

1. policy 只声明"绑哪个 gate、要哪种产物、开哪个开关"，**不声明"怎么做"**；
2. 新增 policy 不得引入新判据（只能复用既有判据）；
3. `prototype` / `throwaway` 产物不得出现在发布证据集；
4. 策略开关必须可查：卡 → `stage_run.baseline_hash` → baseline 里的 `policy`（不单独在卡上存一份，避免两处真源）；
5. 退休清单里的条目若被重新引入，视同新需求，需要 intent + 判据 + 负例。

## 7. 验收读数（M1）

- 同一份代码分别用 `linear` 与 `spike` 跑：**判据数量相同**，只有 gate 绑定不同；
- 一张卡缺"红"证据却标 `tdd` ⇒ 门禁红并指出缺哪条事件；
- 原型产物被塞进发布证据集 ⇒ 红；
- 数值参数只测 min/max、漏 min−1/max+1 ⇒ 边界矩阵红。
