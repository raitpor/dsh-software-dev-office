# 代理池与生命周期

> 子代理是**资源**，不是一次性的执行者。目标是三件事：**能复用**（不重读项目代码）、**能自压缩**（不因上下文耗尽就新起）、**只在无法唤醒时退役**。
> v1 的反面证据：160 个子会话、一次派发刷 82 条 skip 事件、复用靠"猜会话还活着"、代码变动就整库重读。

## 1. 状态机

```text
        ┌──────── wake ────────┐
        ▼                      │
   idle ──claim──▶ busy ──release──▶ idle
     │                │
     │                └─watermark≥70%─▶ compacting ──▶ idle
     ├── capability_changed / idle_too_long / over_pool ──▶ parked
     └── probe_failed×3 ─────────────────────────────────▶ dead
```

| 状态 | 含义 | 可分配 |
|---|---|---|
| `idle` | 空闲、能力匹配、可接活 | ✅ |
| `busy` | 手上有在飞卡 | ❌（直到 release） |
| `compacting` | 正在自压缩，暂不接活 | ❌（短暂） |
| **`parked`** | **暂时不可分配**（能力变了 / 空闲太久 / 超池上限） | ❌，但**可唤醒** |
| **`dead`** | **无法唤醒**——唯一的退役形态 | — |

> **`parked` 不是退役。** v1 把"掩码指纹变了"直接当退役理由，于是池子里堆满永远不会被选中的僵尸，每次派发还要逐个评估。v2 把这类情形全部归到 `parked`，可唤醒。

## 2. 表

```sql
CREATE TABLE agent (
  id                 TEXT PRIMARY KEY,     -- 子会话 id
  capability_hash    TEXT NOT NULL,        -- 能力票据的哈希（不是角色名）
  project_snapshot   TEXT NOT NULL,        -- 绑定的 project frontier + commit
  state              TEXT NOT NULL,        -- idle | busy | compacting | parked | dead
  context_watermark  REAL NOT NULL,        -- 0..1，最近一次读到的用量
  last_active        TEXT NOT NULL,
  probe_failures     INTEGER NOT NULL DEFAULT 0,
  reuse_count        INTEGER NOT NULL DEFAULT 0,
  parked_reason      TEXT
);
CREATE TABLE agent_probe ( agent_id, at, ok, detail );          -- 生存探测记录
CREATE TABLE agent_compaction ( agent_id, at, before_tokens, after_tokens, kept TEXT );
```

## 3. 复用判定（顺序固定）

1. **存活**：`probe` 通过（一次最小往返；3 次失败才判 `dead`）；
2. **无在飞卡**：`state='idle'`；
3. **能力匹配**：`capability_hash` 相同（能力变了 ⇒ `parked`，不是 `dead`）；
4. **水位**：`context_watermark < 70%`；否则**先自压缩**再判；
5. **项目快照**：`project_snapshot` 落后时，**注入增量**（改了哪些文件 + `diff --stat`），**不重读全库**。

命中即复用；不命中且池未满 ⇒ 新建，并记原因（`new(reason)`）。**一次派发只写一条聚合事件**。

## 4. 自压缩（子代理自己发起）

- **触发**：水位 ≥ 70%（可配），或子代理自己判断需要；
- **动作**：`sdo_act(action=compact)` —— 是**子代理的动作**，不是宿主的自动行为；
- **必留四类**：任务目标 / 已改文件与 diff 摘要 / 未决问题 / 最近一次验证读数；
- **绝不动 DB 里的事实**：`claim`、证据、读数都在库里，压缩的只是对话；
- **落事件**：`agent.compacted { before_tokens, after_tokens, kept[] }`。

> 这是"避免上下文耗尽就新起"的关键：**耗尽前压缩，而不是耗尽后新建**。

## 5. 退役：唯一条件是"无法唤醒"

| 触发 | 判定 |
|---|---|
| 连续 **3 次**探测失败（间隔 30s） | `dead` |
| 宿主明确返回"会话不存在" | `dead` |
| 能力票据变化 / 空闲超阈值 / 超池上限 / 项目快照过期 | **`parked`**（可唤醒），**不退役** |

退役必须落 `agent.retired` 事件 + 探测记录（证据），并进 `v_gaps` 供人复核——**退役是一条需要解释的事**。

## 6. 池容量

| 参数 | 缺省 | 超限行为 |
|---|---|---|
| 活跃（idle+busy） | **8** | 新建前先 `parked` 最久未用的 idle |
| `parked` 总数 | **32** | 最久未用的 `parked` ⇒ `dead`（先探测一次） |

**不因池满而杀活跃代理**；只 parked，必要时才退役。

## 7. 视图与度量

`v_agents`：`id, state, watermark, project_snapshot, last_task, last_compaction, reuse_count, parked_reason`。

| 指标 | 用途 |
|---|---|
| **复用率** = 复用 / 总派发 | 核心：低于 60% 说明判定或能力匹配有问题 |
| 平均水位 | 长期 > 80% 说明压缩太晚 |
| 压缩次数 / 代理 | 过低 = 没在自管理；过高 = 任务切得太碎 |
| **僵尸数**（`parked` > 7 天） | 应为 0；不为 0 说明没人清理 |
| **退役数** | 应趋近 0（只有真的唤不醒才退役） |

## 8. 不变式

1. **退役只由 `unwakeable` 触发**；其它情形一律 `parked`；
2. 复用前必须过四项校验（存活 / 空闲 / 能力 / 水位）；
3. 压缩不得丢弃任何 DB 事实的引用；
4. 池满只 `parked`，不杀活跃代理；
5. 一次派发只写 **1 条**聚合事件（复用命中 / 新起 + 原因），不逐候选刷事件。

## 9. 验收读数

- 同一能力连续派两张卡 ⇒ **第二次复用同一会话**，且注入的是增量（`diff --stat`）而非全库重读；
- 水位打到 70% ⇒ 出现 `agent.compacted`，压缩后仍能完成一次 ping 并继续接活；
- 能力票据变化 ⇒ 状态 `parked`（**不是 `dead`**），唤醒探测通过后复用成功；
- 宿主删掉会话 ⇒ 3 次探测失败 ⇒ `dead`，有事件 + 证据；
- 连续派 100 张卡：活跃 ≤ 8、`parked` ≤ 32，**新起数显著低于卡数（复用率 ≥ 60%）**。
