## 2. 落点一：候选重试（修 `DEF-185`）

**改前（形状）**

- `src/domain/pool.ts`：`const taken = reuseCandidateOrder(pool).find((child) => blockedReasonOf(child) === undefined)`
  ⇒ 只产出一个 `reuseChildId`；
- `src/integration/dispatch.ts`：一次 `runtime.sendMessage(...)`；抛错 ⇒ `reuseFailed` ⇒ 直接走"新起一个"。

**改后（形状）**

1. `admitDispatch` 仍然只占**一个池位**，但把过闸门的候选按同一顺序整条交出去：
   `dispatch.push({ task, reuseChildId, reuseCandidates })`（`reuseChildId` 恒为队列第 0 项）。
2. `startDispatch` 按 `reuseCandidates` **逐条** `sendMessage`：
   - 成功即采用（`reused=true` + 该 id，`messageReceipt` 照旧）；
   - 每一条失败进 `reuseAttempts: { childSessionId, reason }[]`（**宿主原话**）；
   - 全部失败才新起；`reuseFailed` 在单候选时**逐字保留**宿主原话（多候选才带 id 前缀），
     这样既有回执与 `M158-01` 的口径不变。
3. `src/index.ts` 把 `reuseAttempts` 的**每一条**落成 `reuseSkipped` 行（并落独立事件
   `dispatch/reuse-skipped`），行文带 ASCII 前缀 `delivery-failed: `。

**改前/改后真机读数对照**

| 场景 | 改前（seq 5298 的真机形状） | 改后（同一形状下新代码的行为） |
|---|---|---|
| 候选数 | 只投 1 个（`.find` 的结果） | 投 **N 个**（`reuseCandidates` 全队列，N=同父可复用候选数） |
| 候选 1 投不进去 | 直接新起；`dispatch/started.reuseSkipped` = 那 1 条（且只在 `reused=false` 时才有） | **接着投候选 2**；成功则 `reused=true`，候选 1 仍落 **1 条** skip（带宿主原话） |
| 全部投不进去 | 1 条 skip（只记第 1 个候选） | **每个候选各 1 条** skip，然后才新起 |
| `idle>0` 与 `reused=false` 并存 | 无解释 | 候选队列 + 逐条 skip ⇒ 有解释（见落点二） |

## 3. 落点二：投递失败进读数（账实一致）

**做法（判据仍然只有一处）**：`reuseBlockedReason` 在掩码判据之后追加一条投递失败判据：

```ts
if (deliveryFailed !== '') return `上一次投递被宿主拒（宿主原话：${deliveryFailed}）⇒ 不再挑它`
```

`deliveryFailed` 来自折叠：`foldPoolChildren` 读 `dispatch/started.reuseSkipped` 与独立事件
`dispatch/reuse-skipped`，只认 `delivery-failed: ` 前缀的那几行，标到**被拒的那个孩子**身上
（孩子认不出就不凭空造）。成功投递到它会**清空**这个标记（自愈路径）。

于是：

- 投递失败的孩子从 `idle` 挪进 **`unusable` 桶并带宿主原话**；
- `unusable` 不占池位（`R-1` 的既有口径）⇒ `freeSlots` 不会被投不进去的会话吃掉；
- **没有放宽任何闸门**：掩码/观测/持卡/余量的判据一个字没动，只是多了一条**更严**的。

**为什么不新增 `deliveryFailed` 计数桶**：`dispatch/started.buckets` 的形状由
`dispatchFace.dispatchReadingFields` 定死（八桶），那个文件不在本卡写范围内；往 `PoolBuckets`
加字段会被静默丢掉（读数写了等于没写）。任务卡允许两种形态之一，因此走"进 `unusable` 桶并带原因"。

**已知代价（如实写）**：这条判据是**保守的** —— 一次宿主拒绝就让该会话不再被挑（除非之后确有成功投递）。
宿主说 `is unavailable` 时这是对的（会话真的没了）；若把它当成瞬时故障，代价是那个会话被闲置。
选择这个方向的理由：不这么做就会回到 `DEF-185` 的病态（同一个投不进去的候选每轮都被挑中）。
前缀识别也只认新行：**旧台账里那批不带前缀的 `reuse-skipped` 不被重新解释**（旧格式与闸门拒在同一承载上
没有稳定字形可分，硬猜就会把"闸门拒"说成"投递失败"）。

## 4. 落点三：掩码指纹改成**两段式**（修 `DEF-194`，不回归 `R-7`）

```ts
face(role)      = (READ_ONLY_INSPECTION_TOOLS ∪ card.allow) − card.deny      // 逐角色段：有效面
globalSegment   = hash(EXECUTOR_DENIED_TOOLS ∪ READ_ONLY_INSPECTION_TOOLS)  // 全局段：整体项
fingerprint     = `2:` + hash(`v2` ‖ face(role) ‖ globalSegment)[0..12]
```

**为什么不是"减法公式"**（任务卡点名的那条）：`EXECUTOR_DENIED_TOOLS` 里的名字**大多不在**任何角色
allow 里 ⇒ 用 `(面 − 禁令)` 去算，从空集里减掉是**空操作** ⇒ 禁令变化时指纹不变 ⇒ 旧会话仍握着被禁
工具却被判可复用（`R-7` 回归）。**全局段作为整体项**没有这个问题：禁令集变一个字节，8 个角色一起变。

**为什么 `deny` 是"减"而不是"加"**（`DEF-194` 的真正病根）：本仓 8 个角色的 `deny` **全部**是冗余项
（逐条都不在自己 allow 里，现算见下），把它们当项加进哈希 ⇒ 改一条空操作就改指纹 ⇒ 整池作废。

**现算（`node --input-type=module -e` 读 `listRoleCards()`）**

**两条如实说明（评审请重点看这两格）**

1. **`developer` 与 `tester` 的 v2 指纹相同**，因为两者的 `allow` 列表逐项相同、`deny` 又全是冗余项
   ⇒ **有效面确实相同**。指纹的口径是"工具面"，不是"角色身份"：池按 `byRole` 分桶，跨角色复用不可能
   发生，所以这里合并**不削弱**任何判据。若将来两个角色的面分化，指纹自动分开。
2. **口径换版 ⇒ 旧会话不被承认**：台账里旧值是 12 位十六进制、无版本前缀，读侧按"版本未知"处理，
   走落点五的回溯判定（下一节）。这是**一次性**代价，且方向保守 —— 与 `DEF-194` 抱怨的
   "每注册一个工具就作废整池"不是同一件事（后者随工具登记**反复**发生）。

## 5. 落点五：v2 回溯的**诚实边界**（不许声称 100% 无损回溯）

**允许做的事**：旧事件里已经存了两份面 —— `dispatch/started.sdoAllow`（当时的 SDO 流程面白名单）与
`dispatch/started.deny`（当时**实际下发**的完整 deny 面）⇒ 不用重建池，也能把"这个会话当时拿到的是什么面"
现算出来。`maskBacktrack(role, { sdoAllow, deny })` 就做这件事。

**证成条件（三条全过才放行）**

1. **今天的禁令集 ⊆ 旧事件的 `deny`** —— 旧事件没有当时禁令集的副本，只能用"它当时已经把今天这些禁令
   都挡了"来证成"禁令没变过"；缺一条就判 **版本不可比 ⇒ 不复用**，理由里点名缺哪几条；
2. **今天的角色 `deny` ⊆ 旧事件的 `deny`** —— 否则旧会话可能握着今天已经禁掉的工具；
3. **可回溯子面相等**：`(只读检视面 ∪ 旧 sdoAllow) − 旧 deny` 与今天的 `face(role)` 在
   `sdo_*` ∪ 只读检视面上逐项相同。

**证不成 ⇒ 保守不复用**，理由走既有的「掩码已变更（旧口径指纹没有版本号，且回溯判不了：…）」——
与池视图**逐字同源**（判据只有 `reuseBlockedReason` 一处）。

**真台账证据：证明"保守"不是纸上推演。** seq 5298 的 `deny` 面只有 22 条，其中属于今天禁令集的只有
`subagent` 与 `exit_plan_mode` 两条；今天禁令集共 11 条 ⇒ 它创建之后**确实**又禁了 8 条：

```
今日禁令集里**不在** seq 5298 deny 面的：
subagent_fork / workflow / plugin_manager / memory_forget / technique_forget
/ failure_forgive / create_goal / update_goal
```

⇒ 那个会话很可能握着 `plugin_manager` / `memory_forget` / `create_goal` 一类今天明确禁止的工具。
判它"版本不可比 ⇒ 不复用"是**正确**的，不是过度保守。
