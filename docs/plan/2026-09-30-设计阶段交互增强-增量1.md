# 设计阶段交互增强 · 增量 1 实施规格（2026-09-30）

> 起因（用户原话）：**"设计阶段明显交互不足，完全由 agent 自己脑补推进，未与我交流，也没有明确的设计文档供我审查；
> 页面 agent 自由发挥没问我要什么风格、有哪些栏目、如何排布。而且也应该接入软件工程的设计方法论。
> 实际这个阶段也应和需求阶段一样反复与我交流。"**
>
> 已确认的四项决定：
> 1. **分两步**：增量 1 = A（交互闭环）+ D（设计文档）+ C（界面视图）；增量 2 = B（方法论方法包）。
> 2. **方法论由用户选**：完成需求阶段后 SDO 必须提问「选哪种设计方法」，并**由模型结合需求给出推荐**。
> 3. **界面**：风格 + 栏目 + 布局**三者都必须用户确认**才允许放行。
> 4. **节奏**：先给「完整设计草案 + 问题清单」→ 用户一次性批注 → 按批注迭代。

## 1. A：设计交互闭环

### 1.1 新增 `sdo_design` 动作

| 动作 | 入参（要点） | 行为 |
|---|---|---|
| `grill` | `round?` | 用**缺口检测器**生成设计问题（见 1.2），落盘并返回「草案 + 问题清单」 |
| `answer` | `id`、`choice`、`note?` | 记录用户答复（含"自定义"），关闭该问题；写 journal |
| `confirm` | `target`（元素/契约/界面条目 id）、`note?` | 打**用户确认**戳（`confirmedAt` + 依据），未确认的关键条目不允许放行 |
| `issues` | `state?: open\|all` | 列出开放/全部设计问题（含我的建议与代价） |
| `render` | — | 生成 `docs/DESIGN.md`（见 §3） |

### 1.2 缺口检测器：只问「agent 不该猜」的点

**必须复用**现有问题存储与 `gates.ts` 的 `questions`/`issueClosure` 机制（**不要另造一套**）。
检测器按「项目事实 → 缺失项 → 生成问题」机械推导，至少覆盖：

- **形态与部署**：单体/分层/微服务；部署目标与拓扑；外部依赖引入与否
- **数据**：存储选型；一致性与事务边界；数据保留/迁移策略
- **并发与性能**：并发模型；性能预算（延迟/吞吐）；超时与重试策略（是否幂等）
- **错误与可观测**：错误处理口径；日志/指标/告警要求
- **演进**：是否允许破坏性变更；兼容窗口；技术债容忍度
- **界面（⚠️ 仅当「含 UI」判定为真，见 §2.1）**：视觉风格；页面栏目；布局排布；响应式断点；无障碍要求 —— 判定为假时**一个问题都不生成**

每题输出：**选项 + 每个选项的代价 + 我的建议（含推荐理由）+ 默认值**（对齐 grill 风格）。

### 1.3 强制交流（防止再"脑补"）

1. **门禁**：G3 判据新增「开放设计问题 = 0」（见 §5）。
2. **注入块**：架构阶段（`phase === 'architecture'` 或流程等价阶段）在 systemPrompt 注入块里**主动提示**
   「有 N 个待你确认的设计问题，先 `sdo_design action=grill` / `action=issues`」——
   让模型无法静默推进（这是"未与我交流"的根因所在）。
3. **方法论选择问题**：需求阶段门禁（G2）通过后、进入架构前，SDO **必须**提出一个问题：
   「本项目用哪种设计方法：结构化 / 面向对象 / 敏捷-演进式 / 组合」，
   并**必须附带模型基于需求给出的推荐与理由**；未回答则 G3 不放行。
   （方法包本身的产物与检查属增量 2；本增量只保证"问得出来、答得进去、拦得住"。）

### 1.4 节奏：草案 + 问题清单 → 批注 → 迭代

`sdo_design action=grill` 的返回体分两段：
① **完整设计草案**（按视图组织，标注每条的来源需求与置信度）；
② **问题清单**（带建议）。
`answer` 后重跑 `grill` 即产出**增量差异**（「本轮变化 / 仍未决 / 需要你重看」）。

## 2. C：界面/交互设计视图（第 6 个视图）

### 2.1 「含 UI」判定 —— 唯一真源是需求，不是模型的判断

**规则（用户明确要求）：不是所有项目都有页面；只有"需求里要写页面"时，`ui` 视图才作为门禁条件。**

判定必须在**每次门禁检查时从需求真源现算**（不缓存、不看模型自述、不按项目类型猜）：

```text
含UI :=  任一需求条目声明了界面/页面面（kind: ui）
      OR 项目级 surfaces 声明含 web/desktop/mobile（在 G0/G2 由用户选定）

判定为真 → ui 视图进入门禁：必须风格 + 栏目 + 布局齐备且经用户 confirm
判定为假 → ui 视图与 ui.* 判据一律 N/A（**不是失败**，也**不是通过**——必须在门禁回执里显式标注 N/A 及理由）
```

补充口径（避免两端都出错）：
- **判真但 ui 视图为空/未确认** → `ui.confirmed` **判失败** ✓（该做没做）
- **判假却写了 ui 视图** → `ui.*` 判据仍 N/A ✓，但该视图的追溯 `requires` 必须指向真实需求，
  否则由既有的**追溯孤儿检查**抓出来（不额外发明判据）
- 需求在后期**新增**了 UI 需求 → 判定立刻翻真 → 下一次 G3 检查即要求确认（不需要人工开关）
- `docs/DESIGN.md` 的 §5「界面方案」在判假时**不省略也不留空**，而是明确写「不适用：本项目的需求未声明界面/页面面」+ 判定依据 ✓

**如果你更想用别的触发字段**（例如只在需求上加 `ui: true` 标记、或干脆用项目级开关），说一声我改 —— 这里我按"需求声明界面面 OR 项目 surfaces 声明"来实现。



新增 `sdo_design action=view view=ui`，字段：

```yaml
id: UI-001
style: { source: follow-host | minimal | enterprise | custom, tokens: {...}, rationale: "…" }
screens:
  - id: SCR-001
    name: 需求列表
    columns: [ { name: 编号, kind: text }, { name: 标题, kind: text }, { name: 状态, kind: badge } ]
    layout: { grid: "1fr 2fr 80px", regions: [header, filter-bar, table, pager] }
    interactions: [筛选, 排序, 分页, 行点击进入详情]
    states: { empty: "…", error: "…", loading: "…" }
    requires: [REQ-003, REQ-007]
breakpoints: [ { name: sm, width: "<=640px", changes: [表格改卡片] } ]
accessibility: { contrast: ">=4.5:1", keyboard: true, screenReader: "…" }
confirmed: false   # 风格/栏目/布局三者都必须 true 才放行
```

**确认强度**：`style`、每页 `columns`、每页 `layout` **三者都必须**由用户 `confirm`（§1.1）才允许进入开发；
`requires` 必须指向真实需求（追溯图孤儿检查会抓）。

## 3. D：可审查的设计文档 `docs/DESIGN.md`

由 `sdo_design action=render` 生成（**派生视图，绝不反向写入台账**），固定章节：

1. 范围与关键约束（来自 G0/G1）
2. 视图与元素（context/component/data/runtime/deployment/**ui**）
3. 接口与契约（含超时/重试/幂等口径）
4. 关键决策（ADR：决定 + 被否决备选 + 后果）
5. 界面方案（风格 / 页面栏目 / 布局 / 响应式 / 无障碍）
6. 追溯矩阵（需求 ↔ 设计元素/契约/界面条目）
7. **待你确认的问题清单**（含我的建议与代价）
8. 与上一版差异（本轮新增/变更/作废）
9. 未决与已知风险

## 4. i18n 与代码纪律（硬要求）

- **所有**新增用户可见文案走语言包：`zh-CN.yml` 与 `en.yml` **同时**补齐；
  段名沿用现有 `uiGates.*` / `uiTools.*` / `uiDescribe.*` 等；**en 必须覆盖基准包全部键**（守卫测试会拦）。
- **禁止在代码里硬编码中文/英文文案**（棘轮基线为 0，加一个字面量就红）。
- 不引入新依赖；不改 `presets/` 结构（除必要行）。
- 台账路径、工具名、动作名等**标识不翻译**。

## 5. G3 新增判据（增量 1 落地的部分）

| 判据 id | 内容 |
|---|---|
| `design.no-open-questions` | 开放设计问题 = 0（复用 `issueClosure`） |
| `design.confirmed` | 关键条目（元素/契约/**界面条目**）均有用户确认戳 |
| `design.doc` | `docs/DESIGN.md` 存在且包含上述 9 章（增量 1 时的章数；增量 2 起为 **11** 章，见 `DESIGN_DOC_SECTIONS`） |
| `design.method-chosen` | 方法论选择题已回答（增量 2 再校验产物齐备） |
| `ui.confirmed` | **仅当 §2.1 判定为真**：风格 + 每页栏目 + 每页布局均已 `confirm`；判定为假时本判据 = **N/A**（回执显式标注 N/A + 理由，不计失败） |

（门禁文案一律走语言包；未实现的检查器必须**判失败**，不允许"查不到就算过"。）

## 6. 验收（必须给出可核对的证据）

```bash
./node_modules/.bin/tsc -p tsconfig.json     # 0 错
node scripts/run-tests.mjs                   # 原有 142 全绿 + 新增用例全绿
```

新增测试至少覆盖（**判据要有区分度**，不能写永远为真的断言）：
1. `grill` 生成的每个问题都带选项、代价、建议 —— 且**未回答时 G3 不通过**、回答后通过（两方向都测）。
2. `confirm` 之前 `ui.confirmed` 判据**不通过**；`style`/`columns`/`layout` 三项**缺任一项**仍不通过。
3. **含 UI 判定双向**：需求声明了界面面 → 未确认时 `ui.confirmed` **失败**、确认后通过；
   **需求未声明界面面 → `ui.*` 判据为 N/A（既不是失败也不是通过，回执里有 N/A + 理由）**。
4. `render` 产出的 `docs/DESIGN.md` 含 9 个章节标题 + 至少一条追溯矩阵行 + 待确认清单。
5. 方法论选择题：未回答 → G3 不通过；回答后通过（且返回值里含模型推荐）。
6. i18n：新键在 `en.yml` 全部有对应（现有守卫测试覆盖）；无新增硬编码文案（棘轮）。
