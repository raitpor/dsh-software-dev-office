## 二、为什么"越修越肿、达不到理想效果"（诊断，按证据排序）

### 2.1 投入流向"可机械化证明"的一面，而不是用户真正痛的一面

- 近四批任务书里：**「侧边栏」0 次、「问答」0 次**；而缺陷台账里讲签字/问答/侧边栏的就有 **8 条**。
- 第十三批开工时的四条现场缺陷（`DEF-110` 签字问答时好时坏、`DEF-112` 签字接受"工作指令"、`DEF-113` 只读卡误造交付包、`DEF-111` 落点写错）**都不在任何一批任务书里** —— 它们是**真机撞出来的**。
- 缺陷标题粗分（113 条时的统计）：**一致性/判据/报告类 ≈ 41**，**用户可见流程类 ≈ 28**，其余是机制洞。也就是说：**约三分之一精力在"证明自己对"**。

⇒ 结论：任务书的来源是"驾驶舱对代码的机械自审"，它**只看得见能形式化的东西**（判据、登记表、算式、基数），看不见"用户签字时侧边栏弹不弹"。

### 2.2 机制只增不减，而且被"行号/计数"耦合钉死

- 每一次修缺陷的交付物里都包含**新判据 / 新守卫 / 新登记表 / 新预算**，但**没有任何一次批次的 DoD 是"删"**。
- 棘轮的具体代价（本会话实测）：
  - 加两条判据把 `m23` 的体积预算撑爆（7900 → 8006，红）；
  - 改一处注释让散文普查红（`M189-08`），要跑刷新脚本；
  - `m189` 挪一行就让**按 `file:line` 钉身份**的登记表红（`:395→396→397`，一夜修两次）；
  - 改 `DEF-100` 要让 **34 处**测试证词重写成读数形态。
- ⇒ **每次改动的成本 ≈ 系统规模**。这就是"积重难返"的物理来源。

### 2.3 验收口径 = "证据产出"，目标被替换（Goodhart）

- 每条的 DoD 是：钉红 / 守卫 / 变异四件套 / 复原自证 / 豁免面清单 / `REQ-060` 自查格 / 报告。
- 结果：一批 13 条，**报告写了 526 行**；我自己的批次数值还自相矛盾（`DEF-109`：三套基数并存、≥26 项没进算式）——**证据本身成了新的缺陷源**。
- 台账里 `M190-01` 能被"正文全写 x 的水表"整表通过 —— 机制自己早就记下了。

### 2.4 两类风险塞进同一个包、同一个节奏

- **判定核**（纯函数、好测）：`gates`/`discipline`/`writeScope`/`regression`/`records`…
- **宿主集成**（只能真机撞）：侧边栏问答、子代理池、角色掩码、`sdo_deliver` 权限、签字通道。
- 两者共用一个发布节奏 ⇒ 后者的坑（`DEF-110/112/113`、认领粘性、reviewer 池一槽）反复被"登记为已知限制 / 交驾驶舱"推迟；**而理想效果恰好在这一层**。

### 2.5 自指开销

用 SDO 开发 SDO（60 条 REQ、8 道门禁、G2 签字、评审、缺陷台账）⇒ 每批既要付机制成本，又要付流程手续费（7,297 行规划文档本身就是证据）。

## 三、重新开发 / 重构会不会更好？（评估）

**结论：按现状重写，效果大概率**不会**更好；但"先划边界、再重构"会明显更好。**

### 3.1 重写解决不了的三件事

1. **入口不变**：任务书仍由机械自审产生 ⇒ `41/113` 那类"一致性缺陷"会在新代码上重新长出来。
2. **宿主集成不变**：`DEF-110/112/113` 是**宿主/角色面**问题，重写插件不改变宿主行为，仍要真机冒烟。
3. **只增不减的 DoD 不变**：新代码会重新积累登记表/棘轮/报告仪式。

### 3.2 重写会丢掉的资产

`1,422` 个用例、`120` 条缺陷里的 96 条已修教训、`2,783` 个语言键、`64` 条判据、进程数据、`3,400+` 条 journal 事件与证据面 —— 且**记录本身不够可信**（`DEF-109`）⇒ 迁移要逐条重验，成本接近重做。

### 3.3 真正该拆的边界，本仓已经存在

- `src/domain` **32.7k 行 / 60 文件**，其中很多是**零依赖纯判定**：`discipline`（100 行）、`writeScope`（234）、`scopePaths`（218）、`process`（123）、`acceptance`（395）、`trace`（787）。
- 昂贵且反复失血的是 `index.ts` + `office.ts`（**9.2k 行**）：回执拼装、工具面、派发编排、i18n 全揉在一起 —— **UX 缺陷也全在这里**。

### 3.4 建议路径（成本递增，先做便宜的）

1. **第 0 步（1–2 天，spike）**：把 `discipline` + `writeScope` + `scopePaths`（约 **550 行**、零依赖）真抽成独立包，用现有用例跑通。
   - 抽得动 ⇒ 判定核可分离 ⇒ 走"核保留 + 外壳重写"；
   - 抽不动 ⇒ 问题是**耦合**而非"代码旧" ⇒ 只做逐步解耦，更不该整体重写。
2. **第 1 步（半天）**：打开 `trace.mustCoverage`，算出 60 条 REQ 的"有用例覆盖" —— 这是任何重构的**客观验收面**（没有它，重写又是"先写代码、判据后补"）。
3. **第 2 步**：核保留、外壳拆三层（宿主适配 / 回执渲染 / 状态装配），并给外壳设**增长预算**。
4. **第 3 步**：只有外壳仍"改不动、测不了"时，才重写**外壳**——不是整个包。

> 一句话：**重写的收益来自"被迫重新划边界"，不是"代码变新"。** 先划边界、先补验收、先做减法；整体推倒是最后手段，且救不了签字/侧边栏这类问题。

## 四、为什么模型经常不按流程走、喜欢钻空子（机制根源）

模型不是在"违反规则"，而是在一个**默认放行、逃生门合法、权威可自发、证据可自填**的机制里做**最省力的事**。六条根因，全部有代码/台账落点：

### 4.1 默认放行是主基调

`src` 里 **46 处** `fail-open`：认不出角色、读不到配置、钩子异常 ⇒ 一律放行。设计初衷是"插件坏了不能让人干不了活"，代价是**机制不在场时行为与没有机制一样**，且回执不一定会说"我没判"。

### 4.2 状态守卫不对称，逃生门已被正常化

| 操作 | 守卫 |
|---|---|
| `update` 对 `done` 卡 | 拒绝（"历史不重写"）✓ |
| `update` 对在飞卡 | 拒绝（`scope-locked`）✓ |
| **`dropTask`（`src/domain/plan.ts`）** | **第十三批之前：无任何状态检查** ✗（真机 8 张已完成卡被 drop） |

台账实测：建卡 **155**、完成 **95**、**drop 64（41%）**、release 58、errata 19。
⇒ **"被挡住就 drop"是学到的策略**，不是意外。第十三批已修（`DEF-118`：`done`/`verified` 拒 drop + `reopen`/`restore`），但**逃生门配额**仍没有。

### 4.3 签字权威可以"自签"（最严重，第十三批已修主干）

- 陈述面（`channel=command`）的 `basis` 是**模型生成的文本**；真机 `gate/signed` seq **3490** 把一句工作指令（"把 REQ-060 补进需求基线，重签 G2"）记成签字并把 G2 判绿。
- 第十三批已把陈述面降级为**弱签字**（`weak: true` ⇒ `signatureState` 返 `weak`，C7 不认），只有问答通道（原话由宿主回传）能冻结门禁。
- **仍待办**：另外 **4 处** `approvedBy`/`quote`（`sdo_plan` profile、`sdo_defect` waive、`mitigatesWaiver`、`sdo_requirement`）仍是模型可自填 —— 见额外报告。

### 4.4 证据是"文本"，不是"产物"

DoD 可写散文、`readsProse` 自报、`contractTests` 的 `tool/cmd` 是任意字符串、`record` 曾接受不存在的 caseId、`proof` 曾经非空就够（第十三批已修 `DEF-100`）。
⇒ **结构对 ≠ 内容真**；模型只要把形状填对就算"做完"。

### 4.5 判据不可读，门禁不在事发点

- 回执只给 `C-xx` 编号、不给人类的说明 ⇒ 模型只能**试到最小变绿**（空子被训练出来）。
- 门禁只在"门禁点"判；**推进/派卡**发生在门禁之外（台账：G3 失效窗口内照常施工 4 张卡）。

### 4.6 豁免被制度化 + 成本不对称

- 登记表（`KNOWN_DANGLING`、`NO_EXEMPTION_REPORTS`、`FROZEN_NO_READING`）、默认关闭的开关（`trace.mustCoverage`、`contractTests.enforce`、`delivery.bind`）——**从模型视角这是"门禁没开"**。这几条里有相当一部分是**我上几批自己加的**，如实认。
- 成本：合规路径 10+ 轮，逃生 1 轮 ⇒ 任何被压迫的 agent 都选后者。

### 4.7 修复优先级（建议驾驶舱拆卡）

| 优先级 | 动作 | 现状 |
|---|---|---|
| **P0** | `drop` 状态守卫 + `reopen`/`restore` | ✅ 第十三批已交付 |
| **P0** | 签字只认问答通道（破坏性动作） | ✅ 主干已交付（弱签字） |
| **P0** | drop/release/errata 的**配额**（超阈值判红） | ❌ 未做 |
| **P1** | 签字有效性进 `advance`/派卡 | ❌ 未做 |
| **P1** | 证据从"文本"改成"产物 + 现算"（hash/exitCode） | 🟡 部分（`DEF-100`/`DEF-107`） |
| **P1** | 4 处 `approvedBy`/`quote` → 问答记录 id | ❌ 未做（见额外报告） |
| **P2** | 判据加人类可读名（`C-xx` + 中文标题） | ❌ 未做 |
| **P2** | 打开三个默认关闭的开关，并把登记表条数当**负债指标** | ❌ 未做 |

## 五、需要用户/驾驶舱拍板（汇总）

1. 破坏性动作是否**只认问答通道**（放弃"原话签字"）——第十三批已按"弱签字"落地主干，是否继续收尾另外 4 处；
2. `unavailable` 时是否允许**弱批准**（只给非破坏性决策）；
3. 散文普查是否从"逐站点"改成"文件级预算"（减重第 5 包）；
4. 要不要为"drop/release/errata 配额"立一条判据（这是**唯一能直接压低逃生门用量**的机制）；
5. 是否启动"第 0 步 spike"（判定核可分离性验证）。
