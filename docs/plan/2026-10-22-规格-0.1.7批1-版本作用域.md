# 规格：版本作用域（0.1.7 批 1）—— v2 集合式

> 出具：驾驶舱 ｜ 2026-10-22 **v2** ｜ 依据：`REQ-063`（已基线，`AC-266`…`AC-278`/`AC-287`/`AC-288`）、`ADR-022`、`ADR-025`
>
> **本文件是判据规格**：先有它，再有实现与守卫。凡与实现冲突，以本文件为准；改本文件必须留理由。
>
> **v1 → v2 改了什么**：v1 把 `targetVersion`/`deferredTo` 四字段当成**权威**；用户 2026-10-22 核对后确认这与已基线的 `REQ-063`（**集合式**：release 文件 + 范围/非范围集合 + 冻结人签）冲突。**以 `REQ-063` 为准**：字段降级为**派生**（`AC-287`），权威是 release 文件里的集合。v1 与集合式不冲突的部分（`deferApprovedBy` 只认 human、缺口清单与实际集合恰好相等、`journal` 不动）全部保留。

---

## 1 要解决的问题（一句话）

台账里**没有"版本"这个维度**：42 条 open 缺陷、169 张卡、7 条风险都是"无版本"的，而 `C-51`（阻塞缺陷必须关）是**全量判据**。台账一旦跨版本累积，门禁只有两条路 —— 永久红，或被迫放宽。0.1.6 走的是第三条：**手写「已知缺口」糊过去**（台账无来源，`ADR-021` 那句"必须一致"因此**不可机械核对**）。

`REQ-063` 给的解法是**把版本表达成对需求基线的一次范围声明**，而不是给每个实体贴一个版本标签。

## 2 数据模型：release 文件（权威）

### 2.1 落点与形状

`.sdo/releases/<release-id>.yml`：

| 字段 | 必填 | 说明 |
|---|---|---|
`id` | 是 | **形如 `r-0.1.7`**（`AC-278`）。**不得**直接取 `package.json.version` 当主键 |
`packageVersion` | 否 | 与包版本号的显式映射；允许一个包版本含多个 release。`id` 若取包版本号而不写本字段 ⇒ **红** |
`scope` | 是 | **本版范围**：`{ requirements: [REQ-…], acceptance: [AC-…] }` |
`nonScope` | 否 | **明确不进本版**：`[{ id, reason, deferCount, approvedBy }]`。`approvedBy` 只认 `human` |
`frozenAtSeq` | 是（冻结后） | 冻结那一刻的 `journal` 序号 |
`frozenBy` | 是（冻结后） | 只认 `human`（`AC-276`：冻结是一次**人签**，走问答通道） |

### 2.2 字段是派生的（`AC-287`）

`defects` / `tasks` / `requirements` 上的 `targetVersion` / `deferredTo` **一律由 release 的集合派生**：写侧由工具按集合算出，**不得手填**；两者不一致 ⇒ 判红并点名差异。派生规则：

- **当前 release 的定义**（`currentRelease`）：**最新已冻结**的那一版；一版都没冻结时退回**版本最高**的那一版。依据 `AC-276`（集合的权威来自冻结＝人签）与 `AC-275`（旧版已冻结、新版待开工时，「本版」必须是签过字的那版）。
- id 在某个 release 的 `scope` 里 ⇒ `targetVersion` = 该 release 的 `packageVersion`。**这一句不限定「当前版」**：同一实体被更晚的 scope 带进来时，`targetVersion` 取那一版（草案可以占未来版本号，但**不能改变当前版的身份** —— 后者只由 `currentRelease` 决定）。
- id 在**当前 release 的** `nonScope` 里 ⇒ `deferredTo` = 顺延到的 release 的 `packageVersion`，并带 `deferReason` / `deferredBy`。**`nonScope` 只取当前版**（`REV-076` 第 3 条）：旧版 `nonScope` 里的条目**不构成永久豁免**，否则就是 `AC-277` 要判红的「静默顺延」。
- **既不在任何 scope、也不在当前版 nonScope** ⇒ 缺省视为**当前 release**（fail-closed，`R8`）。
- **只在旧版 `nonScope` 里、且顺延目标已到账** ⇒ 同样归入**当前 release** 参与判定，但**必须与「从没规划过」区分开**（`REV-076` 第 2 条）：前者是「规划过且到账」，后者是「未规划」。具体编码（独立标记 `landedFrom` 或三值 `failClosed`）**待 `REV-076` 核实结论定**，未定之前实现侧不得用同一个 `failClosed` 标记兼表两义。

### 2.3 术语不混用

`requirements.version`（`0.1/0.2/0.3`）是**架构轮次**，与本节的 `targetVersion` **语义不同，不许迁、不许混用**。

## 3 判据

### 3.1 `C-71 作用域闭合`（只对实现/验证/交付类门禁：G4/G6/G7）

作用域内（见 §2.2）= 当前 release 的 `scope` ∪ **缺省归入者**（未规划）∪ **顺延到账者**（只在旧版 `nonScope` 里、目标已到账）—— 后两个分量都必须参与判定，但**判据回执里要能分开点名**（`REV-076` 第 2 条：把「顺延到账」混进「未规划」会让 C-71 的点名失去意义）。逐类必须闭合：

| 对象 | 闭合条件 |
|---|---|
`defects` | `status ∈ {fixed, closed}`；`wontfix` 须带 `waiveReason` + `waiveApprovedBy`（沿用 `DEF-038`） |
`tasks` | `status ∈ {done, verified, dropped}` |
`requirements`（`priority: must`） | 至少一条 `pass` **且已采纳**的用例（复用 `C-41` 的采纳口径） |
`contracts` | 有 `contractTest` 记录（复用契约面判据，不另造） |

作用域**外**的对象：**不判红**，但必须满足 §3.2。

### 3.2 `C-72 缺口清单与实际集合恰好相等`

`CHANGELOG.md` 本版「已知缺口」点到的 id 集合，必须**恰好等于**当前 release 的 `nonScope` 集合。

- 多写（清单有、集合没有）⇒ 红，点名**粉饰项**；
- 少写（集合有、清单没有）⇒ 红，点名**隐瞒项**；
- 两边都空 ⇒ 绿（此时清单小节可以不存在）。

> 这是 0.1.6 的补洞：`ADR-021` 说过"清单必须与台账一致"，但当时台账没有集合可对，只能手写。

### 3.3 `C-73 顺延留痕与次数上限`（`AC-277`）

一条需求/缺陷被顺延时，`nonScope` 条目必须带 `reason` 与 `deferCount`；`deferCount` 有上限（默认 2），**超上限即红并要求用户裁决**。**反例必红**：只从 `scope` 里消失、没有任何 `release/deferred` 记录 ⇒ 红（静默顺延）。

### 3.4 `C-74 门禁分工`（`AC-266`/`AC-275`）

- `G2` / `G3`：对**整条基线**判定，**不按版本切片**；
- `G4` / `G6` / `G7`：**只对当前 release 的 scope** 判定。

两侧都要有可观察断言（见反例 `R11`）。

### 3.5 冻结与变更（`AC-268`/`AC-276`）

1. 冻结 = **人签动作**（问答通道 `channel=question`），落 `frozenAtSeq` / `frozenBy`；模型自行声明集合而不经签字 ⇒ 红。
2. 冻结后要往 `scope` 加东西**只能走 `change` 控制**（带影响分析 + 决策）；直接改集合 ⇒ 红（`C-75`）。

## 5 回填策略（本批最危险的一步）

1. **只碰未终结对象**：`defects status=open`（42 条）＋ `tasks status ∈ {planned, blocked}`（5 张）。已 `fixed/closed/done/dropped` 的**一律不动**（历史不重写）。
2. **先建 `r-0.1.7` 的 release 文件**：把"本版要做"的放进 `scope`（当前 17 条缺陷 + 4 张卡），"本版不做"的放进 `nonScope`（25 条，带 reason / deferCount / `approvedBy: human`）。
3. **旧四个字段与新集合必须一致**：回填后 `targetVersion`/`deferredTo` 只作**派生视图**保留，由脚本从集合重算；不一致 ⇒ 判红（`R14`）。
4. **先在副本上演练**：真源层副本 → 建 release → 跑 `C-71`/`C-72`/`C-73` 预演 → 出报告（改了多少、作用域内多少）。
5. 真账动笔前必须：① 演练报告经用户过目；② 手工备份 `journal.jsonl` + 受影响目录（`.sdo/drafts/backup-*/` 已有先例）。

## 7 明确不做（本批边界）

- **不**给 `reviews` / `decisions` / `tests` 加版本维度 —— 它们是**留痕类**，没有"关闭"语义。
- **不**做 `journal` 归档、**不**做 evidence 清理（批 4）。
- **不**改 `C-51`/`C-65`/`C-66` 的现有语义，只在其外层加"作用域过滤"。
- **不**把 `requirements.version`（架构轮次）迁成 `targetVersion`。
- **不**给 `.sdo` 建独立 git 仓库（`ADR-025`）。
