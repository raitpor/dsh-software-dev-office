**现状**：`R11` 已把判据从"描述文本启发式"改成**从消费面推导**（扫 `compositeArg(args.X)` / `Array.isArray(args.X)` ⇒ 每个 X 的声明处必须是 `listDecl(`），并把洞（`parseList`/`jsonOr`/`json<T>` 不作信号）写进判据文案 —— 这部分**已复验**（`TASK-128` 的三处争议会给最终结论）。
**本项要做的**：把 **`steps`** 也改成 `listDecl`（见 §3.2 的现象），因为它是**同一根因的活标本**：**语义上是列表、却声明成纯 `string`**。用户已裁定**并入本项、不单独立卡**（`ADR-017`）。

**现象**：`src/interface/tools.ts:1158` 的 `steps: { type: 'string', … }` **不是 `listDecl`**；`:1264` 对非 string **静默丢成 `undefined`**。⇒ 调用方**只能**走 JSON 文本，而**宿主会拒文本里的 `", "` 分隔符**（两路建卡会话独立复现：**13/13** 与 **3/3**，文案 `invalid arguments: "steps" must be a string`，**零写盘、无内容丢失**；只把分隔符换成紧凑 `","` 即通过）。
**修法**：`steps` 改用 `listDecl`（声明处给 `oneOf:[string,array]`）+ 调用面归一（走既有 `compositeArg` 一族）⇒ 调用方**传真数组**即可，分隔符地雷与静默丢弃一起消失。
**DoD**：① 真注册工具 + **真数组** `steps` 可用；② JSON 文本形态**仍可用**（向后兼容：既有 149 条 TC 的写法不能坏）；③ 消费面判据（`M176-05`）**认得出** `steps` 是被当列表用的参数（否则反例：把 `steps` 的 `listDecl` 去掉 ⇒ 必须**判红**）；④ 不引入任何新名单。
**验收**：**行为**（真数组 / 文本 / 都不给 三态）+ **结构**（消费面判据覆盖 `steps`）。

### 3.7 `DEF-081`（major，**open**）—— 作废一张卡不检查依赖者

**现象**：`drop` **不扫"谁在等这张卡"**，也不在回执里提示 ⇒ 被作废卡留下的 `blockedBy` 边**永远不会满足**，依赖它的卡（及其下游）**永久进不了派发队列**，而且**看起来完全正常**（状态 `planned`、理由充分、无人报错）。`sdo_plan action=next why=true` 会把它列在"依赖未满足"里 —— 但**只有主动去查才看得见**，没有任何判据/门禁会因"存在永不满足的依赖边"判红。
