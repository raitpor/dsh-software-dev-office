### 3.1 `DEF-054`（major，**仍复现**）—— 同一提交里两道门用了**不同判据**，fail-open 仍在

**现象**：`DEF-054` 原缺陷是"定位向上爬 + 归属不到工作区时 fail-open"。第三批修掉了**向上爬**（唯一出口 `office.workspaceRootFor`，三来源绝不向上）与"完全拿不到工作区"那一态，但**两段判定用的不是同一个判据**：

| 位置 | 判据 | 后果 |
|---|---|---|
| `src/index.ts:3980`（fail-closed 门） | `isChildSession && workspaceRoot === ''` | 工作区**能**解析 ⇒ **放行** |
| `src/index.ts:3988`（角色归属） | `if (call.cwd === undefined) return { kind: 'unknown', role: 'cockpit' }` | `call.cwd` 缺省 ⇒ `kind='unknown'` ⇒ **掩码与写范围两段一起跳过** |

**复现（第三批复验 V6 用真实装配驱动，驾驶舱读代码复核成立）**：执行者子会话（`delegationDepth:1`）**有凭据/有登记**（在 BASE 认领了 `TASK-911`、`role=developer`、`writeScopes=['src/index.ts']`）但**本次调用没有 `agent.cwd`** ⇒ 同一会话、同一张卡，只差 `call.cwd`：

- `sdo_plan`（执行者禁用）｜cwd=BASE ⇒ **deny**；｜**cwd 缺省 ⇒ allow**
- 写范围外 `edit src/other.ts`｜cwd=BASE ⇒ **deny**；｜**cwd 缺省 ⇒ allow**

**为什么 `m171` 没守住**：`M171-03` 用的正是同一个 `cwd: undefined` 状态，但**只覆盖"无凭据"那半**（无凭据时 `workspaceRoot === ''` 被第一道门拦住）。

**修法**：把 `:3988` 的归属判定改为按**已解析的 `workspaceRoot`**（或 `rootCall.cwd`）判，而不是按 `call.cwd === undefined`；归因不到时**不要**退回 `{kind:'unknown', role:'cockpit'}` 的放行态。
**DoD**：① 有凭据 + cwd 缺省 ⇒ 掩码与写范围**照判**（该 deny 的 deny）；② 无凭据 + cwd 缺省 ⇒ 仍 fail-closed（第三批已成立，别弄坏）；③ 正常 cwd ⇒ 行为不变；④ 驾驶舱**不受限**且豁免**不是硬编码身份**（现盘用 `delegationDepth >= 1 || typeof parentSession === 'string'` 判血缘 —— 保持这个口径，别引入会话名/会话 id 白名单）。
**验收**：**行为**四态探针 + 新守卫 `M171-07`。

### 3.2 `DEF-077`（major，**新立**）—— `unfrozen` 只有文本形态可用；根因是"一处归一"被做成**白名单**

**现象**：`sdo_task action=done` 的 `unfrozen` 参数**描述**写着 `JSON **text** (or a real array)`、`src/index.ts:2412` 的**注释**也写"数组 / JSON 文本二选一"，但 schema 是 `type:'string'` ⇒ 传真数组时**宿主在 schema 阶段就拒**：`invalid arguments: "unfrozen" must be a string`（插件 `execute` 从未被调用）。JSON 文本形态完好、未知 id 可读拒绝零写盘 ⇒ **后果有限（拒绝是响亮的、非静默丢参），但"数组形态"确实不通**。

**根因**：注册出口的"一处归一"是**白名单**，不是**从声明推导**：`src/interface/tools.ts:19-43` 的 `LIST_PARAM_NAMES`（23 项）与 `:67-75` 的 `withListParams` —— 只有"名单内 + 声明为纯 `string`"的参数才升成 `oneOf:[string,array]` ⇒ **每新增一个列表型参数，不加名单就静默退回纯 string**。

**为什么本批自己的守卫没抓住（`escaped=true`）**：`test/m174` 只断言"参数在注册面"，且夹具**直调 `tool.execute`、跳过宿主 `dsh-tools` 的 schema 校验** ⇒ 走的是比真机**更宽**的路。技术库 `tq_ff348198`（"**参数在注册面 ≠ 真机可用**"）的原话又犯一次。

**修法方向（二选一，报告里说明为什么选它）**：(a) 把 `unfrozen` 加进 `LIST_PARAM_NAMES`（一行）；或 (b) 把 `withListParams` 从"白名单"改成"**按声明推导**"（凡是 `type:'string'` 且描述/声明承诺数组的参数自动升 `oneOf`）。**推荐 (b)**：本缺陷的成因是"白名单会漏"，(a) 只治这一次，下次新增参数还会漏同一个坑。
**DoD**：① 真数组形态可用（真注册工具 + 真数组）；② JSON 文本形态仍可用（向后兼容）；③ `src/index.ts:2412` 的注释与 schema **一致**；④ 若是 (b)：至少再加一条**机械判据**防止未来再漏（例如"声明承诺数组却未升 oneOf ⇒ 判红"）。
**验收**：**行为**（真数组 / 文本 / 两者都不给 三态）+ **结构**（注释与 schema 一致）。
