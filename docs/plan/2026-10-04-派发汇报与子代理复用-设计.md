# 派发汇报（子 agent 取汇报）与子代理复用 · 设计（2026-10-04）

## 0. 问题（真机发现）

插件用宿主 `subagents.start` 派发是 **fire-and-forget**：只记 `dispatch/started`。子代理的收尾报告只写在**它自己的会话**里
（宿主不会把子会话的最终消息投递给父会话 —— 只有模型侧 `subagent` 工具起的子代理才有回调）⇒
**卡在台账里 done 了，但驾驶舱看不到"干完了没、干了什么"**（B4 的加重版：连报告也没有回传通道）。

## 1. 事件探测结论（2026-10-04，真机 + 事件形状实测）

| 问题 | 结论 |
|---|---|
| 插件能否收到**子会话**的 `session/event`？ | **能**：真机 `.sdo/evidence/child-tools.jsonl` 里有 8 条 depth=1 子会话的 `request/header`/`tool/call` 观测 |
| 结算信号是什么？ | 子会话**没有** `session/end`；**`turn/end`**（`{turn, reason:{kind}}`）就是结算信号（one-shot 子会话一轮即结束） |
| 最终消息能否拿到？ | **能**：`assistant/message` 事件带全文（`data.message.content[].text`）⇒ 取 `turn/end` 前的最后一条 |
| 能否把摘要**回注**父会话？ | **暂不能**：`agent/inbox/spliced` 是宿主侧事件，未找到插件可调的注入入口 ⇒ 见 §3 的方案 ③ |

## 2. 三个方案与实施状态

| 方案 | 内容 | 状态 |
|---|---|---|
| **① 低成本** | `sdo_status` 增「最近完成的派发」块（卡 / 子会话 / 结论 / 耗时 / 报告落点 + 摘要） | ✅ 已实现（真工具用例 `M34-01`） |
| **② 中成本** | 订阅子会话 `turn/end` ⇒ 写 `dispatch/finished` + 报告落 `.sdo/evidence/child-reports/<childSessionId>.md`（内容 = 最后一条助手消息） | ✅ 已实现 |
| **③ 完整** | 把报告摘要**自动送达**驾驶舱 | ✅ **已实现「推」半**：驾驶舱**下一次调用任何 SDO 工具**时，未读报告会**贴在该次回执**上（载体=工具回执，因为宿主没有子会话→父会话的投递通道）；送达一次就记 `dispatch/reported`（append-only ⇒ 重启也不重推）。状态块仍保留（拉取侧） |
| 附带修复 | `session/event` 监听器原本整段 `catch {}` **静默吞异常**（真机丢过三次派发的观测）⇒ 现在记 `dispatch/observe-failed`（仍 fail-open，但不再无声） | ✅ 已实现 |

## 3. 子代理复用：决定 **1 + 3**（不做 2）

宿主事实（读码，可复跑）：

```text
dsh-subagent 的**持久化描述符校验**里明确列了两个字面量： one-shot 与 continuable
dsh-subagent 的 **Service.start()** 里把描述符**写死** mode: one-shot（另有 descriptor 构造处同）
```

⇒ 宿主**内部**支持"可续聊的子代理"（Activation / 常驻 epoch / inbox / `interrupt` —— 这正是模型侧 `subagent` 工具能 `send_message` 续聊的原因），
但**插件可调的 `start()` 只发 one-shot** ⇒ SDO 每次派发都是全新会话（重新装 persona/skill/工具面 + 重读上下文）。

- **方案 1（要宿主开 continuable 入口）**：插件侧已就绪 —— `reuseCapability()` 只认**显式存在**的入口
  （`startContinuable`/`activate`/`resume`，`typeof === 'function'`），派发回执按探测结果说话（今天如实说"暂不可用，每次都是新会话"）；
  **宿主一旦开放，回执口径自动改变，无需再改插件**。已记录：向宿主提 continuable `start` 需求。
- **方案 3 的池化口径（2026-10-04 用户定稿）**：**每个角色一个子 agent 池**（各自并行上限）；**任务卡当消息队列** ——
  每一轮把卡分发给该角色池里的空闲子 agent；**池内全忙则队列阻塞**，直到有子 agent 完成任务、再把卡派给空闲者。
  与"同角色常驻"一致（同一池内的子 agent 复用），不同角色的池互相独立（职责分离与掩码不变）。
- **方案 3（同角色常驻、多轮派卡）**：等 1 落地后做。设计已定：
  - **同角色复用**（归属与掩码靠"认领的卡"推 ⇒ 跨角色复用会破坏职责分离）；
  - **developer 可多实例并行**，上限用现成的 `maxParallelDispatch`（默认 4），并按角色分池（developer 池 > 其它角色池）；
  - A2 写范围对账按**每张卡的 `claim` 基线 seq** 切 ⇒ 复用**不会串账**；
  - `scale=critical` 建议仍用 one-shot（隔离 + 证据干净）。
- **不做方案 2（多卡合并派发）**：会丢信息 / 上下文过长导致漏关键信息 / 单次时长过长。

## 4. 已知边界（如实）

- 报告落点**按「卡 + 子会话」切**（`<task>-<子会话前 8 位>.md`）：复用（方案 3）下同一子会话服务多张卡时**不会互相覆盖**；读者一律按 `dispatch/finished.report` **记录读回**，不自己拼文件名（评审 N2）；
- **结算取「最新一条」派发记录**（`filter(...).at(-1)`）：复用形态下同一子会话会有多条 `dispatch/started`，取第一条会认错卡（我写 M34-05 时正是这样发现的）；
- `childLastMessage` 是**内存缓存**（上限 32 个会话）：插件实例重载会丢 ⇒ 那种情况下报告文件为空，但 `dispatch/finished` 仍会落账（能看到"完成了、报告缺失"）；
- 观测失败**留痕**（`dispatch/observe-failed`）已用**确定性构造**复现并收进用例（`M34-04`：把 `evidence/child-reports` 预占成普通文件 ⇒ 写报告 `EEXIST` ⇒ 留痕，且**不**误记 `dispatch/finished`）—— 评审 N3 指出的那条边界已关闭；
- `dispatch/finished` 的失败原因取自 `turn/end` 的 `reason.kind`（`completed`/`error`…），不是子代理的**业务**结论 ⇒ 业务结论要看卡状态与报告正文。

## 5. 实施记录（角色池 + 卡队列，2026-10-04）

**范围（用户裁定）**：只做池与队列，**投递仍由驾驶舱触发**（`sdo_plan action=next`）；插件不自主起代理。

### 5.1 纠正：宿主能力一直在，缺的是插件侧实现

上一轮我写「宿主 `subagents.start` 写死 one-shot ⇒ 插件拿不到可续聊子代理 ⇒ 已向宿主提入口需求」——**这句不准确**，
只看了 `start(name, request)` 就下了结论。实测（`dsh-subagent@0.2.0-rc.1/lib/index.js`）：

| 入口 | 位置 | 语义 |
|---|---|---|
| `start(name, request)` | `:3121` 描述符写死 `mode:"one-shot"` | 便捷方法：一次性子代理 |
| `startContinuable(spec)` | `:2879` → 实现 `:1671`（描述符 `mode:"continuable"` `:1685`） | 建**可续聊**子代理，返回 `{childId, messageId}` |
| `sendMessage(sender, targetId, content, {signal})` | `:2897` → `:1762` | 宿主注释：「运行中在最近步骤边界收下；**空闲则起一轮**；不存在则从持久化冷恢复」⇒ **复用的投递原语** |

两者都由 `requireContinuations()` 提供，并在 `ctx.inject(['agents'], …)`（`:2839-2845`）时装载 ⇒ 只要 `agents` 服务在就能用；
插件通过 `ctx.get('subagents')` 拿到的就是这个服务对象（`src/index.ts` 的 `ctx.inject(['subagents'], …)`）。
约束：`sendMessage` 要求**同一个活着的 sender Agent**（`:1763` 校验 `agents.get(sender.id) === sender`）——
本轮的投递发生在工具调用里，`call.agent` 正是那个活着的驾驶舱 Agent，因此不需要额外取回。

### 5.2 口径（实现里的两个决定）

1. **池上限管"子代理个数"，不是"并发卡数"**：`freeSlots = cap − 在飞 − 空闲`。所以"池里躺着一个空闲可复用者"时
   新建位子是 0，但**仍能接卡**（投给那个人）。写错这一条会在池满时继续新建子代理，把池撑爆、复用也就没意义了
   （M36-02/03 钉住；这也是实现时被测试抓出来的一处真错误）。
2. **一张卡只在一个子代理里**：已有在飞派发（`started` 未 `finished`）的卡不重复派。代价如实写：
   派发丢了的卡会一直算"在飞"，直到结算或人工处置（既有 `staleTasks` 管的是认领，不是派发）。

**僵尸的成因（独立复核过）**：该台账 8 笔 `dispatch/started` 里 **6 笔没有 `dispatch/finished`**
（最早的 2026-10-03，跨了两次重启）。池状态从台账现算、**没有孤儿回收** ⇒ 池被永久占满。

### 6.1 修法（`dispatchOrphanTtlMinutes`，默认 60）

- 超过 TTL 仍无结算的在飞 ⇒ `stale`：不占池位、不进"空闲可复用"、不挡同一张卡的重新派发；
- TTL 之内照旧占位；`startedAt` 读不出的手写事件按保守口径仍占位；
- 池块如实标注「未结算超时 N」+ TTL + 调法。
- **为什么不采用"插件启动时一律算孤儿"**（驾驶舱给的三个选项之一）：可续聊子代理是**持久化**的
  （不存在则从持久化冷恢复），重启不等于它死了 —— 那会把还活着的子代理的位子也放掉。
- **诚实边界**：TTL 是**启发式**。真跑超过 TTL 的子代理会被误判为孤儿（它不会进"空闲可复用"，
  只是把位子让给**新**子代理），所以① 可配、② 回执点名 TTL、③ 本仓不把它写成"精确判定"。
