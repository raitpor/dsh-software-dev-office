# DEF-067 设计：写范围争用的**派发面**收口（语言无关）

> 状态：**新设计（待用户批准后立卡）** ｜ 日期：2026-10-14 ｜ 作者：驾驶舱
> 真源：缺陷本体在 `.sdo/defects/DEF-067.yml` 与其 `defect/recorded` 事件（本文件只是设计与取舍，冲突时以台账为准）。
> 需求约束：**REQ-060**（2026-10-14 用户补需求）——「插件功能语言无关，不能针对某个具体的项目做特殊方案判定，判定应对大部分场景普适」。本设计**逐条**受它约束；被它淘汰的两版方案记在 §4。

## 0. 一句话结论

DEF-067 的**危害**不在「互斥太严」，而在「**派发不查写范围** ⇒ 派出注定认领失败的卡，白烧一个会话」。
所以本设计的落点是**派发面**（外加两条零配置的可读性修复），**不动互斥语义**，也**不引入任何文件格式知识**。

## 1. 现场（全部可复算）

1. **三张互不相干的卡争同一批文件**：`TASK-090` / `TASK-104` / `TASK-106` 的 `writeScopes` 都含 `src/data/lang/zh-CN.yml` + `src/data/lang/en.yml`（现读 `.sdo/tasks/*.yml` 可验）。
2. **认领被拒**：一手报告 `.sdo/evidence/child-reports/TASK-106-e386d180.md` 第 3 行逐字 ——「TASK-106 未能开工 —— 认领被写范围冲突连拒两次，本轮零产品改动」。
3. **本次接手实测（2026-10-14）**：驾驶舱用 `sdo_plan action=next limit=3` 派三张核实卡（写范围都是 `.sdo/reviews/`）⇒ journal `seq 2867-2872` 三条 `dispatch/started` **全部派出**，随后 `TASK-113`(`305e4e62`) 与 `TASK-114`(`a3734ef9`) 双双 `write-scope-conflict` 认领失败，**各白烧一轮**（两个会话都把只读核实做完却无法落账）。
4. **三处机制的现读口径**：
   - `src/domain/plan.ts:774-790`（`readyTasks`）只按 **status + `blockedBy`** 过滤 ⇒ **完全不看写范围**。这是 §1.3 的直接成因。
   - `src/domain/plan.ts:673-683`（`validatePlan`）*已经*有一条 `write-scope-disjoint` 计划读数，且**点名了重叠范围**（`overlap.join`）并给了修法 ⇒ **计划面已有一半**，但它是计划问题（警告），**派发面看不见**。
   - `src/domain/collab.ts:356-359` 认领拒签的 `detail` 是：`写范围与正在进行的 <对方卡>（owner=…）冲突：` + **对方 writeScopes 全量**。⇒ 读者**看不出撞的是哪个文件**，且**零出路提示**。

## 2. 不变量（拟新增，语言无关）

> **I-INV-派发可认领**：一张卡被派出时，它必须**能够认领成功**。即「可派发」= 依赖已满足 **∧** 写范围不与任何在飞卡相交。

这条不变量不含任何格式知识、不认识语言包、不依赖项目布局 —— 它只用到插件已有的两个事实（依赖图、路径集合相交）。
它也正是本轮被违反的那条（§1.3）。**是否将其落入 `.sdo/design/method-invariants.yml` 由用户在批准本设计时一并裁决**（真源改动走 `sdo_design artifact`）。

## 3. 设计：三个落点

### 落点一（主）· 派发前置检查：不可认领的卡**不派**

- `next` 挑选可派发卡时，除 `blockedBy` 外**再过滤掉**「写范围与任一 `in-progress` 卡相交」的卡（相交口径沿用插件既有实现，不新造）。
- 被挡下的卡**必须在派发回执里单列一行**并点名：卡 id、与哪张在飞卡、**重叠的哪个/哪些路径**、以及它现在的状态（`ready` 但暂不可派）。否则会复现 DEF-058 的误判（首屏看不到派发行 ⇒ 以为没派）。
- **不做**：不改互斥语义、不释放对方的范围、不自动改 `blockedBy`（那是人的裁决）。

### 落点二 · 认领拒签回执**可执行化**

- `detail` 改为点名**重叠的那个路径**（不是对方 writeScopes 全量），并给三条出路：① 等对方释放；② **把该共享文件的更新单独拆成一张卡**（见落点三的建议）；③ 用 `blockedBy` 显式声明先后。
- 保留对方 card id 与 owner（便于找人），但**重叠路径提行**，全量范围不再倾倒。

### 落点三 · 计划读数补一条**与格式无关的处置建议**

- 既有 `write-scope-disjoint` 读数保持不动（它已点名重叠范围）。
- 修法文案里**补上**「拆出该文件的独立卡」这一条 —— 即把「共享文件由**一张卡独占**」作为首选处置。这正是用户提出的拆卡纪律，落到**建议**层而不是插件替人判定。
- 同理适用于任何"多卡都要追加的同一份文件"（变更日志、注册表、既有测试文件的追加用例……）：插件只说"这个路径被两张卡同时声明"，**不判断它是什么文件**。

## 4. 被否决的备选（含代价）—— 两版都是被 REQ-060 淘汰的

| 备选 | 做法 | 为什么否决（代价） |
|---|---|---|
| **A. 键级不相交预检**（DEF-067 记录里的修法 (c)，也是本设计的第一版） | 认领时比对两张卡要写的 **YAML 键面**，键不相交即放行 | **违反 REQ-060**：`键面` 是 YAML 特有结构。换成 `.po`（msgid）、`.properties`、纯 markdown 文档、二进制资源，这套判定**根本不成立** ⇒ 是一个只为某个项目/某种格式写的特例 |
| **B. 新增 `shared`/`shared-append` 类别以「允许并发写」**（修法 (a)） | 声明为共享的文件，两张卡可同时认领 → 同时写 | **不安全，且普适性不等于正确性**：两个会话对同一文件做 read-modify-write 就会**丢更新**（一份文案被静默覆盖）。插件**没有**跨会话的工具级写锁（那是宿主能力），所以"放宽互斥"= 把响亮的串行化换成**静默的数据丢失**。宁可慢，不可悄悄丢 |
| **C. 语言包分片、构建期合并**（修法 (b)） | 每卡写自己的分片，构建时合并 | 要改**真源布局**，会同时触动 `m7`/`m110` 的双包对齐守卫（`en` 必须逐键覆盖 `zh`、`en` 不得含中文）；**风险与收益不成比例**。且"分片+合并"同样是把一个通用问题用某类文件的结构去解 |
| **D. 只改回执，不加派发前置检查** | 只做落点二 | 保留 §1.3 的白烧：派出去、认出失败了才知道。**危害不除** |
| **E. 自动改写卡的写范围 / 自动串行化** | 插件自行把卡改为 `blockedBy` 或削范围 | 越权：`blockedBy` 与范围是**人的裁决**（DEF-071 同族教训：卡面不得被插件悄悄改动） |

**接受的后果**（明确写下来）：落点一**会推迟**一张本来会被派出的卡 —— 它要等到对方释放、或等到下一次 `next`。这是**有意的**代价：换来的是「派出去的卡必定能开工」。若某项目确实希望"先派出去排队"，那是**另一个提案**（且需要先解决 §4-B 的丢更新问题），不在本设计内。

## 5. 守卫与变异（先钉红再改，红绿绑同一份被检文件）

守卫新建 `test/m111.test.ts`，四态：

1. **① 派发前置检查（修前必红）**：造一张写范围与某在飞卡相交的 `planned`/`ready` 卡 ⇒ 断言它**不被派出**，且派发回执**点名了重叠路径**与在飞卡 id。
2. **② 不相交照常派**：写范围与在飞卡不相交的卡 ⇒ 派发不受影响（防"一刀切不派"）。
3. **③ 计划读数含拆卡建议**：两张可能并行的卡重叠 ⇒ `write-scope-disjoint` 读数仍点名重叠范围，且修法文案里出现"拆"这一处置。
4. **④ 拒签回执点名重叠文件（修前必红）**：构造对方写范围含 `A`、`B` 两文件、我方只与 `A` 重叠 ⇒ 断言回执**出现 `A`**、且**不出现 `B`**（直接钉死"倒全量"）。

变异自证：回退落点一（去掉派发过滤）⇒ ① 转红并记 `killed`；回退落点二（回执改回倒全量）⇒ ④ 转红并记 `killed`。

## 6. 普适性自证（对 REQ-060 的正面回答）

把同一个机制依次换成三种完全不同的项目，**不做任何代码改动**：

| 场景 | 共享的「同一份文件」 | 本设计的行为 |
|---|---|---|
| Node/TS 项目 | `src/data/lang/*.yml`（键值对） | 派发前置检查挡下第二张卡，回执点名该 yml 路径，建议独立成卡 |
| Go 项目 | `po/zh.po`（msgid/msgstr） | 同上 —— 插件**不解析**该文件，只看路径 |
| 文档型项目 | `CHANGELOG.md` / `docs/README.md`（追加段落） | 同上 |

⇒ 机制只依赖「路径集合」与「依赖图」，**不含任何格式/语言/项目特例**；需要项目特有信息时，本设计**不需要**新增任何声明（区别于被否决的 A/B/C）。

## 7. 与既有卡/判据的关系

- 与 **DEF-057**（相交判定只有目录级前缀粒度）**同一个模型的两面**：那条要**修正判定本身**，本条要**把判定结果前置到派发面**。
- ⚠️ **必须同批处置（这不是"建议"，是落点一的已知副作用）**：现行相交判定是**双向 `startsWith` 前缀匹配**（`src/domain/collab.ts:348-354` 现读）。**2026-10-14 驾驶舱自己造例现算**（`node -e` 直接跑该布尔式）得到的三条事实，取代任何凭标题的猜测：
  | 一对写范围 | 现盘判定 | 是否符合直觉 |
  |---|---|---|
  | `src/a.ts` \| `src/b.ts` | **不相交** | ✓ 同目录的不同文件本来就不冲突（**所以"同目录各写各文件被判互斥"这个说法只在有一方声明目录级范围时才成立**，不能笼统这么写） |
  | `src/a.ts` \| `src/a.tsx` | **相交** ✗ | ✗ **文件名前缀假阳性**：`src/a.tsx`.startsWith(`src/a.ts`) 为真 |
  | `src/domain/` \| `src/domain/plan.ts` | 相交 | ✓ 目录范围确实覆盖其下（这条**不是**假阳性，不要放宽） |
  因此落点一的真实副作用是：**任何声明了目录级范围的卡（如 `test/`、`src/`）会与它底下的一切相交**，前置到派发面后就是"整批卡被静默抑制"（看起来像"没卡可派"）。**所以落点一必须与 DEF-057 的判定修正同批落地、且判定修正先行**；单独落地点一 = 用一个更早的静默抑制换掉一个响亮的失败，是**倒退**。
- 与 **DEF-053**（派发≠认领）**同源**：本条是它在"写范围"这一维上的具体化 —— DEF-053 说"派出去不等于能认领"，本条给出**一类可机械预防的成因**。
- 与 **DEF-058**（批量派发回执被撑爆）**有交叠**：落点一新增的"暂不可派"行必须在首屏可见，否则修好一处又添一处误判。
- 本条**不改** G5/G6 任何判据，因此不触发门禁基线变更；但若 §2 的不变量被采纳，则属于设计真源变更 ⇒ G3 签字需重签（与 CT-001 同款处置）。
