## 1. 阻塞级（先做这三条，其余都在等它们）

### 1.1 `DEF-119`（**blocker**）—— 校验器与写面死锁：`next` 永久红

**现象（驾驶舱实测）**

```
$ sdo_plan action=next
⛔ 本次没有派发：计划有 6 处问题
  · [write-scope-empty] TASK-145 / TASK-151 / TASK-152 / TASK-153   ← 四张都是 done
  · [write-scope-empty] TASK-155
  · [size-cap]          TASK-155
```

**根因（代码级，已定位到行）**

- `src/domain/plan.ts:719-721`：`for (const task of tasks) { if (task.status === 'dropped') continue ... }` ⇒ **只跳过 dropped**。
- `:733`（`write-scope-empty`）、`:741`（`dod-nonempty`）、`:749`（`size-cap`）、`:757`（`evidence-required`）⇒ **都不看状态**，对 `done`/`verified` 卡照判。
- `:782` 的 `impact-undeclared` **有**放行：`if (task.status !== 'done' && task.status !== 'verified')`，其 `:780` 注释逐字写：「时机：只在**还没落地**的卡上判 —— 拆卡期判红才有意义（**落地后是历史，不重写历史**）；存量卡不追溯」。
  ⇒ **同一个函数里已有正确口径，另外四条没照办。**
- 写面（`sdo_task action=update`）对这些卡**一律拒**：`not-updatable`「已是 done：历史不重写（要改就新立一张卡）」；对在飞卡 `scope-locked`「会造出两个写者」。
  ⇒ **校验器要的字段，合法手段永远补不上** ⇒ 死锁。

**修法（最小、与既有口径一致）**

把 §上面四条（以及 `:741` 的 `dod-nonempty`、必要时 `:722` 的 `single-role`）一并收进「只在未落地卡上判」的状态门：

```ts
 for (const task of tasks) {
   if (task.status === 'dropped') continue
+  // **DEF-119**：已落地卡（done/verified）是历史 —— 与下面 impact-undeclared 同一口径，不重写历史
+  const settled = task.status === 'done' || task.status === 'verified'
   if (!isRole(task.role)) { /* 建议一并收进 !settled：历史卡改不了角色，判红只会挡住派发 */ }
-  if (task.writeScopes...) { /* write-scope-empty */ }
-  if (task.dod.length === 0 ...) { /* dod-nonempty */ }
-  if (task.size === 'large') { /* size-cap */ }
-  if (task.evidenceRequired.length === 0) { /* evidence-required */ }
+  if (!settled) {
+    /* 上面四块原样搬进来，文案与 code 一个字都不要改 */
+  }
-  if (task.status !== 'done' && task.status !== 'verified') {
+  if (!settled) {
     /* impact-undeclared —— 逻辑不动，只是复用 settled */
   }
```

**守卫（必须先找对文件）**：`validatePlan` 的既有用例在 `test/m101.test.ts` 一带（先 `grep -rn "validatePlan" test/` 定位，**不要另造测试文件**）。加一格：

- 构造 `{ status:'done', writeScopes:[], dod:['x'], size:'large', evidenceRequired:[] }` ⇒ `validatePlan` 对它**不含** `write-scope-empty` / `dod-nonempty` / `size-cap` / `evidence-required`；
- 同形状但 `status:'planned'` ⇒ **四条全在**（两态都要断言，不许只测"松了"）。

**验收（三格，缺一不算）**

1. 现盘（含 `TASK-145/151/152/153` 四张 done 且空写范围的卡）跑 `sdo_plan action=next` ⇒ **不再因这几条判红**，能正常挑卡（把回执原文贴进报告）。
2. 新建一张 `planned` + 空写范围的卡（可以先建后 drop 掉）⇒ 仍判 `write-scope-empty`（**没松过头**）。
3. 全量套件全绿 + 新增两态用例各一条。

### 1.2 `DEF-118`（major，破坏力=blocker）—— `drop` 能抹掉已完成卡

**已发生的事（驾驶舱自己的误操作，如实记）**：驾驶舱把校验器的 `write-scope-empty` 提示误读成"废卡证据"，对 8 张**已完成**的 reviewer 卡（`TASK-081/082/083/085/086/087/088/089`，各自评审 `TASK-068/072/073/077/078/079/074/080`、带 `REV-037…046`）连发 8 次 `drop` ⇒ **全部成功、零警告**：`status` 变 `dropped`、卡面 `evidence` **清空**（现读 8 张卡的 evidence 条数均为 `0`）。台账 `task/done` 仍在（seq 2512/2509/2526/2522/2675/2659/2674/2668），8 条 errata 已逐张追加。

**为什么这是机制缺陷**：`update` 对 done 卡会拒（"历史不重写"），**`drop` 却能把整张卡的完成态抹成"作废"并丢掉 evidence** ⇒ 结构上**只能向下、不能向上**（`TASK_ACTIONS` 里没有 reopen/restore，`src/types.ts:1449`）。

**修法（三件，缺一不可）**

1. `drop` 前若 `status ∈ {done, verified}` ⇒ **拒绝**，并给两条确定出路：① 先显式 `reopen`（见 3）并给理由；② 或改用 `update` 补字段。回执里要逐字说明"这张卡已完成，不能 drop"。
2. **卡面 `evidence` 不因 `drop` 清空**（evidence 是历史事实，与 status 无关）。
3. 新增 `reopen`（done/verified → in-progress）与 `restore`（dropped → 上一状态）两个动作：**必须带 `reason` 与 `approvedBy`**，落 `task/reopened` / `task/restored` 事件，回执回显前后状态。

**验收**：① 对 done 卡 `drop` ⇒ 被拒 + 给出路；② drop 一张未落地卡后，它的 evidence（若有）仍在；③ `reopen`/`restore` 可用且落事件、无 reason 被拒。

### 1.3 `DEF-117`（major）—— `verify-review` 缺「核实者 ≠ 评审作者」闸

**证据**：`TASK-153` 的会话 `a2d4b198` 既是 `REV-056` 的作者，又落了那 9 条 `verify-review`（走 `claim-released` + `same-role` 放行）⇒ **自证**。现存的 `M103-09/10` 只判"谁能核"，不判"是不是同一个人"。台账里也**无法区分** independent / same-author。

**修法**：① `verifier.sessionId === review.sessionId`（或同一 agent 身份）⇒ **拒**，回执给两条出路（换同角色会话 / 走人工核实并留痕）；② `review/verified` 事件加显式字段 `independence: 'independent' | 'same-author'`，历史记录缺省 `unknown`；③ 与 `DEF-099` 合并成同族注释（"闸门在`谁`上做对了、在`是不是同一个人`上没做"）。

**验收**：① 作者本人再核 ⇒ 被拒；② 换会话同角色 ⇒ 通过且事件带 `independence: independent`；③ 既有 `verified.yml` 里的记录不被改写（只加缺省）。

### 1.4 `DEF-120`（major）—— `m38` 的「对照态」依赖台账现值 ⇒ 台账一动就假红

**这是写书当天（2026-10-18）新暴露的一条**，属 `DEF-114` 的同族反向：`DEF-114` 是"真源存在即红"，本缺陷是"**台账一动就红**"。

**实测**（连采两次一致）：

```
not ok 13 - TASK-019 真机接线：本仓现取一次回归链（真源在盘上 / 不在盘上两态都必须判得出可复算的结论）
对照态（齐备 + 哈希一致）必须判绿，否则下面的"判红"没有判别力：
  回归链不通过（不完整）：变更集 101 项 → 影响集 424 项（走过 1154 条边 / 图里共 577 条）
  → 影响集内用例 59 条；回归集 59 条（通过 59 / 未通过 0 / 没跑 0 / 过期 0 / 未绑产物 0 / 产物找不到 0）
`incomplete` !== `ok`
```

**根因**：`.sdo/testing/regression.yml` 是 `TASK-064` 在 18:25 落的快照（当时**变更集 100 项** = 6 条已批准 CR + 94 条 `status=fixed`）；驾驶舱随后把 **`DEF-114` 置 `fixed`**（+1 ⇒ **101**）、做了 8 次 `drop` / 7 次 `update` / 若干评审落账 ⇒ **台账合法地动了** ⇒ 影响集里出现没有结果的用例 ⇒ `incomplete`（**这是正确读数**），但探针的"对照态"要求 `ok` ⇒ 假红。

**修法**：把"对照态"改成**纯夹具世界**（不读真实 `.sdo/`：合成 store + 自造 changeSet/impact/graph/results/artifact），并加一格**台账无关性**守卫：同一份夹具在**两份不同的台账快照**下都必须判 `ok`。
**验收**：① 现盘（101 / 59）跑全量 ⇒ m38 全绿；② 再动一次台账（例如另一条缺陷置 fixed）⇒ m38 **仍**全绿；③ 真实 `stale`/`incomplete` 的判别力仍在（用夹具构造出来）。

> 附带：这条缺陷也解释了为什么**不要**把"当前台账读数"写进测试的**绿侧**断言 —— 只要项目还在推进，台账就会动。

## 2. 签字与交付真源（安全性，都是"信任根"上的洞）

### 2.1 `DEF-112` —— 签字完整性

- **已发生**：`gate/signed` 事件 seq **3490** 的 `channel` 被记成 **`command`**，`basis` 是一句**工作指令**（"把 REQ-060 补进需求基线，重签 G2"）⇒ **指令被当成批准**、门禁当场变绿（后被驾驶舱用 `requirement/updated` 作废）。
- **修法**：① `channel === 'command'`（或插件判定"引用是祈使句/指令形态"）⇒ **拒签**并说明"你给的是一句指令，不是审核后的批准"；② 签字前必须有**可核的"已呈现"记录**（审核单内容 sha256 + 呈现时刻；用户回执里至少引用该 sha 或审核单里的一个判据 id），缺失即拒；③ 未呈现时回执给可执行出路（"先把审核单正文贴给你/在侧边栏打开，再签"）。
- **验收**：① 纯指令形态 ⇒ 被拒；② 无"已呈现"记录 ⇒ 被拒；③ 正经路径（用户看过审核单后表态）**仍能签过**。

### 2.2 `DEF-110` —— 签字问答通道时好时坏

- **证据**：同一条通道历史上成功过 4 次（`gate/signed` seq 1195/1197/1706/1741）；本轮 seq **3479** 成功传回用户选择，seq **3484** 却记下**插件自己的诊断**「侧边栏没弹出」；`tools.ts:1443-1444` 注释写明"需要宿主注入的 answerer"。
- **修法**：① 拿不到 answerer 时，回执**必须**给可执行出路（不要让用户只看到"没弹出"）；② 台账把「没弹/未答复」与「用户拒签」**分成两个事件**（现在都落 `sign-rejected`，事后无法区分）；③ 建议把"问答通道可用性"作为启动自检（不可用就提前说）。

### 2.3 `DEF-113` —— 只读卡能写交付真源

- **已发生**：`TASK-150`（tester，只读补核卡）误调 `sdo_deliver action=package` ⇒ 生成了本项目**第一个**交付包 `DLV-001` + 两份派生文档；子会话自己发现"`gates.ts:2182` 的 `delivery.manifest` 判据会读它"并删回原状，但 **journal `delivery/packaged`（seq 3497）抹不掉**。
- **修法**：① 把 `sdo_deliver` 从 `tester` 面移除（它属于 `delivery` 角色）；② 若确需，只给只读的 `sdo_deliver action=show` 子面；③ `action=package` 前校验调用方角色/卡上是否声明交付落点；④ 台账补一条"作废标注"（`delivery/voided {id: DLV-001, reason}`），让判据与读者能区分误记录。

### 2.4 `DEF-107` —— 交付绑定实践

`delivery.bind: commit` 已通电（`ea82e05` 提交信息里有 23 个 64 位 hex），但**交付包记录几乎为空**（`DLV-001` 还是误操作）。修：明确"什么时候必须 `sdo_deliver action=package`"（建议：每条交付卡 done 时、以及每次门禁签字前），并给"没有交付包"一个可读的判据读数。

## 8. 已知的坑（沿用第 12 版清单 + **本批新增 6 条**）
