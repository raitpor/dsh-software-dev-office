# 需求变更强制回退（语义 A）· 设计（2026-10-04）

## 0. 问题（真机证据，sdo-test 台账）

```text
12:36:24Z  change/requested   CR-001
12:36:24Z  change/decided     CR-001 → approved
12:36:24Z  requirement/updated REQ-012
12:36:47Z  task/claimed       TASK-041     ← 批准后 23 秒，开发照常继续
12:37:02Z  dispatch/started   TASK-041
```

⇒ 变更批准后**没有回到需求阶段**，构造阶段一路绿灯。**用户的判断（本设计的动机）**：
> 需求变更后若不重新设计，这个需求就是让模型自由发挥了 —— 那这条需求**无法管控**。

## 1. 根因（代码侧）

1. `src/domain/change.ts` 里 **`phase` 出现 0 次** —— 变更只做"登记 + 决策 + 影响面"，**不改阶段、不碰基线**；
2. 四个流程的 `rollback:` 块里都写着旧口径注释：
   > 「未列入 requirements —— 改需求走 `sdo_requirement action=change` 的变更控制，不靠回退绕行」

   而那条"变更控制"实际只**让 G3 签字失效**（设计侧），**没有任何判据**说"变更没消化完，后面不许开工"；
3. `construction: [design-plan, architecture]` —— **没有**直达 `requirements` 的边（`architecture: [requirements]` 有）。

## 2. 目标语义（A，本次确认）

**批准的需求变更 ⇒ 强制回到需求阶段重走整条链**：

```text
change approved
  → 阶段回退到 requirements（留痕：reason = CR-xxx）
  → 更新受影响需求（REQ-* 版本 +1）并**重新冻结 G2**（重新基线）
  → 重走设计：受影响设计元素/契约重新确认 → **G3 重新通过**（签字重签）
  → 之后才允许继续开发（构造阶段的写入/认领重新开放）
```

要点：**不是"提醒"，而是"拦住"** —— 在 G2 重新冻结且 G3 重新通过之前，构造阶段的 `claim` / 代码写入一律拒绝。

## 3. 改动点（四处 + 用例/变异）

### 3.1 流程数据（`src/data/processes/*.yml`）

- 给 `construction` / `iteration` / `verification` / **`delivery`** 的 `rollback` 补 `requirements`（让"回到需求阶段"是**合法回退边**，
  这样 `phase.rollback-recorded`（C-2E）的留痕检查照旧成立）；
- **删掉/改写**那句"不靠回退绕行"的旧注释 —— 它与本设计相反，留着会误导后来者。

### 3.2 变更批准时执行回退（`change.ts` + `office`）

- `sdo_requirement action=change` 在写入 `change/decided(approved)` 后：
  - 若是**批准**：追加 `change/rollback`（`{change: CR-xxx, from, to: 'requirements'}`）并执行
    `office.rollbackPhase(→ requirements, reason = 'CR-xxx 已批准：需求变更后必须重走需求→设计' )`；
  - 回执明确写三步走：**更新受影响需求 → 重新冻结 G2 → 重走设计并重过 G3**（之后才能继续开发）；
- 若决策是 `rejected`：**不动阶段**（不打断当前工作）。

### 3.3 机械拦截（`claim` + 纪律钩子）

- 新错误码 **`change-not-digested`**：存在**已批准且未消化**的变更时，构造阶段的 `claim` 直接拒绝，详情点名 CR 与"下一步做什么"；
- "未消化"的机械定义（从 journal 现算，不新增真源）：
  `存在 change/decided(approved) 的 CR，其 `change/rollback` 之后的**最近一次 `requirement/baselined` 早于它**，
  或该 CR 引用的需求（`impact.requirements`）不在当前基线里` ⇒ 未消化；
- **G3 之后才能继续开发**这一半由"阶段纪律"天然承担：回退到 `requirements` 后，代码写入本就被阶段纪律挡住；
  `claim` 这一半由上面的新拦截补上（`claim` 今天不受阶段纪律约束）。

### 3.4 用例与变异（实现时同步做）

| 用例 | 断言 |
|---|---|
| `M35-01` 批准变更 ⇒ 阶段回到 requirements | `phase` 事件序列 + `change/rollback` 留痕 |
| `M35-02` 未消化期间 `claim` 被拒 | 错误码 `change-not-digested` + 点名 CR |
| `M35-03` 重新冻结 G2 后仍不能开发，直到 G3 重新通过 | 回退链走完后 `claim` 放行；**只冻结 G2 时仍拒绝** |
| `M35-04` 反向 | 无变更 / 已消化 / `rejected` 的 CR ⇒ 不拦（避免误伤正常流程） |
| 变异 | 去掉自动回退 ⇒ M35-01 红；去掉拦截 ⇒ M35-02 红；把"待 G3"降级成"待 G2" ⇒ M35-03 红 |

## 4. 兼容与边界（如实）

- **会影响正在构造阶段的项目**（升级后第一次批准变更就会触发回退）⇒ 写进 CHANGELOG 的升级须知；
- **低影响变更也走同一条路**（不按影响面分级）：分级会引入"什么算低影响"的判断口子，正是本设计要堵的；
- **交付后重开**（`delivery` 的 `architecture` 回退边）与本次的变更回退并存：两者都由 `C-2E` 留痕约束；
- 回退本身**不动历史事件**（append-only）⇒ 已完成的卡不被追溯判红，但**新**的认领/写入会被拦住。

## 5. 与既有机制的关系（复用而不新造）

| 需要的东西 | 复用 |
|---|---|
| 阶段回退与合法边 | `office.rollbackPhase` + `legalRollbackTargets`（流程数据声明） |
| 回退留痕 | 既有 `phase/rollback-recorded` 判据（`C-2E`） |
| 重签 | 既有签字/确认机制（内容指纹绑定，G3 重过即重签） |
| 代码写入的阶段纪律 | 既有 `discipline`（`requirements` 阶段不允许写实现代码） |
| 变更登记 | 既有 `change/requested` / `change/decided` |

## 7. 实施记录（2026-10-04 完成）

这一节记录**实施与原设计的差异**与**已核实的证据**，便于后来者复核（不修改上面的设计意图）。

### 7.1 与原设计的差异（两处，都是有意的）

| 差异 | 原因 |
|---|---|
| 目标阶段不写死 `requirements`，而是取**出口门禁是 `G2` 的那个阶段**（`change.ts`/`office.rollbackForChange`） | 阶段 id 是流程数据的一部分；四个随包流程当前都叫 `requirements`，但数据改名不该让代码判错 |
| "设计门"不写死 `G3`，而是取**需求阶段之后那个阶段的 `exit`**（新增 `process.designExitGates`） | 同上；同时让"必须重过哪道门"这件事**只有一个来源**（流程数据），回执里点的门与实际判的门同源 |
| `delivery` 也补了到 `requirements` 的边（原设计只列 construction/iteration/verification） | 否则在交付阶段批准变更会**回退失败**（没有合法边）：代码写入虽然仍被阶段纪律挡住、认领也被拦，但"回到需求阶段"这一半做不成。统一成"任何阶段的批准变更都能回到需求"更好推理 |

### 7.2 "未消化"的最终判据（实现口径，与 §3.3 等价但更精确）

```text
对每条 change/decided(decision=approved) 的 CR（记批准序号 S）：
  ① 存在 requirement/baselined 且 seq > S，且其 ids 含该 CR 的受影响需求
     （`ids` 形状坏掉 ⇒ 不算覆盖；N-14：内容没变的需求重新基线不写事件 ⇒ "没真改需求"消化不掉）
  ② 存在 gate/result 且 gate ∈ 设计门 且 status ∈ {passed, waived} 且 seq > ①的序号
  两条缺一 ⇒ 未消化 ⇒ 构造阶段 claim 拒绝（change-not-digested）
```

取"设计门"用**阶段出口**而非**签字状态**，是为了让 `G3` 被显式豁免（`waivedGates`）的项目也能消化 ——
签字状态在豁免下永远是 `missing`，会把项目**永久卡死**。顺序上 ① 先于 ②，且只在 ② 缺失时回报
"已重新基线、缺设计重过"（回执能直接指向下一步）。

### 7.4 事后出口（实施中补的一条）

`sdo_status` 增「已批准但尚未消化的需求变更」块，文案**复用** `describeUndigestedChanges`（与拒认领同一份口径）。
理由：拒绝回执只在**那一次**调用里出现，重启/上下文压缩之后就没了 —— 状态块是模型能主动拉的唯一出口。
