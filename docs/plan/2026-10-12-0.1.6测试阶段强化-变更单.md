## 6. 六个面的方法学结论

| 面 | 结论 |
|---|---|
| **面1 测试级别** | 单元 / 集成 / 系统 / 验收**都做**（V 模型，验收准备左移到 G2）；**回归**做成一等纪律；**冒烟**复用既有真机运行记录（`RUN-`）作口径，不新造实体；**探索式**只登记、只产出缺陷；**非功能**本轮只做「承接复核」（把实现侧记录按测试者口径复算），不接工具链 |
| **面2 用例设计技术** | **黑盒**：等价类 / 边界值 / 判定表 / 状态迁移 / 场景 / 组合（REQ-048）；**白盒**：控制流图 / 圈复杂度 / 独立路径集 / 条件组合 / def-use（REQ-056）。两侧同规：必产项被用例反向引用、出处可核对（防凑数） |
| **面3 充分性（怎么算测够了）** | 准出准则由**流程官**声明、门禁**逐条现算**、**禁止加权合并**（REQ-050）；覆盖率、变异得分、风险矩阵可当准则，缺陷密度无基线时只能作可见依据；**用户签字是最终解释，但不改变机械判定**（REQ-051） |
| **面4 判定基准与独立性** | 每条用例必填 oracle 四类之一（REQ-054）；执行者 ≠ 采纳者，开发侧单元结果须独立评审采纳（REQ-053） |
| **面5 过程与策略** | 选包主体 = 流程官（被考核者不自己定标准）；时序：**G2 验收大纲 → G4 计划 + 设计规格 + 准出准则 → G6 报告 + 用户签字 → G7 验收 + 用户签字**；计划先过 **plan mode** 评审（REQ-047）；已过门禁不追溯 |
| **面6 缺陷闭环** | 缺陷含根因 / 发现级别 / 逃逸；`fail → 修复 → 同用例重跑通过` 现算；逃逸必须反向补用例（REQ-016 + REQ-012 的缺陷边） |

## 9. 影响面与回退（含诚实说明）

- **机械影响面为空**：变更批准的瞬间，追溯图里没有任何 `req-des` / `req-task` / `req-tc` 边 —— 当时设计尚未落笔。插件如实报「本次影响分析只能给出空集」，并**仍然作废了设计门 G3**（理由：不拿「图里没写」当放行理由）。这条口径写进了回执。
- **强制回退事实**：`architecture → requirements`，G2–G7 旧判定全部作废；`sdo_task action=claim` 在变更未消化期会被 `change-not-digested` 拒绝。
- **消化路径**：① 更新受影响需求（已完成：CR-001/002/003 + REQ-045 update）→ ② 重签 G2 并冻结 57 条基线 → ③ 重走设计并重过 G3。
- **恢复代价**：低 —— 设计未落笔、G2 未签字时插入变更，回退几乎零代价；这正是本次选择在此刻插入的原因。

## 10. 治理观察（本轮的实际收获）

用户点出的一条价值，值得留在档里：

> 本次补白盒需求就是本插件的其中一个重要意义 —— **对齐需求，以及人审门禁，避免了要做的遗漏**。

具体表现：变更落地后 G2 仍未签字，用户在复核时连问两次 ——「测试相关的新增需求在哪里」「有白盒相关内容吗」—— 第一次促使我把 13 条新增需求摊开，第二次**直接暴露了白盒侧只有读数、缺设计技术与未覆盖处置的缺口**（黑盒 6 项对齐了，白盒没对齐）。若当时直接签字进入设计，这个缺口会一直留到实现阶段才被发现。

**可复用的教训**：门禁签字之前的复核不能只看"有没有"，还要按**对称性**逐面检查 —— 黑盒有技术集，白盒也必须有；有覆盖读数，就必须有未覆盖项处置；有变异存活项处置，就不能漏掉未覆盖项处置。
