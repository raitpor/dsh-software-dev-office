## 二、建议的目标模型（供讨论，未实施）

### 2.1 需求阶段新增一份「设计适用性声明」（G2 由用户确认）

```yaml
# .sdo/design-applicability.yml（需求阶段产出，G2 门禁要求已确认）
nature: greenfield | refactor | port      # 项目性质（用户选，模型给推荐）
surfaces: [web, desktop, mobile]          # 已有字段，复用
behaviour: preserve | change | extend     # 重构/移植默认 preserve：逻辑必须保持不变
uiChange: none | light | redesign         # 界面是否要动（纯后端 = none）
confirmed: { by: 用户名, at: 时间 }
```

派生规则（**门禁现算，不缓存**）：

```text
必需视图      := f(nature)                     # 见下表
必需方法产物  := g(method 选择)                # 沿用已实现的方法包
不变量        := behaviour == 'preserve' ? 必需 : N/A
旧→新映射     := nature in {refactor, port} ? 必需 : N/A
差分验证策略  := behaviour == 'preserve' ? 必需 : N/A
ui.*          := (任一需求 kind: ui) ∨ surfaces 非空     # 已实现，保持
```

### 2.2 各性质下的必修工件（草案，**需要你定**）

| 工件 | greenfield | refactor（逻辑不变） | port（旧写法→新写法） |
|---|---|---|---|
| 五视图（context/component/data/runtime/deployment） | 必需（现状） | **只画受影响部分**（增量视图） | **只画受影响层** + 平台映射视图 |
| 方法包（结构化/OO/演进式最小必产项） | 按所选方法必需 | 按所选方法必需（但产物可只覆盖改动面） | **建议不适用或另设"迁移设计"**（见 §4.3） |
| **不变量清单**（哪些逻辑/数值/接口必须不变 + 如何验证） | N/A | **必需** | **必需** |
| **旧→新映射表**（模块/类/API ↔ 目标写法） | N/A | 建议 | **必需** |
| **差分验证策略**（同输入同输出 / 回归基线） | N/A | **必需** | **必需** |
| 界面方案（风格/栏目/布局） | 视 `surfaces`/`kind: ui`（现状） | 视 `uiChange` | 视 `uiChange` |
| 交付包（sha256/验收矩阵/回滚点） | 必需（现状） | 必需 | 必需 |

## 四、需要你决策的四个点

1. **`nature` 取值**：就 `greenfield | refactor | port` 三类，还是要更细（如 `rewrite`=重写、`migration`=数据迁移、`integration`=接第三方）？
2. **是否引入第 4 个方法包"迁移/映射设计"**：`structured / oo / evolutionary` 这三轴对"移植 MC 模组"其实都**不贴合** ✗ —— 移植的核心是*映射 + 不变量 + 差分*。建议把它做成第 4 个包（如 `porting`），与三套并列可选。
3. **refactor/port 下"五视图"到底怎么裁**：A) 必须给"增量视图"（只画受影响部分）；B) 视图判据判 N/A，只要求不变量+映射+差分；C) 保留五视图但允许 `elements` 只填受影响项。
4. **存量项目默认值**：缺 `nature` 字段的老项目按 `greenfield` 处理 ✓（我认为是唯一安全默认）；旧的方法论答案（如"组合（主干结构化+前端面向对象）"）是否自动折算，或强制重答？

## 六、用户决策记录（2026-09-30）

1. **项目性质在需求阶段确定**（不再留到设计阶段才问）。
2. **设计门禁的适用性由性质推导**：按 §2.2 的表决定"要不要求各视图齐备、要不要不变量/映射/差分验证"。
3. **设计阶段允许回退需求阶段**：设计途中若与客户沟通发现需求缺口或性质判断有误 → **回退到 requirements**，需求明确后再继续 design。
4. **G3 必须经用户签字确认才可通过**（在逐条 `confirm` 之上再加一道**门禁级签字**）；其余判据照常按性质派生。

### 6.1 新增能力一：阶段回退（今天没有）

现状：`SdoProject.phase` + `phaseHistory` 只记录**前进**（`types.ts:106-112`），没有回退动作 ✗。

规格（建议）：

```text
sdo_phase action=rollback to=requirements reason="…" by=<用户>
  · 要求 reason 非空（写清发现了什么需求缺口）
  · 落 journal：谁、何时、因何回退、从哪个阶段退到哪个阶段
  · 标记"门禁失效"：回退后 G2 需**重新通过**（需求基线可能变成新版本 v0.2→v0.3），再进 G3
  · 允许的合法回退边（不要任意跳）：design → requirements、design → feasibility、
    plan → design、build → design…（按流程数据声明，而不是硬编码）
```

判据：`phase.rollback-recorded`（回退必须有 reason + 恢复后对应的门禁重新通过 ✓）。

### 6.2 新增能力二：门禁级用户签字（今天没有）

现状：已有**逐条**确认戳（`ui:<id>:style`、`DESC-001`、`CT-001`…）✓，但**没有**"整个 G3 由用户批准"这一级 ✗。

规格（建议）：

```text
sdo_gate action=sign gate=G3 by=<用户名> note="…"      # 或 /sdo-sign G3 --by …
  · 门禁判定时：signature 缺失 → G3 **不可通过**（哪怕其余判据全绿）
  · 签字记录落 journal，含来源通道（命令面 / 问答面）与时间
  · 需求或设计在签字之后发生变更 → 签字**自动失效**（按 journal 序号比签字时间更晚）
```

### 6.3 ⚠️ 必须先定：签字"是谁签的"

这是可信度问题 ✗：工具（`sdo_*`）**由模型调用** ✗ → 若签字做成工具动作，**模型可以替用户签** ✗，门禁就形同虚设。

| 方案 | 真实性 | 可用性 |
|---|---|---|
| **A. 只用命令面** `/sdo-sign G3 --by 张三` | ✅ 最强：命令只能由**人**输入（模型无法调用命令面） | ❌ headless / ACP 环境没有命令面（命令是交互式 Web/CLI 专属） |
| **B. 只用问答面**（走 `ask_user_question` 类人机关口） | ⚠️ 中等：用户确实点了，但答案经模型之手转记 | ✅ 所有环境可用 |
| **C. 两者都支持，记录"来源通道"**（命令面 = 强签字 / 问答面 = 弱签字，回执如实标注） | ✅ 诚实且不牺牲可用性（默认要求强签字，headless 下显式放宽） | ✅ 覆盖面最广 |

**我建议 C**，默认要求**强签字**（命令面），headless 场景需显式开启"弱签字可用"并让门禁回执标注来源。

## 七、最终决策与实现规格（2026-09-30 二次确认，**以此为准**）

> 用户答复要点：**项目性质不定枚举**；**不靠机械推导门禁，改由模型定**，但**必须向用户说明视图情况（哪些有哪些没有）**；
> **签字 = 用户在会话中明确说明签字确认，或在 ask 选择里明确选"签字"**；新增 `porting` 方法包；五视图保留结构但只要求受影响部分有内容；存量项目**强制重新声明**。

### 7.1 设计适用性声明（替代"性质枚举 + 机械推导"）

```yaml
# .sdo/design/applicability.yml —— 需求阶段产出，设计阶段受它约束
focus: "旧系统重构：只优化流程与效率，业务逻辑不变"      # 自由文本（模型写，说明本项目性质与设计重点）
viewsPresent: [context, component, runtime]            # 模型声明：本项目要做哪些视图
viewsAbsent:                                            # 必须逐条给理由，且必须让用户看到
  - { kind: data, why: "数据模型沿用旧库，本次不改" }
  - { kind: deployment, why: "部署形态不变，仅替换内部实现" }
artifacts: [invariants, mapping, diffVerify]           # 本次必需的非视图工件（见 7.3）
confirmed: { by: "张三", at: "…", basis: "用户原话/问答选项" }
```

**规则**：
- 声明由**模型**起草（在需求阶段末/设计阶段初），但**不得静默**：必须在**注入块 + `sdo_design action=issues` + `docs/DESIGN.md`** 三处向用户列出「本项目要做哪些视图、哪些不做及理由」。
- 门禁**不做性质到判据的机械映射** ✗；改为：
  · `viewsPresent` 里的视图 → 必须非空且经确认 ✓
  · `viewsAbsent` 里的视图 → 相关判据 **N/A + 该条理由** ✓（沿用三态 ✓）
  · `artifacts` 里的工件 → 必须齐备 ✓（见 7.3）；未列入的不要求 ✓
- **签字绑定这份声明**：声明变了 → 签字自动失效 ✓（按 journal 序号比较时间 ✓）。

### 7.2 门禁签字（按用户口径）

- **来源**只承认两种：① 用户在会话中**明确表述**"签字确认/批准"；② 用户在**人机关口问答**里**明确选择**"签字/批准"选项。
- **记录要求（防伪造的关键）**：签字记录必须同时写入**用户原话引用**或**所选选项原文** + 会话轮次引用 ✓ →
  回执与 journal 里显示的是**引用文本** ✓，模型若凭空记录，引用对不上即暴露 ✓（这是本方案唯一的可审计保障 ✓，必须实现 ✓）。
- **未签字 → G3 不可通过**（其余判据全绿也不行 ✓）；回执要明确写"等待用户签字确认"。
- 设计/需求在签字后发生变更 → 签字失效 ✓，需重新签字 ✓。

### 7.3 新增方法包 `porting`（与三套并列可选）

| | 内容 |
|---|---|
| **最小必产项** | ① **旧→新映射表**（模块/类/API 级：旧写法 → 目标写法，含替代方案与被否决原因）<br>② **不变量清单**（行为 / 数值 / 存档格式 / 协议与 id 映射 必须保持不变；**每条必须带验证方法**）<br>③ **差分验证策略**（同输入同输出、回归基线、对照版本仓库等） |
| 机械检查 | 映射表每条两侧非空且引用真实存在的模块/类型；不变量每条 `verify` 非空；差分策略必须给出可比对的基线来源（测试/黄金样本/上游分支）✓ |

### 7.4 五视图规则（用户选择）

保留五视图**结构** ✓；`viewsPresent` 的视图必须**非空** ✓（"受影响部分有内容"即可 ✓，不要求覆盖全系统 ✓）；
`viewsAbsent` 的视图判 N/A + 理由 ✓。**必须向用户说明哪些有哪些没有** ✓（见 7.1）。

### 7.5 存量项目

无 `applicability` 声明的项目 → **G3 判红**（强制重新声明 ✓）。
⇒ 影响：`sdo-test / PRJ-001` 需要补一次声明（它正在重走设计交互，可合并做 ✓）。

### 7.6 验收要点（实现时必须双向覆盖）

1. 无声明 → G3 红；声明后（视图齐备 + 工件齐备 + **签字**）→ 绿。
2. `viewsAbsent` 的视图：其判据 `na===true && ok===false && naReason` 非空且等于声明理由 ✓；且**声明中未列入也未说明的视图**不得出现（必须显式二选一 ✓）。
3. 签字：**未签字时即便其余全绿也判红** ✓；签字后绿 ✓；签字后声明变更 → 签字失效 → 再红 ✓。
4. 签字**必须带引用文本**：无引用的签字视为无效 ✓（防伪造 ✓）。
5. `porting` 包：缺映射/缺不变量/不变量无 verify → 红；补上 → 绿 ✓。
6. 存量项目（无声明）→ 红，且提示是"未声明适用性"而不是其它原因 ✓。
