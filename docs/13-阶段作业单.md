# 阶段作业单：每个阶段要产出什么、什么时候算完

> **框架坐标**（对齐 [01 理论与边界](01-理论与边界.md)）
>
> - 守的层：**L1 · L2 · L3**
> - 涉及真源：三者
> - 对应命题：命题 1–5
> - 本文引入/定义的概念：阶段产出、24 条阶段判据、最小作业单

> 前 12 篇回答的是**机制怎么运作**（真源、判据、签字、派发、影响链）。
> 这一篇回答另一半：**一个项目从想法到交付，每个阶段人要产出什么、什么算完成、什么不做**。
> 没有这一篇，机制是空转的——知道"条款必须有 consumer"，不等于知道"需求阶段该写哪几样东西"。

## 1. 这一篇是什么：`waterfall` 的作业单，不是写死的生命周期

**阶段由 policy 决定，不是写死的。** 本篇列出的是**每一类阶段要做哪些作业**；下表是 `waterfall`（[08](08-方法论与策略.md) 的内置 preset 之一，等价旧称 `linear`）的五段映射，其它 policy 用同一批作业按各自阶段名组合。

**policy 是配置不是分支**：内置三个 preset（`waterfall` / `prototype` / `incremental`），用户也可以写自定义 policy（同一份 schema）；它随 baseline 一起**立项冻结、运行期不换**（换 = 新 baseline + 签字）。

| policy | 对应本篇的阶段 | 说明 |
|---|---|---|
| `waterfall`（旧称 `linear`） | 需求 → 设计 → 实现 → 评审 → 交付 | 本篇正文按这个写；stage 名与 `kinds` 的对应见 [08](08-方法论与策略.md) §1 |
| `prototype`（旧称 `spike`） | explore（只验可行性）→ harden（补需求 + 设计 + 实现 + 评审）→ deliver | `explore` 只承担 `implement` kind ⇒ 需求/设计/评审类判据在那里记 **`na`**（`reason='stage_not_applicable'`）；`harden` 承担 `requirement/design/implement/review` ⇒ 从那里起重新适用（「harden 补评审」靠的就是这个 `review` kind）。**注意 `na_stages[]` 记的是整个 policy 缺哪个 kind**（这个 preset 五个 kind 齐 ⇒ 为空），不是逐阶段的 `na` |
| `incremental` | 每 lane 走实现+评审，全局 integrate ≈ 交付 | 需求/设计在 lane 外做一次（`req_design` 承担 `requirement/design` kind）；**lane 是派发层的并行**，不是 policy 字段 |

**stage 名是自取的，`kinds` 才是接缝**：判据的 `applies_to` 只认 `requirement/design/implement/review/deliver` 五个 kind（[04](04-判据-门禁与负例.md) §4.1），所以 policy 里每个 stage 必须声明 `kinds[]`；`na` 由"该 stage 的 kinds 与判据的 applies_to 是否相交"算出。

**`na` 的语义**：`stage.*` 判据在当前 policy 下**不适用**时，判 `na`（不是 `pass`，也不是 `pass` 的别名）；`verify` 与视图必须能把 `na` 与 `pass` 分开显示，否则"没评估"会被读成"通过了"。

**`explore` 是单人的默认起手，不是降级模式**：需求还在脑子里时，先写 `intent` + 一句可判的验收，跑通再补 `spec`；把探索逼成"先编条款"会制造假精确，比返工更贵。

## 2. 阶段作业（下表按 `waterfall` 的五段列，policy 可换阶段名）

### 2.1 每个阶段的"对齐检查点"（唯一不能省的作业）

**返工不是执行不力，是两边理解不一致还动工了。** 所以每个阶段在**产出物之后、进入下一阶段之前**，必须先过一道对齐检查——不是评审，不是签字，是"你说的和我理解的是不是一回事"：

| 检查点 | 谁做 | 产出 | 不过怎么办 |
|---|---|---|---|
| **复述** | agent 先独立复述意图（不看条款） | `restatement` + `restatement_diff` | 每条差异必须处置（accept/reject/block）；`defer` 视同没对齐 |
| **例子** | agent 给 **2 个具体例子 + 1 个反例** | 写进 `scenario` 或 `criterion` 夹具 | 给不出反例 ⇒ 说明边界没想清，回去问 |
| **回指** | 人用自己的话确认"这就是我要的" | 人对每条 `restatement_diff` 给出 `accept`/`reject`（**不存在"我看过了"这种处置**） | 有未处置行就进入下一阶段 ⇒ 记 `rework`（返工来自没对齐） |

> 三条都过了才算对齐。**对齐的花费必须远小于一次返工**：一轮复述 + 三个例子是分钟级；做错一个模块是小时到天级。

### 2.2 五段作业表

| 阶段 | 目的 | 必须产出（台账行 / 仓库文件） | 完成的判据 | 主要执行者 |
|---|---|---|---|---|
| **需求** | 说清"要什么" | **`restatement` + 差异处置**（先对齐）· `intent`（一句话，人签）· `spec` 条款 · `scenario`（人审步骤）· `criterion`（正负例 + remedy）· `scope` 声明 | **对齐三件套先过**（复述/例子/回指）；每条条款**被一条判据或一个场景消费**；每条判据 ≥1 正 1 负，且条款有 2 正 1 反 | 人主导，agent 起草 |
| **设计** | 说清"怎么做" | `spec(kind=design)` 条款 · `spec(kind=contract)` 跨模块契约 · **影响面声明** | 每条设计承诺有 consumer；**设计↔代码一致在实现/交付复查**（`design.code_matches`）；**不存在“只在对话里讲过的设计”** | 人决策，agent 起草 |
| **实现** | 把设计变成可验证的改动 | `task` + **`work_unit`（一卡一判据一证据一行）** · 工作副本 · 准入 diff | 判据绿 · 证据绑产物指纹 · `verify` 过 | agent，人抽查 |
| **评审** | 让"完成"不是自说自话 | `review`（发现逐条）· 核实记录 | 每条发现被核实（reproduced / refuted）；`signer ≠ producer` | 另一个会话/人 |
| **交付** | 把版本固定下来（**人先亲手跑几条**） | `release`（范围集合 + 缺口清单）· **人执行的 `scenario` 抽样（≥3 条；高风险条款每条款 ≥1）** · 审计快照 · 冻结签字 | 独立性成立 · 缺口清单 = 集合差集 · 快照可复算 · **`scenarios_run[]` 非空且 `ran_by` 是人** · **只按一把尺子判**（`baseline_hash` 非空且覆盖全部 `in` 证据） | 人签 |

**一条贯穿全部阶段的总则**：**没有落到台账或带指纹的仓库文件的产出，不算产出。**

> **本文不写排期**：没有甘特图、时间线、时间盒、里程碑日期。v2 不做通用项目管理（[01](01-理论与边界.md) 的非目标）——阶段只规定**产出与完成判据**，不规定"多久做完"。

## 3. 需求阶段

### 3.1 要做的六件事

| # | 产出 | 具体形态 |
|---|---|---|
| 1 | **意图** | `intent` 一行：一句话说清"要什么"，带人签的 `decision(kind='intent')`（`approved_by` 只是投影） |
| 2 | **条款** | 每条 `spec`：可判的写 `mech_checkable=1` + `scenario_id`；不可机械判的**必须**挂 `scenario` |
| 3 | **场景** | `scenario`：人审的步骤与预期（"点哪里、看到什么"），**不是断言** |
| 4 | **判据** | `criterion`：`remedy` 非空 + 至少 1 正 1 负夹具 |
| 5 | **风险标记** | **`spec.risk_flags[]`**：`payment` / `auth` / `irreversible` / `cross_module` 任一命中 ⇒ **必须红队**（不填即空集放行，是 `redteam.disposed` 的输入） |
| 6 | **范围** | **`scope_decl(stage='requirement', paths[])`**：本期允许动哪些路径（按前缀）。**注意**：`07` 的 `scope` 是**权限域**，不是项目范围——两者别混 |

### 3.2 什么时候算完

> **每条条款必须被一条判据或一个场景消费；两条都没有的条款 = 没写完。**

配套一条机械检查：条款的 consumer 集合为空 ⇒ `stage.requirement_complete` 红。

### 3.3 不做什么

- **不拆卡**（拆卡是实现阶段的事，需求阶段拆出来的卡一定错）；
- **不写实现细节**（出现"用 Redis 还是 SQLite"就是越界，那是设计阶段）；
- **不写判据实现**（只声明"这条要判什么"，判据怎么写是实现阶段）。

### 3.4 常见反模式

| 反模式 | 症状 | 后果 |
|---|---|---|
| 形容词需求 | "要快"、"要稳" | 无法判据化，后面必然吵 |
| 场景写成断言 | "系统应支持并发" | 人审无步骤，等于没验收 |
| 条款无 consumer | 写了 30 条，判据只有 5 条 | 25 条永远没人验 |
| 意图由 agent 代签 | 没有有效 `decision(kind='intent')`，或 `approved_by` ≠ signer | 越界（见 07 的独立性） |

## 4. 设计阶段

### 4.1 要做的五件事

| # | 产出 | 具体形态 |
|---|---|---|
| 1 | **设计条款** | `spec(kind=design)`：数据模型、接口、状态机；每条能指到一个 consumer |
| 2 | **跨模块契约** | `spec(kind=contract)` + `contract.defined` 事件（必须在第一次写代码前） |
| 3 | **影响面声明** | **`spec(kind='impact')`**：这次设计波及哪些既有条款/判据/卡；越界要显式写 |
| 3.5 | **设计替代方案** | 每条 `spec(kind='design')` 写 `alternatives[]`（考虑过什么）或 `no_alternative_reason`；**≥2 个可行方案** ⇒ 必须链 `assumption` 或开 `attention`（判据 `design.alternatives_declared`） |
| 4 | **分解与集成** | `goal_node` 树（根 = intent，叶 = 可独立验收的块）+ `integration` 清单；**拆法由人声明，不靠运行时自行生长**；**人审的是节点，不是整份设计**：叶（行/不行）→ 父（只看集成清单），单节点判断 ≤ 2 分钟、待审 ≤ 7 项（[01](01-理论与边界.md) §14 · [03](03-链条-意图到声明.md) "分解树首先是人的决策面"） |
| 5 | **产物落盘** | 设计产物进仓库（带指纹）或进台账（`spec.design_artifact_sha256`）；**二者必居其一** |

### 4.2 什么时候算完

> **每条设计承诺都有 consumer**（`view` / `renderer` / `criterion` 任一）。**指纹不在设计阶段查**——`design_artifact_sha256` 记录设计产物，`code_artifact_sha256/ref` 由实现回填，`design.code_matches` 在**实现/交付**复查（否则设计阶段会拿两个不同的哈希硬比）。

机械检查：设计条款的 consumer 为空 ⇒ `stage.design_traceable` 红。

**`no_alternative_reason` 是自报的，必须抽查**：`risk_flags` 非空的设计条款**必须全查**（派红队问"真的没有第二个可行方案？"），其余抽样；否则"没有替代"会变成模型跳过思考的万能理由。

### 4.3 不做什么

- **不写实现代码**（`prototype` 例外：`explore` 阶段允许，但产物只进 `explore`，不进 release）；
- **不宣称"设计已完成"而没有落盘产物**——"我在对话里讲过"不算。

### 4.4 常见反模式

| 反模式 | 症状 | 后果 |
|---|---|---|
| 设计只在对话里 | 找不到文件也找不到台账行 | 无法复核，代码与设计必然漂移 |
| 契约后补 | 代码写完才写 `contract.defined` | 约定形同虚设（[08](08-方法论与策略.md) 的"契约先行"会判红） |
| 影响面不写 | 改一个字段，下游 12 处 stale | 变更阶段才发现，返工 |

## 5. 实现阶段

### 5.1 开工前三问（"没说清楚"的正式出口）

1. **这条卡依赖的每句话都在条款里吗？** 有没被覆盖的选择 ⇒ 要么开 `attention` 问，要么落一条 `spec(kind='assumption')`；
2. **假设处置完了吗？** 关联假设里还有 `open` ⇒ **不许开工**（判据 `assumption.disposed`），不是"先做着看"；
3. **假设错了会怎样？** 写进 `blast_radius`——影响面大且不可逆的假设，必须升级成正式条款，不许留在假设里；
4. **假设被否了，后继在哪？** `rejected` 不算处置完：必须有 `spec.revised`、`converted` 或一条 `change` 指向它，否则仍挡开工。

> 这一节存在的理由：**模型的自由发挥不产生"错误"，产生"没人做过的决定"**。把它挡在开工之前，比事后评审便宜一个数量级。

### 5.2 要做的三件事

1. **拆卡**：一卡 = 一判据 + 一证据 —— 落成**一行 `work_unit(task_id, criterion_id, spec_id, evidence_id)`**（拆不到这么小 ⇒ 这张卡还不该开工）；
2. **认领**：`sdo_dispatch` 发 `lease` → 工作副本 → 写；
3. **收口**：判据绿 + 证据绑产物指纹 + **`evidence.snapshot_id` 填构建来源快照** + `verify` 通过。

### 5.3 完成的判据

`task.complete`（判据）／`task.done`（事件）：判据 `ok=pass`、证据 `artifact_sha256` 非空、`verify` 无新增红。

机械检查：`work_unit` 的 `UNIQUE(task_id)` 保证一卡一行；若需要多条判据 ⇒ 拆卡。

## 6. 怎么保证"意图 = 声明"（独立复述 + 红队）

**先说边界**：意图在人脑里，声明在台账里，**两者之间没有机械等价**。所以能做的只有两件事——**降低漂移概率**、**让漂移可被发现**。任何声称"保证意图=声明"的机制都在撒谎（这是 [01](01-理论与边界.md) 里 L3 漂移的诚实版本）。

四层，缺一层都不完整：

| 层 | 防什么 | 机制 | 判据 |
|---|---|---|---|
| **L1 机械** | 声明被伪造、被改写 | `claim` 只能由视图生成；意图变更必须人签 | `claim.derived_by` 已注册 |
| **L2 独立复述** | **读错意图**（最常见） | 派一个**不参与开发的复述会话**（池里的固定评审会话即可）**只读 `intent`**，独立重写条款与场景；与作者版本 diff，差异逐条处置 | `intent.restated_consistent` |
| **L3 红队**（按风险触发） | 字面满足、实质偏离 | 高风险条款派红队，用例落 **`redteam` 表**（`use_case` + `disposition`），并**转成判据的负例夹具** | `redteam.recorded` 必须被处置 |
| **L4 人签** | 前两层都错 | 人签**两样**：`intent`（要什么，且强度为 `explicit`）+ **条款集合与场景集合**（落 `decision(decision_kind='spec_set')`）；**推断出来的需求（`inferred`）不能当人签** | `intent` 的有效 `decision` + `intent.explicit_for_risk` + `spec_set` 签字 |

### 6.1 L2 独立复述（这是主力）

**输入**：`intent` 原文 + 项目背景。**不给作者已写的条款**——给了就会照抄，复述就失去意义。

**怎么保证"它真的没看过"**（这条机制唯一的漏洞）：

| 手段 | 说明 |
|---|---|
| **顺序约束（主）** | **先复述，后落条款**：`restatement` 行必须先于第一条 `spec` 行；配合“只给 intent”的输入白名单，才是真隔离 |
| 输入白名单 | `restatement.inputs` 与 [11](11-变更与影响链.md) 同形（`{kind,id,hash}[]`），**只含 `intent` 的一条** |
| 事后判定 | 若发现复述会话此前参与过条款起草 ⇒ 该复述**无效**，落 `restatement.invalidated` 事件（带 `reason`）后重派 |

判据侧：`intent.restated_consistent` 同时校验 **`restatement.at < min(spec.at)`**（`spec` 没有顺序保证，不能写 `spec[0]`）——顺序反了即判无效复述。

**输出**：条款草案、场景草案、"哪里没底"的清单。

**diff 共四类**（`agree` / `extra` / `missing` / `conflict`），对应三种病：

| diff | 含义 | 处置 |
|---|---|---|
| 一致 | 两个独立读者得出同一组条款 | 通过 |
| 一方多 / 少 | **缺漏**：作者写了但意图没支撑，或意图里有但作者漏了 | 逐条 `accept`（改条款）或 `reject`（记理由） |
| 表述相反 | **歧义**：intent 那句话本身有两种读法 | `defer` 成待决问题，回头改 `intent` |

判据 `intent.restated_consistent`：**差异未处置 ⇒ 红；`defer` 未决 > 0 ⇒ 阻断进入设计阶段。**

### 6.2 L3 红队（按风险触发，不是常态）

- **触发条件**（满足任一）：涉及支付/计费、鉴权与权限、不可逆操作、跨模块契约；
- **产出**：不是"我觉得不好"，而是**"在不违反字面的前提下，怎么做到偏离意图"**的具体用例；
- **去向**：这些用例转成**判据的负例夹具**（`scenario` 只有 kind、没有正负极；极在 `criterion_fixture`），进而在实现阶段被变异自证检验。

### 6.3 设计阶段的对应物

设计阶段的"意图=声明"= **设计与条款对得上**，两个方向都要查：

| 方向 | 病 | 判据 |
|---|---|---|
| 条款 → 设计 | 条款没人承接（**覆盖缺口**） | `design.covers_spec` |
| 设计 → 条款 | 设计凭空多出条款没要求的东西（**范围蔓延**） | `design.no_spec_creep` |

实现方式：每条设计条款的 `inputs` 必须指向它承接的 `spec`；红队抽查"多出来的那部分"。

### 6.4 为什么这和我们现在的流程是同一件事

现在评审这套设计就是这么跑的：**我写 → 另一个会话审 → 你终裁**。区别只在于：

- 我们**没有把它记进台账**，所以下次还得靠自觉；
- 一旦复述/红队/终裁都落成 `restatement`、`review`、`decision` 行，它就变成**可复查的流程**——而不是"上次我们好像审过"。

## 7. 评审阶段

> **派发评审卡的前置**：被评对象必须已有可评版本（任务 `done`，或条款已有 `spec.defined`/`spec.revised`）——否则评的是「还没做出来的东西」。
>
> 评审对象只有两型：**卡**（`subject_kind='task'`）与**条款**（`subject_kind='spec'`）；设计评审走后者（`spec.kind='design'`）。评审卡自身的 `producer` 定义为 `producer(subject)`——它的 `owner` 认领后是评审者，不能拿来比。

**哪些卡必须评审**（不强制 = 评审靠运气）：

| 必须 review | 为什么 |
|---|---|
| `risk_flags` 非空的卡 | 高风险条款的"做完了"不能只靠自测 |
| 实现 `spec(kind='design'/'contract')` 的卡 | 设计选择与跨模块约定错了，测试绿也没用 |
| **抽样命中的卡**（每 N 张抽 1 张，评审卡除外） | 抽样由 policy 的 `review` 参数（`sample_every`/`sample_seed`）按**单调卡序号**取模（只对 `kind≠review` 的卡），不由作者挑——否则「低风险」自评就能绕开评审。 |
| release 相关的卡与冻结前范围 | 对外交付要有人独立看过。**"release 相关"有定义**：卡的 `spec` 被任一 `release` 的 `in` 集合覆盖，或卡在已冻结 `release` 的 frontier 内——按数据判，不按名字猜 |

**未被抽样命中**的低风险卡可以只走 `task.complete`（判据 + 证据），**但"低风险"必须由 `risk_flags` 空 + 无契约 + 非 release 推出**，不许模型自评"这张不重要"；被抽样命中的卡即使低风险也必须评审。这条门由判据 **`review.required`** 执行（`docs/04`），不是写作规范。

**分工是反的，这点和 v1 一样，但要说清为什么：**

| 角色 | 谁 | 做什么 |
|---|---|---|
| **评审者** | **非作者的子代理**（或人） | 读设计/代码/证据，**产出发现在**（逐条，带可复现命令） |
| **核实者** | **作者本人**（首选） | 对每条发现判 `reproduced` / `refuted`，**给出证据** |
| **裁定者** | 人（决策类）或在 07 的独立性下自动判定 | 判定通过 / 不通过，**落 `review_round(verdict)`**（逐条 finding 在 `review`） |

为什么核实要由作者做：

- 作者最清楚「怎么复现」「这条是不是误读」；让评审者自己核实，等于评审者既当原告又当法官；
- 核实**不是决策**——它只回答"这个现象存不存在"，不回答"该不该放行"。所以它不违反"不可自评"；
- **作者已 dead**（会话无法唤醒，见 [12](12-代理池与生命周期.md)）⇒ 由评审者或另一会话核实，并在核实行里写 `author_unavailable(reason)`。

**不可自评只管决策，不管核实**：`decision.signer ≠ producer` 约束的是"通过/不通过"的签字，不是"能不能复现"。

## 8. 测试在哪里（不设独立测试阶段）

**结论：不设独立测试阶段，测试分布在三处。** 设独立阶段会让"怎么测"推迟到测试阶段才想——而那时候需求已经写完了，判据已经定死了。

| 测试活动 | 落在哪个阶段 | 产出 |
|---|---|---|
| **决定"测什么"** | **需求** | `criterion`（含正负例与 `remedy`）+ `scenario`（人审步骤） |
| **证明"改对了"** | **实现** | 跑判据 → `evidence`（绑 `artifact_sha256`）→ `verify` 通过 |
| **证明"没碰坏别的"** | **交付** | **实现跑影响集、交付跑全量**；验收场景人跑 + 缺口清单 |
| **证明"判据本身有用"** | **实现（随判据一起）** | 变异自证：把实现改坏 ⇒ 判据必须红（[04](04-判据-门禁与负例.md)「变异自证」） |

所以：

- **测试不是阶段，是判据的生命周期**：需求时定义、实现时执行、交付时回归、随时变异自证；
- 一条**自动化判据**只在交付阶段存在（只在发布前跑）⇒ 说明它在实现阶段没跑过，**这是缺陷**；
- **人审场景（`scenario`）不受此约束**：端到端/可用性验收本来就落在交付前，可以在实现阶段只 dry-run 一次；
- 探针/性能/兼容性测试同样落在"实现"与"交付"两处，不单独成阶段。

## 9. 交付阶段

- `release` 的 `in` / `out` 集合都要有 `reason` + `approved_by`（人）；
- **缺口清单 = 集合差集**：少写是隐瞒，多写是粉饰（[09](09-交付与迁移.md)「缺口清单」）；
- 快照在冻结签字**之前**生成，并写 `frozen_at_frontier`；
- 独立性按 [07](07-协作-权限-并行与子代理.md)「关键决策的独立性」判定（`dual_human` 或 `solo_cooldown`）。

## 10. 最小作业单（T0 单人版）

不想要流程、只想开始干活时，按这十条走，每一步都有一句话的完成标准：

| # | 动作 | 完成标准 |
|---|---|---|
| 1 | 写一句 `intent` 并签 | 有 `decision(kind='intent')`（你签的） |
| 2 | **先派另一个会话只读 `intent`，独立复述条款** | 复述**先于**条款落库（顺序可查） |
| 3 | 自己拆 3–7 条条款，与复述版 diff | 每条差异 `accept`/`reject`/`defer` 处置完；`defer` = 0 |
| 4 | 给每条条款配判据或场景 | 没有一条空着 |
| 5 | 写设计条款 + 一个契约 | 每条设计承诺有 consumer；每条设计有 `inputs` 指向条款 |
| 6 | 拆卡：一卡一判据，落一行 `work_unit` | 每张卡只改一件事；`work_unit` 的 `criterion_id` 唯一 |
| 7 | 派发 → 工作副本 → 写 | 有 `lease`，diff 在 scope 内 |
| 8 | 跑判据 + `verify` | 全绿，证据绑指纹 |
| 9 | 派**非作者**子代理评审 → **作者**逐条核实 | 每条发现都有 `reproduced`/`refuted` + 证据 |
| 10 | 判据绿 → **快照** → 冻结签字 | 缺口清单是集合差集；快照在签字之前 |

**这十条不是流程要求，是"没有它们就会返工"的最小集合。**

## 12. 不变式

1. 每个阶段都有**可验收的产出**，且产出要么在台账、要么在仓库（带指纹）；
2. 需求阶段：条款有 consumer，且**过一次独立复述**（差异全处置、无未决）；
3. 设计阶段：每条承诺有 consumer，且**双向可追**（条款→设计无缺口、设计→条款无蔓延）；
4. 实现阶段一卡一判据；评审由**非作者**做，核实由**作者**做（作者 dead 才换人并写明原因）；
5. 交付阶段的缺口清单必须是集合差集，不允许手写汇总；
6. **主工作树不被静默覆盖**：准入时要重新检出，前提是主树与基线快照一致；有未提交改动 ⇒ `block(dirty_main_tree)`，先由人处置（stash / 提交 / 丢弃）再放行。

## 13. 验收读数（M1–M4）

- 给一个真实需求，走完十条最小作业单：**每一步都有对应台账行**，无一步靠"我记得"；
- 故意写一条无 consumer 的条款 ⇒ `stage.requirement_complete` 红；
- 故意写一条无 consumer 的设计承诺 ⇒ `stage.design_traceable` 红；
- 故意把两条无关判据塞进一张卡 ⇒ 第二条 `work_unit` 被 `UNIQUE(task_id)` 拒绝。
