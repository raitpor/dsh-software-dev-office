# 链条：意图 → 真源 → 被遵守 → 声明

> 这一页是 v2 的脊柱。三层漂移（声明≠真源、真源≠被遵守、真源≠意图）在这里被**数据结构**挡住，而不是靠纪律。
> 依据：[01](01-理论与边界.md)「六条失效与它们违反的原理」「三层漂移与 v2 的对应表」。

---

## 1. 六张主表 + 十三张辅助表

```text
intent ─1:N─ spec ─1:N─ scenario
                └──1:N─ criterion ─1:N─ criterion_fixture(正/负)
criterion ─N:M─ evidence
claim ──(derived_by)──► 视图/渲染器 ──(as_of_frontier)──► event
receipt(claim_ids[], renderer, bytes)   ← 回执只引用 claim，不复制文字
field_consumer(field, consumer_kind, consumer_id)  ← 防死字段（view / renderer / criterion 都算）
```

| 表 | 关键列 | 约束 |
|---|---|---|
| `intent` | `id, statement, owner, approved_by, content_hash, at` | `approved_by` 必须是人；`content_hash` 变化 ⇒ 需重签 |
| `spec` | `id, intent_id, clause, kind, mech_checkable, scenario_id, **created_by, producer, content_hash, design_artifact_sha256, code_artifact_sha256, code_artifact_ref, risk_flags[]**, at` | `intent_id` 外键；`kind ∈ {requirement, design, contract, impact}`（设计条款、契约、影响面声明都是条款，没有独立表）；`content_hash` = 条款当前版本的指纹；`risk_flags[]` 由需求阶段声明（`payment`/`auth`/`irreversible`/`cross_module` ⇒ **必须红队**）；**三个指纹分工**：`content_hash` = 条款文字本身；`design_artifact_sha256` = 设计文档/图形的指纹（设计阶段用）；`code_artifact_sha256` + `code_artifact_ref`（`{snapshot_id, path, design_sha256}`）= 实现产物，`task.done` 时回填；**`code_artifact_sha256` 是派生列**：由 fold 按 `sha256(按 evidence_id 升序、去重后拼接的 hex 字符串（无分隔符）)` 计算，**`task.done` / 新增 `work_unit` / `evidence` 变更都触发重算**，不手填；**`design_sha256` 是“我实现的是哪一版设计”**，必须与 `design_lock` 里的只读副本比对（不是与卡片上的字段比）；`mech_checkable=1` 时必须有 `scenario_id`；**`created_by` = 创建者；`producer` = 当前版本（最近一次 `spec.revised`）的作者；从未修订过 ⇒ `producer = created_by`** |
| `work_unit` | `id, task_id, criterion_id, **spec_id**, evidence_id, at` | **一卡一判据一证据 = 一行**；`spec_id` 是**受约束副本**——用**复合外键**实现（`CHECK` 里不许带子查询，SQLite/Postgres 都不接受）：`criterion` 加 `UNIQUE(id, spec_id)`、`evidence` 加 `UNIQUE(id, criterion_id)`，`work_unit` 两个 **FK**：`(criterion_id, spec_id) → criterion(id, spec_id)`、`(evidence_id, criterion_id) → evidence(id, criterion_id)`；由 `task.claimed` + `evidence.attached` 折叠，append-only |
| `snapshot` | `id, git_oid, parent_ids[], external_ref, at` | **快照 = 内嵌 git 仓库（`.sdo/vcs/`）里的一个 commit**：`git_oid` 是它的对象名，内容（blob/tree）由内嵌 git 存；DB 只存引用与父链，`verify` 用它交叉校验——**不依赖宿主 git**；`external_ref` 可选，指向用户仓库的对应 commit（纯展示/审计）。**代码真源 = 内嵌库**：主工作树是当前基线快照的检出，准入后由 SDO 重新检出（不是用户手动 merge）；每张并行卡有**独立 gitdir**（共享对象库），不共用 index |
| `design_lock` | `spec_id, spec_version_hash, design_sha256, at` | 设计指纹的**只读副本**：`spec.defined`/`spec.revised` 时写入（append-only）。判据读它，不读可变的 `spec.design_artifact_sha256`；**`spec_version_hash` 就是该版本的 `spec.content_hash`**；`spec.revised` 时**新增一行**（旧行保留） |
| `stage_run` | `id, stage, **gate_id, baseline_hash**, entered_at, exited_at, verdict, criteria[], at` | 一次阶段运行：`gate_id` + `baseline_hash` 绑定该出口用的 gate 与尺子；**`verdict` 由 `criteria[]` 的 gate 读数算出，不可手填**（手填即 `verify` 红）；`verdict ∈ {pass, changes_requested, na}` |
| `scope_decl` | `id, stage, paths[], created_by, at` | 阶段范围声明（**不是权限域**；权限域在 [07](07-协作-权限-并行与子代理.md)，这里声明"本期允许动哪些路径"）|
| `redteam` | `id, subject_kind, subject_id, **criterion_id, criterion_fixture_id**, use_case, disposition, at` | `disposition` 由 `redteam.disposed` 事件折叠（append-only） | 红队记录（`criterion_id` 指向它转成的负例夹具所在判据）：`use_case` = "如何绕开字面偏离意图"的具体用例；`disposition ∈ {accepted, rejected, deferred}`；**`deferred` 必须落一条 `block(kind='redteam_deferred')`（subject 指向该红队行） 并进 `gaps`**，清空条件 = 该 block 关闭 |
| `review_round` | `id, task_id, **baseline_hash, frontier**, verdict, signer, at` | 一轮评审的**整体结论**（`verdict ∈ {pass, changes_requested}`）；**`signer` 必须是满足 [07](07-协作-权限-并行与子代理.md)「关键决策的独立性」的人**（`dual_human` 或缺省；`solo_cooldown` 下冷却后二次确认），且 `signer ≠ producer(subject)`；**当轮所有 finding 必须已核实**才可 `pass` |
| `scenario` | `id, steps(json), expected(json), kind` | 人审场景（可玩/可点的步骤），不是断言 |
| `restatement` | `id, intent_id, draft_specs(json), inputs, by, at, invalid_reason, accepted_spec_ids[]` | 复述**草案**存 `draft_specs`（不引用尚不存在的 `spec`，从而允许先复述后落条款）；作者合并后才写 `accepted_spec_ids[]`；`inputs` 与 [11](11-变更与影响链.md) 同形（`{kind,id,hash}[]`），只含 `intent` 一条；`at` **必须早于**该 intent 下最小 `spec.at` |
| `restatement_diff` | `id, restatement_id, kind, target_ref, disposition, reason, at` | `target_ref` = 复述草案里的条目序号，或作者版的 `spec` id（差异指向哪一边由 `kind` 决定）； `kind ∈ {agree, missing, extra, conflict}`；`disposition ∈ {accept, reject, defer}`；由 `restatement.diff_dispositioned` 事件折叠而来（append-only，不原位改） |
| `review` | `id, task_id, reviewer, **subject_hash, subject_producer**, finding, verified_by, verdict, reason, at` | `task_id` = **评审卡 id（非空）**；**`subject_hash` = `node(kind=subject_kind, id=subject_id).hash` 的当时值**（[02](02-真源-存储事件与折叠.md)「图模型」的节点哈希；task 取 `task.done` 时的节点哈希，spec 取对应版本）；**`subject_producer` 必须与该 hash 同源**——task 取那次 `done` 的实现者，spec 取那一版的作者，冻结后不随修订/重做变化；判定一律用 `subject_producer`；被评对象由评审卡的 `subject_kind/subject_id` 派生（**不在 review 里重复存**）；**`reviewer` 必须 ≠ `subject_producer`**（非作者评审——用的是被评那一版的作者，不是当前 `producer`）；`verified_by` 默认是作者（作者 dead 才换人并记原因）；`verdict ∈ {reproduced, refuted}` |
| `criterion` | `id, spec_id, kind, status_enum, remedy` | 无 `remedy` 不许注册；**负例由 `criterion_fixture` 派生**（`EXISTS(polarity='negative')`），不设冗余布尔 |
| `criterion_fixture` | `criterion_id, polarity, input, expected_status` | 每条判据至少 1 正 1 负 |
| `evidence` | `id, criterion_id, artifact_uri, artifact_sha256, command, output_digest, **snapshot_id**, at` | `snapshot_id` = 该产物**从哪个快照构建**；由 SDO 自己的 `snapshot` 表记录，不依赖外部版本控制 | 大对象存 uri，不存库 |
| `claim` | `id, subject, predicate, value, as_of_frontier, derived_by, actor, at` | `derived_by` 必须是注册渲染器；`as_of_frontier` 非空 |
| `receipt` | `id, claim_ids[], renderer, bytes, at` | 回执**只引用 claim id**，不复制结论文字；`verify` 检查每个结论都能追到 claim |
| `field_consumer` | `field, consumer_kind, consumer_id`（`consumer_kind ∈ view / renderer / criterion`） | 每个真源字段至少一个消费者；**UI-only 字段由 `view` 消费也算** |

**每个节点还必须有 `inputs`**（`{kind, id, hash}`）：它是派生图的**边**，也是影响链与失效传播的唯一依据。形状与规则见 [11](11-变更与影响链.md)。

## 2. 三层漂移怎么被挡住

| 漂移 | 挡住它的结构 |
|---|---|
| **L1 声明≠真源** | `claim` 只能由 `derived_by` 指向的渲染器写入；渲染器的输入只能是视图（[05](05-观测与交互.md)）。**没有第二条写 claim 的路。** |
| **L2 真源≠被遵守** | `field_consumer`：字段没有消费者 ⇒ `dead_field` 判据红（[04](04-判据-门禁与负例.md)）。 |
| **L3 真源≠意图** | 不假装能消掉：`intent.approved_by` + `content_hash` 把"意图"集中在**人签**一处；判据必须带负例，防止"判据自洽但冤枉人"。 |

## 3. claim 的生成规则（最关键的一条）

```text
允许：renderer(view_row) → claim(row)          # derived_by 记渲染器 id
禁止：任何代码直接 INSERT claim                 # DB 权限层面禁止
禁止：回执/报告里出现 claim 表之外的结论         # 由 verify 检查
```

**例**：回执里写「已完成：TASK-280（证据 3 条，评审 REV-097 已核）」——这句话必须由 `claim(subject=TASK-280, predicate=done, value=true, as_of_frontier=f:…)` 生成；渲染器只负责排版，不负责判断。

**检查**：`verify` 扫描最近 N 条 **`receipt`**（回执只存 `claim_ids[]` + 渲染字节），**回执里每个结论都必须引用存在的 claim id**，找不到 ⇒ 红。`claim` 里**不存渲染文字**（只存 `code + params`），文字是回执的产物。这是 v1 那 57% 缺陷的结构性解药。

## 4. 状态机（只列关键）

**intent**：`draft → proposed → signed → superseded`
- `signed` 必须有 `approved_by` 与 `content_hash`；
- 修改 `statement` ⇒ `content_hash` 变 ⇒ 回到 `proposed`（**必须重签**）。

**spec**：`defined → revised*`；`revised` 必带 `reason` 与影响面。

**criterion**：`draft → active → retired`
- `active` 前置：**存在负例夹具**（`EXISTS(criterion_fixture … polarity='negative')`）且 `remedy` 非空；
- `retired` 必须说明"被哪条取代"。

**task**：`planned → ready → in_progress → (blocked ↔ in_progress) → done | dropped`；**`done → in_progress`** 仅由 `task.reopened(reason)` 触发（上游变更 / 评审推翻），理由必填
- `done` 前置：`claim(done)` 成立 + 关联证据 + （若需评审）`decision` 可验；
- `dropped` 必须带 `drop_kind ∈ {never_done, delivered_deferred}` 与凭据（v1 的教训：`dropped` 可以是"已交付但记账顺延"，不写清会低估自己）。

## 5. 一个需求走完整条链（示例）

```text
intent(   "发布范围必须能按版本声明"                     approved_by=u-liang )
  └ spec( "release 文件含 scope 与 nonScope；nonScope 每项必须有 reason 与 approved_by" )
      └ scenario( 人审：冻结一个版本 → 看缺口清单是否与集合恰好相等 )
          └ criterion( R-12 "缺口清单 = 集合差集"，负例：多写一项 / 少写一项 )
              ├ evidence( 命令 + 读数 + 产物指纹，绑 frontier f:9c1e )
              └ claim( subject=r-0.2.0, predicate=gaps_match, value=true, as_of=f:9c1e,
                       derived_by=render.release_gaps )
                        └─ 签字 decision(d-8f21, signer=u-liang, frontier=f:9c1e)
```

这一条链走通后，任何人（包括新会话）都能回答："这个判据在保护哪条意图"、"这份证据什么时候有效"、"谁签的字"。

## 6. 不变式

1. `criterion.spec_id` 必须能一路追到 `intent.id`（外键 + `verify` 检查）；
2. `claim` 的 `derived_by` 必须在 `renderer_catalog` 里注册（注册即代码，见 [05](05-观测与交互.md)）；
3. `claim.as_of_frontier` 的每个事件 id 必须存在；
4. 任何 `decision` 指向的 frontier 必须是它签发时刻的**当前** frontier（防止"签旧版本"）；
5. `field_consumer` 覆盖全部真源字段（`dead_field` 判据）。

---

## 7. 验收读数（M1）

- 随机抽 20 条 v1 的"结论型回执"，在 v2 的 `claim` 表里能重建 **20/20**；
- 人为删掉一条 `scenario` 的判据：`verify` 能报出"哪条意图失去了可判定条款"；
- 新增一个真源字段但不加消费者：`dead_field` 立即红。
