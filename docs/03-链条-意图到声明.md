# 链条：意图 → 真源 → 被遵守 → 声明

> **框架坐标**（对齐 [01 理论与边界](01-理论与边界.md)）
>
> - 守的层：**L3**
> - 涉及真源：意图
> - 对应命题：命题 3（证据绑定）
> - 本文引入/定义的概念：intent/spec/goal_node/criterion/evidence/claim/work_unit

> 这一页是 v2 的脊柱。三层漂移（声明≠真源、真源≠被遵守、真源≠意图）在这里被**数据结构**挡住，而不是靠纪律。
> 依据：[01](01-理论与边界.md)「六条失效与它们违反的原理」「三层漂移与 v2 的对应表」。

## 1. 六张主表 + 十八张辅助表

```text
intent ─1:N─ spec ─1:N─ scenario
                └──1:N─ criterion ─1:N─ criterion_fixture(正/负)
criterion ─N:M─ evidence
claim ──(derived_by)──► 视图/渲染器 ──(as_of_frontier)──► event
receipt(claim_ids[], renderer, bytes)   ← 回执只引用 claim，不复制文字
field_consumer(field, consumer_kind, consumer_id)  ← 防死字段（view / renderer / criterion 都算）
```

| 表 | 关键列 | 约束 |
|---|---|---|
| `intent` | `id, statement, **source_text**, owner, approved_by, **strength, baseline_hash**, content_hash, at` | `approved_by` 必须是人；**`statement` 是模型摘要，`source_text` 是用户原话**（可脱敏）：复述 diff 对**原话**，不对摘要，否则"记录是否忠实于我说的话"无从核对；**`strength ∈ {explicit, inferred}`**：`explicit` = 人直接提，`inferred` = 从上下文推断；**`inferred` 不得进 `risk_flags` 非空的条款**，必须显式升级；`baseline_hash` = 批准时依据的尺子，`reopen` 时重验；`content_hash` 变化 ⇒ 需重签 |
| `spec` | `id, intent_id, clause, kind, mech_checkable, scenario_id, **is_core, status, blast_radius, created_by, producer, content_hash, design_artifact_sha256, code_artifact_sha256, code_artifact_ref, risk_flags[], alternatives[], no_alternative_reason**, at` | `intent_id` 外键；`kind ∈ {requirement, design, contract, impact, **assumption**}`（设计条款、契约、影响面声明、假设都是条款，没有独立表）；`content_hash` = 条款当前版本的指纹；`risk_flags[]` 由需求阶段声明（`payment`/`auth`/`irreversible`/`cross_module` ⇒ **必须红队**）；**三个指纹分工**：`content_hash` = 条款文字本身；`design_artifact_sha256` = 设计文档/图形的指纹（设计阶段用）；`code_artifact_sha256` + `code_artifact_ref`（`{snapshot_id, path, design_sha256}`）= 实现产物，`task.done` 时回填；**`code_artifact_sha256` 是派生列**（**G2 已定：应用层重算**）：由 fold 按 `sha256(按 evidence_id 升序、去重后拼接的 hex 字符串（无分隔符）)` 计算，**`task.done` / 新增 `work_unit` / `evidence` 变更都由 L1 fold 的 recompute 重算（`design/01` §9），该列不开放写入接口**；`verify` 重算比对；**`design_sha256` 是“我实现的是哪一版设计”**，必须与 `design_lock` 里的只读副本比对（不是与卡片上的字段比）；`mech_checkable=1` 时必须有 `scenario_id`；**`created_by` = 创建者；`producer` = 当前版本（最近一次 `spec.revised`）的作者；从未修订过 ⇒ `producer = created_by`** |
| `goal_node` | `id, parent_id, goal, kind, acceptance_criterion_id, scope_paths[], at` | **分解树**：把“要什么”逐层拆成可独立验收的块；`kind ∈ {intent, part}`，根节点唯一且指向 `intent`；**只由需求/设计阶段显式声明**（不是运行时自行生长）；叶节点必须绑验收判据；**每个节点是一次人审单位** |
| `integration` | `id, parent_goal_id, child_goal_id, state, evidence_id, note, at` | 集成清单：`state ∈ {connected, pending, dropped}`；**父节点的验收 = 全部 `connected` + 整体跑一次**，不是“子都绿了”；人审父节点时**只看这张清单**，不重读子块 |
| `report` | `id, task_id, state, evidence_id, note, at` | 执行者的一次进度报告；`state ∈ {progress, ready, blocked, failed, dropped}`（**没有 `waiting`**）；**进度与 `task.status` 分开**；**“在等谁”的唯一源是 `attention`**，report 只回答“做到哪了” |
| `attention` | `id, task_id, question, options[], answered_by, at` | 等一个人回答的**结构化**问题（选择题优先）；未答即进待审队列；禁止用自由文本描述“在等人” |
| `work_unit` | `id, task_id, criterion_id, **spec_id**, evidence_id, at`，**`UNIQUE(task_id)`**（G4 已定：一卡一行由表约束保证） | **一卡一判据一证据 = 一行**；`spec_id` 是**受约束副本**——用**复合外键**实现（`CHECK` 里不许带子查询，SQLite/Postgres 都不接受）：`criterion` 加 `UNIQUE(id, spec_id)`、`evidence` 加 `UNIQUE(id, criterion_id)`，`work_unit` 两个 **FK**：`(criterion_id, spec_id) → criterion(id, spec_id)`、`(evidence_id, criterion_id) → evidence(id, criterion_id)`；由 `task.claimed` + `evidence.attached` 折叠，append-only |
| `snapshot` | `id, git_oid, external_ref, at` | **快照 = 内嵌 git 仓库（`.sdo/vcs/`）里的一个 commit**：`git_oid` 是它的对象名，内容（blob/tree）由内嵌 git 存；DB 只存引用与父链，`verify` 用它交叉校验——**不依赖宿主 git**；`external_ref` 可选，指向用户仓库的对应 commit（纯展示/审计）。**代码真源 = 内嵌库**：主工作树是当前基线快照的检出，准入后由 SDO 重新检出（不是用户手动 merge）；每张并行卡有**独立 gitdir**（共享对象库），不共用 index |
| `design_lock` | `spec_id, spec_version_hash, design_sha256, at` | 设计指纹的**只读副本**：`spec.defined`/`spec.revised` 时写入（append-only）。判据读它，不读可变的 `spec.design_artifact_sha256`；**`spec_version_hash` 就是该版本的 `spec.content_hash`**；`spec.revised` 时**新增一行**（旧行保留） |
| `snapshot_parent` | `snapshot_id, parent_id` | 快照父链（**G1 已定：链接表**）；两个外键都指向 `snapshot`，祖先闭包用递归 CTE |
| `stage_run` | `id, stage, **gate_id, baseline_hash**, entered_at, exited_at, verdict, criteria[], at` | 一次阶段运行：`gate_id` + `baseline_hash` 绑定该出口用的 gate 与尺子；**`stage` 存的是 policy 里的 stage `id`**（如 `harden`），它的 `kinds` 经 baseline 的 policy 反查，**不在这里存第二份**（否则 stage 语义可以绕开 baseline 改）；**`verdict` 由 `criteria[]` 的 gate 读数算出，不可手填**（手填即 `verify` 红）；`verdict ∈ {pass, changes_requested, na}` |
| `scope_decl` | `id, stage, paths[], created_by, at` | 阶段范围声明（**不是权限域**；权限域在 [07](07-协作-权限-并行与子代理.md)，这里声明"本期允许动哪些路径"）|
| `redteam` | `id, subject_kind, subject_id, **criterion_id, criterion_fixture_id**, use_case, disposition, at` | `disposition` 由 `redteam.disposed` 事件折叠（append-only） | 红队记录（`criterion_id` 指向它转成的负例夹具所在判据）：`use_case` = "如何绕开字面偏离意图"的具体用例；`disposition ∈ {accepted, rejected, deferred}`；**`deferred` 必须落一条 `block(kind='redteam_deferred')`（subject 指向该红队行） 并进 `gaps`**，清空条件 = 该 block 关闭 |
| `review_round` | `id, task_id, **baseline_hash, frontier**, verdict, signer, at` | 一轮评审的**整体结论**（`verdict ∈ {pass, changes_requested}`）；**`signer` 必须是满足 [07](07-协作-权限-并行与子代理.md)「关键决策的独立性」的人**（`dual_human` 或缺省；`solo_cooldown` 下冷却后二次确认），且 `signer ≠ producer(subject)`；**当轮所有 finding 必须已核实**才可 `pass` |
| `scenario` | `id, steps(json), expected(json), kind` | 人审场景（可玩/可点的步骤），不是断言 |
| `restatement` | `id, intent_id, draft_specs(json), inputs, by, at, invalid_reason, accepted_spec_ids[]` | 复述**草案**存 `draft_specs`（不引用尚不存在的 `spec`，从而允许先复述后落条款）；作者合并后才写 `accepted_spec_ids[]`；`inputs` 与 [11](11-变更与影响链.md) 同形（`{kind,id,hash}[]`），**只含 `intent` 一条，且 hash 必须等于当前 `intent` 行的 `content_hash`**——intent 改过而 restatement 还是旧的 ⇒ **旧复述作废**（`restatement.invalidated`），必须重跑；`at` **必须早于**该 intent 下最小 `spec.at` |
| `restatement_diff` | `id, restatement_id, kind, target_ref, disposition, reason, at` | `target_ref` = 复述草案里的条目序号，或作者版的 `spec` id（差异指向哪一边由 `kind` 决定）； `kind ∈ {agree, missing, extra, conflict}`；`disposition ∈ {accept, reject, defer}`；由 `restatement.diff_dispositioned` 事件折叠而来（append-only，不原位改） |
| `review` | `id, task_id, reviewer, **subject_hash, subject_producer**, finding, verified_by, verdict, reason, at` | `task_id` = **评审卡 id（非空）**；**`subject_hash` = `node(kind=subject_kind, id=subject_id).hash` 的当时值**（[02](02-真源-存储事件与折叠.md)「图模型」的节点哈希；task 取 `task.done` 时的节点哈希，spec 取对应版本）；**`subject_producer` 必须与该 hash 同源**——task 取那次 `done` 的实现者，spec 取那一版的作者，冻结后不随修订/重做变化；判定一律用 `subject_producer`；被评对象由评审卡的 `subject_kind/subject_id` 派生（**不在 review 里重复存**）；**`reviewer` 必须 ≠ `subject_producer`**（非作者评审——用的是被评那一版的作者，不是当前 `producer`）；`verified_by` 默认是作者（作者 dead 才换人并记原因）；`verdict ∈ {reproduced, refuted}` |
| `criterion` | `id, spec_id, kind, status_enum, remedy` | 无 `remedy` 不许注册；**负例由 `criterion_fixture` 派生**（`EXISTS(polarity='negative')`），不设冗余布尔 |
| `criterion_fixture` | `id, criterion_id, polarity, input, expected_status` | **同一极性可多条**（`UNIQUE(criterion_id, polarity, input)`，同一输入不许重复）；**“至少 1 正 1 负”由注册门槛保证**（[04](04-判据-门禁与负例.md)），不是表约束 |
| `evidence` | `id, criterion_id, artifact_uri, artifact_sha256, command, output_digest, **snapshot_id**, at` | `snapshot_id` = 该产物**从哪个快照构建**；由 SDO 自己的 `snapshot` 表记录，不依赖外部版本控制 | 大对象存 uri，不存库 |
| `claim` | `id, subject, predicate, value, as_of_frontier, derived_by, actor, at` | `derived_by` 必须是注册渲染器；`as_of_frontier` 非空 |
| `receipt` | `id, claim_ids[], renderer, bytes, at` | 回执**只引用 claim id**，不复制结论文字；`verify` 检查每个结论都能追到 claim |
| `field_consumer` | `field, consumer_kind, consumer_id`（`consumer_kind ∈ view / renderer / criterion`） | 每个真源字段至少一个消费者；**UI-only 字段由 `view` 消费也算** |

**每个节点还必须有 `inputs`**（`{kind, id, hash}`）：它是派生图的**边**，也是影响链与失效传播的唯一依据。形状与规则见 [11](11-变更与影响链.md)。

**`status` 与 `blast_radius` 只对 assumption 有意义**：

- `status ∈ {open, confirmed, rejected, converted}`（`NULL` = 非假设条款），由 `assumption.recorded` / `assumption.invalidated` / 相关 `decision(assumption_set)` 折叠而来——**状态不是手填列，是投影**；
- `blast_radius` = 假设错了会波及什么（受影响 `spec`/`task`/`release` 的 id 列表或路径前缀）：**`kind='assumption'` 时必填**，否则"错了会怎样"只剩一句空话；
- `is_core` = 是否关键条款：**`risk_flags` 非空自动为真**；此外**只能由人在需求阶段标记**（不是模型自评）——它决定复述要绑哪些条款的 hash（P11）。

**`kind='assumption'` 是"没说清楚"的正式出口**（对应 [01](01-理论与边界.md) §1 第 2 件事）：

- 当意图/条款**没有覆盖**某个必须做的选择时，模型**不许自己选一个就开工**；要么开 `attention` 问（阻塞型），要么落一条 `assumption` 条款（非阻塞型）；
- 一条 `assumption` 必须写清三样：**我假设什么**（`clause`）、**排除了哪些方案**（`alternatives[]`）、**如果假设错了会怎样**（`blast_radius`）；
- 状态 `open → confirmed | rejected | converted`：`confirmed` = 人认可这个假设——**必须来自一条 `decision(decision_kind='assumption_set')`，且该假设在该 decision 的 `spec_ids[]` 里**（不能"口头认了"）；`rejected` = 人不认，必须改；`converted` = 假设升级成了正式条款（`spec.revised` 或新 `requirement`）；
- **卡关联怎么算**：`task.inputs[]` 里可以包含 `{kind:'assumption', id}`；判据 `assumption.disposed` **只查 `task.inputs[]` 里的假设**。所以**raise 假设时必须同时写进受影响卡片的 `inputs`**（否则它不属于任何卡，也就不会被检查）；没有卡的假设由 `assumption_set` 兜住；
- **开工前置**：卡关联的假设里有一个 `open`（或 `rejected` 但没有后继）⇒ 不许派发/开工（判据 `assumption.disposed`）。它保证的是**"不能静默开工"**：没声明的选择仍可能发生，但一旦声明就必须处置完——**不能静默选，必须留下可审计的声明**，而不是"不靠模型自觉"。

**什么必须"问"（`attention`），不能记成假设**：

- **影响不可逆**（删数据、迁移、发布、对外契约）——猜错不可回退，人必须当时决定；
- **两个方案代价差异大且都不便宜**——这不是实现细节，是取舍，属于人；
- **条款之间互相冲突**——冲突本身就是"没说清楚"，不能拿缺省值糊过去；
- **假设的 `blast_radius` 会波及已完成的卡**——事后返工比当时问一句贵得多。

其余（命名、内部结构、可轻易改回来的选择）可以走假设；**但假设必须被看见，且在被推翻时能算出影响面**。

**"发现"这一半：设计选择必须自证没有替代方案**（只管"写下来的假设"是假的安全）：

- 每条 `spec(kind='design')` 必须声明 **`alternatives[]`**（考虑过哪些方案）**或** **`no_alternative_reason`**（为什么没有第二个可行方案）；
- `alternatives[]` 里 **≥2 个可行** ⇒ 必须链一条 `assumption`（选哪个、排除哪个、错了怎么办）或开 `attention`；不许"选了一个、别的没提"；
- 这条约束的对象是**设计条款**，不是所有条款：需求的替代方案由人决定（`spec_set`），设计的替代方案是模型做的取舍，必须显式。

**拒绝不是处置**：`rejected` 的假设必须链后继（`spec.revised` / 转成 `converted` / `change`），否则**仍挡开工**——"人不认，必须改"不等于"改过了"。

**确认也会过期**：`confirmed` 必须绑它成立时依据的 `inputs`（intent/spec 的 hash）。被依赖的条款一改，假设自动回到 `open`（`assumption.invalidated`），必须重签 `assumption_set`——否则"三周前认过的假设"会悄悄支撑今天的实现。

**数据库表达不了的 5 处**（父链数组、派生列、注册门槛、一卡一行、事件 kind 闭包）已由 [可执行性探针](../probe/GAPS.md) 定位，待结构化设计决定；决定之前，这些约束**只能由判据与 `verify` 保证**，不能声称"库会拦住"。

**分解树首先是人的决策面，其次才是派发结构**（[01](01-理论与边界.md) §14 注意力预算 · §15 借 Blueprint 的"可独立验收的块"）：

- **每个节点一次审完**：一屏能读完，判断 ≤ 2 分钟——人一次能比较的项数有限，把大项整审必然滑成"看着挺合理"；
- **顺序是叶 → 父**：先认可可独立验收的小块，再看父节点的集成清单——叶有具体判据，人容易说"行/不行"；父只回答"接上了吗"；
- **决策粒度 = 节点，不是文档**：对一整份 `spec` 的"整体批准"是伪决策，人没真读、也没真负责；
- **待审节点 > 7 个 ⇒ 先拆或先分组**（对齐 §4.1 A 组"单次决策项数 ≤ 7"）。

## 2. 三层漂移怎么被挡住

| 漂移 | 挡住它的结构 |
|---|---|
| **L1 声明≠真源** | `claim` 只能由 `derived_by` 指向的渲染器写入；渲染器的输入只能是视图（[05](05-观测与交互.md)）。**没有第二条写 claim 的路。** |
| **L2 真源≠被遵守** | `field_consumer`：字段没有消费者 ⇒ `dead_field` 判据红（[04](04-判据-门禁与负例.md)）。 |
| **L3 真源≠意图** | 不假装能消掉：`intent.approved_by` + `content_hash` 把"意图"集中在**人签**一处；判据必须带负例，防止"判据自洽但冤枉人"。 |

## 3. claim 的生成规则（最关键的一条）

```text
允许：renderer(view_row) → claim(row)          # derived_by 记渲染器 id
禁止：任何代码直接 INSERT claim                 # DB 权限层面禁止
禁止：回执/报告里出现 claim 表之外的结论         # 由 verify 检查
```

**例**：回执里写「已完成：TASK-280（证据 3 条，评审 REV-097 已核）」——这句话必须由 `claim(subject=TASK-280, predicate=done, value=true, as_of_frontier=f:…)` 生成；渲染器只负责排版，不负责判断。

**检查**：`verify` 扫描最近 N 条 **`receipt`**（回执只存 `claim_ids[]` + 渲染字节），**回执里每个结论都必须引用存在的 claim id**，找不到 ⇒ 红。`claim` 里**不存渲染文字**（只存 `code + params`），文字是回执的产物。这是 v1 那 57% 缺陷的结构性解药。

## 4. 状态机（只列关键）

**intent**：`draft → proposed → signed → superseded`
- `signed` 必须有 `approved_by` 与 `content_hash`；
- 修改 `statement` ⇒ `content_hash` 变 ⇒ 回到 `proposed`（**必须重签**）。

**spec**：`defined → revised*`；`revised` 必带 `reason` 与影响面。

**criterion**：`draft → active → retired`
- `active` 前置：通过 [04](04-判据-门禁与负例.md)「注册门槛」五条（`guarantee` 声明、`remedy`、正例实跑 `pass`、负例实跑 `fail`、单次预算）——**这里不重复列**，唯一家是 `04`；
- `retired` 必须说明"被哪条取代"。

**stage_run**：`running → closed`（`stage.entered` 开，`stage.exited` 关；`na` 是 `verdict` 取值，不是状态）
**review_round**：`open → closed`（`review.round_closed` 是唯一关闭入口；`verdict` 是属性，不是状态）

**task**：`planned → ready → in_progress → (blocked ↔ in_progress) → done | dropped`；**`done → in_progress`** 仅由 `task.reopened(reason)` 触发（上游变更 / 评审推翻），理由必填
- `done` 前置：`claim(done)` 成立 + 关联证据 + （若需评审）`decision` 可验；
- `dropped` 必须带 `drop_kind ∈ {never_done, delivered_deferred}` 与凭据（v1 的教训：`dropped` 可以是"已交付但记账顺延"，不写清会低估自己）。

---

## 5. 一个需求走完整条链（示例）

```text
intent(   "发布范围必须能按版本声明"                     approved_by=u-liang )
  └ spec( "release 文件含 scope 与 nonScope；nonScope 每项必须有 reason 与 approved_by" )
      └ scenario( 人审：冻结一个版本 → 看缺口清单是否与集合恰好相等 )
          └ criterion( R-12 "缺口清单 = 集合差集"，负例：多写一项 / 少写一项 )
              ├ evidence( 命令 + 读数 + 产物指纹，绑 frontier f:9c1e )
              └ claim( subject=r-0.2.0, predicate=gaps_match, value=true, as_of=f:9c1e,
                       derived_by=render.release_gaps )
                        └─ 签字 decision(d-8f21, signer=u-liang, frontier=f:9c1e)
```

这一条链走通后，任何人（包括新会话）都能回答："这个判据在保护哪条意图"、"这份证据什么时候有效"、"谁签的字"。

---

## 6. 不变式

1. `criterion.spec_id` 必须能一路追到 `intent.id`（外键 + `verify` 检查）；
2. `claim` 的 `derived_by` 必须在 `renderer_catalog` 里注册（注册即代码，见 [05](05-观测与交互.md)）；
3. `claim.as_of_frontier` 的每个事件 id 必须存在；
4. 任何 `decision` 指向的 frontier 必须是它签发时刻的**当前** frontier（防止"签旧版本"）；
5. `field_consumer` 覆盖全部真源字段（`dead_field` 判据）。

---

## 7. 验收读数（M1）

- 随机抽 20 条 v1 的"结论型回执"，在 v2 的 `claim` 表里能重建 **20/20**；
- 人为删掉一条 `scenario` 的判据：`verify` 能报出"哪条意图失去了可判定条款"；
- 新增一个真源字段但不加消费者：`dead_field` 立即红。
