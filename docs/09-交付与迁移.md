# 交付与迁移

> **框架坐标**（对齐 [01 理论与边界](01-理论与边界.md)）
>
> - 守的层：**L1**
> - 涉及真源：内容
> - 对应命题：命题 3（交付绑快照）
> - 本文引入/定义的概念：release、缺口清单、冻结、迁移

> 合并自「交付与版本」+「迁移-里程碑与验收」：两者都是**生命周期**——一次发布怎么冻结，一条旧线怎么搬过来。
> 冻结需要哪种“独立性”见 [07](07-协作-权限-并行与子代理.md)「关键决策的独立性」。

## 1. 两种"版本"必须分开



| 概念 | 例 | 谁决定 | 能否共存 |
|---|---|---|---|
| **发布号**（package version） | `0.2.0` | 打包产物的语义化版本 | 一个发布号可以含多个 release |
| **release**（范围声明） | `r-2026-11-a` | 人签的基线快照 | 一个 release 只对应一条冻结记录 |
| **schema 版本** | `schema_version=7` | 迁移脚本 | 与发布号完全无关 |

**禁止**用 package version 当 release 主键（v1 踩过：一个包版本里有多次范围变化，台账失去粒度）。

## 2. 数据模型



```sql
CREATE TABLE release (
  id               TEXT PRIMARY KEY,      -- r-<yyyy-mm>-<slug>，人可读
  package_version  TEXT,                  -- 交付时才填；允许先冻结后打包
  status           TEXT NOT NULL,         -- draft | frozen | delivered | rolled_back
  frozen_at        TEXT,
  frozen_by        TEXT,                  -- JSON 数组：至少两个 human actor
  frontier         TEXT NOT NULL,         -- 冻结那一刻的事件 frontier（hash）
  baseline_hash    TEXT NOT NULL,         -- 本版交付按哪把尺子判的；发布证据只能来自同一版（04 §5.2 第 5 条）
  scope_spec_set   TEXT NOT NULL,         -- 本版考核的 requirement 全集：冻结时引用的有效 decision(kind='spec_set') 的 id
  note             TEXT
);

CREATE TABLE release_item (
  release_id  TEXT NOT NULL REFERENCES release(id),
  kind        TEXT NOT NULL,              -- requirement | spec | defect | risk | deprecation
  target      TEXT NOT NULL,              -- requirement 行 = spec id；证据行 = 条款/缺陷/风险 id
  requirement_id TEXT REFERENCES spec(id), -- kind='requirement' 时 = target；证据行必填（挂在哪条 requirement 下）
  CHECK (kind = 'requirement' OR requirement_id IS NOT NULL),  -- “必填”是约束，不是注释
  disposition TEXT NOT NULL,              -- in | out
  reason      TEXT,                       -- disposition=out 时必填
  defer_count INTEGER NOT NULL DEFAULT 0, -- 顺延次数（由历史现算，不手填）
  approved_by TEXT,                        -- disposition=out 时必须 human
  PRIMARY KEY (release_id, kind, target)
);
```

**`in` / `out` 是集合，不是字段**：某个缺陷属于哪一版，由"它在哪个 release 的 `out` 集合里"决定，而不是给它贴 `targetVersion`（v1 的 `AC-287` 教训）。

## 3. 冻结（freeze）



前置条件（全绿才允许冻结）：

1. 该 release 范围内所有**门禁**通过，或豁免带有效期与签字（[04](04-判据-门禁与负例.md)）；
2. `out` 集合每项有 `reason` + `approved_by`（human）；
3. **关键决策的独立性**：`dual_human`（两个不同 human，同一 frontier）或 T0 的 `solo_cooldown(15m)`（[07](07-协作-权限-并行与子代理.md)）；
4. 审计快照已生成（`export`），且**顺序固定**：判据绿 → **生成快照** → 冻结签字；快照里显式写 `frozen_at_frontier`（即随后签字绑定的那个 frontier），因此不存在“快照里含不含 freeze 事件”的歧义——**不含**；
5. 一张"缺口清单＝requirement 差集"的对账（见「缺口清单」）：`release` 的 `scope_spec_set` 列 已声明且指向有效 `decision(kind='spec_set')`，其载荷 `spec_ids[]` 是本版 requirement 全集，`release_item` 对全集逐条有 `in`/`out` 行；
6. **人亲手跑过 `scenario`**（这是唯一不依赖模型自证的验收锚）：每个 release 至少 **3 条**、`risk_flags` 非空的条款**每条款至少 1 条**，由 **human** 执行并记结果；模型跑的 scenario 不算。跑过的清单写进冻结签字 payload 的 `scenarios_run[]`（`{spec_id, scenario_id, ran_by, result, note}`），随 `release.frozen` 一起落账。**这是"产品对不对"的外部锚，不是又一道流程**——一次 release 抽几条，分钟级。
7. **本版只按一把尺子判**：`release` 表的 `baseline_hash` 必须声明且非空，**每条发布证据（`in` 集合里的条款所依赖的判定）的 `baseline_hash` 都必须等于它**；旧 baseline 下通过的卡要进这一版 ⇒ **先在新 baseline 下重判**（[04](04-判据-门禁与负例.md) §5.2 第 5 条）。缺 `baseline_hash` 或证据来自两版 ⇒ 拒绝 `freeze_blocked(baseline_mixed)`——否则"用旧尺子交付新标准"就是一次合法绕过。

冻结之后：

- `release` 行不可改（只能新增 `release.superseded` 事件与新的 release）；
- 冻结**落一条 `release.frozen`**（含 in/out 集合、`baseline_hash`、签字与 frontier）；这条事件是 `status='frozen'` 的唯一生产者，别处不许把状态直接写成 frozen；
- 冻结时**生成审计快照**（确定性 JSONL + hash 链），作为发布物导出（[02](02-真源-存储事件与折叠.md)）；
- 冻结事件的 `frontier` 就是"这一版的事实边界"。

## 4. 交付物（deliverable）



| 类型 | 内容 | 校验 |
|---|---|---|
| **包产物** | **从 `snapshot_id` 检出 → 构建 → 打包**（不是从主工作树直接打包） | sha256 与 `SHA256SUMS` 一致，且记录 `snapshot_id` + `package_sha256`；两者缺一 ⇒ 不能进发布证据 |
| **离线包** | 运行所需数据（语言包、流程 policy、preset） | 与仓库快照逐字节比对（`diff -rq` 数为 0） |
| **发布快照** | `export --at <frontier>` 的 JSONL | hash 链自洽 + `verify` 通过 |
| **委托决策** | `delegated` 且 `pending_audit` 的决策 | **不能进发布证据**：审计确认（转正）后方可作为发布依据（见 [07](07-协作-权限-并行与子代理.md)）。**M1–M3 该集合恒为空**（grant 未启用） |
| **争议结论** | `disputed` 的对象 | **不能进发布证据**：裁定（一次签字）后方可（见 [07](07-协作-权限-并行与子代理.md)「分歧裁定」） |
| **发布说明** | 变更摘要（由 claim 生成，不许手写结论） | 每句结论能在 claim 表找到出处 |
| **回滚点** | 上一版 frontier + 产物 sha256 | 可寻址、可恢复 |

**交付落 `release.delivered`**：打包产物与 `SHA256SUMS` 对得上、`package_sha256` + `snapshot_id` 都记上之后，才写这条事件；`status='delivered'` 的唯一生产者是它。冻结与交付**分开两条事件**——允许"先冻结、后打包"，但反过来（先打包后冻结）不成立。

**发布说明必须由渲染器生成**（[03](03-链条-意图到声明.md)）：v1 的"已知缺口"手写、无来源，是 C-72 那类"多写＝粉饰、少写＝隐瞒"的根源。

## 5. 缺口清单：多写＝粉饰，少写＝隐瞒



**"范围"有载体**：`release` 的 `scope_spec_set` 列 指向冻结时引用的那版有效 `decision(kind='spec_set')`；它的载荷 `spec_ids[]` 就是本版的 requirement 全集——不是"当前所有 requirement"，也不许手填。`release_item` 里 `kind='requirement'` 的行对全集逐条给出 `in`/`out`；`spec/defect/risk/deprecation` 行**必须带 `requirement_id`**，只是挂在 requirement 下的证据，不参与差集。

```text
缺口清单 = 全集里"未通过"的 requirement（绑定的门禁读数非 pass / 缺读数）
         ∪ 全集里 disposition='out' 的 requirement
```

- **单位是 requirement，不是缺陷**：缺陷/风险/弃用是挂在 requirement 下的**证据**，不再单独充当缺口的顶层条目——否则“修了 30 个 bug”可以粉饰“还有 5 条需求没达标”；
- 由**视图**生成（`v_release_gaps`），不许手写；每行必须带 `requirement_id` 与 `reason_code`（`fail` / `out`）；
- 对账判据：`gaps == requirement 差集`——差集的两边都从 `scope_spec_set` 载荷与 `release_item` 行现算（多一项、少一项都红）；
- 顺延项必须有理由与署名，否则判红；
- **写入路径强制**：冻结前置校验（P8 步骤 2）逐行校验 `requirement_id`（证据行缺 ⇒ 拒，`invalid_field`，不落 `release.frozen`）；DDL 的 `CHECK` 只兜住直接插库，两者都要有。

这是 v1 唯一"像产品"的产出（56 项逐项署名），v2 保留并机械化。

## 6. 顺延（deferral）的定价



| 规则 | 说明 |
|---|---|
| `defer_count` 现算 | 该 target 在历史 `out` 集合里出现的次数（不手填） |
| 目标版本必须存在 | `deferred_to` 指向的 release 必须已存在（draft 也可），否则红 |
| 连续顺延 ≥3 次 | 告警进 `gaps`，要求"要么进范围、要么明确不修" |
| `approved_by` 只认 human | agent 不得批准顺延 |

## 7. 回滚与热修



**回滚**：`decision(kind=rollback)`，指向目标 release 的 frontier 与产物 sha256（**已交付版必填；未交付的 frozen 版为 null**，见下）；`release.status='rolled_back'`（原记录保留）。回滚后**必须**开一个新 release，不许"就地改回"。

**未交付的冻结版也要能作废**（不变式 7 的处置侧）：`frozen` 态因 scope 被撤而不能交付时，同一个 `decision(kind=rollback)` 也可以作用于它——此时载荷的 `artifact_sha256` 为 `null`（还没有产物），`release.superseded` 只把本版收尾（本版进 `rolled_back`、原行保留），不分配新版本号；重做时另起一个 release，用新的 `scope_spec_set`。**`release.superseded` 的载荷**：`{release_id, frontier, artifact_sha256|null, decision_id}`——**回滚不建 successor 行**：新版本走常规路径（声明范围 → 人签 `spec_set` → P8 冻结），这样不必给 `draft` 行编造 `frontier`/`baseline_hash`/`scope_spec_set`，也不用为"建行"另造事件。回滚只做一件事：把旧版收尾，并把"为什么重做"留在 decision 里。没有这条路径，冻结版就是"不能交付也不能收尾"的死胡同。

**热修**（hotfix）：新 release，`scope` 最小；必须带一条签字说明"为什么不能等下一版"；**不得跳过任何 gate**，只能缩小范围。

## 8. 版本 diff



```bash
sdo_ledger diff --from r-2026-10-a --to r-2026-11-a
```

输出四块（都来自视图，不只说话）：

| 块 | 内容 |
|---|---|
| 范围变化 | 哪些 spec 进/出，哪些缺陷进/出 |
| 证据变化 | 哪些 claim 失效（frontier 变了）、哪些新增 |
| 豁免变化 | 生效/过期/新增 |
| 顺延变化 | 新增顺延、连续顺延告警 |

用途：PR 里贴一份，弥补"台账不在仓库里 ⇒ code review 看不到变更"。

## 9. 弃用（deprecation）



- 弃用是一条**一等 release item**（`kind=deprecation`），不是一个注释；
- 窗口：至少一个 minor 版本；到期后仍在使用 ⇒ 判红；
- 弃用声明必须给出"替代路径"与"迁移命令"。

## 12. 判据（release 组）



| code | 判据 |
|---|---|
| `release.gaps_match` | 缺口清单 = requirement 差集（未通过 ∪ 顺延；多/少均红，每行须有 `requirement_id`） |
| `release.out_signed` | 每项 `out` 有 reason + human 署名 |
| `release.independence_satisfied` | 冻结满足 `independence_satisfied`（`dual_human` 两个不同 human，或 T0 的 `solo_cooldown(15m)`，见 [07](07-协作-权限-并行与子代理.md)「关键决策的独立性」） |
| `release.evidence_valid` | 发布证据全部在冻结 frontier 内有效，**且 `scope_spec_set` 指向的 `decision(kind='spec_set')` 仍为 `valid`**（被撤 ⇒ 红，不是「照缺口公式算绿」） |
| `release.artifact_sha256` | 产物 sha256 与清单一致 |
| `release.snapshot_verified` | 审计快照 `verify` 通过，**且该 `verify_run` 由人/独立服务执行或经人签**（agent 自跑的不算） |
| `release.deprecation_window` | 弃用未到期或已给替代路径 |

## 13. 不变式



1. 冻结后 `release` 行不可变；改范围 = 新 release（含"重开冻结"的签字）；
2. 发布说明与缺口清单**只能由视图生成**；
3. 一个包版本可含多个 release，但**一个 release 只有一个冻结 frontier**；
4. 回滚不删除历史，只新增状态；
5. 热修不得跳过 gate；
6. **一个 release 只按一把尺子判**：`baseline_hash` **必须非空**（`NULL` 一律算违规，不能靠「证据也都是 NULL 所以等值」混过），且其 `in` 集合的全部证据都来自这一版；两版 baseline 的证据不能混进同一版（混了 ⇒ `baseline_mixed`，冻结被拒）；
7. **范围决定必须仍有效**：`scope_spec_set` 指向的 `decision(kind='spec_set')` 在冻结与交付两个时点都必须 `status='valid'`；被 `decision.revoked` 撤销 ⇒ 本 release 与其缺口读数**失效**（不自动挑一版新集合顶替——换全集是换尺子，要重新声明并重签；不原地改状态，见下）。冻结时指向的 decision 不是 `valid`、或证据行 `requirement_id` 不在该 decision 载荷的 `spec_ids[]` 内 ⇒ `freeze_blocked(scope_invalid)`（写入路径校验，见 P8 前置⑥）；**冻结后被撤** ⇒ 本 release 不能交付，`verify` 记 `runtime_inconsistent` 并落 `defect.recorded(kind=consistency, criterion_id='release.evidence_valid')`（`gaps_match` 的公式本身不红——红的载体是 `evidence_valid`）；已冻结行**不改状态**（与不变式 1 一致），只能以 `release.superseded` 另开新 release 重做，旧版的缺口读数标为失效、不许当作“已对账”继续引用。
8. **release 状态是折叠结果，终态互斥**：`delivered` 只能由 `frozen` 且无 `release.superseded` 的行产生；`rolled_back` 之后不再接受 `release.delivered`。写入路径断言（P8 步骤 11，违反 ⇒ `state_conflict`），历史里已违反 ⇒ `verify` 红。

## 14. 验收读数（M3–M4）



- 故意在缺口清单里多写 / 漏写一条 requirement ⇒ `release.gaps_match` 红，并指出是哪一条；
- 冻结的独立性不成立 ⇒ 红：`dual_human` 下只有 1 个签字即红；`solo_cooldown` 下冷却未到期即红（`cooldown_active`）；
- 冻结后手工改 `release` 行 ⇒ 数据库层拒绝（不可变触发/权限）；
- 回滚后旧 release 仍可查、新 release 必须存在；
- `sdo_ledger diff` 能列出"因 frontier 变化而失效的 claim"条数（不是 0）。

## 15. 迁移策略：B（v1 冻结只读）



| 方案 | 代价 | 结论 |
|---|---|---|
| A 事件映射器（v1 journal → v2 event） | 高：10 410 条要逐条重验语义 | 不做 |
| **B v1 冻结为只读档案，v2 新台账** | 中 | **采用** |
| C 双写过渡 | 最高 | 不做 |

**v1 冻结的具体做法**

- v1 代码在 **`v1` 分支 + `v1-final` tag**（只读归档）；工作树只有 `docs/`，`dsh plugin` 不再加载 v1 的写路径；
- 提供 `sdo1 export` 只读导出（人可查历史卡、缺陷、评审）；
- **v1 的判据库、测试用例、语言键是资产**：逐条迁到 v2（判据要补负例，见 [04](04-判据-门禁与负例.md)）。

**哪些资产搬、哪些不搬**

| 资产 | 处理 |
|---|---|
| 判据语义（三态、fail-closed） | 搬（补负例） |
| 证据绑定（产物指纹 + frontier） | 搬（frontier 取代 seq） |
| 顺延定价（scope / nonScope + 人签） | 搬（表结构重写） |
| 变异自证 | 搬（记录落 evidence） |
| 1 883 个测试用例 | **按价值搬**：产品行为类搬，字符串比对标 bbox 类不搬 |
| 68 条判据 | 搬（逐条审"它挡哪条漂移"，挡不住的退休） |
| `office.ts` / `index.ts` | **不搬**（壳重写） |
| 每轮状态块注入 | **不搬**（由 UI + 视图取代） |

## 16. 里程碑（每个都有判死读数）



### 16.1 M0 · 真源与视图（2–3 周）

**做**：SQLite schema + 约束 + 13 个视图 + `fold` + `sdo_query` + 只读控制台页（3 个页面）。

**判死读数**

1. 一次 `status` 查询中 `event` 表读取 **1 次**；
2. 同一 `as_of` 两次查询**逐字节相同**；
3. agent 用 `bash`/`read` **读**库时只有探针线索（纯读不改哈希）；**写入/篡改**由 `verify` 发现；两者都**不承诺归因**；
4. `gaps` 能看到 `query_miss` 的聚合。

### 16.2 M1 · 链条、对齐与返工面（2–3 周）

**做（已收窄）**：intent/spec/scenario/criterion/evidence/claim 六表 + **对齐三件套（复述/例子/回指）** + **判据框架**（注册、`applies_to`、有效绑定、负例强制）+ **P15 静态校验器**（对 baseline 文件跑：空 gate、未注册判据、`core` 三条未有效绑定、缺 engine 一律拒；**不落冻结、不写 `baseline.rejected`**）+ `sdo_check`（离线，对六表；**只读预览，不落 `gate.judged`**——判定行必须绑 frozen `baseline.hash`，那是 M2）+ **preview 的 `rework_units`**。

> **M1 只做 core 三条判据的强制绑定**（`spec_set.signed` / `assumption_set.signed` / `provenance.present`）；其余 21 条在 M2 随签字链落地。假设处置链、评审抽样、晚到条款链**整体后移到 M2**——它们都依赖签字，先做会造出“有规则、无授权”的半成品。

> **冻结与门禁在 M2**：M1 的 P15 只对**文件**跑静态校验（不需要签字，也不需要 `baseline` 行）；`baseline` 冻结要人签 `decision(kind='baseline')`，门禁判定要 `stage_run.baseline_hash`，两者都依赖 M2 的签字链——所以里程碑这样切，`make all` 的"尺子先冻"不会变成"先有签字再做校验"的倒挂。

> **顺序按价值排，不按模块完整度排**：v2 要证明的第一件事是"少返工"，所以对齐与返工面必须在签字/发布之前落地。签字与发布是**高风险场景的加法**，不是这套东西的存在理由。

**判死读数**

1. 抽 20 条 v1 结论型回执，在 `claim` 表能重建 **20/20**；
2. 新增判据无负例 ⇒ **注册被拒**；
3. 新增真源字段无消费者 ⇒ `dead_field` **红**；
4. **对齐**：一个真实意图走完复述 + 2 正 1 反，人能在**第一次写代码前**说"对/不对"；分歧前移率 ≥ 80%；
5. **返工可见**：每次变更的 preview 都带 `rework_units`，且与事后实际作废数一致（抽样 3 次）；
6. **静态校验可用**：空 gate 配置（`criteria: []`）⇒ P15 静态校验拒（`gate_empty`）；core 三条未有效绑定 ⇒ `core_not_effective`；缺 `engine` ⇒ `engine_missing`（此时还没有 `baseline` 行，冻结是 M2 的事）；
7. **判定行零产出**：M1 跑完 `sdo_check` 后，`gate.judged` 行数为 **0**（预览不写判定；若写了，说明给"没有 baseline 的判定"开了口子）。

### 16.3 M2 · 交互与签字（2–3 周）

**做**：待审队列（四项契约）+ 登录 + 签章口令 + signerd + 免密窗口 + **baseline 冻结**（P15 通过 → 人签 `decision(kind='baseline')` → `prev`/`direction` → 收/放宽都建新行；落 `baseline.rejected`）+ **门禁判定**（`stage_run.baseline_hash` + `gate.judged`）+ **假设处置链**（`assumption_set` 先签后处置、`assumption.disposed` 投影、失效 fold、撤销级联）+ **评审抽样**（`sample_every`/`sample_seed` 进 baseline，P14 按卡序号单调取模）+ **晚到条款链**（`clause_readings[]`/`readings_hash` 进 `spec_set` 载荷、P13 依赖闭包重判 pre-work、P4 `clause_unjudged` 准入）+ 撤销（**含撤销 `assumption_set` / `spec_set` 的级联**：覆盖的假设回 `open`、覆盖的需求集合失效、必须重签）+ **PM 最小环路**（读 `pm_queue`/`alignment` → 建卡 → 预占/派发 → `request_sign`；`plan`/`assign` 权在此里程碑先落最小版，`escalate` 与独立性留到 M3）。

> **M2 的目标不是"有签字"，是"签字便宜"**：认证走 passkey/平台认证器，免密窗口内连签，签字页 ≤ 2 次交互。判死读数里加一条：单次签字的人工时间中位数 **≤ 10 秒**。超过就说明认证设计错了，不是人多事。

**判死读数**

1. 未解锁时签字 ⇒ `awaiting_unlock`，**不产生** decision 行；
2. 免密窗口内，frontier 改变后签字 ⇒ **要求重新解锁**；
3. decision 缺 `proposition` ⇒ `no_blind_sign` 红；
4. agent 尝试签字 ⇒ 拒绝 + 告警事件。

### 16.4 M3 · 协作与权限（1–2 周）

> **M1/M2 的 PM 是人**（或人临时授权的单个 agent）：M2 起有 PM 最小环路，但多 PM、按 domain 分权、`escalate` 的独立性要到 M3 才齐。

**做**：actor/scope/right、冲突可见、**独立性**（`dual_human` / `solo_cooldown`）。

**判死读数**

1. 两人并发改同一字段 ⇒ 一个成功、一个 409；`conflicts` 可见双方主张（**不是 `disputed`**）；
2. 版本冻结的独立性不成立 ⇒ 门禁红（`dual_human` 缺一个签字 / `solo_cooldown` 冷却未到期）；
3. 撤销权限后待审项消失且显示"申请入口"。

### 16.5 M4 · 并行与复用（2 周）

**做**：工作副本、锁表、公共面单写者、复用 reason code、**PM 的预占与收回**（`task.assigned`/`task.unassigned`/`lease.revoked`）。

**判死读数**

1. 同文件并发写：**一成一败（409）**；
2. 一次派发的 `agent.pick_declined` **≤ 1 条**；
3. 连续 3 次新起 ⇒ 告警进 `gaps`；
4. **预占期内的认领者必须等于 `reserved_by`**（被绕过次数应为 0，`verify` 每日报）。

> 总计约 **9–12 周**（单人 + agent 协作）。若某个 M 的判死读数不达标，**不进下一个 M**，先修。

## 18. 风险与对策



| 风险 | 对策 |
|---|---|
| 重写后"判据库"退化 | 搬迁时逐条问"挡哪条漂移"；挡不住的退休，不许原样搬 |
| 里程碑拖期 | 每个 M 有判死读数；不达标停，不叠加 |
| 单人开发无人评审 | 用 agent 做评审，但**判据与签字不能由 agent 代**；人签集中在 M2 |
| v1 历史丢失 | 只读导出 + 快照；不要求可复算 |
| 需求膨胀 | 任何新机制必须能回答"挡哪条漂移"，否则不进 v2（[01](01-理论与边界.md)） |
