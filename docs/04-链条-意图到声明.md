# 链条：意图 → 真源 → 被遵守 → 声明

> 这一页是 v2 的脊柱。三层漂移（声明≠真源、真源≠被遵守、真源≠意图）在这里被**数据结构**挡住，而不是靠纪律。
> 依据：[01](01-理论支撑.md) P2/P3/P4 与 §6。

---

## 1. 六张表

```text
intent ─1:N─ spec ─1:N─ scenario
                └──1:N─ criterion ─1:N─ criterion_fixture(正/负)
criterion ─N:M─ evidence
claim ──(derived_by)──► 视图/渲染器 ──(as_of_frontier)──► event
field_consumer(field, criterion_id)      ← 防死字段
```

| 表 | 关键列 | 约束 |
|---|---|---|
| `intent` | `id, statement, owner, approved_by, content_hash, at` | `approved_by` 必须是人；`content_hash` 变化 ⇒ 需重签 |
| `spec` | `id, intent_id, clause, mech_checkable, scenario_id` | `intent_id` 外键；`mech_checkable=1` 时必须有 `scenario_id` |
| `scenario` | `id, steps(json), expected(json), kind` | 人审场景（可玩/可点的步骤），不是断言 |
| `criterion` | `id, spec_id, kind, status_enum, has_negative_fixture, remedy` | 无 `remedy` 不许注册；无负例不许注册 |
| `criterion_fixture` | `criterion_id, polarity, input, expected_status` | 每条判据至少 1 正 1 负 |
| `evidence` | `id, criterion_id, artifact_uri, artifact_sha256, command, output_digest, at` | 大对象存 uri，不存库 |
| `claim` | `id, subject, predicate, value, as_of_frontier, derived_by, at` | `derived_by` 必须是注册渲染器；`as_of_frontier` 非空 |
| `field_consumer` | `field, criterion_id` | 每个真源字段至少一个消费者 |

**每个节点还必须有 `inputs`**（`{kind, id, hash}`）：它是派生图的**边**，也是影响链与失效传播的唯一依据。形状与规则见 [14](14-变更与影响链.md)。

---

## 2. 三层漂移怎么被挡住

| 漂移 | 挡住它的结构 |
|---|---|
| **L1 声明≠真源** | `claim` 只能由 `derived_by` 指向的渲染器写入；渲染器的输入只能是视图（[06](06-观测-视图工具与预算.md)）。**没有第二条写 claim 的路。** |
| **L2 真源≠被遵守** | `field_consumer`：字段没有消费者 ⇒ `dead_field` 判据红（[05](05-判据-门禁与负例.md)）。 |
| **L3 真源≠意图** | 不假装能消掉：`intent.approved_by` + `content_hash` 把"意图"集中在**人签**一处；判据必须带负例，防止"判据自洽但冤枉人"。 |

---

## 3. claim 的生成规则（最关键的一条）

```text
允许：renderer(view_row) → claim(row)          # derived_by 记渲染器 id
禁止：任何代码直接 INSERT claim                 # DB 权限层面禁止
禁止：回执/报告里出现 claim 表之外的结论         # 由 verify 检查
```

**例**：回执里写「已完成：TASK-280（证据 3 条，评审 REV-097 已核）」——这句话必须由 `claim(subject=TASK-280, predicate=done, value=true, as_of_frontier=f:…)` 生成；渲染器只负责排版，不负责判断。

**检查**：`verify` 扫描最近 N 条回执（存进 `claim` 的渲染产物），任何一句"结论型文字"在 claim 表里找不到对应行 ⇒ 红。这是 v1 那 57% 缺陷的结构性解药。

## 4. 状态机（只列关键）

**intent**：`draft → proposed → signed → superseded`
- `signed` 必须有 `approved_by` 与 `content_hash`；
- 修改 `statement` ⇒ `content_hash` 变 ⇒ 回到 `proposed`（**必须重签**）。

**spec**：`defined → revised*`；`revised` 必带 `reason` 与影响面。

**criterion**：`draft → active → retired`
- `active` 前置：`has_negative_fixture=1` 且 `remedy` 非空；
- `retired` 必须说明"被哪条取代"。

**task**：`planned → ready → in_progress → (blocked ↔ in_progress) → done | dropped`
- `done` 前置：`claim(done)` 成立 + 关联证据 + （若需评审）`decision` 可验；
- `dropped` 必须带 `drop_kind ∈ {never_done, delivered_deferred}` 与凭据（v1 的教训：`dropped` 可以是"已交付但记账顺延"，不写清会低估自己）。

## 5. 一个需求走完整条链（示例）

```text
intent(   "发布范围必须能按版本声明"                     approved_by=u-liang )
  └ spec( "release 文件含 scope 与 nonScope；nonScope 每项必须有 reason 与 approved_by" )
      └ scenario( 人审：冻结一个版本 → 看缺口清单是否与集合恰好相等 )
          └ criterion( R-12 "缺口清单 = 集合差集"，负例：多写一项 / 少写一项 )
              ├ evidence( 命令 + 读数 + 产物指纹，绑 frontier f:9c1e )
              └ claim( subject=r-0.2.0, predicate=gaps_match, value=true, as_of=f:9c1e,
                       derived_by=render.release_gaps )
                        └─ 签字 decision(d-8f21, signer=u-liang, frontier=f:9c1e)
```

这一条链走通后，任何人（包括新会话）都能回答："这个判据在保护哪条意图"、"这份证据什么时候有效"、"谁签的字"。

---

## 6. 不变式

1. `criterion.spec_id` 必须能一路追到 `intent.id`（外键 + `verify` 检查）；
2. `claim` 的 `derived_by` 必须在 `renderer_catalog` 里注册（注册即代码，见 [06](06-观测-视图工具与预算.md)）；
3. `claim.as_of_frontier` 的每个事件 id 必须存在；
4. 任何 `decision` 指向的 frontier 必须是它签发时刻的**当前** frontier（防止"签旧版本"）；
5. `field_consumer` 覆盖全部真源字段（`dead_field` 判据）。

---

## 7. 验收读数（M1）

- 随机抽 20 条 v1 的"结论型回执"，在 v2 的 `claim` 表里能重建 **20/20**；
- 人为删掉一条 `scenario` 的判据：`verify` 能报出"哪条意图失去了可判定条款"；
- 新增一个真源字段但不加消费者：`dead_field` 立即红。
