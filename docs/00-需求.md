# 需求：这是一个什么插件、要干什么、怎么干

> **框架坐标**（对齐 [01 理论与边界](01-理论与边界.md)）
>
> - 守的层：**产品意图层**（最上游；本层不产生事件）
> - 涉及真源：无（它解释"为什么需要这些真源"）
> - 对应命题：命题 1–5 的来源
> - 本文引入/定义的概念：功能需求（F-x）、机制约束（M-x）、明确不做（N-x）

> 这一篇只回答三件事：**这是什么插件、它要干什么、它必须怎么干**。
> 不写开发流程与协作纪律（那些不属于产品需求）；每条都标了设计落点。

## 1. 定位

**SDO 是一个"可验收的项目管理插件"**：让人把"产品要什么"交给一个 PM agent，由 PM 指挥多个实现 agent 干活，并让每一件"完成"都能被独立复核。

它交付的不是任务列表，而是**"产品是否符合要求"的证据链**：谁提的要求、谁签的、哪条判据验的、产物指纹是什么、失败在哪一步。

一句话：**把"我觉得做完了"变成"有据可查地做完了"。**

它不是：通用看板、CI/CD、代码生成器、聊天记录归档、也不是"替人做决定"的工具。

## 2. 用户与场景

| 角色 | 用它做什么 | 得到什么 |
|---|---|---|
| **人类（产品负责人）** | 提要求、在必须决定时签字、验收产品 | 不被琐事打断；每次签字都能看到"签什么、影响几条、降没降保证" |
| **PM（agent）** | 拆解、派发、盯进度、收口 | 一屏"下一步做什么"；派发有授权、收回有依据 |
| **实现者（agent）** | 领一张卡、在授权范围内改、交证据 | 边界清楚（scope/租约/工作副本）、判据清楚、做完有据 |

典型场景：一个项目从"一句需求"走到"可交付版本"，中间有需求变更、假设、评审、返工、多 agent 并行——每一步都留痕、都能复核。

## 3. 要干什么（功能需求）

- **F-01 意图与声明**：把意图变成可反驳的条款（需求/设计/契约），每条条款有验收判据与正反例；意图与条款之间有复述与差异处置。
- **F-02 分解**：把目标拆成可独立验收的节点与工作卡；每个叶节点有验收判据，父节点验收 = 集成清单。
- **F-03 卡与授权**：一张卡一个判据一个证据；派发即授权（租约 + 写范围 + 工作副本），越界可发现、可拒绝准入。
- **F-04 判据与门禁**：判据可注册（必须有 remedy、正例、负例）；阶段出口由 gate 判定，三态（pass/fail/na），`na` 不算通过。
- **F-05 签字**：只签决策（意图、条款集合、假设集合、冻结、豁免、回滚）；签字绑内容哈希与前沿；模型不能签、不能验签。
- **F-06 假设**：模型不许静默选择；声明成假设，逐条处置（确认/转正/推翻），没处置不许开工。
- **F-07 变更**：改需求/设计要有影响面预览（会重开哪些卡、返工多少），改完旧结论作废、走复位。
- **F-08 评审**：非作者评审；按风险、契约、release 相关触发，另加抽样强制；评审结论可追溯到发现与处置。
- **F-09 交付**：冻结版本绑快照与产物指纹；交付清单与缺口对得上；没有"带病交付"。
- **F-10 观测**：给人看的页面（总览/待审/计划/证据…）与给 PM 看的下一步队列；所有数字来自只读视图，前端不算数。
- **F-11 多 agent 协作**：代理池与复用、并行时的单写者与锁、冲突可见、分歧可裁定。
- **F-12 迁移**：旧项目的只读导入与缺口清单；迁移不伪造历史。

## 4. 必须怎么干（机制约束）

- **M-01 事件真源**：状态变化只追加事件，当前状态由折叠得出；声明只能由视图派生，模型不能直写结论。
- **M-02 判据驱动**："完成"由判据读数决定，不由模型自述；判定记录绑当时的 baseline 与读数，事后可复算。
- **M-03 一条不变量一个守卫点**：每条规则只有一处拦截点（表约束、领域服务或注册器），审计只做事后对账、不当守卫。
- **M-04 授权与上下文分离**：`inputs[]` 只提供信息、不扩权；写权只来自租约与 scope。
- **M-05 集合签字**：需求集合、假设集合由工具按当前状态渲染，人签"这一批"，模型改不了集合内容。
- **M-06 派生由工具算**：影响面、返工量、保证升降级、抽样集合都由工具计算；手填值一律忽略。
- **M-07 分层**：L1 真源/存储、L2 领域与门禁、L3 编排/视图；依赖单向，不跨层反向调用。
- **M-08 不引入图数据库**：节点与边用邻接表 + 递归查询，查询仍走 SQL 与索引。
- **M-09 不对宿主提要求**：不要求宿主改行为或加接口；宿主能力（如团队/子代理）只作可选执行器，没有就退化运行。
- **M-10 可审计而非不可篡改**：写入进哈希链、`verify` 能发现篡改；不承诺阻止篡改。

## 5. 明确不做

- **N-01 不做通用项目管理**：不做甘特图、工时、OKR、看板模板；只做"可验收"的那部分。
- **N-02 不做 CI/CD 与代码生成**：构建、部署、代码由外部完成；SDO 只验证据与门禁。
- **N-03 不替人做决定**：不自动签字、不自动豁免、不在"该问人"的地方给默认值。
- **N-04 不引入自生长意图树**：模型不能无声改小目标；树的生长必须由人签的 `plan` 落地（三陷阱见 §6）。
- **N-05 不做第二真源**：不把宿主的任务板、聊天记录、外部系统当账本；账本只有一个。
- **N-06 不引入图数据库**（同 M-08）。
- **N-07 不把长期凭据交给 agent**：凭据只在签字瞬间用，模型不接触私钥。
- **N-08 不做"看起来在管"的机制**：加不了执行点的规则不要；留住不删的机制要能说出挡哪条漂移。

## 6. 三条保证（产品的成功标准）

| # | 保证 | 什么意思 | 靠什么 |
|---|---|---|---|
| 1 | **记录忠实 + 按判据做对** | 记录忠实于说过的；判据本身要经红队/抽样复核 | 复述 + 条款指纹 + 意图签字 + 判据读数 |
| 2 | **已声明的假设必须处置完** | 不许"模型自己选了一个还装作没事" | 假设集合签字 + 派发前检查 |
| 3 | **能证明按约定标准做对了** | 不是模型自己说做对了 | 非作者评审 + 判据负例 + 证据绑指纹 + `verify` |

三条都成立，才叫"产品正确"；任何一条降级，签字页必须显示降了哪条（保证等级表 + delta）。

## 7. 三陷阱与替代设计

评估"自生长意图树"那类方案后，明确不引入这三样；分解树本身借鉴，但必须改成可验收的形态：

| 陷阱 | 为什么不能引入 | SDO 的替代 |
|---|---|---|
| **自生长 = L3 漂移的制造机** | 模型可以悄悄把目标改小、把难的部分切掉，然后每块都"完成" | 每个叶节点必须能追回 `intent` 的条款；树一旦生长就落账（走影响链），不许无声重切 |
| **selector 的自由度** | "下一步做什么"由模型选、可跳可回退，在工程里等于流程逃逸 | 节点级阶段可以选，但**门禁不可跳**：每类出口都有 gate，缺读数即红 |
| **投入档位是隐参数** | 用它控制"块多大、何时算完成"等于改判据阈值 | 档位必须进 baseline 并签字，否则就是偷改尺子 |

结论：**是可验收的分解树**——树负责"切"，判据负责"验"，影响链负责"改"（落点见 [03](03-链条-意图到声明.md) 的 `goal_node`：锚定、父验收=集成清单、生长即变更）。

## 8. 取舍

| 冲突 | 取舍 | 代价 |
|---|---|---|
| 管得严 vs 用得动 | 只在"必须人决定"处打断；其余由判据兜 | 判据没覆盖的地方仍靠评审抽样 |
| 不对宿主提要求 vs 要调度 agent | 执行器可依赖、真源不依赖 | 没装宿主团队插件时退化为"人 + 单 agent" |
| agent 是一等用户 vs 只有人能签 | PM 只发 `request_sign`，交付由签后流程执行 | PM 不能自主收口 |
| 图模型 vs 不引入图库 | 邻接表 + 递归 CTE | 深层图查询性能一般 |
| 少机制 vs 防漂移 | 加机制必须能指出挡哪条漂移、给退休条件 | 有些漂移只能容忍 |

## 9. 待确认（进实现前必须拍板）

| # | 待确认 | 现状 |
|---|---|---|
| 1 | 部署上限缺省值（成员 8 / attention 16 / payload 64 KiB / 清理 5 秒） | 已定为部署配置（`config.changed`，需 `admin`，不进 baseline）；数值本身待实测确认 |
| 2 | 抽样缺省 `sample_every=5`、上限 10 | 设计已定，未实测 |
| 3 | PM 默认是人还是 agent | 设计已定：M1/M2 的 PM 是人，agent PM 从 M3 起；是否改默认待定 |
| 4 | 多 PM / 多 domain 的授权划分 | 建议一 scope 一个 PM，未定 |
| 5 | 自生长残留风险（以"变更"名义慢慢改小目标） | 影响链只记账、不阻止，靠抽样 |
